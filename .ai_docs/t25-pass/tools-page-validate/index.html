tools 7.1.3 (new, after "How the schema of the specification is composed") · new:tools-7-1-validate · предложение от 2026-11-21 · ждёт вашего согласия
Обоснование
Каждая команда опирается на структуру, которую схема задаёт для файла. Только проверка по схеме показывает, где файл отступает от этой структуры и что там не так. sheriff reindex строит каждый файл из всех файлов, поэтому если записать лишь некоторые из них, файлы разойдутся друг с другом. Ключ, записанный дважды, объединяется первым, потому что файл, прочитанный без объединения, хранит только последнее значение. То, что записал более ранний выпуск, изменяется первым, потому что схема отвергает его старые имена. То, что sheriff reindex пишет сам, исключается, потому что узел, написанный вручную, получает это только тогда, когда команда запущена.
Reason
Each command relies on the structure that the schema defines for a file. Only validation against the schema shows where a file departs from that structure and what is wrong there. sheriff reindex builds each file from all the files, so writing only some of them would leave the files inconsistent with one another. A key written more than once is merged first, since a file read without the merge holds only its last value. What an earlier release wrote is changed first, since the schema refuses its old names. What sheriff reindex writes itself is excluded from the validation, since a node written by hand receives it only when sheriff reindex runs.

Текущий текст узла по-русски
`sheriff validate` проверяет каждый файл валидатором JSON Schema по базовой схеме SpecSheriff guidelines, составленной с расширением проекта (§s-eferktypcj7njt5).

Сначала расширение проверяется по схеме расширения. Эта схема позволяет расширению добавлять только NodeKinds, свойства существующего NodeKind и свойства файла или связи.

То, что добавляет расширение, присоединяется к базовой схеме:

- его NodeKinds присоединяются к NodeKinds, которые может иметь узел;
- его условия присоединяются к тем, которым подчиняется каждый узел;
- его свойства файла и связи присоединяются к тем, которые могут иметь файл и связь.

`sheriff binding` проверяет каждый файл по той же схеме, прежде чем проверять что-либо.

`sheriff reindex` проверяет каждый файл после того, как объединил каждый ключ, записанный дважды, и изменил то, что записал более ранний выпуск, как говорит §s-f5rz6b7dhxejjts. Он делает это прежде, чем что-либо вычислять. Из этой проверки он исключает только то, что пишет сам:

- связи, указывающие на узел;
- вне архива — sid, которого у узла нет, каждое расположение, оглавление разделов в заголовке, значения, собранные рядом с полем, и статус раздела и заголовка домена.

Если схема отвергает файл или схема расширения отвергает расширение проекта, каждая из двух команд называет этот файл или расширение и каждый отказ в нём. После этого она больше ничего не проверяет, а `sheriff reindex` не пишет ни одного файла.

Обоснование. Каждая команда написана для того вида файла, который задаёт схема. Только проверка по схеме называет, где файл отступает от этого вида и что там не так. `sheriff reindex` строит каждый файл из всех них, поэтому если записать лишь некоторые, файлы разойдутся друг с другом.

Ключ, записанный дважды, объединяется первым, потому что файл, прочитанный без объединения, хранит только последнее значение. То, что записал более ранний выпуск, изменяется первым, потому что схема отвергает его старые имена. То, что `sheriff reindex` пишет сам, исключается, потому что в узле, написанном вручную, этого нет, пока команда не запущена.
Текущий текст узла (English)
`sheriff validate` validates each file with a JSON Schema validator against the base schema of the SpecSheriff guidelines, composed with the project's extension (§s-eferktypcj7njt5).

The extension is validated first, against the schema of an extension. That schema lets an extension add only NodeKinds, properties of an existing NodeKind, and properties of a file or of a link.

What the extension adds joins the base schema:

- its NodeKinds join the NodeKinds a node may have;
- its conditions join those every node is held to;
- its properties of a file and of a link join those a file and a link may hold.

`sheriff binding` validates each file against the same schema before it checks anything.

`sheriff reindex` validates each file once it has merged each key written twice and changed what an earlier release wrote, as §s-f5rz6b7dhxejjts says. It does so before it computes anything. It leaves out of that validation only what it writes itself:

- the links pointing at a node;
- outside the archive, a sid a node lacks, every location, a header's index of its sections, the values gathered beside a field and the status of a section and of a domain's header.

Where the schema refuses a file, or the schema of an extension refuses the project's extension, each of the two commands names that file or the extension and every refusal in it. It then checks nothing more. `sheriff reindex` then writes no file.
