TRANSLATION: **Как запускается собственная проверка проекта.**
Если проверка, которую добавляют собственные guidelines проекта, не проходит, `sheriff validate` отклоняет изменение. Если правило, в списке которого стоит проверка, говорит, что о её провале только сообщается, `sheriff validate` вместо отклонения сообщает о провале. Отказ или сообщение называет проверку и показывает, что она вывела в стандартный вывод и в стандартный поток ошибок. Если проверка ничего не вывела, оно показывает её код завершения.
`sheriff validate` запускает каждую собственную проверку проекта командой, которую для неё называет `sheriff.config.json`. Проверка выполняется в каталоге, в котором выполняется `sheriff validate`. При коммите этот каталог содержит то, что содержит коммит. На стандартный ввод проверка получает модель спецификации в том виде, в каком её печатает `sheriff json`. Проверка пройдена, только если её процесс завершился с кодом ноль.
Правило, которое `sheriff.config.json` называет для проверки, перечисляет её в своём `TextRule.list` как элемент, значение которого — имя проверки. `sheriff validate` читает это правило в его последней одобренной формулировке. Если этот элемент — объект, у которого `onFailure` равен `reported`, правило говорит, что о провале проверки только сообщается. Если правило в этой формулировке не содержит элемента со значением, равным имени проверки, `sheriff validate` отклоняет изменение. Отказ называет проверку и правило и говорит, что последняя одобренная формулировка правила не перечисляет эту проверку.
`sheriff validate` запускает собственные проверки проекта только после того, как файлы спецификации прошли проверку на ключ, записанный более одного раза, и валидацию по своей схеме. `sheriff validate` отклоняет изменение, если одна из собственных проверок проекта добавляет, изменяет или удаляет файл в каталоге, в котором она выполняется, кроме файла, который git игнорирует. Отказ называет проверку и каждый такой файл.

Остальные проверки `sheriff validate` дают одинаковые результаты с этой опцией и без неё.

**Порядок, в котором инструменты и проверки выполняются при коммите и при push.**
При коммите и при push собственные инструменты проекта, инструменты SpecSheriff и проверки выполняются в три шага:
1. инструменты, переписывающие файлы: сначала те собственные инструменты проекта такого рода, которые перечисляют его собственные guidelines, например форматтеры, затем генераторы — и генераторы инструментов SpecSheriff, и собственные генераторы проекта;
2. собственные проверки проекта и остальные собственные инструменты проекта, каждый из которых оставляет файлы такими, какими они были, кроме тех, которые git игнорирует;
3. проверки SpecSheriff guidelines.
После первого шага ничто не меняет содержимое коммита. Каждый шаг выполняется независимо от того, что нашли предыдущие шаги. Коммит или push проходит, только если пройдена каждая проверка и ни один инструмент не завершился с ошибкой.
При коммите, в виде исключения из шагов выше, сразу после первого шага выполняются следующие проверки:
- проверка того, что в каждом объекте файла спецификации, её архива или её схемы каждый ключ записан только один раз;
- проверка того, что каждый файл спецификации соответствует своей JSON Schema.
Собственные проверки проекта и остальные проверки SpecSheriff guidelines выполняются только после того, как эти проверки пройдены.
Если инструменты SpecSheriff не могут выполниться, собственные инструменты проекта всё равно выполняются. Тогда коммит или push проходит, если ни один из них не завершился с ошибкой. Тому, кто делает коммит или push, сообщается, что ни одна проверка SpecSheriff не выполнялась.
**Причина.** Проект может запускать при коммите или push собственные инструменты, например сканирование, проверяющее, что ничто внутреннее не попадает в публичный репозиторий. Принятие метода не должно их останавливать, даже там, где инструменты SpecSheriff не могут выполниться, например на машине без плагина. Команда, которой нужно, чтобы проверки применялись ко всем, запускает их в CI.
Порядок позволяет каждой проверке полагаться на то, что она читает. Всё, что переписывает файлы, выполняется раньше любой проверки, поэтому каждая проверка читает коммит в окончательном виде. Генератор выполняется после любого форматтера, чтобы ни один форматтер не изменил то, что он генерирует. Проверка, читающая узлы спецификации, выполняется только на файлах, прошедших проверки своей структуры. Инструмент, который изменил бы коммит после проверок, пропустил бы то, чего не читала ни одна проверка.
**Пример.** Собственные guidelines проекта перечисляют форматтер. При коммите форматтер сначала переписывает файлы в коммите, затем генераторы инструментов SpecSheriff пишут свои файлы. Далее идут проверки того, что в каждом объекте каждый ключ записан только один раз и что каждый файл соответствует своей JSON Schema. После них выполняется сканирование на секреты, а остальные проверки SpecSheriff guidelines выполняются последними, на окончательных файлах.
