    описание инструментов 7.1.2 · s-xzcw3hv4hmxz7h7

    The schema and a project's extension

    sheriff validate validates each file with a JSON Schema validator against the base schema of the SpecSheriff guidelines, composed with the project's extension (§s-eferktypcj7njt5). The extension is validated first, against the schema of an extension. That schema lets an extension add only NodeKinds, properties of an existing NodeKind, and properties of a file or of a link. What the extension adds joins the base schema: - its NodeKinds join the NodeKinds a node may have; - its conditions join those every node is held to; - its properties of a file and of a link join those a file and a link may hold. sheriff binding validates each file against the same schema before it checks anything. sheriff reindex validates each file once it has merged each key written twice and changed what an earlier release wrote, as §s-f5rz6b7dhxejjts says. It does so before it computes anything. It leaves out of that validation only what it writes itself: - the links pointing at a node; - outside the archive, a sid a node lacks, every location, a header's index of its sections, the values gathered beside a field and the status of a section and of a domain's header. Where the schema refuses a file, or the schema of an extension refuses the project's extension, each of the two commands names that file or the extension and every refusal in it. It then checks nothing more. sheriff reindex then writes no file.

    Each command is written for the shape the schema gives a file. Only a validation against the schema names where a file departs from that shape and what is wrong there. sheriff reindex builds each file from all of them, so writing only some would leave the files disagreeing with one another. A key written twice is merged first, since a file read without the merge holds only its last value. What an earlier release wrote is changed first, since the schema refuses its old names. What sheriff reindex writes itself is left out, since a node written by hand lacks it until the command runs.

    Схема и расширение проекта

    sheriff validate проверяет каждый файл валидатором JSON Schema по базовой схеме SpecSheriff guidelines, составленной вместе с расширением проекта (§s-eferktypcj7njt5). Сначала проверяется само расширение — по схеме расширения. Эта схема позволяет расширению добавлять только NodeKind, свойства существующего NodeKind и свойства файла или связи. Добавленное расширением входит в базовую схему: - его NodeKind — в NodeKind, которые может иметь узел; - его условия — в те, которым подчиняется каждый узел; - его свойства файла и связи — в те, что могут быть у файла и у связи. sheriff binding проверяет каждый файл по той же схеме, прежде чем проверять что-либо ещё. sheriff reindex проверяет каждый файл после того, как слил каждый ключ, записанный дважды, и изменил то, что записал прежний выпуск, как говорит §s-f5rz6b7dhxejjts. Он делает это прежде, чем что-либо вычислять. Из этой проверки он исключает только то, что пишет сам: - связи, указывающие на узел; - вне архива — sid, которого у узла нет, все location, индекс разделов в заголовке домена, значения, собранные рядом с полем, и статус раздела и заголовка домена. Если схема отклоняет файл или схема расширения отклоняет расширение проекта, каждая из этих двух команд называет файл или расширение и каждую причину отказа в нём. Дальше она ничего не проверяет. sheriff reindex тогда не пишет ни одного файла.

    Каждая команда рассчитана на ту форму, которую схема задаёт файлу. Только проверка по схеме называет, где файл отходит от этой формы и что там не так. sheriff reindex строит каждый файл из всех файлов, поэтому если записать только часть, файлы разошлись бы между собой. Ключ, записанный дважды, сливается первым, потому что файл, прочитанный без слияния, хранит только последнее значение. То, что записал прежний выпуск, меняется первым, потому что схема отклоняет его старые имена. То, что sheriff reindex пишет сам, исключается, потому что в узле, написанном вручную, этого нет, пока команда не запущена.

    A node is cited by its sid

    A node of the specification has a sid, given to it once and never changed. A node, and so its rule, is cited by its sid everywhere: in the links between nodes, in the code, in the tests and in commits.

    A reference to a place breaks whenever the place changes. As a specification grows, it is reordered, and its rules may move between the parts of the specification. Since a sid is a node's permanent identifier, moving a node changes its location but never its sid, so no reference by sid breaks.

    На узел ссылаются по его sid

    У узла спецификации есть sid, данный ему один раз и никогда не меняющийся. На узел, а значит и на правило, ссылаются по его sid везде: в связях между узлами, в коде, в тестах и в коммитах.

    Ссылка на место ломается, как только место меняется. Растущую спецификацию переупорядочивают, и её правила могут переходить между частями спецификации. Поскольку sid — постоянный id узла, то перенос узла меняет его расположение, но никогда не меняет сам sid, а значит, что ни одна ссылка, использующая sid, не ломается.

    When the status is approved

    The specification, a section and a rule have different approval conditions: - The specification as a whole is approved if an owner has carried out the approval procedure by hand (§s-qzthyh7yqvfhsa2). - A section is approved while every rule in it is approved (§s-9kfdycuq34beqvs).     Whether the specification is approved determines whether the tests of the system's code must pass before a change reaches the project's shared branch (§s-m4h279nbaqkpa3t) and whether the checks take into account code that is outside the commit and carries no SpecTag (§s-kkbqcb9xrpaepwn).     What an approval covers

    The wording an approval covers is a node's title, text, reason and examples, and the fields the node's kind adds alongside them, such as TextRule.list. A change to any of these makes the node a draft, even where one of the node's owners makes it. An approval survives a change to: - the node's links or its metadata; - who its owners are; - what is built into it from other nodes; - where it is in the specification.

    The archive

    The archive holds the nodes that have ever been approved and have since been removed from the specification. Such a node goes there together with the reason for its removal and the sid of the node that replaces it, if one does. An archived node has no sid of its own. An archived node names as its replacement only a node of the specification. When that replacement is removed from the specification in turn, each archived node that names it then names the replacement's own replacement instead, or none if the replacement has none. A section with no node left in it is deleted outright, whatever cites it. So is a node that was never approved. A node may later be deleted from the archive. A node restored from the archive returns to the specification as a new node, with a new sid.

    The archive keeps the removed rules that the code may have implemented, so that each can be restored. It also keeps what later work can learn from them. The last wording of such a rule shows which line of reasoning or which approach to its problem proved mistaken. A node that was never approved was never implemented, and a section requires nothing, so in the archive either would only bury the rules that had to be removed. A node may be deleted from the archive at any time, so anything relying on an archived node could break. For that reason, an archived node has no sid by which anything could name it.     What a link is

    A link is a directed relation from one node to another. Every link states its meaning through its type. The types of link are: - implements — the linking node states how the linked one is implemented. - refines — the linking node states the linked node more precisely, or for a narrower case. - constrains — the linking node states a condition the linked rule depends on. - exempts — the linking node exempts the linked rule, or every rule under the linked section, from being implemented (§s-gf6n8ge4mke3pr2). - checks — the linking node is a check, and it verifies that the linked rule is followed. Such a link is written by hand. - cites — the linking node cites the linked one (§s-cxtt6jvhqcey2k9), and no other type says how the two relate to each other. So the linking node has no link of another type to the linked one. - term-relation — the linking term and the linked term are bound, for as long as both exist, in the ratio the link carries. - uses — what the linking term names makes use of what the linked term names while taking part in a process. The link carries no ratio. A term that only starts a process, such as an operator who starts an export, uses nothing the process uses. An extension of the guidelines or a project's own guidelines (§s-u7tw6m8npxmv5tu) may define further types of link. Each such type states its meaning and contradicts no rule of the SpecSheriff guidelines.

    A link without a type records only that somebody thought of two nodes together. No check can evaluate it. No diagram can draw it. A type named without its meaning is the same guess, one step removed. A project may need a relation that the guidelines do not provide for, so its own guidelines may add a type of link, as they may add a kind of node.

    Что такое связь

    Связь — это направленное отношение одного узла к другому. Каждая связь называет, что она означает, своим типом. Типы связей такие: - implements — связывающий узел показывает, как выполняется связанный. - refines — связывающий узел говорит о связанном точнее или для более узкого случая. - constrains — связывающий узел содержит условие, от которого зависит связанное правило. - exempts — связывающий узел освобождает от реализации связанное правило или каждое правило под связанным разделом (§s-gf6n8ge4mke3pr2). - checks — связывающий узел — это проверка, и она следит за тем, чтобы связанное правило выполнялось. Такую связь записывают вручную. - cites — связывающий узел ссылается на связанный (§s-cxtt6jvhqcey2k9), и никакой другой тип связи не говорит, как эти два узла соотносятся.     What a link is

    A link is a directed relation from one node to another. Every link states its meaning through its type. The types of link are: - implements — the linking node states how the linked one is implemented. - refines — the linking node states the linked node more precisely, or for a narrower case. - constrains — the linking node states a condition the linked rule depends on. - exempts — the linking node exempts the linked rule, or every rule under the linked section, from being implemented (§s-gf6n8ge4mke3pr2). - checks — the linking node is a check, and it verifies that the linked rule is followed. Such a link is written by hand. - cites — the linking node cites the linked one (§s-cxtt6jvhqcey2k9), and no other type says how the two relate to each other. So the linking node has no link of another type to the linked one. - term-relation — the linking term and the linked term are bound, for as long as both exist, in the ratio the link carries. - uses — what the linking term names makes use of what the linked term names while taking part in a process. The link carries no ratio. A term that only starts a process, such as an operator who starts an export, uses nothing the process uses. An extension of the guidelines or a project's own guidelines (§s-u7tw6m8npxmv5tu) may define further types of link. Each such type states its meaning and contradicts no rule of the SpecSheriff guidelines.

    A link without a type records only that somebody thought of two nodes together. No check can evaluate it. No diagram can draw it. A type named without its meaning is the same guess, one step removed. A project may need a relation that the guidelines do not provide for, so its own guidelines may add a type of link, as they may add a kind of node.

    Что такое связь

    Связь — это направленное отношение одного узла к другому. Каждая связь называет, что она означает, своим типом. Типы связей такие: - implements — связывающий узел показывает, как выполняется связанный. - refines — связывающий узел говорит о связанном точнее или для более узкого случая. - constrains — связывающий узел содержит условие, от которого зависит связанное правило. - exempts — связывающий узел освобождает от реализации связанное правило или каждое правило под связанным разделом (§s-gf6n8ge4mke3pr2). - checks — связывающий узел — это проверка, и она следит за тем, чтобы связанное правило выполнялось. Такую связь записывают вручную. - cites — связывающий узел ссылается на связанный (§s-cxtt6jvhqcey2k9), и никакой другой тип связи не говорит, как эти два узла соотносятся. Поэтому у него нет связи другого типа с этим узлом. - term-relation — связывающий термин и связанный термин соединены, пока существуют оба, в соотношении, которое указывает связь. - uses — то, что называет связывающий термин, пользуется тем, что называет связанный термин, участвуя в процессе. У связи нет соотношения. Термин, который только запускает процесс, как оператор, запускающий экспорт, не использует ничего из того, что использует процесс.           How the technical appendix relates to the base specification

          The technical appendix is inseparable from the base specification. The technical appendix never contradicts a rule of the base specification but extends and refines it. A rule too narrow for an implementation is widened in the base, and its detail goes to the technical appendix. A node of the appendix describes how the nodes of the base specification it implements are to be carried out. It does so in enough detail to be read in only one way: exact values, examples and the edge cases of that implementation. It never restates what those nodes state. Each node of the appendix implements at least one node of the base specification, except: - a section, which requires nothing (§s-7445ahgjck2aefg); - a choice covering the whole system, which goes in the section on the stack; - the technical debt (§s-2r7k2aeyusgy6fw).

          A part allowed to contradict the base would leave the base without force anywhere, since no rule could be relied on without reading the implementation too. Described less exactly, a node would leave a choice to whoever implements it (§s-tj38pvm38nepaf5). Read alongside the nodes it implements, an appendix node restating them would be a second copy, and a copy drifts away from what it copies. A node bound to the rule it implements is found when that rule changes, and is read alongside it.

          Как техническое приложение связано с базовой спецификацией

          Техническое приложение неотъемлемо связано с базовой спецификацией. Техническое приложение никогда не противоречит правилу базовой спецификации, а расширяет и уточняет его. Правило, слишком узкое для реализации, расширяют в базе, а его детали уходят в техническое приложение. Узел приложения описывает, как должны выполняться узлы базовой спецификации, которые он реализует. Он делает это так подробно, чтобы прочесть его можно было только одним способом: точные значения, примеры и эйджкейсы этой реализации. Он никогда не повторяет того, что говорят они. Каждый узел приложения реализует хотя бы один узел базовой спецификации, кроме: - раздела, который ничего не требует (§s-7445ahgjck2aefg); - выбора, охватывающего всю систему, который стоит в разделе стека; - технического долга (§s-2r7k2aeyusgy6fw).

          Часть, которой позволено противоречить базе, лишила бы базу силы везде, потому что ни на одно правило нельзя было бы положиться, не прочитав ещё и реализацию. Описанный менее точно, узел оставил бы выбор тому, кто его реализует (§s-tj38pvm38nepaf5). Узел приложения, который читают рядом с узлами, которые он реализует, и который их повторяет, был бы второй копией, а копия отстаёт от того, что копирует. Узел, связанный с правилом, которое он реализует, находят, когда это правило меняется, и читают рядом с ним.

          Technical debt

          The technical debt section lists the accepted shortcomings in the internal quality of the system's implementation. The system still does what the rules require. A defect is not technical debt. The description of a shortcoming need not carry a reason. It may refine the nodes it concerns. Where the shortcoming lies in a technology the implementation uses, its description names the version of that technology it was seen in. Being listed there is the whole of the choice to accept the shortcoming: - no decision records that choice; - the change that removes the shortcoming removes its description.

          Technical debt needs a place of its own, or it is forgotten.

          Технический долг

          Раздел технического долга перечисляет осознанно принятые недостатки внутреннего качества реализации системы. Система при этом делает то, что требуют правила. Дефект техническим долгом не является. Описание недостатка не обязано содержать обоснование. Оно может уточнять узлы, которых касается. Если недостаток кроется в технологии, которую использует реализация, его описание называет версию этой технологии, в которой он замечен. Нахождение там и есть весь выбор принять недостаток: - решение об этом выборе нигде не записывается; - изменение, которое устраняет недостаток, удаляет его описание.

          What the checks enforce, and when they run

          Two things are checked mechanically: - that the specification conforms to the rules of the guidelines that the main table of checks, or the table of checks of an extension, lists; - that the specification and the code still agree with each other. Every check except the review is deterministic. In the review, an independent reviewer judges the following (§s-nyh9yk22ba6g77q): - on every commit that changes code: whether that code does what the rules named in the commit say and does nothing that they do not say; - on a commit whose message states that a rule's implementation needs no change: whether that statement is true; - on a commit in which a node of the technical appendix (§s-qmmzf9nksfsa3qp) is approved, if the node has an implements link (§s-sn6au3vcr9uy5pm) to a rule of the base specification: whether the node refines the rules of the base specification that it implements and contradicts no rule of the base specification. The checks run when a commit is made. Where an agent writes the specification, the tests or the code, the checks also run after each of its edits (§s-epaw9sgyaajzn8g). Some of its edits are refused before they are made (§s-83ev4wwesbwnhnp). As long as the specification has the status approved, the tests of the system's code and of a project's own checks and generators must pass before a change reaches the project's shared branch. The project's own guidelines (§s-u7tw6m8npxmv5tu) name where the tests run, such as on every push or on a shared server before a merge. A failed check refuses the change, unless the table that lists the check says otherwise (§s-jau82aq9juv9zzh).

          Every check but the review is binary, so a refusal requires nobody's judgement. A check that sometimes refuses for a reason nobody can reproduce is bypassed at the first opportunity and never trusted again. The review needs a reviewer, because no script can decide whether code does only what its rules say, whether a rule's implementation really needs no change, or whether a node of the technical appendix agrees with the base specification. Run after each of an agent's edits, a check finds a mistake where it is made. The order in which the test and the code are written can be seen only edit by edit, since a commit contains the test and the code together. The tests are not run on a commit, since a test suite takes longer than anyone should wait for a commit. A change not yet shared misleads nobody, so its tests can wait until it is shared. Where they run is the project's choice, since some suites take hours or need what a developer's machine lacks. While the specification is a draft, the work is focused on the specification itself, so no test has to pass.

          Механически проверяются две вещи: - что спецификация соответствует тем правилам guidelines, которые перечислены в основной таблице проверок или в таблице проверок расширения; - что спецификация и код по-прежнему согласованы между собой.           The review of a commit

          sheriff review has a runner judge every commit that changes the system's code. A runner is an agent's CLI, started apart from the session that wrote the code (§s-xr5xxa9cxf2mq5u). It refuses the commit where the code: - does something no named node states in its text; - leaves out what a named node requires. It also refuses the commit where a changed symbol: - does something no node its SpecTags name states in its text; - carries a SpecTag naming a node it does not implement; - carries the SpecTag that names no node while it implements the system's logic.               The specification's approval status

              Only an owner of the specification approves it or returns it to draft. That owner records each such act in a separate entry, which names that owner. Only the latest such entry determines the specification's approval status. Before the approval procedure records an approval of the specification, it runs the checks listed in the main table of checks (§s-jau82aq9juv9zzh) or in the table of checks of an extension. It skips the review and the checks that need a commit message or a run of the tests. It runs the others as if the specification were approved and one commit added the whole specification and all of the system's code (§s-hheus6f395ynqvc). It shows the approving owner what they find, for example a symbol without a SpecTag (§s-8xw4mgvpexyvw5q) or an approved rule that has no test or no code. If the checks find anything, the procedure records the approval only after the owner confirms the approval. While the specification's strict flag is on, the procedure refuses to record the approval in the cases that the rule on that flag names (§s-q3pfzyaxvpr2zj2).

              Whether the specification is approved determines whether the tests must pass before a change reaches the project's shared branch (§s-m4h279nbaqkpa3t). So its owners decide it, in both directions, by an act of their own. The owners may need to return the specification to draft for any reason. While the specification is changing fundamentally, for example when another version of it is adopted or the system's architecture changes, the code and the tests are secondary. Approving the specification is a decision of its own, separate from approving any rule. Were the specification's approval status tied to a rule, anyone editing that rule would change it. The owners base their decision on what they see. Old code without a SpecTag may still work correctly, so while the strict flag is off, such code does not block the approval. The checks that run at a commit judge only what the commit contains, so they never show everything that the specification and the code still lack.                     What a draft means

                    The specification, a section or a rule that is not approved at present is a draft: - While the specification as a whole is a draft, no test has to pass before a change reaches the project's shared branch (§s-m4h279nbaqkpa3t), and the checks give no warning about code that is outside the commit and carries no SpecTag (§s-kkbqcb9xrpaepwn). - For a section, the status sums up the state of all the rules inside it. If at least one rule is a draft, the section is a draft too. - A draft rule is not implemented: no code or test is written or changed for it. - If a rule's title, text or reason changes, the rule is automatically set to draft.

                    While the specification is a draft, the work is above all on the specification, with the code and the tests secondary. While the specification or a rule has not yet been approved, it may be incomplete or wrong, so implementing it would either lock its gaps into the code or build the code on guesses. The status of a section shows at a glance which parts of the specification are in progress and need the rules inside them approved. Giving sections and nodes a status of their own lets an already broadly approved specification be developed and refined without withdrawing its approval.

                    How code is bound to its rules

                    The system's code (§s-hheus6f395ynqvc) outside its tests is bound to the rules it implements by SpecTags (§s-8xw4mgvpexyvw5q). Code that implements no rule has a SpecTag that says so. A symbol is a named unit of code, such as a function, a class or a member of one, a type, a constant or a component. Whoever writes code binds it to its rules in one of the following ways: - by a SpecTag directly before each symbol, if the checks (§s-jau82aq9juv9zzh) can identify the file's symbols; - by SpecTags in a comment placed as near the start of the file as its format allows, if the checks cannot identify the file's symbols; - by an entry in the bindings file at the root of the repository, for a file whose format allows no comments. A SpecTag before a symbol binds that symbol and every symbol nested in it. SpecTags at the start of a file, and an entry in the bindings file, bind the whole file. A change anywhere in a file bound as a whole is a change to the code its SpecTags bind. The formats that allow no comments are JSON and those that a project's own guidelines (§s-u7tw6m8npxmv5tu) name as allowing none. Each entry in the bindings file names an existing file and holds that file's SpecTags.

                    Binding each file of the system's code as precisely as its format allows lets the checks immediately find code that has lost its link to the specification.

                        What the checks enforce, and when they run

                        Two things are checked mechanically: - that the specification conforms to the rules of the guidelines that the main table of checks, or the table of checks of an extension, lists; - that the specification and the code still agree with each other. Run after each of an agent's edits, a check finds a mistake where it is made.                         What the reviewer is given

                        The SpecSheriff tools give the independent reviewer of a commit the following: - the commit's message; - the commit's change, less the files generated from the specification; - the wording of each rule or term that the commit's message names; - the wording of each rule to which a SpecTag (§s-8xw4mgvpexyvw5q) binds code that the commit adds or changes, not counting the tests; - for each rule whose implementation, according to the commit's message, needs no change: the rule's wording as it was before the commit and as it is after it, and the tests and the code bound to the rule, directly or through a chain of implements links, as they are after it; - for each node of the technical appendix (§s-qmmzf9nksfsa3qp) that is approved in the commit and has an implements link (§s-sn6au3vcr9uy5pm) to a rule of the base specification: - the node's wording; - the wording of each rule of the base specification that the node implements, that has a link to or from such a rule, or that is in the same top-level section of the base specification as such a rule. A node's wording here is its title, its text, its reason, its examples and the fields its kind adds, as an approval covers them (§s-5ah25f6gy99panq). The SpecSheriff tools give the reviewer nothing from the session in which the change was made. They tell the reviewer that each file left out of the change is generated from the specification. The reviewer treats what a rule requires of generated code as implemented by that code.

                        The reviewer makes the judgements that no deterministic check can make: whether code does only what its rules say, whether a rule's implementation really needs no change, and whether an approved node of the technical appendix agrees with the base specification. It can judge only from what it is shown. Shown what each judgement needs, and nothing of what the author of the change meant, it judges by the rules alone.

                        Что получает рецензент

                        Инструменты SpecSheriff передают независимому рецензенту коммита следующее: - сообщение коммита; - изменение коммита, кроме файлов, сгенерированных из спецификации; - формулировку каждого правила или термина, которые называет сообщение коммита; - формулировку каждого правила, к которому SpecTag (§s-8xw4mgvpexyvw5q) привязывает код, добавленный или изменённый коммитом, не считая тестов; - для каждого правила, реализация которого, согласно сообщению коммита, не требует изменений: формулировку правила в том виде, в каком она была до коммита и в каком стала после него, а также тесты и код, привязанные к правилу напрямую или через цепочку связей implements, в том виде, в каком они стали после коммита; - для каждого узла технического приложения (§s-qmmzf9nksfsa3qp), который одобрен в коммите и имеет связь implements (§s-sn6au3vcr9uy5pm) с правилом базовой спецификации: - формулировку узла; - формулировку каждого правила базовой спецификации, которое узел реализует, которое связано с таким правилом связью в любую сторону или которое входит в тот же раздел верхнего уровня базовой спецификации, что и такое правило. Формулировка узла здесь — его заголовок, текст, обоснование, примеры и поля, которые добавляет его тип, как их покрывает одобрение (§s-5ah25f6gy99panq). Ничего из сессии, в которой было сделано изменение, инструменты SpecSheriff рецензенту не передают. О каждом файле, не вошедшем в изменение, они сообщают рецензенту, что он сгенерирован из спецификации. То, что правило требует от сгенерированного кода, рецензент считает выполненным этим кодом.

                        Рецензент выносит суждения, которых не может вынести ни одна детерминированная проверка: делает ли код только то, что говорят его правила; действительно ли реализацию правила не нужно менять; согласуется ли одобренный узел технического приложения с базовой спецификацией. Решать он может только по тому, что ему показали. Получив то, что нужно для каждого суждения, и ничего о намерениях автора изменения, он судит только по правилам.

                        The review of a commit

                        sheriff review has a runner judge every commit that changes the system's code. A runner is an agent's CLI, started apart from the session that wrote the code (§s-xr5xxa9cxf2mq5u). The runner is given: - the commit's message; - the commit's change, less the files generated from the nodes, each of which is named to it with what it holds; - each node the message or a changed symbol's SpecTag names, with its text and its reason. A RecordType is given with its RecordType.fields, and a node of a project's own NodeKind with the values its NodeKind declares; - each symbol of the system's code outside its tests the commit changes, whole as the commit leaves it, with its file, its lines and its SpecTags. The symbols are those sheriff binding finds changed (§s-2x58az67bm6cxq2). A symbol's SpecTags are its own or those of the symbol it stands in. The runner judges the commit against the nodes. It judges each changed symbol, whole, against the nodes its SpecTags name. It refuses the commit where the code: - does something no named node states in its text; - leaves out what a named node requires. It also refuses the commit where a changed symbol: - does something no node its SpecTags name states in its text; - carries a SpecTag naming a node it does not implement; - carries the SpecTag that names no node while it implements the system's logic. A finding of the last sort names as its node the rule that every symbol carries a SpecTag (§s-kgbzk2ph9e6jfb4).

                        A SpecTag says which node a symbol is held to. The checks can tell that a SpecTag names a node that exists, not that the symbol does what that node says. Nor can they tell whether a symbol whose SpecTag names no node carries the system's logic. A reader of the code can tell both. A changed symbol is judged whole, since a change anywhere in it counts as a change of the whole symbol. The whole symbol is then held to the nodes the commit names. Shown only the changed lines, the reviewer would pass the lines beside them that do what no node says.
