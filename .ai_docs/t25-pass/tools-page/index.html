Где лежат файлы · Where the files are

tools 1 · s-zefk589ykh37b8u · предложение от 2026-11-21 · ждёт вашего согласия
Обоснование
Инструменты SpecSheriff находят каждый файл без настройки, указывающей, где он лежит, в каком бы проекте они ни работали и куда бы ни был установлен плагин. Человек или агент, знающий, где лежит файл в одном проекте, находит его в любом другом. Инструменты SpecSheriff узнают репозиторий, где пишутся SpecSheriff guidelines, по переменной окружения, чтобы настройки каждого проекта не содержали того, что нужно только этому репозиторию. Переменная содержит путь к корню этого репозитория, поэтому никакой другой репозиторий на той же машине не принимается за него.
Reason
The SpecSheriff tools find every file without a setting that says where it is kept, whatever the project and wherever the plugin is installed. A person or an agent who knows where a file is kept in one project finds it in any other. The SpecSheriff tools recognize the repository where the SpecSheriff guidelines are written by an environment variable, so that the settings of every project contain nothing that only that repository needs. The variable holds the path to that repository's root, so that no other repository on the same machine is recognized as that repository.

- контракты — в `specs/contracts/`;
- техническое приложение — в `specs/tech/`, каждый его раздел в отдельном файле: раздел домена — в `<domain>.json`, раздел стека — в `stack.json`, раздел технического долга — в `debt.json`;
- guidelines — в `specs/_guidelines/`.

Часть, разделённая на файлы по одному на раздел, хранит свои файлы в своей папке.

В `specs/_guidelines/` собственные guidelines проекта хранятся в `project.json`. В репозитории, где пишутся SpecSheriff guidelines, там же хранятся база — в `spec.json` и описание инструментов — в `tools.json`. Все остальные проекты читают базу и описание инструментов из плагина своего агента (§s-zh2vcr3xjumppg5, §s-2pdy9gw2jrjvfb4).

Схема хранится в `specs/_schema/` репозитория, где пишутся SpecSheriff guidelines. Все остальные проекты читают её из плагина. Схема состоит из файлов:
- `node.schema.json` — для узла и его метаданных;
- `section-file.schema.json` — для файла части;
- `extension.schema.json` — схема расширения.

Расширение схемы, которое добавляет проект (§s-eferktypcj7njt5), хранится в `specs/_schema/project.schema.json`. Оно проверяется по схеме расширения и читается вместе со схемой (§s-xzcw3hv4hmxz7h7). Любой другой файл, который другой проект хранит в `specs/_schema/`, отклоняется как копия схемы.

Одобрения хранятся в `specs/_approvals.jsonl`. Архив удалённых узлов хранится в `specs/_archive/<name>.json`.

`specs/_viewer/` (карта) и `md-version/` (экспорт для чтения) строятся заново после каждого изменения спецификации. Ни то, ни другое не хранится в git.

Инструменты SpecSheriff предоставляют команду `sheriff`. В терминале она запускается как `node <tools>/dist/cli.js` из инструментов, которые плагин хранит на машине (§s-4mej6ccn7xu3d3p). `<tools>` — папка данных плагина для Claude Code или папка `tools/` плагина для Codex CLI в кэше Codex.

Их плагин для pytest, пакет `pytest-specsheriff`, устанавливается через pip из ветки `release`: `pip install "pytest-specsheriff @ git+https://github.com/non4me/SpecSheriff@release#subdirectory=skills/pytest-specsheriff"`.

Настройки инструментов SpecSheriff, общие для проекта, хранятся в `sheriff.config.json` в корне репозитория. Настройки запусков рецензента, которые подтверждает каждый пользователь, хранятся в git-конфигурации пользователя (§s-xr5xxa9cxf2mq5u). Настройка `"writesSpecSheriffGuidelines": true` отмечает репозиторий, где пишутся SpecSheriff guidelines.

Среди настроек glob-шаблоны указывают, где находится код системы и где находятся её тесты. Код и тесты читаются на SpecTag, а файл, не указанный ни как код, ни как тесты, не читается ни на что. Так конфигурация репозитория, его собственные инструменты и их тесты остаются вне кода системы по тому, где они лежат (§s-hheus6f395ynqvc).

Среди настроек есть и команда, которая запускает каждую проверку и каждый генератор, добавленные собственными guidelines проекта (§s-2fau85dfyyeq66m, §s-km4x4s26kv7pjze). Для каждого из них настройки содержат и glob-шаблоны, указывающие файлы его кода и его тестов (§s-utf4mbt7ref8g9c).

Документы — это markdown-файлы, которые репозиторий хранит вне `specs/`.

Инструменты спецификации — это файлы инструментов SpecSheriff. Проект хранит только те файлы, которые пишет `sheriff init`. Репозиторий, где пишутся SpecSheriff guidelines, хранит их в `skills/`, где тесты читаются на SpecTag, которые в них объявлены.

В `project.json` находятся:
- ответственные за спецификацию — те, кого называет её верхний узел;
- уровни, на которых стоят домены, — элементы `TextRule.list` её правила, уточняющего §s-nkyty4dy9x2v2a4;
- правило, которое одобряет спецификацию, — её правило, уточняющее §s-qzthyh7yqvfhsa2;
- файлы, которые хранятся как фикстуры тестов, — те, что указывают glob-шаблоны, перечисленные её правилом, уточняющим §s-6hha5en226aj8hu.
Текущий текст узла (English)
The parts of the specification are kept under `specs/`:

- each domain under `specs/<domain>/`, opening with its header in `specs/<domain>/00-<domain>.json`;
- contracts under `specs/contracts/`;
- the technical appendix under `specs/tech/`, each of its sections in a file of its own — a domain's in `<domain>.json`, the stack's in `stack.json`, the technical debt's in `debt.json`;
- the guidelines under `specs/_guidelines/`.

A part divided into one file per section keeps its files in its directory.

In `specs/_guidelines/`, a project's own guidelines are kept in `project.json`. In the repository the SpecSheriff guidelines are written in, the base is kept there in `spec.json` and the appendix of the tools in `tools.json`. Every other project reads the base and the appendix of the tools from the plugin of its agent (§s-zh2vcr3xjumppg5, §s-2pdy9gw2jrjvfb4).

The schema is kept in `specs/_schema/` of the repository the SpecSheriff guidelines are written in. Every other project reads it from the plugin. The schema is made of these files:

- `node.schema.json` for a node and its metadata;
- `section-file.schema.json` for the file of a part;
- `extension.schema.json`, the schema of an extension.

A project's extension of the schema (§s-eferktypcj7njt5) is kept in `specs/_schema/project.schema.json`. It is validated against the schema of an extension and read together with the schema (§s-xzcw3hv4hmxz7h7). Any other file another project keeps under `specs/_schema/` is refused as a copy of the schema.

Approvals are kept in `specs/_approvals.jsonl`. The archive of removed nodes is kept in `specs/_archive/<name>.json`.

`specs/_viewer/` (the map) and `md-version/` (the readable export) are rebuilt after every change to the specification. Neither is stored in git.

The SpecSheriff tools provide the command `sheriff`. In a terminal it is run as `node <tools>/dist/cli.js`, from the tools a plugin keeps on the machine (§s-4mej6ccn7xu3d3p). `<tools>` is the data directory of the plugin for Claude Code, or the `tools/` of the plugin for Codex CLI in Codex's cache.

Their plugin for pytest, the package `pytest-specsheriff`, is installed by pip from the branch `release`: `pip install "pytest-specsheriff @ git+https://github.com/non4me/SpecSheriff@release#subdirectory=skills/pytest-specsheriff"`.

The settings of the SpecSheriff tools that a project shares are kept in `sheriff.config.json` at the root of the repository. The settings of the reviewer's runs, which each user confirms, are kept in the user's git configuration (§s-xr5xxa9cxf2mq5u). The setting `"writesSpecSheriffGuidelines": true` marks the repository the SpecSheriff guidelines are written in.

Among the settings, glob patterns name where the system's code lives and where its tests live. The code and the tests are read for SpecTags, and a file named neither as code nor as tests is read for neither. That is how the repository's configuration, its own tools and their tests are kept out of the system's code by where they live (§s-hheus6f395ynqvc).

Among the settings, too, is the command that runs each check and each generator the project's own guidelines add (§s-2fau85dfyyeq66m, §s-km4x4s26kv7pjze). For each of them, the settings also hold the glob patterns naming the files of its code and of its tests (§s-utf4mbt7ref8g9c).

The documents are the markdown files the repository keeps outside `specs/`.

The tools of the specification are the files of the SpecSheriff tools. A project keeps only the files `sheriff init` writes. The repository the SpecSheriff guidelines are written in keeps them under `skills/`, where the tests are read for the SpecTags they declare.

The following are found in `project.json`:

- the specification's owners are those its top node names;
- the levels the domains stand at are the members of the `TextRule.list` carried by its rule that refines §s-nkyty4dy9x2v2a4;
- the rule that approves the specification is its rule that refines §s-qzthyh7yqvfhsa2;
- the files kept as fixtures of tests are those named by the glob patterns its rule refining §s-6hha5en226aj8hu lists.
