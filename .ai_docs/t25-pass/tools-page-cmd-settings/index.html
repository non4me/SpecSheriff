Настройки, которые меняет только ответственный за спецификацию · The settings that only an owner of the specification changes

tools 2.10 (new) · new:tools-2-settings · предложение от 2026-11-21 · ждёт вашего согласия
Обоснование
Агент может записать изменение статуса одобрения спецификации, её флага strict или выбранных расширений только через процедуру (§10.3). sheriff settings — эта процедура, одна и для ответственного в терминале, и для агента, работающего на этого ответственного.
Reason
An agent may record a change to the specification's approval status, its strict flag or its chosen extensions only through a procedure (§10.3). sheriff settings is that procedure, for an owner at a terminal and for an agent working for that owner alike.

Новое, предложено рецензентом.

Пример
Агент запускает sheriff settings status approved. Проверки находят два символа без SpecTag; команда печатает их и ничего не записывает. Ответственный соглашается, и агент запускает sheriff settings status approved --confirm. Но не так: одобрение записывается уже при первом запуске.
Example
The agent runs sheriff settings status approved. The checks find two symbols without a SpecTag, and the command prints them and records nothing. The owner agrees, and the agent runs sheriff settings status approved --confirm. But not: the first run records the approval.

Текущий текст узла (English)
`sheriff validate`, `sheriff binding`, `sheriff citations`, `sheriff guard`, `sheriff message` and `sheriff review` implement the checks as the rules of §s-4kd2pave7vm4hmd describe them.

`sheriff init` sets a repository up for the SpecSheriff tools (§s-7unxytshhc4md54). `sheriff remove` takes SpecSheriff out of it (§s-7unxytshhc4md54).

`sheriff reindex` is run after every change to the specification. It does the following:

- it gives a sid to every node that has none;
- it computes every node's location from where it is;
- it empties every incoming list and rebuilds it from the outgoing ones;
- it rebuilds the index in every domain's header from the domain's sections;
- beside each field of type `one of`, it writes the values gathered for it from elsewhere in the specification, each with the sid of the node it comes from (§s-ju5vcanbjph7mgh);
- it makes a draft each approved node whose latest line for it and its wording's fingerprint is not an approval. It leaves out of this a section, a domain's header and the SpecSheriff guidelines the project takes.

It then writes the status of each section and domain's header from the nodes under it (§s-9kfdycuq34beqvs).

`sheriff reindex` adds the rule `sheriff init` writes, as a draft, at every run where `project.json` holds no rule refining §s-qzthyh7yqvfhsa2 (§s-7unxytshhc4md54).

Before anything else, `sheriff reindex` renames each key and value an earlier release of the SpecSheriff tools wrote under another name. In every file of the specification and of its archive, it renames:

- the key `id` to `location`;
- the key `rationale` to `reason`;
- the NodeKinds `record` and `recordType` to `RecordType`;
- the NodeKind `rule` to `TextRule`;
- the NodeKind `domain` to `header`;
- a node's status `""` to `draft`;
- a node's status `checked` to `approved`;
- the key `owner` of a domain's header or a section, holding an email, to `owners`, holding a list holding that email.

A renamed key keeps its place among the node's keys. `sheriff reindex` renames those NodeKinds also where a field's values are the sids of a NodeKind's nodes, and where the project's extension of the schema adds properties to a NodeKind.

A field of type `one of` whose own list an earlier release wrote empty takes the values the domains add as its source instead. Under that release, the empty list stood for those values.

`sheriff reindex` also renames `specs/_confirmations.jsonl` to `specs/_approvals.jsonl`. In each line of that file, it renames the key `owner` to `by`. Where `specs/_approvals.jsonl` already stands, it appends those lines to it and removes the old file.

Then, in every file it rewrites, `sheriff reindex` merges the values an object holds under one key, each into those written before it:

- two lists into one, holding the members of the first and then those of the second that the first does not hold;
- two objects key by key in the same way, each key where it was first written;
- two values JSON Schema holds equal into one.

It names every key it merged, with the file and each value's line. It refuses any other two values under one key, naming the file, the key and each one's line and value. It then writes no file.

`sheriff reindex` also rewrites each test that names its node by a bare sid, the form an earlier release of the SpecSheriff tools read. A bare sid is a word of the form of a sid that stands in one of these places:

- it opens the test's name, followed by a space or the name's end;
- it stands alone as the argument of the test's mark.

In the files the settings name as the tests of the system's code or of a project's own check or generator, `sheriff reindex` puts `@spec ` before that sid. Each node's `meta.tests` then names the test by its new name. `sheriff reindex` names each file it rewrites.

`sheriff approve` records an approval or its withdrawal (§s-v4qus7raqnwzneb).

`sheriff export` writes the readable export in markdown, one file for each file of the specification, each node as §s-k4nqjr96ux7a5m7 says.

`sheriff render` writes the map, the mindmap of the specification's structure drawn from its nodes (§s-rpv4fkdqqguptqd).

`sheriff guide` prints the following:

- every node of the guidelines — the base, the appendix of the tools and the project's own — as §s-k4nqjr96ux7a5m7 says;
- the figures counted off the model as it prints: how many nodes each part holds and how many of them are approved;
- whether the specification is approved.

`sheriff show` prints a node, found by its sid or its location, as §s-k4nqjr96ux7a5m7 says.

`sheriff model` prints as JSON the model of the specification where it runs. The model holds every node as its file holds it, with its location, the part and the file it stands in, and the owners named nearest above it. A project's own check or generator is handed the model on its standard input (§s-2fau85dfyyeq66m, §s-km4x4s26kv7pjze).

`sheriff todos` prints, as text, every item of `meta.todos` in the specification where it runs, the archive left out, and the SpecSheriff guidelines too where the project takes them. The items come the newest first, and those of one day in the order the specification reads. Each item comes with its date, who its author is, what is to be done, and the sid, location and title of its node (§s-t28j22vbdmmeqnh).

`sheriff types` generates the following:

- from the RecordTypes, the types and the RuntimeChecks of the system's code, where the technical appendix says they stand;
- the files each generator the project's own guidelines add prints.

A project's generator is run by the command the settings name for it, and is handed what `sheriff model` prints on its standard input. It prints as JSON each file's path, its content and the sids of the nodes the file is written from (§s-km4x4s26kv7pjze).

`sheriff types` writes a file only where the file is missing or holds, line endings aside, anything other than what it generates. It names each file it writes.

`sheriff types` names each refusal and writes no file where one of the following holds:

- the check of generated copies refuses the list of the files it generates, or a RecordType (§s-dbk2vyeg8z5jxna);
- a project's generator ends with an exit code other than zero.

`sheriff types` writes a file only once every node that file is generated from is approved. It names each node it waits for:

- the types and RuntimeChecks wait for every RecordType;
- a file a project's generator prints waits for the nodes it is written from and for the rule listing that generator.
