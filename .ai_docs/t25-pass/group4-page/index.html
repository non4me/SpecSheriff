Title

How a project's own check is run

Text

Where a check that a project's own guidelines add (§10.8) fails, sheriff validate refuses the change. Where the rule that lists the check says that the check's failure is only reported, sheriff validate reports the failure instead (§10.1.37). The refusal or the report names the check and shows what the check printed to its standard output and its standard error. Where the check printed nothing, the refusal or the report shows the check's exit status.

sheriff validate runs each of the project's own checks with the command that sheriff.config.json names for it (§tools 1). The check runs in the directory in which sheriff validate runs. On a commit, that directory holds what the commit contains (§tools 6). On its standard input, the check receives the model of the specification in the form that sheriff json prints (§tools 2.7). A check passes only if its process exits with status zero.

In its TextRule.list (§5.1), the rule that sheriff.config.json names for a check lists the check as a member whose value (§tools 7.2.6) is the check's name. sheriff validate reads that rule in its last approved wording (§tools 2.5). Where that member is an object whose onFailure is reported, the rule says that the check's failure is only reported. Where the rule, in that wording, lists no member whose value is the check's name, sheriff validate refuses the change. The refusal names the check and the rule, and says that the rule's last approved wording does not list the check.

sheriff validate runs the project's own checks only after the files of the specification have passed the check for a key written more than once (§tools 7.1.1) and the validation against their schema (§tools 7.1.2). It runs them before the rest of its checks (§spec 10.12). It makes the rest of its checks regardless of what the project's own checks find.

sheriff validate refuses the change where one of the project's own checks adds, changes or removes a file in the directory in which the check runs, other than a file that git ignores (§spec 10.1.37a). The refusal names the check and each such file.

Given the option --strict, sheriff validate gives each of the project's own checks a model of the specification in which the specification is approved and the specification's strict flag is on (§10.6, §10.7). It does so regardless of how the entries in sheriff.config.json (§tools 1) set the approval status and the flag. The other checks of sheriff validate give the same results with or without the option.

Before sheriff settings records an approval of the specification, it runs the project's own checks (§tools 2.10, §10.6). It gives them a model in which the specification is approved and the strict flag has the value that the entries in sheriff.config.json set. Before sheriff settings turns the strict flag on, it runs the project's own checks as sheriff validate --strict runs them (§10.7).

sheriff validate runs the project's own checks regardless of whether the specification is approved or a draft (§10.1.37).

Reason

Whenever sheriff validate makes its checks of the SpecSheriff guidelines, it also runs a project's own checks, on the same files. Such a check therefore binds every participant, rather than depending on whoever remembers to run it (§10.8).

Example

The rule that lists the project's own checks has name as its TextRule.list.property, and one of its members is {"name": "spelling", "onFailure": "reported"}. The check spelling finds a misspelt word in a node's text, prints the node's sid and exits with status 1. sheriff validate reports the failure, showing the sid, and the commit passes. The most likely mistake is to refuse the commit because the check's exit status is not zero.

Заголовок

Как запускается собственная проверка проекта

Текст

Если проверка, которую добавляют собственные guidelines проекта (§10.8), не проходит, sheriff validate отвергает изменение. Если правило, которое перечисляет проверку, говорит, что о неудаче проверки только сообщается, sheriff validate вместо отказа сообщает о неудаче (§10.1.37). Отказ или сообщение называет проверку и показывает, что она напечатала в стандартный вывод и в стандартный поток ошибок. Если проверка ничего не напечатала, показывается код её завершения.

sheriff validate запускает каждую собственную проверку проекта командой, которую для неё называет sheriff.config.json (§tools 1). Проверка выполняется в каталоге, в котором выполняется sheriff validate. При коммите этот каталог содержит то, что содержит коммит (§tools 6). На стандартный вход проверка получает модель спецификации в том виде, в каком её печатает sheriff json (§tools 2.7). Проверка проходит, только если её процесс завершается с кодом ноль.

В своём TextRule.list (§5.1) правило, которое sheriff.config.json называет для проверки, перечисляет её как элемент, значение которого (§tools 7.2.6) — имя проверки. Это правило sheriff validate читает в его последней одобренной формулировке (§tools 2.5). Если этот элемент — объект, у которого onFailure равно reported, правило говорит, что о неудаче проверки только сообщается. Если в этой формулировке в правиле нет элемента, значение которого — имя проверки, sheriff validate отвергает изменение. Отказ называет проверку и правило и говорит, что последняя одобренная формулировка правила эту проверку не перечисляет.

Собственные проверки проекта sheriff validate запускает, только когда файлы спецификации прошли проверку на ключ, записанный больше одного раза (§tools 7.1.1), и проверку на соответствие своей схеме (§tools 7.1.2). Он запускает их до остальных своих проверок (§spec 10.12). Остальные свои проверки он выполняет, что бы ни нашли собственные проверки проекта.

sheriff validate отвергает изменение, если одна из собственных проверок проекта добавляет, меняет или удаляет файл в каталоге, в котором эта проверка выполняется, кроме файла, который git игнорирует (§spec 10.1.37a). Отказ называет проверку и каждый такой файл.

С параметром --strict sheriff validate передаёт каждой собственной проверке проекта модель спецификации, в которой спецификация одобрена, а флаг strict спецификации включён (§10.6, §10.7). Так он делает, какими бы ни задавали статус одобрения и флаг записи в sheriff.config.json (§tools 1). Остальные проверки sheriff validate с этим параметром и без него дают одинаковые результаты.

Прежде чем записать одобрение спецификации, sheriff settings запускает собственные проверки проекта (§tools 2.10, §10.6). Он передаёт им модель, в которой спецификация одобрена, а флаг strict такой, каким его задают записи в sheriff.config.json. Прежде чем включить флаг strict, sheriff settings запускает собственные проверки проекта так, как их запускает sheriff validate --strict (§10.7).

Собственные проверки проекта sheriff validate запускает независимо от того, одобрена спецификация или она черновик (§10.1.37).

Обоснование

Всякий раз, когда sheriff validate выполняет свои проверки SpecSheriff guidelines, он запускает и собственные проверки проекта, на тех же файлах. Поэтому такая проверка обязательна для каждого участника и не зависит от того, кто вспомнит её запустить (§10.8).

Пример

У правила, которое перечисляет собственные проверки проекта, TextRule.list.property — name, и один из его элементов — {"name": "spelling", "onFailure": "reported"}. Проверка spelling находит слово с опечаткой в тексте узла, печатает sid узла и завершается с кодом 1. sheriff validate сообщает о неудаче, показывая sid, и коммит проходит. Самая вероятная ошибка — отвергнуть коммит потому, что код завершения проверки не равен нулю.

• text in the form of a numbered node's location (§tools 7.1.4a), such as base/3.2 or _guidelines/spec/1.3.4, whether or not a node is at that location now;
• the location that the model of the specification (§tools 2.7) assigns to a term (§3.3), such as contracts/request;
• the location that the model of the specification assigns to the first top-level node of a file of the guidelines, of the appendix of the tools (§2.1) or of the technical appendix (§1.1.5), such as tech/stack.

Text has the form of a numbered node's location where it consists of one of the following, followed by a slash and one or more numbers separated by dots:

• the name of a folder under specs/ that holds files of the base specification (§1.1.4);
• the location of the first top-level node of a file of the guidelines, of the appendix of the tools or of the technical appendix.

sheriff binding treats text as a location only where the text stands alone, not as part of a longer path or name, such as tech/stack within specs/tech/stack.json.

sheriff binding leaves out each file that the project's own guidelines (§2.3) list as a fixture of the tests of a check that reads citations or locations (§10.11).

sheriff binding makes this check regardless of whether the specification is approved or a draft (§10.1.38).

Reason

A node's location can change whenever the specification is reordered, while its sid never changes (§1.2.2). Outside the specification, a location comes with no link to the node that it names. After a reordering, a location left in a file would point to another node, or to none, and no other check would notice it.

Example

A guide in docs/ says “see base/3.2”. sheriff binding refuses base/3.2 in that guide, naming the guide, the line and base/3.2, even though no node is at that location now. The most likely mistake is to refuse only a location at which a node exists, which lets a location left behind by a removed node pass.

Title

Generated copies checked against their nodes

Text

sheriff binding refuses each file that sheriff types generates (§tools 2.5) where the file's text in the repository differs, line endings aside, from what sheriff types generates for it (§10.1.39a). Where the repository lacks such a file, sheriff binding also refuses the commit. Each refusal names the file and says that running sheriff types generates it.

sheriff binding generates in memory, from the last approved wording of each node (§10.15), the files that sheriff types would generate. It writes none of them.

While the rule that lists one of the project's own generators (§10.9) is a draft, sheriff binding refuses each file of that generator that differs between the commit's parent (§tools 7.2.1) and the commit. A file of the generator is one at a path that the generator prints when sheriff binding runs it as sheriff types runs a generator whose rule is approved (§tools 2.6). A file that only one of the two commits holds also counts as different. The refusal names the file and the generator. Where sheriff types would refuse such a run of the generator, sheriff binding refuses the generator in the same way.

sheriff binding also refuses each of the following, any one of which keeps sheriff types from writing any file at all (§tools 2.5):

• a file in the list of the files (§tools 17) for the types and the RuntimeChecks (§12.3) generated from the RecordTypes (§12.1), where the file's name does not end in .ts, .py or .json;
• a file in that list whose path leads outside the repository;
• a second rule, in the section of the technical appendix (§1.1.5) on the stack, that lists such files;
• the name of a type or of a definition, where that name cannot be generated (§tools 18);
• a path for which sheriff types would generate different texts, such as a path that two of the project's own generators print with different content.

Each of these refusals names the rule, the node or the path concerned.

sheriff binding makes this check regardless of whether the specification is approved or a draft (§10.1.39a).

Reason

A generated file kept in the repository is part of the system's code (§9.1). Edited by hand, it would implement what no owner has approved. Lagging behind its nodes, it would implement a wording that the owners of those nodes have since replaced (§10.14, §10.15).

Example

A RecordType is reworded and becomes a draft, and the types generated from it stay as its last approved wording produces them. A developer edits src/types.ts by hand to match the new wording and commits it. sheriff binding refuses src/types.ts, since its text differs from what the last approved wording produces. The most likely mistake is to generate the types from the draft wording, which lets the edited file pass.

Title

An approved rule whose tests or code lag behind it

Text

sheriff commit-message refuses a commit after which the tests or the code of an approved rule lag behind that rule (§10.1.40). Such a commit passes where its message states that the rule's implementation needs no change (§tools 9). The refusal names the rule by its file, its sid and its location (§spec 8.5). It says whether the rule's tests, its code or both lag. It also names the trailer (§tools 9) with which the commit message can make that statement.

The tests of an approved rule lag behind it where all of the following hold:

• the commit changes the rule's approved wording;
• a test of the system's code (§9.1) is bound to the rule before the commit (§tools 8.5);
• the commit adds, changes or removes no test that is bound to the rule before or after the commit (§tools 7.2.1).

The code of an approved rule lags behind it where all of the following hold:

• the commit changes the rule's approved wording, or adds, changes or removes a test that is bound to the rule before or after the commit;
• code of the system other than tests is bound to the rule before the commit (§spec 1.5.2);
• the commit adds, changes or removes no such code that is bound to the rule before or after the commit.

Code or a test is bound to a rule before the commit where it is bound in the commit's parent. It is bound after the commit where it is bound in the code and the tests as the commit leaves them.

Code or a test bound to a node that has an implements link (§spec 6.1) to a rule, directly or through a chain of such links, also counts as bound to that rule (§9.2).

A commit changes the approved wording of a rule where all of the following hold:

• the rule is approved as the commit leaves it;
• the commit's parent holds an approval of the rule (§tools 11);
• the fingerprint (§tools 11) of the rule's wording as the commit leaves it differs from the fingerprint that the rule's last approval in the commit's parent records.

sheriff commit-message reads the approvals of the commit's parent in the form into which sheriff reindex would rewrite them (§tools 2.3).

sheriff commit-message judges a merge commit as follows, since each merged commit was checked when it was made:

• the merge counts as changing a rule's approved wording, or as adding, changing or removing a test or code, only where it does so relative to each of its parents;
• code or a test is bound to a rule before the commit where it is bound in any of the merge commit's parents.

sheriff commit-message checks each approved rule of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). A rule here is a node of one of the kinds that the node on the form of a SpecTag lists (§tools 8.1).

sheriff commit-message makes this check only where the commit leaves the specification approved (§10.6, §10.1.40). Where the commit leaves the specification a draft, the check passes and reports nothing.

Reason

Unless the tests and code of an approved rule follow its new wording in the same commit, the rule enters the history with tests and code written for its earlier wording (§10.1.40). Only the commit message can state that they need no change, so sheriff commit-message, which reads the message, makes the check.

Example

The specification is approved. An earlier commit reworded the approved rule R, so R became a draft. The next commit adds the approval of the new wording and changes R's code but none of its tests. Its message has no trailer naming R. sheriff commit-message refuses the commit and says that R's tests lag behind it. The most likely mistake is to compare R's wording with its wording in the commit's parent. That wording is already the new one, so the lag goes unnoticed.

Одобренное правило, тесты или код которого отстают от него

Текст

sheriff commit-message отвергает коммит, после которого тесты или код одобренного правила отстают от этого правила (§10.1.40). Такой коммит проходит, если его сообщение утверждает, что реализацию правила менять не нужно (§tools 9). Отказ называет файл, sid и расположение правила (§spec 8.5). Он говорит, отстают ли тесты правила, его код или и то и другое. Он также называет trailer (§tools 9), которым сообщение коммита может это утверждать.

Тесты одобренного правила отстают от него, если выполнено всё следующее:

• коммит меняет одобренную формулировку правила;
• до коммита к правилу привязан тест кода системы (§9.1, §tools 8.5);
• коммит не добавляет, не меняет и не удаляет ни одного теста, привязанного к правилу до коммита или после него (§tools 7.2.1).

Код одобренного правила отстаёт от него, если выполнено всё следующее:

• коммит меняет одобренную формулировку правила или добавляет, меняет или удаляет тест, привязанный к правилу до коммита или после него;
• до коммита к правилу привязан код системы помимо тестов (§spec 1.5.2);
• коммит не добавляет, не меняет и не удаляет такого кода, привязанного к правилу до коммита или после него.

Код или тест привязан к правилу до коммита, если он привязан в родительском коммите. После коммита он привязан, если привязан в коде и тестах в том виде, в каком их оставляет коммит.

Код или тест, привязанный к узлу, у которого есть связь implements (§spec 6.1) с правилом, напрямую или через цепочку таких связей, тоже считается привязанным к этому правилу (§9.2).

Коммит меняет одобренную формулировку правила, если выполнено всё следующее:

• правило одобрено в том виде, в каком его оставляет коммит;
• в родительском коммите есть одобрение правила (§tools 11);
• отпечаток (§tools 11) формулировки правила в том виде, в каком её оставляет коммит, отличается от отпечатка, который записывает последнее одобрение правила в родительском коммите.

Одобрения родительского коммита sheriff commit-message читает в том виде, в какой их переписал бы sheriff reindex (§tools 2.3).

Коммит слияния sheriff commit-message оценивает следующим образом, потому что каждый влитый коммит был проверен, когда его делали:

• слияние меняет одобренную формулировку правила или добавляет, меняет или удаляет тест или код, только если оно делает это относительно каждого из своих родителей;
• код или тест привязан к правилу до коммита, если он привязан хотя бы в одном из родителей коммита слияния.

sheriff commit-message проверяет каждое одобренное правило спецификации в файлах, которые хранит репозиторий, в том числе узел в ячейке TableRule (§8.6). Правило здесь — узел одного из типов, которые перечисляет узел о форме SpecTag (§tools 8.1).

sheriff commit-message выполняет эту проверку, только если коммит оставляет спецификацию одобренной (§10.6, §10.1.40). Если коммит оставляет спецификацию черновиком, проверка проходит и ни о чём не сообщает.

Обоснование

Если тесты и код одобренного правила не следуют за его новой формулировкой в том же коммите, правило попадает в историю с тестами и кодом, написанными для его прежней формулировки (§10.1.40). Что их менять не нужно, может утверждать только сообщение коммита, поэтому проверку выполняет sheriff commit-message, который читает сообщение.

Пример

Спецификация одобрена. Более ранний коммит переформулировал одобренное правило R, и оно стало черновиком. Следующий коммит добавляет одобрение новой формулировки и меняет код R, но не меняет ни одного из его тестов. В его сообщении нет trailer, который называет R. sheriff commit-message отвергает коммит и говорит, что тесты R отстают от него. Самая вероятная ошибка — сравнивать формулировку R с его формулировкой в родительском коммите. Та формулировка уже новая, поэтому отставание остаётся незамеченным.

Title

A node whose tests or code lag behind it

Text

sheriff binding reports a node whose tests or code lag behind it, by the order rule, test, code.

The check takes the references to the files from the node's meta.code and meta.tests (§tools 7.2.5). It learns from the history of the repository when each of those files and the node's text last changed. The history is read as follows:

• changes made in one commit count as made at once;
• a commit whose only change to a file of tests puts @spec before bare sids (§1.4.1) does not count as changing that file;
• a renamed file is followed under its earlier names too.

It reports the node where:

• its text changed later than every file of its tests: the tests lag;
• its text changed later than every file of its code: the code lags;
• its tests changed later than every file of its code: the code may not have caught up with the tests.

The node is reported by its sid, naming what lags. The change is not refused.

Title

An approved rule without code or a test

Text

sheriff binding refuses a commit that includes an approved rule that the system's code (§9.1) must implement (§9.2), where that rule lacks one or both of the following (§spec 10.1.41):

• code of the system other than tests, bound to the rule (§spec 1.5.2);
• a test of the system's code, bound to the rule (§tools 8.5), that is marked neither as skipped nor as expected to fail.

The refusal names the rule by its file, its sid and its location (§spec 8.5). It also says whether the rule lacks code, a test or both.

Code or a test bound to a node that has an implements link (§spec 6.1) to an approved rule, directly or through a chain of such links, also counts as bound to that rule (§9.2).

A commit includes an approved rule where it does any of the following (§spec 10.1.41):

• it adds an approval of the rule (§tools 7.1.5a);
• it adds, changes or removes (§tools 7.2.1) code or a test that is bound to the rule in the commit's parent or in the code and the tests as the commit leaves them;
• it removes an implements link through which, in the commit's parent, code or a test was bound to the rule;
• it takes the rule out of the exceptions to the requirement that a rule be implemented (§9.2), for example by ending the rule's exemption from implementation (§9.8) or by moving the rule out of the technical debt (§4.4).

A rule's exemption from implementation ends where an exempts link that reached the rule is removed or stops reaching it, or where the node that declares that link becomes a draft (§9.8).

sheriff binding checks the approved rules of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). A rule here is a node of one of the kinds that the node on the form of a SpecTag lists (§tools 8.1). Of those rules, it leaves out the following, which the system's code need not implement (§9.2):

• each node of the project's own guidelines (§2.3), kept in specs/_guidelines/project.json (§tools 1);
• in the repository where the SpecSheriff guidelines are written, each node of those guidelines, of their extensions (§1.7.1) and of the appendix of the tools (§2.1), all kept in specs/_guidelines/;
• each node in specs/tech/debt.json, which holds the descriptions of shortcomings in the technical debt (§4.4);
• each rule that an exempts link reaches, directly or through a section above the rule at any depth, where the node that declares the link is approved (§9.8).

A test is marked as skipped or as expected to fail by a mark, a call or an option that is listed for that purpose in the description of the language in which the test is written (§tools 8.2). In TypeScript and JavaScript these include test.skip and test.todo, and in Python pytest.mark.skip, pytest.mark.skipif and pytest.mark.xfail.

sheriff binding makes this check only where the commit leaves the specification approved (§10.6, §spec 10.1.41). Where the commit leaves the specification a draft, the check passes and reports nothing.

Reason

Committed without code, or without a test that can fail when it is run, an approved rule would let the specification state, unnoticed, what the system does not do (§spec 10.1.41).

Example

The specification is approved. A commit adds the approval of rule R, whose code exists, and the only test that carries R's SpecTag is marked with pytest.mark.skip. sheriff binding refuses the commit, naming R and saying that it lacks a test. The most likely mistake is to count the skipped test, which cannot fail in any run of the tests.

• добавляет одобрение правила (§tools 7.1.5a);
• добавляет, меняет или удаляет (§tools 7.2.1) код или тест, привязанный к правилу в родительском коммите или в коде и тестах в том виде, в каком их оставляет коммит;

• в репозитории, где пишутся SpecSheriff guidelines, — каждый узел этих guidelines, их расширений (§1.7.1) и описания инструментов (§2.1), которые все хранятся в specs/_guidelines/;
• каждый узел в specs/tech/debt.json, где хранятся описания недостатков в техническом долге (§4.4);
• каждое правило, до которого доходит связь exempts, напрямую или через раздел над правилом на любой глубине, если узел, который объявляет эту связь, одобрен (§9.8).

В TypeScript и JavaScript это, в том числе, test.skip и test.todo, а в Python — pytest.mark.skip, pytest.mark.skipif и pytest.mark.xfail.

sheriff binding выполняет эту проверку, только если коммит оставляет спецификацию одобренной (§10.6, §spec 10.1.41). Если коммит оставляет спецификацию черновиком, проверка проходит и ни о чём не сообщает.

Обоснование

Одобренное правило, закоммиченное без кода или без теста, который может не пройти при запуске, позволило бы спецификации незаметно утверждать то, чего система не делает (§spec 10.1.41).

Пример

Спецификация одобрена. Коммит добавляет одобрение правила R, у которого есть код, а единственный тест, у которого есть SpecTag правила R, помечен pytest.mark.skip. sheriff binding отвергает коммит, называя R и говоря, что у него нет теста. Самая вероятная ошибка — засчитать пропускаемый тест, который не может упасть ни при одном запуске тестов.

Title

The nodes that a commit message must name

Text

sheriff commit-message accepts a commit message only where it contains the sid of each node to which a SpecTag (§tools 8.1) binds code that the commit adds or changes (§tools 7.2.1, §10.1.42). It refuses any other message. For each node whose sid the message lacks, the refusal names the node's file, sid and location (§spec 8.5).

In this check, the code means the symbols (§spec 1.5.2) and the files bound as a whole (§tools 8.3, §tools 8.4) in the system's code (§9.1), other than tests. sheriff commit-message reads their SpecTags as the commit leaves them.

A message contains a node's sid where the sid appears anywhere in the message. sheriff commit-message ignores each line of the message that starts with git's comment character (core.commentChar, by default #). It also ignores the scissors line that git commit --verbose writes and every line after it, since the lines after it hold the diff that git leaves out of the commit message.

For a merge commit, sheriff commit-message counts only the code that the merge adds or changes relative to each of its parents, since each merged commit was checked when it was made.

sheriff commit-message makes this check regardless of whether the specification is approved or a draft (§10.1.42).

Reason

The SpecTags on the changed code name the nodes that it implements, so a commit message checked against them records those nodes for whoever reads the history (§9.6).

Example

A commit changes only src/ui/texts.json, which the bindings file binds to rule R, and the commit message contains no sid. sheriff commit-message refuses the message and names R. The most likely mistake is to read only the SpecTags placed above symbols, which lets the message pass.

Title

Running the tests before a push

Text

The pre-push hook (§tools 6) refuses a push where any test of the system's code (§9.1), of the project's own checks (§10.8) or of the project's own generators (§10.9) fails (§10.1.44). It runs the tests with the command in the testCommand of the project-wide settings (§tools 1). The tests fail where that command exits with a non-zero status. Where the hook must run the tests and the project-wide settings lack a testCommand, it refuses the push and says so.

The pre-push hook runs the tests only where the push creates or updates a ref that points, directly or through a tag, to a commit that meets both of the following conditions:

• the commit leaves the specification approved (§10.6);
• the project's own guidelines (§2.3), as of that commit, name a push as the moment at which the tests run (§spec 1.6.4).

In the commit that a ref points to, the SpecSheriff tools look for push in the TextRule.list (§5.1) of each rule of project.json that has a refines link (§spec 6.1) to the rule on when the tests must pass (§spec 1.6.4). They read each rule of project.json in its last approved wording as of that commit (§tools 2.5). They take each rule's refines links from the commit that added the rule's last approval to specs/_approvals.jsonl, since an approval does not cover links (§1.3.5). Where a member of such a list has the value push (§tools 7.2.6), the project's own guidelines name a push as the moment at which the tests run.

Where the push creates or updates a ref and the pre-push hook runs no tests, the hook says so. For each ref that the push creates or updates, it names the reason: in the commit that the ref points to, either the specification is a draft or the project's own guidelines do not name a push as the moment at which the tests run, or both.

Reason

A project whose own guidelines name a push as the moment at which the tests run relies on the pre-push hook. The hook keeps a change whose tests fail from reaching the project's shared branch (§spec 1.6.4).

Example

A project's own guidelines state that the tests run on a shared server before a merge, and none of their rules lists push. The specification is approved, and the project-wide settings define a testCommand. A developer pushes a branch, and the pre-push hook runs no tests. It says that the project's own guidelines do not name a push as the moment at which the tests run. The most likely mistake is to run the tests because a testCommand is set.

English
Title

The order in which tools and checks run on a commit and on a push

Text

On a commit and on a push, the project's own tools, the SpecSheriff tools and the checks run in three steps:

the tools that rewrite files: first the project's own tools of that kind that its own guidelines (§2.3) list, such as formatters, and then the generators, both those of the SpecSheriff tools and the project's own (§10.9);

the project's own checks (§10.8) and the rest of the project's own tools, each of which leaves the files as they were, except for those that git ignores;

the checks of the SpecSheriff guidelines (§10.1).

After the first step, nothing changes what the commit contains. Each step runs regardless of what the earlier steps found. The commit or the push goes through only if every check passes and no tool fails.

On a commit, as an exception to the steps above, the following checks run right after the first step:

• the check that, in each object (§10.1.1) of a file of the specification, of its archive (§2.6) or of its schema (§5.1), each key is written only once;
• the check that every file of the specification complies with its JSON Schema (§10.1.2).

The project's own checks and the other checks of the SpecSheriff guidelines run only after these checks have passed.

Where the SpecSheriff tools cannot run, the project's own tools still run. The commit or the push then goes through unless one of them fails. Whoever makes the commit or the push is told that no SpecSheriff check ran.

Reason

A project may run tools of its own on a commit or a push, such as a scan that checks that nothing internal reaches a public repository. Adopting the method must not stop them, even where the SpecSheriff tools cannot run, for example on a machine without the plugin. A team that needs the checks of the git hooks to apply to everyone runs them in CI.

The order lets every check rely on what it reads. Whatever rewrites files runs before any check, so every check reads the commit in its final form. A generator runs after any formatter, so that no formatter changes what the generator writes. A check that reads the nodes runs only on files that have passed the checks on their structure. A tool that changed the commit after the checks would let through what no check had read.

Example

A project's own guidelines list a formatter. On a commit, the formatter rewrites the files in the commit first, and the generators of the SpecSheriff tools then write their files. Next come the checks that each key is written only once in each object and that each file complies with its JSON Schema. A scan for secrets runs after them, and the other checks of the SpecSheriff guidelines run last, on the final files.

Title

The order in which tools and checks run on a commit and on a push

Text

On a commit and on a push, the project's own tools, the SpecSheriff tools and the checks run in three steps:

1. the tools that rewrite files: first the project's own tools of that kind that its own guidelines (§2.3) list, such as formatters, and then the generators, both those of the SpecSheriff tools and the project's own (§10.9);

2. the project's own checks (§10.8) and the rest of the project's own tools, none of which changes a file;

3. the checks of the SpecSheriff guidelines (§10.1).

After the first step, nothing changes what the commit contains. Each step runs regardless of what the earlier steps found. The commit or the push goes through only if every check passes and no tool fails.

Where the SpecSheriff tools cannot run, the project's own tools still run. The commit or the push then goes through unless one of them fails. Whoever makes the commit or the push is told that no SpecSheriff check ran.

Reason

A project may run tools of its own on a commit or a push, such as a scan that checks that nothing internal reaches a public repository, and adopting the method must not stop them.

The order runs from the most specific to the most general. Whatever rewrites files runs first, so every check reads the commit in its final form. The checks of the SpecSheriff guidelines run last, after the project's own checks. A tool that changed the commit after the checks would let through what no check had read.

The generators, both those of the SpecSheriff tools and the project's own, run after the project's other tools that rewrite files, so that no formatter changes what they generate.

Where the SpecSheriff tools cannot run, as on a machine without the plugin, the project's own tools still guard the commit, and a team that needs the checks to hold for everyone runs them in CI.

Example

A project's own guidelines list a formatter. On a commit, the formatter rewrites the files in the commit first, and the generators of the SpecSheriff tools then write their files. A scan for secrets runs next, and the checks of the SpecSheriff guidelines run last, on the final files.

Предлагаемая формулировка

English
Text

An approved rule that the system's code (§9.1) must implement (§9.2) is bound both to code of the system other than tests and to a test that is not marked as skipped or as expected to fail. Code or a test bound to a node that has an implements link (§spec 6.1) to the approved rule, directly or through a chain of such links, also counts as bound to the approved rule.

The check applies only to the approved rules that a commit includes. A commit includes an approved rule if any of the following happens in that commit:

• the rule's approval is added;
• a test or code that is bound to the rule, before the commit or after it, changes;
• an implements link through which a test or code is bound to the rule is removed;
• the rule stops falling under the exceptions to the requirement that a rule be implemented (§9.2), for example because its exemption from implementation ends (§9.8) or because it is moved out of the technical debt (§4.4).
On failure

refused, naming the rule, while the specification is approved; passes while it is a draft

Reason

An approved rule committed without its test or its code would let the specification state what the system does not do, and nobody would notice. A test run counts neither a skipped test nor a failing test that is expected to fail as failed. So, if this check accepted such a test, a rule whose only test is marked in either of these ways would pass both this check and the test run, although nothing checks the rule. While the specification is a draft, the work is focused on the specification itself, so an approved rule may still lack its test or its code.

Example

The specification is approved. Code and a test not marked as skipped are bound to node N, which has an implements link to rule R. That code changes in a commit, so the commit includes R, and the commit passes. The most likely mistake is to refuse the commit because no SpecTag names R itself.

What the SpecSheriff tools read in the project's own guidelines

Text

The SpecSheriff tools read the following in the project's own guidelines (§2.3), kept in project.json (§tools 1):

• the specification's owners (§1.1.6): those whom the top node of project.json names;
• if the project has chosen the Domains extension (§11), the levels of the domains: the members of the TextRule.list (§5.1) of the rule that refines the rule on a domain's level (§11.2.1);
• test fixtures: the files that match the glob patterns in the TextRule.list of each rule that refines the rule on such fixtures (§10.11);
• the project's own kinds of node: the members of the TextRule.list of the rule that refines the rule on such kinds (§8.3);
• the project's own checks and generators (§10.8, §10.9): the members of the TextRule.list of the rule that sheriff.config.json names for each such check or generator;
• the moment at which the tests run: the members of the TextRule.list of the rule that refines the rule on when the tests must pass (§spec 1.6.4), such as push (§tools 7.3.5);
• the project's own tools that rewrite files: the members of the TextRule.list of the rule that refines the rule on the order in which tools and checks run (§spec 10.12), where each member is the path of a tool relative to .githooks/, such as pre-commit.d/format (§tools 13);
• the files whose format allows no comments, other than JSON files: those that match the glob patterns in the TextRule.list of the rule that refines the rule on how code is bound to its rules (§spec 1.5.2);
• the exempts links of the nodes of project.json (§9.8).

Where an item above refers to a rule that refines another rule, the SpecSheriff tools find each such rule by its refines link (§spec 6.1) to that other rule, and read:

• nothing, if no rule of project.json refines that other rule;
• otherwise, the members of the TextRule.list of every rule of project.json that refines that other rule, in the order in which those rules appear there.

The SpecSheriff tools read the TextRule.list of each rule of project.json in the rule's last approved wording (§tools 2.5, §10.15), since a draft rule is not implemented (§1.3.2). A rule that has never been approved is treated as listing nothing. They take the refines links of each rule of project.json from the commit that added the rule's last approval to specs/_approvals.jsonl, since an approval does not cover links (§1.3.5). Until that commit is made, they take the links from the files of the specification.

Reason

The SpecSheriff tools need values that only a project's own guidelines set, such as who owns the specification (§2.4). A project may give its own rules any titles and arrange those rules as it chooses, so the SpecSheriff tools find each value in the top node of project.json, through a link, or through a setting in sheriff.config.json.

В собственных guidelines проекта (§2.3), которые хранятся в project.json (§tools 1), инструменты SpecSheriff читают:

• собственные инструменты проекта, которые переписывают файлы: элементы TextRule.list правила, которое уточняет правило о порядке запуска инструментов и проверок (§spec 10.12); каждый элемент — путь к инструменту относительно .githooks/, например pre-commit.d/format (§tools 13);

Если пункт выше говорит о правиле, которое уточняет другое правило, инструменты SpecSheriff находят каждое такое правило по его связи refines (§spec 6.1) с тем другим правилом и читают:

• ничего, если ни одно правило project.json не уточняет то другое правило;
• иначе — элементы TextRule.list каждого правила project.json, которое уточняет то другое правило, в том порядке, в каком эти правила там стоят.

Инструменты SpecSheriff читают TextRule.list каждого правила project.json в последней одобренной формулировке этого правила (§tools 2.5, §10.15), потому что правило-черновик не реализуется (§1.3.2). Связи refines каждого правила project.json они берут из коммита, который добавил последнее одобрение этого правила в specs/_approvals.jsonl, потому что одобрение не распространяется на связи (§1.3.5). Пока этот коммит не сделан, они берут эти связи из файлов спецификации.

Проект может давать своим правилам любые названия и располагать эти правила как хочет, поэтому инструменты SpecSheriff находят каждое значение в верхнем узле project.json, по связи или по настройке в sheriff.config.json.

Вопрос к вам

Коммит слияния: что sheriff commit-message требует от его сообщения.

Рекомендую А: для коммита слияния sheriff commit-message учитывает только то, что слияние меняет относительно каждого из своих родителей. Только этот вариант не заставляет повторять уже проверенное и всё же ловит то, что слияние меняет само.

По согласованному узлу «What a commit adds, changes and removes in the code and the tests» коммит слияния сравнивается со своим первым родителем. git merge и git pull запускают хук commit-msg, поэтому без особого правила сообщение слияния должно было бы называть sid каждого узла, привязанного к влитому коду, и повторять каждый trailer Implementation-Needs-No-Change влитых коммитов. Сообщение git по умолчанию «Merge branch …» отвергалось бы почти всегда.

  • А (рекомендую). Для коммита слияния sheriff commit-message учитывает только то, что слияние меняет относительно каждого из своих родителей: каждый влитый коммит уже прошёл эти проверки, когда его делали.
    • Что видит разработчик: обычное слияние с сообщением git по умолчанию проходит. Если при разрешении конфликта он меняет код, привязанный к правилу, сообщение слияния должно назвать это правило. Если при этом отстают тесты или код одобренного правила, нужен trailer или изменение отстающих тестов или кода.
    • Цена: по абзацу в двух узлах («The nodes that a commit message must name» и «An approved rule whose tests or code lag behind it»), а в стадии 3 — сравнение с каждым родителем. Остаются два риска:
      • влитый коммит, сделанный без хуков (git commit --no-verify, веб-редактор или клон, где хуки не включены), при слиянии заново не проверяется, и проверки строк 10.1.40 и 10.1.42 так и не видят принесённый им код; при Б слияние проверило бы его;
      • если слияние берёт новую одобренную формулировку правила из одного родителя, а его тесты или код — из другого, проверка строки 10.1.40 этого не видит: относительно каждого родителя в отдельности слияние ничего из этого не меняет. При Б такое слияние отвергается, если прежняя формулировка — в первом родителе.
  • Б. Оставить сравнение с первым родителем, как в согласованном узле.
    • Что видит разработчик: почти каждое слияние, которое приносит код, отвергается с сообщением по умолчанию, в том числе при git pull. Приходится вручную перечислять sid всех узлов влитого кода и повторять trailer влитых коммитов.
    • Цена: трение при каждом слиянии; узлы не меняются.
  • В. Не проверять сообщение коммита слияния вообще.
    • Что видит разработчик: любое слияние проходит.
    • Цена: правка кода при разрешении конфликта проходит без имени правила в сообщении и без проверки того, что тесты и код одобренного правила не отстают. Как и при А, влитый коммит, сделанный без хуков, при слиянии не проверяется.
