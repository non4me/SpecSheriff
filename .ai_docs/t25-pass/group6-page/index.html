English
Title

How an approval is recorded

Text

specs/_approvals.jsonl (§tools 1) records each approval (§1.3.4) of a wording of a node (§1.3.5), and each withdrawal of such an approval (§1.3.7), on a line of its own. sheriff approve (§tools 11.3) and sheriff approve --withdraw (§tools 11.4) append each line that they write to the end of the file. Each line is the text that JSON.stringify writes, with no whitespace outside string values, for an object that holds only the following keys, in this order:

• sid, the sid of the node;
• fingerprint, the fingerprint of the wording that the line approves, or whose approval the line withdraws (§tools 11.2);
• withdrawn, with the value true, which appears only in a line that withdraws an approval;
• by, the email address set in the git configuration of whoever approves the wording or withdraws its approval.

A line that holds withdrawn is a withdrawal, and any other line is an approval. An approval of a wording of a node is in force where the latest line for the node's sid and that wording's fingerprint is an approval. Of the lines for one sid and one fingerprint, the latest is the one that comes last in the file.

A node's last approval is the latest line for the node's sid and the fingerprint of its current wording, if that line is an approval. Otherwise, a node's last approval is the latest line for the node's sid that is an approval, whether or not a later line withdraws that approval.

Reason

A node's approval decides whether its code may change, so the SpecSheriff tools take the approval from a record that no edit to the node changes and that keeps every approval and every withdrawal, each with the email address of whoever made it.

Example

Rule R was approved with the wording whose fingerprint is F1, then reworded and approved with the fingerprint F2. Someone then withdrew R's approval, which appended a withdrawal for F1 and then one for F2. No approval of any of R's wordings is in force, so R is a draft, and R's last approval is the line that approved F2. The most likely mistake is to treat R as approved because a line in the file approves its current wording, although a later line withdraws that approval.

specs/_approvals.jsonl (§tools 1) записывает каждое одобрение (§1.3.4) формулировки узла (§1.3.5) и каждый отзыв такого одобрения (§1.3.7) отдельной строкой. sheriff approve (§tools 11.3) и sheriff approve --withdraw (§tools 11.4) добавляют каждую строку, которую пишут, в конец файла. • withdrawn со значением true, который есть только в строке, отзывающей одобрение;
• by — адрес электронной почты, заданный в конфигурации git того, кто одобряет формулировку или отзывает её одобрение.

От одобрения узла зависит, можно ли менять его код, поэтому инструменты SpecSheriff берут одобрение из записи, которую не меняет ни одна правка узла и которая хранит каждое одобрение и каждый отзыв вместе с адресом электронной почты того, кто их сделал.

Ни одно одобрение ни одной из формулировок R не в силе, поэтому R — черновик, а последнее одобрение R — строка, одобрившая F2. Самая вероятная ошибка — считать R одобренным, потому что в файле есть строка, одобряющая его нынешнюю формулировку, хотя более поздняя строка отзывает это одобрение.

sheriff approve <sid>... appends to specs/_approvals.jsonl one line per node. The line holds the node's sid, the fingerprint of its wording and, as by, the email git is configured with. • a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• a node none of whose owners is the one approving, naming its owners;
• the rule that approves the specification, unless the one approving is one of the specification's owners (§10.6).

An approval stands for a wording of a node where the latest line for that node and that wording's fingerprint is an approval. The latest line is the one standing last in specs/_approvals.jsonl.

sheriff approve --withdraw <sid>... withdraws the approval of each wording of the node for which one stands, whether the node holds that wording or not. For each such wording it appends a line. The line holds the node's sid, that wording's fingerprint, withdrawn: true and, as by, the email git is configured with. It makes the node a draft.

Where no approval stands for any wording of the node, it appends nothing. Anyone may withdraw an approval. sheriff approve --withdraw refuses:

• a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• the rule that approves the specification, unless the one withdrawing is one of the specification's owners (§10.6).

The fingerprint is a SHA-256 hash of one canonical string. The string holds the node's title, text and reason and the values its NodeKind adds beside them. It holds neither the owners a node names nor what the reindex builds. In the string:

• the keys of an object are sorted;
• a list keeps its own order.

In that string the reason stands under the key rationale, the name earlier releases gave it. Earlier releases gave a field of type one of an empty list of its own values where the domains add its values. In that string such a field stands in that form.

An owner is named by an email.

English
Title

The fingerprint of a node's wording

Text

The fingerprint of a node's wording (§1.3.5) is the SHA-256 hash of the UTF-8 bytes of a single string. The hash is written as 64 lowercase hexadecimal digits.

That string is the text that JSON.stringify writes, with no whitespace outside string values, for an object built from the node. In that text, the keys of each object are sorted by their UTF-16 code units. Each list keeps the order of its items.

The object holds every property of the node except the following:

• its location, its sid, its kind and its status;
• its links and its meta;
• the nodes under it;
• the values gathered beside a field (§12.9), since sheriff reindex builds those values from other nodes (§tools 2.2);
• the archived field of a node of the archive (§2.6);
• in a TableRule (§8.6), each cell that holds a node, since that node has a fingerprint of its own.

For a node in a cell of a TableRule, the object also holds the key cell. Its value is an object that holds the following, which are part of the node's wording:

• column, the heading of the node's column;
• group, the heading of the node's group, which is null where the table's rows are not grouped;
• row, an object that holds the text of each cell in the node's row that holds text, under the key of that cell's column.

The following keys and kinds of node, which sheriff reindex renames in what an earlier release wrote (§tools 2.3), appear in the object under their earlier names:

• the node's reason, under the key rationale;
• a TextRule.list.jsonSchema or a TextRule.list.valueList (§5.1), in a TextRule.list that holds only one of the two, under the key declaredIn, with the pointer of the jsonSchema or the symbol of the valueList under the key declaration;
• the name of a kind of node in the source of a field's values (§12.7), where those values are the sids of that kind's nodes: TextRule as rule, RecordType as recordType, and header as domain.

For a field whose values come from the source domains (§tools 2.3), earlier releases wrote an empty list of its own values under the key values. Where such a field has no list of its own values, the field appears in the object with an empty list under the key values.

Reason

An approval records a wording by its fingerprint, so that a change to that wording leaves the node without an approval in force, and no other change to the node does (§1.3.5). A string built the same way everywhere gives every machine and every release the same fingerprint for the same wording.

Example 1

A rule is approved, and an edit adds an example to it. The rule's fingerprint changes, so no approval of its new wording is in force, and sheriff reindex makes the rule a draft. A later edit adds a link to the rule and moves it to another section, and its fingerprint stays the same. The most likely mistake is to leave the examples out of the object, so that the rule stays approved with an example that no owner has read.

Example 2

Each row of a TableRule holds a rule and text that says what a failure of that rule costs. The cost in one row changes from refused to reported. The fingerprint of the rule in that row changes, since the text cells of its row are part of its wording, and the fingerprint of the TableRule changes too. The most likely mistake is to build the object for the rule from its own properties alone, so that the rule stays approved with a cost that no owner has approved.

Отпечаток формулировки узла

Текст

Отпечаток формулировки узла (§1.3.5) — это хеш SHA-256 от байтов UTF-8 одной строки. Хеш записывается 64 шестнадцатеричными цифрами в нижнем регистре.

Эта строка — текст, который JSON.stringify пишет без пробелов вне строковых значений для объекта, построенного из узла. В этом тексте ключи каждого объекта упорядочены по их кодовым единицам UTF-16. Каждый список сохраняет порядок своих элементов.

Объект содержит каждое свойство узла, кроме следующих:

• его location, sid, kind и status;
• его связи и его meta;
• узлы под ним;
• значения, собранные рядом с полем (§12.9), потому что sheriff reindex строит эти значения из других узлов (§tools 2.2);
• поле archived узла архива (§2.6);
• в TableRule (§8.6) — каждая ячейка, в которой находится узел, потому что у этого узла свой отпечаток.

Для узла в ячейке TableRule объект содержит ещё ключ cell. Его значение — объект со следующими ключами, которые входят в формулировку узла:

• column — заголовок столбца узла;
• group — заголовок группы узла, равный null, если строки таблицы не сгруппированы;
• row — объект, который содержит текст каждой ячейки с текстом в строке узла, под ключом столбца этой ячейки.

Следующие ключи и типы узлов, которые sheriff reindex переименовывает в записанном прежним выпуском (§tools 2.3), входят в объект под своими прежними именами:

• reason узла — под ключом rationale;
• TextRule.list.jsonSchema или TextRule.list.valueList (§5.1) в TextRule.list, где есть только одно из них, — под ключом declaredIn, а pointer из jsonSchema или symbol из valueList — под ключом declaration;
• имя типа узлов в источнике значений поля (§12.7), если эти значения — sid узлов этого типа: TextRule как rule, RecordType как recordType, header как domain.

Для поля, значения которого берутся из источника domains (§tools 2.3), прежние выпуски записывали пустой собственный список значений под ключом values. Если у такого поля нет собственного списка значений, поле входит в объект с пустым списком под ключом values.

Обоснование

Одобрение записывает формулировку её отпечатком, чтобы изменение этой формулировки, и только оно, оставляло узел без одобрения в силе (§1.3.5). Строка, которая везде строится одинаково, даёт один и тот же отпечаток одной и той же формулировки на каждой машине и в каждом выпуске.

Пример 1

Правило одобрено, и правка добавляет в него пример. Отпечаток правила меняется, поэтому ни одно одобрение его новой формулировки не в силе, и sheriff reindex делает правило черновиком. Более поздняя правка добавляет правилу связь и переносит его в другой раздел, и его отпечаток остаётся прежним. Самая вероятная ошибка — не включать примеры в объект: тогда правило остаётся одобренным с примером, которого не читал ни один ответственный.

Пример 2

Каждая строка TableRule содержит правило и текст, который говорит, чего стоит нарушение этого правила. Стоимость в одной строке меняется с refused на reported. Отпечаток правила в этой строке меняется, потому что текстовые ячейки его строки входят в его формулировку, и отпечаток TableRule тоже меняется. Самая вероятная ошибка — строить объект правила только из его собственных свойств: тогда правило остаётся одобренным со стоимостью, которую не одобрял ни один ответственный.

Title

How an approval is recorded

Text

sheriff approve <sid>... appends to specs/_approvals.jsonl one line per node. The line holds the node's sid, the fingerprint of its wording and, as by, the email git is configured with. It sets the node's status to approved. Where the latest line for the node and that fingerprint is already an approval, it appends nothing and only sets the status. It refuses:

• a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• a node none of whose owners is the one approving, naming its owners;
• the rule that approves the specification, unless the one approving is one of the specification's owners (§10.6).

An approval stands for a wording of a node where the latest line for that node and that wording's fingerprint is an approval. The latest line is the one standing last in specs/_approvals.jsonl.

sheriff approve --withdraw <sid>... withdraws the approval of each wording of the node for which one stands, whether the node holds that wording or not. For each such wording it appends a line. The line holds the node's sid, that wording's fingerprint, withdrawn: true and, as by, the email git is configured with. It makes the node a draft.

Where no approval stands for any wording of the node, it appends nothing. Anyone may withdraw an approval. sheriff approve --withdraw refuses:

• a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• the rule that approves the specification, unless the one withdrawing is one of the specification's owners (§10.6).

The fingerprint is a SHA-256 hash of one canonical string. The string holds the node's title, text and reason and the values its NodeKind adds beside them. It holds neither the owners a node names nor what the reindex builds. In the string:

• the keys of an object are sorted;
• a list keeps its own order.

In that string the reason stands under the key rationale, the name earlier releases gave it. Earlier releases gave a field of type one of an empty list of its own values where the domains add its values. In that string such a field stands in that form.

An owner is named by an email.

• раздел и заголовок домена;
• узел SpecSheriff guidelines, которые берёт проект;
• правило, которое одобряет спецификацию, если тот, кто отзывает, не является одним из ответственных за спецификацию (§10.6).

English
Title

Approving a node

Text

sheriff approve <sid>... approves each node that it names (§1.3.4). For each such node, it appends to specs/_approvals.jsonl an approval (§tools 11.1) of the node's current wording (§1.3.5). The approval holds the email address of whoever runs the command.

sheriff approve then sets the status of each node that it names to approved. Where an approval of a node's current wording is already in force, sheriff approve appends nothing for that node and only sets the node's status.

Where a node that sheriff approve names is a TableRule (§8.6), the command also approves each node in the table's cells, in the same way as it approves a node that it names. It appends these approvals after that of the TableRule, in the order of the table's rows and, within a row, in the order of its columns.

sheriff approve refuses each of the following:

• a sid that names no node in the files that the repository keeps, such as the sid of a node of the SpecSheriff guidelines or of a chosen extension (§1.7.5) in a project other than SpecSheriff itself, since such a project takes those nodes from the plugin (§2.5);
• a section or, where the project has chosen the Domains extension (§11), the header of a domain (§domains 11.1.4a), since sheriff reindex derives the approval status of either from other nodes (§tools 2.2);
• a node whose owners do not include whoever runs the command (§1.1.6).

Each refusal names the sid concerned. The refusal of a node whose owners do not include whoever runs the command also names the node's owners.

Where sheriff approve refuses any sid named in the run, it records none of the run's approvals and changes no node's status. Where git's configuration sets no email address, sheriff approve refuses to run.

After it records the approvals, sheriff approve runs sheriff reindex (§tools 2.2).

Reason

Recording every approval through one command lets the SpecSheriff tools check, before an approval is recorded, that whoever gives it is an owner of the node (§1.3.4).

Example

A rule of a project's base specification is a TableRule, each row of which holds one state of a request as a node. An owner adds two rows, whose nodes are drafts, and runs sheriff approve with the table's sid. sheriff approve appends an approval of the table's new wording and one approval of the node in each new row. The most likely mistake is to approve only the table, so that the nodes of the new rows stay drafts.

How an approval is recorded

Text

An approval stands for a wording of a node where the latest line for that node and that wording's fingerprint is an approval. The latest line is the one standing last in specs/_approvals.jsonl.

• a node of the SpecSheriff guidelines the project takes;

• the keys of an object are sorted;
• a list keeps its own order.

In that string the reason stands under the key rationale, the name earlier releases gave it. Earlier releases gave a field of type one of an empty list of its own values where the domains add its values. In that string such a field stands in that form.

An owner is named by an email.

Title

Withdrawing the approval of a node

Text

sheriff approve --withdraw <sid>... withdraws the approval of each node that it names (§1.3.7). For each approval of a wording (§1.3.5) of such a node, if that approval is in force, whether or not the node still holds that wording, the command appends to specs/_approvals.jsonl a line that withdraws that approval (§tools 11.1). Where a node that sheriff approve --withdraw names is a TableRule (§8.6), the command withdraws only the approvals of the table's own wordings. To withdraw the approval of a node in a cell of the table, whoever runs the command names that node.

sheriff approve --withdraw records a withdrawal by whoever runs it, whether or not they are among the node's owners. It refuses each of the following:

• a sid that names no node in the files that the repository keeps, such as the sid of a node of the SpecSheriff guidelines or of a chosen extension (§1.7.5) in a project other than SpecSheriff itself, since such a project takes those nodes from the plugin (§2.5);

After it records the withdrawals, sheriff approve --withdraw runs sheriff reindex (§tools 2.2).

Reason

A withdrawal takes back the approval of the node, not only that of the wording that the node holds now (§1.3.7). An approval left in force for an earlier wording would let an edit that restores that wording make the node approved again without any owner approving it.

Example

Rule R was approved, reworded and approved again, so an approval of each of its wordings is in force. A developer who is not an owner of R finds that R is wrong and runs sheriff approve --withdraw with R's sid. The command appends a withdrawal for each of those wordings, and R becomes a draft. The most likely mistake is to withdraw only the approval of R's current wording, so that an edit that restores R's earlier wording makes R approved again.

Для каждого одобрения формулировки (§1.3.5) такого узла, если это одобрение в силе, — есть ли эта формулировка в узле сейчас или нет, — команда добавляет в specs/_approvals.jsonl строку, которая отзывает это одобрение (§tools 11.1). Каждая такая строка содержит адрес электронной почты того, кто запустил команду. Эти строки команда добавляет в том порядке, в каком в файле идут первые строки для каждой такой формулировки.

Затем sheriff approve --withdraw ставит статус draft каждому узлу, который он называет. Если ни одно одобрение ни одной формулировки узла не в силе, sheriff approve --withdraw ничего не добавляет для этого узла и только ставит ему статус.

Если узел, который называет sheriff approve --withdraw, — TableRule (§8.6), команда отзывает только одобрения формулировок самой таблицы. Чтобы отозвать одобрение узла в ячейке таблицы, тот, кто запускает команду, называет этот узел.

sheriff approve --withdraw записывает отзыв того, кто его запустил, — есть ли он среди ответственных за узел или нет. Он отвергает каждое из следующего:

• sid, который не называет ни одного узла в файлах, которые хранит репозиторий, например sid узла SpecSheriff guidelines или выбранного расширения (§1.7.5) в проекте, который не является самим SpecSheriff, потому что такой проект берёт эти узлы из плагина (§2.5);
• раздел или, если проект выбрал расширение Domains (§11), заголовок домена (§domains 11.1.4a), потому что статус одобрения и того и другого sheriff reindex выводит из других узлов (§tools 2.2).

Каждый отказ называет соответствующий sid. Если sheriff approve --withdraw отвергает хотя бы один sid, названный в запуске, он не записывает ни одного отзыва этого запуска и не меняет статус ни одного узла. Если конфигурация git не задаёт адрес электронной почты, sheriff approve --withdraw отказывается работать.

Записав отзывы, sheriff approve --withdraw запускает sheriff reindex (§tools 2.2).

Обоснование

Отзыв забирает одобрение узла, а не только одобрение формулировки, которая в нём сейчас (§1.3.7). Одобрение, оставленное в силе для прежней формулировки, позволило бы правке, которая возвращает эту формулировку, снова сделать узел одобренным, хотя никто из ответственных не одобрил его заново.

Пример

Правило R одобрили, переформулировали и одобрили снова, поэтому в силе одобрение каждой из его формулировок. Разработчик, который не является ответственным за R, считает, что R ошибочно, и запускает sheriff approve --withdraw с sid R. Команда добавляет отзыв для каждой из этих формулировок, и R становится черновиком. Самая вероятная ошибка — отозвать только одобрение нынешней формулировки R: тогда правка, которая возвращает прежнюю формулировку R, снова делает R одобренным.

Title

How an approval is recorded

Text

sheriff approve <sid>... appends to specs/_approvals.jsonl one line per node. The line holds the node's sid, the fingerprint of its wording and, as by, the email git is configured with. It sets the node's status to approved. Where the latest line for the node and that fingerprint is already an approval, it appends nothing and only sets the status. It refuses:

• a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• a node none of whose owners is the one approving, naming its owners;
• the rule that approves the specification, unless the one approving is one of the specification's owners (§10.6).

An approval stands for a wording of a node where the latest line for that node and that wording's fingerprint is an approval. The latest line is the one standing last in specs/_approvals.jsonl.

sheriff approve --withdraw <sid>... withdraws the approval of each wording of the node for which one stands, whether the node holds that wording or not. For each such wording it appends a line. The line holds the node's sid, that wording's fingerprint, withdrawn: true and, as by, the email git is configured with. It makes the node a draft.

Where no approval stands for any wording of the node, it appends nothing. Anyone may withdraw an approval. sheriff approve --withdraw refuses:

• a section and a domain's header;
• a node of the SpecSheriff guidelines the project takes;
• the rule that approves the specification, unless the one withdrawing is one of the specification's owners (§10.6).

The fingerprint is a SHA-256 hash of one canonical string. The string holds the node's title, text and reason and the values its NodeKind adds beside them. It holds neither the owners a node names nor what the reindex builds. In the string:

• the keys of an object are sorted;
• a list keeps its own order.

In that string the reason stands under the key rationale, the name earlier releases gave it. Earlier releases gave a field of type one of an empty list of its own values where the domains add its values. In that string such a field stands in that form.

An owner is named by an email.

English
Title

The entries of the settings that only an owner changes

Text

sheriff.config.json (§tools 1) keeps the entries of each setting that only an owner of the specification changes (§tools 2.10) in a list of its own, under its own key:

• approvalStatus, for the specification's approval status (§10.6): each entry holds status, whose value is approved or draft, and by;
• strict, for the specification's strict flag (§10.7): each entry holds on, whose value is true or false, and by;
• extensions, for the extensions of the guidelines that the project has chosen (§1.7.5): each entry holds name, whose value is the name of an extension (§tools 1), chosen, whose value is true or false, and by.

An entry's by holds the email address of the owner who made the change that the entry records. An entry holds only the keys given above for its list.

sheriff settings (§tools 2.10) appends each entry to the end of its list. In a commit, each list begins with the entries that the commit's parent holds in that list (§tools 7.2.3). So the last entry of a list is the latest.

The specification's approval status and its strict flag each have the value that the last entry of that setting's list sets. The project has chosen exactly those extensions for which the last entry that names the extension sets chosen to true.

Where sheriff.config.json holds no entry for the approval status, no owner has approved the specification. The specification is then a draft (§1.3.3). Where sheriff.config.json holds no entry for the strict flag, the flag has the value that the schema of sheriff.config.json gives as the default of an entry's on (§tools 1).

sheriff settings records an entry only where the entry changes the value of its setting.

Reason

The entries record every change that an owner has made to the settings that only an owner of the specification changes, each with the email address of the owner who made it, but only the last entry of each list sets the value of its setting. sheriff reindex writes an entry in place of the rule through which an owner approved the specification in an earlier release (§tools 2.3). Since no entry holds anything that depends on when it is written, the check on the entries (§tools 7.2.3) never mistakes the entry that sheriff reindex writes for an entry that was changed.

Example

approvalStatus holds {"status": "approved", "by": "a@example.com"} followed by {"status": "draft", "by": "b@example.com"}. The specification is a draft, since the last entry makes it a draft again. The most likely mistake is to treat the specification as approved because one of the entries approves it.

sheriff.config.json (§tools 1) хранит записи каждой настройки, которую меняет только ответственный за спецификацию (§tools 2.10), в отдельном списке под отдельным ключом:

by записи содержит адрес электронной почты ответственного, сделавшего изменение, которое вносит запись. Запись содержит только ключи, названные выше для её списка.

sheriff settings (§tools 2.10) добавляет каждую запись в конец её списка. В коммите каждый список начинается с записей, которые этот список содержит в родительском коммите (§tools 7.2.3). Поэтому последняя запись списка — самая поздняя.

Статус одобрения спецификации и её флаг strict имеют каждый то значение, которое задаёт последняя запись списка этой настройки. Проект выбрал ровно те расширения, для которых последняя запись, называющая расширение, ставит chosen в true.

Если в sheriff.config.json нет ни одной записи статуса одобрения, ни один ответственный не одобрял спецификацию. Тогда спецификация — черновик (§1.3.3). Если в sheriff.config.json нет ни одной записи флага strict, флаг имеет значение, которое схема sheriff.config.json задаёт как default для on записи (§tools 1).

sheriff settings вносит запись, только если запись меняет значение своей настройки.

Обоснование

Записи хранят каждое изменение этих настроек ответственным вместе с адресом электронной почты ответственного, который его сделал, но значение каждой настройки задаёт только последняя запись её списка. sheriff reindex пишет запись вместо правила, которым ответственный одобрял спецификацию в прежнем выпуске (§tools 2.3). Поскольку ни одна запись не содержит ничего, что зависит от времени её создания, проверка записей (§tools 7.2.3) никогда не принимает запись, которую пишет sheriff reindex, за изменённую.

Title

Approving the specification

Text

Before sheriff settings records an entry that approves the specification (§tools 2.10, §tools 2.10a), it runs every check that the rule on the specification's approval status requires before the specification is approved (§10.6). These are the checks that sheriff validate, sheriff binding and sheriff citations make (§tools 7), and the check for a node from which nothing is generated, which sheriff types makes (§tools 2.5, §10.1.39b).

The checks before an approval treat the specification as approved, whatever the entries in sheriff.config.json set. They judge the files in the working tree as if one commit added the following:

• each node of the specification in the files that the repository keeps;
• the approval that is in force for each approved node (§tools 11.1);
• all of the system's code (§9.1), including its tests;
• the bindings file (§tools 8.4).

The checks before an approval treat everything else that the repository keeps, such as the archive (§2.6), the other lines of specs/_approvals.jsonl and the entries in sheriff.config.json, as unchanged by that one commit. The project's own checks (§10.8, §tools 7.1.23) receive a model of the specification (§tools 2.7) in which the specification is approved and its strict flag (§10.7) has the value that those entries set.

sheriff settings makes the check for a node from which nothing is generated as sheriff types does (§tools 2.5), but writes no file.

sheriff settings shows the owner who approves the specification what the checks before an approval find: every refusal, warning and report. Where they find nothing, it records the entry that approves the specification. Otherwise, it records that entry only after the owner confirms the approval, as the node on sheriff settings says (§tools 2.10).

While the strict flag is on, sheriff settings first runs the checks that the flag makes stricter, as it does when asked to turn the flag on (§tools 2.10c). It refuses to record the approval in each case in which it would refuse to turn the flag on. The run of sheriff settings ends with that refusal. The refusal names what the refusal to turn the flag on names in that case.

Reason

The checks at a commit judge only what the commit contains, so they never show everything that the specification and the code still lack (§10.6). The checks before an approval judge the whole specification and all of the code as one commit, so they show the owner everything that is still missing before the owner approves the specification.

Example

The specification is a draft, and its strict flag is off. An approved rule R has neither code nor a test, and an old function has no SpecTag. The agent runs sheriff settings status approved with no terminal attached. sheriff settings names R, saying that R lacks code and a test, names the function, and records nothing. The owner agrees to the approval, and the agent runs the command again with --confirm. The most likely mistake is to treat R's approval as one that was in force before the single commit that the checks assume. R is then not among the rules that the assumed commit includes, and the owner never sees what R lacks.

Одобрение спецификации

Текст

Прежде чем sheriff settings вносит запись, которая одобряет спецификацию (§tools 2.10, §tools 2.10a), она выполняет каждую проверку, которую правило о статусе одобрения спецификации требует перед одобрением спецификации (§10.6). Это проверки, которые делают sheriff validate, sheriff binding и sheriff citations (§tools 7), и проверка узла, из которого ничего не генерируется, которую делает sheriff types (§tools 2.5, §10.1.39b).

Проверки перед одобрением считают спецификацию одобренной, что бы ни задавали записи в sheriff.config.json. Файлы рабочего дерева они оценивают так, будто один коммит добавил следующее:

• каждый узел спецификации в файлах, которые хранит репозиторий;
• одобрение, которое в силе для каждого одобренного узла (§tools 11.1);
• весь код системы (§9.1), включая его тесты;
• файл привязок (§tools 8.4).

Всё остальное, что хранит репозиторий, например архив (§2.6), остальные строки specs/_approvals.jsonl и записи в sheriff.config.json, проверки перед одобрением считают не изменённым этим одним коммитом. Собственные проверки проекта (§10.8, §tools 7.1.23) получают модель спецификации (§tools 2.7), в которой спецификация одобрена, а флаг strict (§10.7) имеет значение, которое задают эти записи.

Проверку узла, из которого ничего не генерируется, sheriff settings делает так же, как sheriff types (§tools 2.5), но не пишет ни одного файла.

sheriff settings показывает ответственному, который одобряет спецификацию, всё, что находят проверки перед одобрением: каждый отказ, предупреждение и отчёт. Если они ничего не находят, она вносит запись, которая одобряет спецификацию. Иначе она вносит эту запись только после того, как ответственный подтвердит одобрение, как говорит узел о sheriff settings (§tools 2.10).

Пока флаг strict включён, sheriff settings сначала выполняет проверки, которые флаг делает строже, так же как когда её просят включить флаг (§tools 2.10c). Она отказывается вносить одобрение в каждом случае, в котором отказалась бы включить флаг. Запуск sheriff settings на этом отказе заканчивается. Этот отказ называет то же, что называет в этом случае отказ включить флаг.

Обоснование

Проверки при коммите оценивают только то, что содержит коммит, поэтому никогда не показывают всего, чего ещё не хватает спецификации и коду (§10.6). Проверки перед одобрением оценивают всю спецификацию и весь код как один коммит, поэтому показывают ответственному всё, чего ещё не хватает, до того как он одобрит спецификацию.

Пример

Спецификация — черновик, флаг strict выключен. У одобренного правила R нет ни кода, ни теста, а у старой функции нет SpecTag. Агент запускает sheriff settings status approved без терминала. sheriff settings называет R, сообщая, что у R нет кода и теста, называет функцию и ничего не вносит. Ответственный соглашается на одобрение, и агент запускает команду снова с --confirm. Самая вероятная ошибка — считать, что одобрение R было в силе ещё до того единственного коммита, который предполагают проверки. Тогда R не входит в правила, которые включает этот предполагаемый коммит, и ответственный так и не видит, чего R недостаёт.

Title

Turning the strict flag on

Text

sheriff settings (§tools 2.10) refuses to turn the strict flag on (§10.7) where a check that the flag makes stricter would refuse a commit or a push that changes nothing. It makes these checks on the files in the working tree, as if the specification were approved and the flag were on. The refusal names, for each check that would refuse, the command that lists what that check finds. Where no such check would refuse, sheriff settings records the entry that turns the flag on (§tools 2.10a).

The checks that the strict flag makes stricter, the cases in which each would refuse a commit or a push that changes nothing, and the command that the refusal to turn the flag on names for each are the following:

• the check for code and tests outside the commit (§tools 7.2.2b) that no SpecTag (§9.3) binds: it would refuse where sheriff untagged (§tools 2.11) would list anything, and the refusal to turn the flag on names sheriff untagged;
• each of the project's own checks (§10.8), any of which a rule of the project's own guidelines (§2.3) may make stricter (§10.7): such a check would refuse where sheriff validate --strict would refuse because of that check (§tools 7.1.23), and the refusal to turn the flag on names sheriff validate --strict.

sheriff settings also refuses to turn the strict flag on while the files of the specification fail the check for a key written more than once (§tools 7.1.1) or the validation against their schema (§tools 7.1.2). The refusal names sheriff validate, which lists what those checks find.

Reason

The flag lets the owners make the checks stricter by an act of their own without stopping all work when they do (§10.7). Turned on while a check that it makes stricter would refuse a commit that changes nothing, the flag would make every commit fail, or keep the specification from being approved, until that check passed.

Example

The specification is a draft, and two functions in an old file have no SpecTag. An owner runs sheriff settings strict on. sheriff settings refuses to turn the flag on and names sheriff untagged, which lists those functions. The most likely mistake is to turn the flag on because the specification is a draft. sheriff settings then refuses to approve the specification until each of the two functions has a SpecTag.

Эти проверки она выполняет над файлами рабочего дерева так, будто спецификация одобрена, а флаг включён. Отказ называет для каждой проверки, которая отвергла бы такой коммит или push, команду, перечисляющую то, что эта проверка находит. Если ни одна такая проверка его не отвергла бы, sheriff settings вносит запись, которая включает флаг (§tools 2.10a).

Проверки, которые флаг strict делает строже, случаи, в которых каждая из них отвергла бы коммит или push, который ничего не меняет, и команда, которую для каждой из них называет отказ включить флаг, — следующие:

• проверка кода и тестов вне коммита (§tools 7.2.2b), которые не связывает ни один SpecTag (§9.3): она отвергла бы, если sheriff untagged (§tools 2.11) перечислила бы хоть что-нибудь, и отказ включить флаг называет sheriff untagged;
• каждая из собственных проверок проекта (§10.8), любую из которых правило собственных guidelines проекта (§2.3) может сделать строже (§10.7): такая проверка отвергла бы, если бы из-за неё отверг sheriff validate --strict (§tools 7.1.23), и отказ включить флаг называет sheriff validate --strict.

sheriff settings отказывается включить флаг strict и тогда, когда файлы спецификации не проходят проверку на ключ, записанный больше одного раза (§tools 7.1.1), или проверку на соответствие своей схеме (§tools 7.1.2). Отказ называет sheriff validate, который перечисляет то, что находят эти проверки.

Обоснование

Флаг позволяет ответственным сделать проверки строже собственным действием, не останавливая при этом всю работу (§10.7). Включённый, пока проверка, которую он делает строже, отвергла бы коммит, который ничего не меняет, флаг заставил бы отвергать каждый коммит или не дал бы одобрить спецификацию, пока эта проверка не пройдёт.

Пример

Спецификация — черновик, и у двух функций в старом файле нет SpecTag. Ответственный запускает sheriff settings strict on. sheriff settings отказывается включить флаг и называет sheriff untagged, которая перечисляет эти функции. Самая вероятная ошибка — включить флаг, потому что спецификация — черновик. Тогда sheriff settings отказывается одобрить спецификацию, пока у каждой из двух функций не появится SpecTag.

Title

Withdrawing the choice of an extension

Text

sheriff settings (§tools 2.10) refuses to record an entry that withdraws the choice of an extension of the guidelines (§1.7.5, §tools 2.10a) while anything depends on that extension (§1.7.6). The refusal names each node that depends on the extension by its file, its sid and its location (§spec 8.5). Where nothing depends on the extension, sheriff settings records the entry.

A node other than the extension's own nodes depends on the extension where any of the following holds, whether or not the node is in the archive (§2.6):

• the node's kind is one that the kinds of the extension's schema (§tools 1) add;
• the node holds a property that the fields of the extension's schema add to the node's kind;
• the node has a link whose type is one of the linkTypes of the extension's schema;
• the node has a link that holds a property that the link of the extension's schema adds;
• the node is outside the archive and has a link to a node in the extension's file.

The refusal names a node of the archive by its file and its location, since it has no sid.

A reference in the project's extension of the schema (§5.2) depends on the extension of the guidelines where the reference points to a definition that the $defs of the schema of that extension of the guidelines add (§tools 7.1.2). The fields of the project's extension of the schema depend on the extension of the guidelines where they set conditions for a kind that the kinds of the schema of that extension of the guidelines add. The refusal names each such reference and each such kind by the file of the project's extension of the schema and the JSON Pointer to that reference or kind.

sheriff settings checks each node in the files that the repository keeps, including a node in a cell of a TableRule (§8.6) and each node of the archive. It also checks each reference in the project's extension of the schema and each kind in its fields. It makes this check regardless of whether the specification is approved or a draft.

Reason

An extension's schema declares, and its file holds, everything that the extension adds, so together they show everything that would rely on rules and definitions that no longer apply in the project once the choice of the extension is withdrawn (§1.7.6).

Example

The project has chosen the RecordType extension, whose name is recordtype, and the project's base specification holds a RecordType. An owner runs sheriff settings extension recordtype off. sheriff settings refuses and names the RecordType by its file, its sid and its location. The most likely mistake is to look only for links to the extension's nodes, so that a node of a kind that the extension adds goes unnoticed.

Отзыв выбора расширения

Текст

sheriff settings (§tools 2.10) отказывается вносить запись, которая отзывает выбор расширения guidelines (§1.7.5, §tools 2.10a), пока от этого расширения что-нибудь зависит (§1.7.6). Отказ называет каждый узел, который зависит от расширения, по его файлу, sid и расположению (§spec 8.5). Если от расширения ничего не зависит, sheriff settings вносит запись.

Узел, который не входит в само расширение, зависит от расширения, если выполнено что-нибудь из следующего, будь он в архиве (§2.6) или нет:

• тип узла — один из тех, что добавляют kinds схемы расширения (§tools 1);
• у узла есть свойство, которое fields схемы расширения добавляют типу узла;
• у узла есть связь, тип которой — один из linkTypes схемы расширения;
• у узла есть связь со свойством, которое добавляет link схемы расширения;
• узел находится вне архива, и у него есть связь с узлом из файла расширения.

Узел архива отказ называет по его файлу и расположению, потому что sid у него нет.

Ссылка в расширении схемы проекта (§5.2) зависит от расширения guidelines, если она указывает на определение, которое добавляют $defs схемы этого расширения (§tools 7.1.2). fields расширения схемы проекта зависят от расширения guidelines, если задают условия для типа, который добавляют kinds схемы этого расширения. Каждую такую ссылку и каждый такой тип отказ называет по файлу расширения схемы проекта и указателю JSON Pointer на эту ссылку или этот тип.

sheriff settings проверяет каждый узел в файлах, которые хранит репозиторий, в том числе узел в ячейке TableRule (§8.6) и каждый узел архива. Она проверяет и каждую ссылку в расширении схемы проекта, и каждый тип в его fields. Эту проверку она выполняет независимо от того, одобрена спецификация или она черновик.

Обоснование

Схема расширения объявляет, а его файл содержит всё, что добавляет расширение, поэтому вместе они показывают всё, что после отзыва выбора расширения опиралось бы на правила и определения, которые в проекте больше не действуют (§1.7.6).

Пример

Проект выбрал расширение RecordType, имя которого recordtype, и базовая спецификация проекта содержит RecordType. Ответственный запускает sheriff settings extension recordtype off. sheriff settings отказывается и называет этот RecordType по его файлу, sid и расположению. Самая вероятная ошибка — искать только связи с узлами расширения: тогда узел типа, который добавляет расширение, остаётся незамеченным.

Title

Setting a repository up and taking SpecSheriff out of it

Text

sheriff init sets a repository up for the SpecSheriff tools. For the git hooks, it does the following:

• it writes them into .githooks/ (§tools 12);
• it stages, with the executable mode 100755, each hook there that holds what it would write, unless git's index already holds that hook with that mode, and names each hook that it stages;
• where it cannot stage a hook, it names the hook and says how to stage it as executable;
• it turns the hooks on by setting git's core.hooksPath to .githooks, and says how to set core.hooksPath where it cannot set it.

sheriff init stages only the git hooks.

sheriff init writes the following for the agent that the option --agent names, claude or codex, or for claude where the option is not given:

• for claude, it adds the marketplace and the plugin to .claude/settings.json as a project declares them (§tools 14), keeping any other key there;
• for codex, it writes the agent's hooks for Codex into .codex/hooks.json (§tools 16), keeping any other hook there.

sheriff init refuses any other agent name, naming the agents that it supports.

sheriff init configures git to merge specs/_approvals.jsonl (§tools 11.1) by union. What sheriff init does depends on the state that git check-attr merge specs/_approvals.jsonl reports for the merge attribute of that file:

• where git reports the attribute as unspecified, sheriff init appends the line specs/_approvals.jsonl merge=union to the .gitattributes file at the repository's root, creating that file where it is missing;
• where git reports union, sheriff init appends nothing;
• where git reports any other state of that attribute, sheriff init appends nothing and names that state.

Outside a git repository, sheriff init appends the line specs/_approvals.jsonl merge=union to .gitattributes unless the file already holds it, spacing and line endings aside. The appended line starts on a line of its own and ends with the same line ending as the other lines of the file.

sheriff init writes each of the following files where it is missing (§tools 1):

• a sheriff.config.json that holds only code and tests, each an empty list of glob patterns;
• a specs/_guidelines/project.json whose top node is a section that names, as the specification's owner (§tools 3), the email address set in git's configuration.

The top node of project.json holds, as a draft, a rule with a refines link (§spec 6.1) to the rule on when the tests must pass (§spec 1.6.4). The rule's title is “When the tests run”. Its text is “The tests run before every push.” Its reason is “Running the tests before every push keeps a change whose tests fail from reaching the project's shared branch.”

The draft rule's TextRule.list (§5.1) lists push (§tools 7.3.5). The list's of is “the moments at which the tests run”.

Where git's configuration sets no email address, sheriff init writes no project.json and says how to set that address.

Where sheriff.config.json holds an empty list of glob patterns for code or for tests, or holds no testCommand, sheriff init says how to set what the file lacks (§tools 7.3.5).

sheriff init replaces a hook, or a declaration that it writes into .claude/settings.json or .codex/hooks.json, where that hook or declaration holds what an earlier release of sheriff init wrote, and names each. It leaves as it is any other hook or declaration that differs from what it would write, and any .claude/settings.json or .codex/hooks.json that is not JSON, and names each. So sheriff init, when run again, changes nothing (§10.13).

A hook or a declaration holds what an earlier release wrote where, line endings aside, it equals one of the texts that the earlier releases wrote. The SpecSheriff tools store those texts.

Where the repository's hooks previously ran from elsewhere, that is, from .git/hooks/ or from another folder that core.hooksPath pointed to, sheriff init names each hook found there, apart from git's sample hooks. It says that none of them runs until it is moved into .githooks/<hook>.d/ (§tools 13).

sheriff remove takes out of a repository what sheriff init writes outside specs/, for each agent that sheriff init supports:

• each git hook, the marketplace and the plugin in .claude/settings.json, and the agent's hooks for Codex in .codex/hooks.json, where each holds what sheriff init writes now or wrote in an earlier release;
• each line of the .gitattributes file at the repository's root that matches the line that sheriff init appends there, spacing and line endings aside;
• core.hooksPath, where it names .githooks;
• a key of .claude/settings.json or of .codex/hooks.json that is left holding nothing, and either file where it is left holding no key;
• .gitattributes, where it is left holding nothing but blank lines;
• .githooks/, .claude/ or .codex/, where it is left empty;
• sheriff.config.json, whatever it holds, including the entries of the settings that only an owner of the specification changes (§tools 2.10a).

sheriff remove leaves each hook and declaration that differs from every text that sheriff init writes now or wrote in an earlier release, and names it. It leaves specs/ and the bindings file (§tools 8.4) as they are, and names each of them. It names each .githooks/<hook>.d/ folder that it leaves in place, and says that the project's own tools in that folder (§tools 13) no longer run.

sheriff remove stages nothing. Run again, it changes nothing.

Reason

Adopting the method and removing it each take one command, so that nobody has to know every file and setting that the SpecSheriff tools need. What sheriff init writes reaches every clone through git, so the checks run the same way for everyone who works on the project (§10.2). Each command changes only what serves the SpecSheriff tools, and leaves the rest of the repository to the project.

Example 1

Someone runs sheriff init in a project on Windows. Git on Windows does not read the executable mode from a file, so sheriff init stages with the mode 100755 each hook that it wrote and names it. The most likely mistake is to make the hooks executable on disk only: git on Windows does not record that mode, so a clone on Linux or macOS runs none of the hooks.

Example 2

Two branches each approve a node, and each appends a line to specs/_approvals.jsonl. Because sheriff init configured git to merge that file by union, the merge keeps both lines and puts the line from the branch being merged after the line from the current branch. Without the union merge, git would report a conflict in that file. The most likely mistake is to resolve that conflict by keeping the lines of one branch, which loses the approval made on the other branch.

Example 3

The owner runs sheriff init in a new repository. project.json then holds a section that names the owner and holds, as a draft, the rule on when the tests run. So the first commit passes the check that every section contains a rule (§10.1.18). The most likely mistake is to write the section without a rule, so that the check refuses the first commit.

Настройка репозитория и удаление из него SpecSheriff

Текст

sheriff init настраивает репозиторий для инструментов SpecSheriff. Для git-хуков он делает следующее:

• записывает их в .githooks/ (§tools 12);
• добавляет в стейджинг с исполняемым режимом 100755 каждый хук в этой папке, который содержит то, что он записал бы, если индекс git ещё не содержит этот хук с этим режимом, и называет каждый хук, который добавил;
• если не может добавить хук в стейджинг, называет его и говорит, как добавить его в стейджинг исполняемым;
• включает хуки, задавая в git core.hooksPath равным .githooks, а если не может задать core.hooksPath, говорит, как его задать.

sheriff init добавляет в стейджинг только git-хуки.

sheriff init пишет следующее для агента, которого называет параметр --agent, claude или codex, а без этого параметра — для claude:

• для claude — добавляет marketplace и плагин в .claude/settings.json так, как их объявляет проект (§tools 14), сохраняя там все остальные ключи;
• для codex — записывает хуки агента для Codex в .codex/hooks.json (§tools 16), сохраняя там все остальные хуки.

Любое другое имя агента sheriff init отвергает, называя агентов, которых он поддерживает.

sheriff init настраивает git так, чтобы он сливал specs/_approvals.jsonl (§tools 11.1) по union. Что делает sheriff init, зависит от состояния, которое git check-attr merge specs/_approvals.jsonl сообщает для атрибута merge этого файла:

• если git сообщает, что атрибут не задан, sheriff init добавляет строку specs/_approvals.jsonl merge=union в файл .gitattributes в корне репозитория, а если этого файла нет, создаёт его;
• если git сообщает union, sheriff init ничего не добавляет;
• если git сообщает любое другое состояние этого атрибута, sheriff init ничего не добавляет и называет это состояние.

Вне репозитория git sheriff init добавляет строку specs/_approvals.jsonl merge=union в .gitattributes, если файл её ещё не содержит, без учёта пробелов и концов строк. Добавленная строка начинается с новой строки и заканчивается тем же концом строки, что и остальные строки файла.

sheriff init пишет каждый из следующих файлов, если его нет (§tools 1):

• sheriff.config.json, который содержит только code и tests, каждый — пустой список glob-шаблонов;
• specs/_guidelines/project.json, верхний узел которого — раздел, называющий ответственным за спецификацию (§tools 3) адрес электронной почты, заданный в конфигурации git.

Верхний узел project.json содержит черновик правила со связью refines (§spec 6.1) на правило о том, когда тесты должны проходить (§spec 1.6.4). Название правила — «When the tests run». Его текст — «The tests run before every push.». Его обоснование — «Running the tests before every push keeps a change whose tests fail from reaching the project's shared branch.».

TextRule.list (§5.1) этого черновика правила перечисляет push (§tools 7.3.5). of этого списка — «the moments at which the tests run».

Если конфигурация git не задаёт адрес электронной почты, sheriff init не пишет project.json и говорит, как задать этот адрес.

Если в sheriff.config.json пуст список glob-шаблонов кода или тестов или нет testCommand, sheriff init говорит, как задать недостающее (§tools 7.3.5).

sheriff init заменяет хук или объявление, которое он пишет в .claude/settings.json или .codex/hooks.json, если этот хук или объявление содержит то, что писал прежний выпуск sheriff init, и называет каждый из них. Любой другой хук или объявление, которые отличаются от того, что он записал бы, а также .claude/settings.json или .codex/hooks.json, который не является JSON, он оставляет как есть и называет каждый из них. Поэтому при повторном запуске sheriff init ничего не меняет (§10.13).

Хук или объявление содержит то, что писал прежний выпуск, если без учёта концов строк совпадает с одним из текстов, которые писали прежние выпуски. Эти тексты хранят инструменты SpecSheriff.

Если раньше хуки репозитория запускались из другого места — из .git/hooks/ или из другой папки, которую называл core.hooksPath, — sheriff init называет каждый найденный там хук, кроме образцов git. Он говорит, что ни один из них не запускается, пока его не переместят в .githooks/<hook>.d/ (§tools 13).

sheriff remove убирает из репозитория то, что sheriff init пишет вне specs/, для каждого агента, которого поддерживает sheriff init:

• каждый git-хук, marketplace и плагин в .claude/settings.json и хуки агента для Codex в .codex/hooks.json, если каждое из них содержит то, что sheriff init пишет сейчас или писал в прежнем выпуске;
• каждую строку файла .gitattributes в корне репозитория, которая без учёта пробелов и концов строк совпадает со строкой, которую туда добавляет sheriff init;
• core.hooksPath, если он называет .githooks;
• ключ .claude/settings.json или .codex/hooks.json, в котором ничего не осталось, и любой из этих файлов, в котором не осталось ни одного ключа;
• .gitattributes, если в нём остались только пустые строки;
• .githooks/, .claude/ или .codex/, если папка осталась пустой;
• sheriff.config.json, что бы он ни содержал, в том числе записи настроек, которые меняет только ответственный за спецификацию (§tools 2.10a).

Каждый хук и каждое объявление, которые не совпадают ни с одним текстом, который sheriff init пишет сейчас или писал в прежнем выпуске, sheriff remove оставляет и называет. specs/ и файл привязок (§tools 8.4) он оставляет как есть и называет каждый из них. Он называет каждую оставленную папку .githooks/<hook>.d/ и говорит, что собственные инструменты проекта в ней (§tools 13) больше не запускаются.

sheriff remove ничего не добавляет в стейджинг. При повторном запуске он ничего не меняет.

Обоснование

Принять метод можно одной командой, и отказаться от него — тоже одной, чтобы никому не нужно было знать все файлы и настройки, которые нужны инструментам SpecSheriff. То, что пишет sheriff init, попадает в каждый клон через git, поэтому проверки работают одинаково для всех, кто работает над проектом (§10.2). Каждая из команд меняет только то, что служит инструментам SpecSheriff, а остальное в репозитории оставляет проекту.

Пример 1

Кто-то запускает sheriff init в проекте на Windows. Git на Windows не читает исполняемый режим из файла, поэтому sheriff init добавляет в стейджинг с режимом 100755 каждый записанный им хук и называет его. Самая вероятная ошибка — сделать хуки исполняемыми только на диске: git на Windows этот режим не записывает, и клон на Linux или macOS не запускает ни одного хука.

Пример 2

Две ветки одобряют по узлу, и каждая добавляет строку в specs/_approvals.jsonl. Поскольку sheriff init настроил git так, чтобы он сливал этот файл по union, слияние сохраняет обе строки и ставит строку вливаемой ветки после строки текущей ветки. Без слияния по union git сообщает о конфликте в этом файле. Самая вероятная ошибка — разрешить этот конфликт, оставив строки одной ветки: так теряется одобрение, сделанное в другой ветке.

Пример 3

Ответственный запускает sheriff init в новом репозитории. Тогда project.json содержит раздел, который называет ответственного и содержит черновик правила о том, когда запускаются тесты. Поэтому первый коммит проходит проверку того, что каждый раздел содержит правило (§10.1.18). Самая вероятная ошибка — записать раздел без правила: тогда эта проверка отвергает первый коммит.

What sheriff reindex changes in what an earlier release wrote

Text

sheriff reindex rewrites whatever an earlier release of the SpecSheriff tools wrote or read differently from the release that sheriff reindex belongs to. It does so after it has merged the duplicate keys (§tools 2.4), and before it validates the files. In every file of the specification and of its archive (§2.6), it makes the following changes:

• a node's key id becomes location;
• a node's key rationale becomes reason;
• the kinds of node record and recordType become RecordType;
• the kind of node rule becomes TextRule;
• the kind of node domain becomes header;
• a node's status "" becomes draft;
• a node's status checked becomes approved;
• a node's key owner, which holds an email address, becomes owners, which holds a list that contains that email address;
• a RecordType's fields and unknown become its schema (§12.2), as follows:
◦ each field becomes a property whose schema is the one given for the field's neutral type (§tools 20);
◦ the field's text becomes the property's description;
◦ each field that the RecordType marks as required is listed in the schema's required;
◦ a field that is required only "where it holds a value" becomes an optional property;
◦ unknown: "refused" becomes additionalProperties: false;
• the source of a field's values becomes the field's x-enumSource (§12.7);
• TextRule.list.declaredIn (§5.1) is removed where it points to the field kinds of the project's extension of the schema (§5.2);
• TextRule.list.declaredIn becomes TextRule.list.jsonSchema, and its key declaration becomes pointer, where it points to any other place in a JSON Schema;

• a link of the type supersedes is removed (§spec 6.1);
• a node of the archive loses its sid and every link that points to it (§2.6, §6.4).

A renamed key keeps its place among the node's keys.

The name of a kind of node is also changed in each of these places:

• the source of a field's values, where those values are the sids of that kind's nodes;
• the fields of the project's extension of the schema, where the name is the key under which those fields add properties to that kind.

A bare sid is a word that has the form of a sid and meets one of these conditions:

• it opens a test's name, followed by a space or by the end of the name;
• it is the only argument of a test's mark.

sheriff reindex also makes the following changes:

• the key owner in each line of specs/_confirmations.jsonl becomes by;

• where sheriff.config.json holds no entry that sets the specification's approval status, an approved rule of project.json that refines the rule on that status (§10.6) is replaced by an entry that approves the specification (§tools 2.10a);
• the entry that approves the specification names the owner who last approved the rule that the entry replaces;
• the rule that the entry replaces is moved to the archive (§2.6), with the reason "Replaced by the entry in sheriff.config.json that records the specification's approval status";
• where sheriff.config.json holds no entry that sets the specification's approval status, a draft rule of project.json that refines the rule on that status is moved to the archive with the reason "The specification's approval status is recorded in sheriff.config.json" if it was ever approved, and is deleted otherwise (§2.6);

• in each file that sheriff.config.json names as tests of the system's code (§9.1) or of a project's own check (§10.8) or generator (§10.9), @spec is inserted before each bare sid.

Where a node of the specification is of a kind, or holds a link of a type, that an extension of the guidelines (§1.7.1) adds, and the project has not chosen that extension (§1.7.5), sheriff reindex names that extension.

When sheriff reindex adds the draft rule on when the tests run, it names that rule, since the SpecSheriff tools read the rule only after an owner approves it (§tools 3).

A renamed key and a renamed kind of node leave a node's fingerprint (§tools 11.2) unchanged, so the approval of the node's wording stays in force (§tools 11.1).

sheriff reindex names each file that it rewrites because an earlier release wrote or read that file differently, including the files of the specification.

Reason

Each file and each test of a project follows the form used by the release of the SpecSheriff tools that last wrote or read it. A release that writes or reads them in a different form rewrites them, so that nobody has to rewrite a project by hand and no approval is lost because of a rename.

The most likely mistake is to add that draft rule again in a later run, after the project has deleted it.

Title

How a project's own check is run

Text

Where a check that a project's own guidelines add (§10.8) fails, sheriff validate refuses the change. Where the rule that lists the check says that the check's failure is only reported, sheriff validate reports the failure instead (§10.1.37). The refusal or the report names the check and shows what the check printed to its standard output and its standard error. Where the check printed nothing, the refusal or the report shows the check's exit status.

sheriff validate runs each of the project's own checks with the command that sheriff.config.json names for it (§tools 1). The check runs in the directory in which sheriff validate runs. At a commit, that directory holds what the commit contains (§tools 6). On its standard input, the check receives the model of the specification in the form that sheriff json prints (§tools 2.7). A check passes only if its process exits with status zero.

In its TextRule.list (§5.1), the rule that sheriff.config.json names for a check lists the check as a member whose value (§tools 7.2.6) is the check's name. sheriff validate reads that rule in its last approved wording (§tools 2.5). Where the rule, in that wording, lists no member whose value is the check's name, sheriff validate refuses the change. The refusal names the check and the rule, and says that the rule's last approved wording does not list the check.

Where the member that lists the check is an object whose onFailure is reported, the rule says that the check's failure is only reported. Where that member's onFailure is reportedUnlessStrict, the rule says that, while the specification's strict flag (§10.7) is off, the check's failure is only reported. sheriff validate reads the flag from the model of the specification that it gives the check.

sheriff validate runs the project's own checks only after the files of the specification have passed the check for a key written more than once (§tools 7.1.1) and the validation against their schema (§tools 7.1.2). It runs them before the rest of its checks (§spec 10.12). It makes the rest of its checks regardless of what the project's own checks find.

sheriff validate refuses the change where one of the project's own checks adds, changes or removes a file in the directory in which the check runs, other than a file that git ignores (§spec 10.1.37a). The refusal names the check and each such file.

Given the option --strict, sheriff validate gives each of the project's own checks a model of the specification in which the specification is approved and the specification's strict flag is on (§10.6, §10.7). It does so regardless of how the entries in sheriff.config.json (§tools 1) set the approval status and the flag. The other checks of sheriff validate give the same results with or without the option.

sheriff validate runs the project's own checks regardless of whether the specification is approved or a draft (§10.1.37).

Reason

Whenever sheriff validate makes the checks that the SpecSheriff guidelines require, it also runs a project's own checks, on the same files. Such a check therefore binds every participant, rather than depending on someone remembering to run it (§10.8).

Example 1

The rule that lists the project's own checks has name as its TextRule.list.property, and one of its members is {"name": "spelling", "onFailure": "reported"}. The check spelling finds a misspelt word in a node's text, prints the node's sid and exits with status 1. sheriff validate reports the failure, showing the sid, and the commit passes. The most likely mistake is to refuse the commit because the check's exit status is not zero.

Example 2

The member that lists the check spelling is {"name": "spelling", "onFailure": "reportedUnlessStrict"}. While the strict flag is off, sheriff validate reports each misspelt word, and the commit passes. An owner runs sheriff settings strict on, and the check fails when sheriff validate --strict runs it, so sheriff settings refuses to turn the flag on and names sheriff validate --strict. The most likely mistake is to read the flag from the entries in sheriff.config.json rather than from the model that the check receives. The flag is then turned on, and the next commit is refused because of that check.

Как запускается собственная проверка проекта

Текст

Если проверка, которую добавляют собственные guidelines проекта (§10.8), не проходит, sheriff validate отвергает изменение. Если правило, которое перечисляет проверку, говорит, что о неудаче проверки только сообщается, sheriff validate вместо отказа сообщает о неудаче (§10.1.37). Отказ или сообщение называет проверку и показывает, что она напечатала в стандартный вывод и в стандартный поток ошибок. Если проверка ничего не напечатала, показывается код её завершения.

sheriff validate запускает каждую собственную проверку проекта командой, которую для неё называет sheriff.config.json (§tools 1). Проверка выполняется в каталоге, в котором выполняется sheriff validate. При коммите этот каталог содержит то, что содержит коммит (§tools 6). На стандартный вход проверка получает модель спецификации в том виде, в каком её печатает sheriff json (§tools 2.7). Проверка проходит, только если её процесс завершается с кодом ноль.

В своём TextRule.list (§5.1) правило, которое sheriff.config.json называет для проверки, перечисляет её как элемент, значение которого (§tools 7.2.6) — имя проверки. Это правило sheriff validate читает в его последней одобренной формулировке (§tools 2.5). Если в этой формулировке в правиле нет элемента, значение которого — имя проверки, sheriff validate отвергает изменение. Отказ называет проверку и правило и говорит, что последняя одобренная формулировка правила эту проверку не перечисляет.

Если элемент, который перечисляет проверку, — объект, у которого onFailure равно reported, правило говорит, что о неудаче проверки только сообщается. Если onFailure этого элемента равно reportedUnlessStrict, правило говорит, что, пока флаг strict спецификации (§10.7) выключен, о неудаче проверки только сообщается. sheriff validate читает флаг из модели спецификации, которую передаёт проверке.

Собственные проверки проекта sheriff validate запускает, только когда файлы спецификации прошли проверку на ключ, записанный больше одного раза (§tools 7.1.1), и проверку на соответствие своей схеме (§tools 7.1.2). Он запускает их до остальных своих проверок (§spec 10.12). Остальные свои проверки он выполняет, что бы ни нашли собственные проверки проекта.

sheriff validate отвергает изменение, если одна из собственных проверок проекта добавляет, меняет или удаляет файл в каталоге, в котором эта проверка выполняется, кроме файла, который git игнорирует (§spec 10.1.37a). Отказ называет проверку и каждый такой файл.

Title

How a project's own check is run

Text

Where a check that a project's own guidelines add (§10.8) fails, sheriff validate refuses the change. Where the rule that lists the check says that the check's failure is only reported, sheriff validate reports the failure instead (§10.1.37). The refusal or the report names the check and shows what the check printed to its standard output and its standard error. Where the check printed nothing, the refusal or the report shows the check's exit status.

sheriff validate runs each of the project's own checks with the command that sheriff.config.json names for it (§tools 1). The check runs in the directory in which sheriff validate runs. On a commit, that directory holds what the commit contains (§tools 6). On its standard input, the check receives the model of the specification in the form that sheriff json prints (§tools 2.7). A check passes only if its process exits with status zero.

In its TextRule.list (§5.1), the rule that sheriff.config.json names for a check lists the check as a member whose value (§tools 7.2.6) is the check's name. sheriff validate reads that rule in its last approved wording (§tools 2.5). Where that member is an object whose onFailure is reported, the rule says that the check's failure is only reported. Where the rule, in that wording, lists no member whose value is the check's name, sheriff validate refuses the change. The refusal names the check and the rule, and says that the rule's last approved wording does not list the check.

sheriff validate runs the project's own checks only after the files of the specification have passed the check for a key written more than once (§tools 7.1.1) and the validation against their schema (§tools 7.1.2). It runs them before the rest of its checks (§spec 10.12). It makes the rest of its checks regardless of what the project's own checks find.

sheriff validate refuses the change where one of the project's own checks adds, changes or removes a file in the directory in which the check runs, other than a file that git ignores (§spec 10.1.37a). The refusal names the check and each such file.

Given the option --strict, sheriff validate gives each of the project's own checks a model of the specification in which the specification is approved and the specification's strict flag is on (§10.6, §10.7). It does so regardless of how the entries in sheriff.config.json (§tools 1) set the approval status and the flag. The other checks of sheriff validate give the same results with or without the option.

Before sheriff settings records an approval of the specification, it runs the project's own checks (§tools 2.10, §10.6). It gives them a model in which the specification is approved and the strict flag has the value that the entries in sheriff.config.json set. Before sheriff settings turns the strict flag on, it runs the project's own checks as sheriff validate --strict runs them (§10.7).

sheriff validate runs the project's own checks regardless of whether the specification is approved or a draft (§10.1.37).

Reason

Whenever sheriff validate makes its checks of the SpecSheriff guidelines, it also runs a project's own checks, on the same files. Such a check therefore binds every participant, rather than depending on whoever remembers to run it (§10.8).

Example

The rule that lists the project's own checks has name as its TextRule.list.property, and one of its members is {"name": "spelling", "onFailure": "reported"}. The check spelling finds a misspelt word in a node's text, prints the node's sid and exits with status 1. sheriff validate reports the failure, showing the sid, and the commit passes. The most likely mistake is to refuse the commit because the check's exit status is not zero.
