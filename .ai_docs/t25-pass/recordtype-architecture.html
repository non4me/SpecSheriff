Архитектура RecordType

По согласованным 12.1, 12.6 и 12.10 и по набору проверок вариантов, принятому 19 ноября (строки 12.12.4–12.12.9).

Правка 12.12.5 меняет только формулировку проверки. Устройство вариантов задаёт согласованный 12.6, и с правкой оно не меняется. Строка 12.12.5 проверяет одну связь на схеме — стрелку refines от варианта к его RecordType.

Схема

Белая стрелка с полым треугольником — связь refines, как обобщение в UML: от частного к общему. Жёлтым — строка 12.12.5, которая сейчас согласуется; голубым — следующие строки; зелёным — согласованная 12.12.4.

Как это записано и как выглядят данные

Узлы спецификации (упрощённо: без sid, text и полей, не нужных для вариантов)

// RecordType «Уведомление» — раздел «Уведомления»
{
  "kind": "RecordType",
  "title": "Уведомление",
  "identifiedBy": "id",
  "chosenBy": ["channel"],
  "fields": [
    { "name": "id",       "type": { "is": "text" } },
    { "name": "channel",  "type": { "is": "one of",
                                    "values": ["email", "sms", "app"] } },
    { "name": "text",     "type": { "is": "text" } },
    { "name": "delivery", "type": { "is": "variant" } }
  ]
}

// Вариант «Уведомление по email» — тот же раздел
{
  "kind": "RecordType",
  "title": "Уведомление по email",
  "answersTo": { "channel": "email" },
  "fields": [
    { "name": "address", "type": { "is": "email address" } }
  ],
  "refs": [{ "type": "refines", "to": "<sid «Уведомления»>" }]
}                                   ↑ эту связь проверяет 12.12.5

Записи данных

// channel = email: поля варианта — в delivery
{
  "id": "n-1042",
  "channel": "email",
  "text": "Заказ отправлен",
  "delivery": { "address": "anna@example.org" }
}

// channel = sms: в delivery — фрагмент «Номер телефона»
{
  "id": "n-1043",
  "channel": "sms",
  "text": "Заказ отправлен",
  "delivery": {
    "phone": { "country": "+420", "number": "601234567" }
  }
}

Каналу app вариант не нужен: значение не приносит полей (12.6).

Проверки вариантов в таблице 12.12

  • 12.12.4согласованаRecordType содержит не более одного поля типа variant, считая унаследованные.
  • 12.12.5сейчасВариант RecordType ссылается через refines на RecordType, поля которого он дополняет. Предложенная формулировка.
  • 12.12.6впередиВариант объявлен там же, где его RecordType. Требование из принятого набора; одобренная строка говорит ещё по старому правилу.
  • 12.12.7впередиУ варианта есть собственные поля. Требование из принятого набора.
  • 12.12.8впередиВариант называет по одному значению каждого поля, которое выбирает вариант. Требование из принятого набора.
  • 12.12.9впередиНикакие два варианта одного RecordType не соответствуют одним и тем же значениям. Требование из принятого набора.

Решения и сложившаяся практика

Шесть решений, из которых складывается устройство на схеме, сравнены с тем, как ту же задачу решают распространённые языки и форматы описания данных. Ниже матрица — затем по каждому решению плюсы и минусы.

Р1

Вариант сам ссылается на свой RecordType через refines

проверяет 12.12.5
  • ●Kotlin, JavaПодкласс сам называет родителя: class Email : Notification(), extends.
  • ●OpenAPI 3Схема варианта ссылается на базовую: allOf: [$ref: Notification].
  • ●UMLСтрелка обобщения идёт от частного к общему.
  • ○TypeScript, JSON Schema, Protobuf, serdeНаоборот: родитель перечисляет варианты в одном месте (A | B, oneOf, oneof, enum).

Плюсы

  • Новый вариант не меняет одобренный RecordType, и его не нужно одобрять заново.
  • У каждого варианта свой sid, своё одобрение и свои тесты, как у любого правила.
  • Список вариантов всё равно виден у RecordType: входящие связи refines строит sheriff reindex.

Минусы

  • Можно записать вариант, который ни на что не ссылается. В Kotlin такой код не скомпилируется, а здесь нужна отдельная проверка — строка 12.12.5.
  • Чтобы увидеть все варианты, нужна свежая переиндексация.
Р2

Каждый вариант сам называет значения, которым соответствует (answersTo)

  • ●TypeScriptКаждый член union несёт свой литерал: { channel: "email"; … }.
  • ●serdeЗначение тега задаётся на самом варианте: #[serde(rename = "email")].
  • ◐Kotlin, JavaТег — сам класс; значение в данных задают на подклассе: @SerialName, @JsonTypeName.
  • ◐JSON Schemaconst на поле-дискриминаторе внутри каждой ветки oneOf.
  • ◐UMLДискриминатор набора обобщений; значения задаются через powertype, приём редкий.
  • ○OpenAPI 3Таблица discriminator.mapping лежит у родителя.
  • ○ProtobufЗначения нет: вариант определяется тем, какое поле oneof заполнено.

Плюсы

  • Всё о варианте — в одном узле.
  • Новое значение с новыми полями не меняет RecordType.

Минусы

  • Что два варианта не претендуют на одно значение, видно только по всем вариантам сразу. Поэтому нужна строка 12.12.9.
Р3

Поля варианта в записи данных лежат в одном поле типа variant, а значение, выбирающее вариант, — в обычном поле рядом

  • ●serdeТак называемый adjacently tagged: {"t": "email", "c": {…}} — один из четырёх способов serde.
  • ◐Protobufoneof тоже держит вариант отдельно, но отдельного поля-тега нет.
  • ○TypeScript, Kotlin, Java, OpenAPI, JSON SchemaОбычно плоско: тег и поля варианта на одном уровне с общими полями.

Плюсы

  • Имена полей варианта не сталкиваются с полями RecordType.
  • Читатель, которому варианты не нужны, пропускает одно поле, а общие поля остаются неизменными.

Минусы

  • Лишний уровень вложенности.
  • Что содержимое delivery соответствует значению channel, проверяет только сгенерированная проверка данных во время работы системы.
  • Генератор для плоских форматов (OpenAPI, TypeScript) должен перестраивать структуру.
Р4

Вариант выбирают значения одного или нескольких полей, по одному варианту на сочетание

отступление от практики
  • ◐TypeScriptСужает тип и по двум полям, но на практике громоздко.
  • ◐JSON Schemaif/then выражает любое условие, в том числе по нескольким полям.
  • ◐UMLНесколько наборов обобщений с разными дискриминаторами, приём редкий.
  • ○Kotlin, Java, OpenAPI, Protobuf, serdeОдин дискриминатор.

Плюсы

  • Описывает данные, у которых поля зависят сразу от двух признаков, без искусственного составного поля.

Минусы

  • Нестандартно: разработчик не узнаёт привычный приём.
  • Число вариантов может расти как произведение числа значений.
  • Генерация в TypeScript и OpenAPI сложнее: нужен составной ключ или вложенные union.
Р5

Вариант объявлен там же, где его RecordType: в том же разделе или в контрактах

  • ●KotlinПрямые наследники sealed-класса — в том же пакете и модуле.
  • ●Java 17Разрешённые подклассы sealed-класса — в том же модуле.
  • ●TypeScript, Protobuf, serdeUnion, oneof и enum объявляются целиком в одном месте.
  • ◐OpenAPI 3, JSON SchemaВарианты могут лежать в любом файле, на них ведут ссылки.

Плюсы

  • Тот, кто читает данные, находит все варианты там же, где RecordType, — как говорит обоснование 12.6.
  • Набор вариантов закрыт, поэтому генератор может построить исчерпывающий разбор по значениям.

Минусы

  • Другая часть системы не может добавить свой вариант: ей нужен собственный RecordType.
Р6

RecordType ссылается только на RecordType своей части системы и на фрагменты формата из контрактов

  • ●DDDОграниченные контексты не делят модели. Фрагменты в контрактах — общее ядро (shared kernel), RecordType как часть API — опубликованный язык (published language).
  • ◐Kotlin, JavaГраницы модулей и видимость internal закрывают чужие типы, но только на уровне кода.
  • ◐OpenAPI, JSON Schema, ProtobufИмпорт чужих типов разрешён; ограничение держится на договорённости.

Плюсы

  • Изменение формата одной части не ломает типы другой.
  • Фрагменты вроде адреса или телефона описаны один раз.

Минусы

  • Части, которой нужны чужие данные, приходится хранить идентификатор как обычное значение, например text. Что он указывает на «Уведомление», спецификация уже не проверяет.
