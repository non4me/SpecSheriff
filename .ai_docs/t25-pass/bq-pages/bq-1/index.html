The human-readable export

Text

The human-readable export is the specification written for a person to read, for example in Markdown. It contains every node with every value that the node's file holds for that node. It shows each link with the node at the link's other end: that node's sid, location (§s-kag2m9tzdnduxdx) and title. Reason

The files that a schema checks are hard for a person to read. The export lets a person read everything those files hold, and see where each link leads, without opening them.

Examples

A person outside the team reads a rule in the export and sees its reason, the decisions taken on it, and the title of every node it links to, without opening the specification's files.

Title

The map of the specification

Text

The map is the specification seen from above. It is drawn from the nodes and holds no facts of its own.

The map shows only the title and the approval status (§s-tgrnpagrb58tya7) of each node, nested as the nodes are nested in the specification. It labels a node that has no title, such as a node in a cell of a TableRule (§s-5fewsp22mmdz7y6), with its location (§s-kag2m9tzdnduxdx). A branch of the map can be opened and closed, so that a reader goes to the part they came for while the rest of the map stays in view.

The top-level branches of the map appear in this order: the guidelines, the appendix of the tools, the base specification and the technical appendix (§s-qmmzf9nksfsa3qp).

Reason

A specification is read one rule at a time, yet it has to be understood as a whole. The full text is more than anyone can hold in mind at once, and a rule read on its own loses its place in the specification. Seen from above, the specification shows the shape of the whole and the detail of whatever is opened, together with the parts of it that still wait for their owners' approval.

Examples

Drawn as a mind map, the map opens with its top-level branches. A reader opens the branch of the base specification and one of its sections, and sees the titles of that section's rules, each with its approval status, while the other branches stay closed.

В каком порядке запускаются инструменты и проверки при коммите и при push изменённый узел

Title

The order in which tools and checks run on a commit and on a push

Text

On a commit and on a push, the project's own tools, the SpecSheriff tools and the checks run in the following steps:

  1. the tools that rewrite files: first the project's own tools of that kind that its own guidelines (§s-u7tw6m8npxmv5tu) list, such as formatters, and then the generators, both those of the SpecSheriff tools and the project's own (§s-km4x4s26kv7pjze);
  2. the project's own checks (§s-2fau85dfyyeq66m) and the rest of the project's own tools, each of which leaves the files as they were, except for those that git ignores;
  3. the checks of the SpecSheriff guidelines (§s-jau82aq9juv9zzh).

After the first step, nothing changes what the commit contains. Each step runs regardless of what the earlier steps found. The commit or the push goes through only if every check passes and no tool fails.

On a commit, as an exception to the steps above, the following checks run after the first step and before any other check:

  • the check that, in each object (§s-d5cgda5bdsn7bzy) of a file of the specification, of its archive (§s-f2b5zvc565s242f) or of its schema (§s-eferktypcj7njt5), each key is written only once;
  • the check that every file of the specification complies with its JSON Schema (§s-emrfpzw2d5bgb6x).

The project's own checks and the other checks of the SpecSheriff guidelines run only after these checks have passed.

Where the SpecSheriff tools cannot run, the project's own tools still run. The commit or the push then goes through unless one of them fails. Whoever makes the commit or the push is told that no SpecSheriff check ran.

Reason

A project may run tools of its own on a commit or a push, such as a scan that checks that nothing internal reaches a public repository. Adopting SpecSheriff must not stop them, even where the SpecSheriff tools cannot run, for example on a machine without the SpecSheriff plugin. A team that needs the checks that the git hooks run to apply to everyone runs them in CI.

The order lets every check rely on what it reads: files in their final form and, where it reads nodes, nodes whose structure has passed the structure checks.

Examples

A project's own guidelines list a formatter. On a commit, the formatter rewrites the files in the commit first, and the generators of the SpecSheriff tools then write their files. A scan for secrets, one of the project's own tools for the pre-commit hook, runs next. The checks that each key is written only once in each object and that each file complies with its JSON Schema follow, and the other checks of the SpecSheriff guidelines run last, on the final files.

В каком порядке запускаются инструменты и проверки при коммите и при push

Текст

При коммите и при push собственные инструменты проекта, инструменты SpecSheriff и проверки запускаются по следующим шагам:

  1. инструменты, которые переписывают файлы: сначала такие собственные инструменты проекта, которые перечисляют собственные guidelines проекта (§s-u7tw6m8npxmv5tu), например форматтеры, а затем генераторы — и инструментов SpecSheriff, и собственные генераторы проекта (§s-km4x4s26kv7pjze);
  2. собственные проверки проекта (§s-2fau85dfyyeq66m) и остальные собственные инструменты проекта, каждый из которых оставляет файлы такими, какими они были, кроме тех, которые git игнорирует;
  3. проверки SpecSheriff guidelines (§s-jau82aq9juv9zzh).

После первого шага ничто не меняет содержимого коммита. Каждый шаг запускается, что бы ни нашли предыдущие. Коммит или push проходит, только если проходят все проверки и все инструменты.

При коммите, в виде исключения из описанных выше шагов, следующие проверки выполняются после первого шага и раньше любой другой проверки:

  • проверка того, что в каждом объекте (§s-d5cgda5bdsn7bzy) файла спецификации, её архива (§s-f2b5zvc565s242f) или её схемы (§s-eferktypcj7njt5) каждый ключ записан только один раз;
  • проверка того, что каждый файл спецификации соответствует своей JSON Schema (§s-emrfpzw2d5bgb6x).

Собственные проверки проекта и остальные проверки SpecSheriff guidelines запускаются, только когда эти проверки прошли.

Там, где инструменты SpecSheriff не могут запуститься, собственные инструменты проекта всё равно запускаются. Тогда коммит или push проходит, если ни один из них не отклонил его. Тот, кто его делает, получает сообщение, что ни одна проверка SpecSheriff не запускалась.

Обоснование

Проект может запускать при коммите или push свои инструменты, например проверку того, что ничего внутреннего не попадает в публичный репозиторий. Переход на SpecSheriff не должен их останавливать, даже там, где инструменты SpecSheriff не могут запуститься, например на машине без плагина SpecSheriff. Команда, которой нужно, чтобы проверки хуков git действовали для всех, запускает их в CI.

Порядок позволяет каждой проверке полагаться на то, что она читает: на файлы в окончательном виде, а если она читает узлы, — на узлы, структура которых уже прошла проверки структуры.

Примеры

Собственные guidelines проекта перечисляют форматтер. При коммите форматтер сначала переписывает файлы коммита, а затем генераторы инструментов SpecSheriff записывают свои файлы. Дальше запускается поиск секретов — один из собственных инструментов проекта для хука pre-commit. За ним идут проверки того, что каждый ключ записан в каждом объекте только один раз и что каждый файл соответствует своей JSON Schema, а остальные проверки SpecSheriff guidelines запускаются последними, на окончательных файлах.

  3. the checks of the SpecSheriff guidelines (§s-jau82aq9juv9zzh).

After the first step, nothing changes what the commit contains. Each step runs regardless of what the earlier steps found. The commit or the push goes through only if every check passes and no tool fails.

On a commit, as an exception to the steps above, the following checks run right after the first step:

  • the check that, in each object (§s-d5cgda5bdsn7bzy) of a file of the specification, of its archive (§s-f2b5zvc565s242f) or of its schema (§s-eferktypcj7njt5), each key is written only once;
  • the check that every file of the specification complies with its JSON Schema (§s-emrfpzw2d5bgb6x).

The project's own checks and the other checks of the SpecSheriff guidelines run only after these checks have passed.

Where the SpecSheriff tools cannot run, the project's own tools still run. The commit or the push then goes through unless one of them fails. Whoever makes the commit or the push is told that no SpecSheriff check ran.

Reason

A project may run tools of its own on a commit or a push, such as a scan that checks that nothing internal reaches a public repository. Adopting the method must not stop them, even where the SpecSheriff tools cannot run, for example on a machine without the plugin. A team that needs the checks of the git hooks to apply to everyone runs them in CI.

The order lets every check rely on what it reads. Whatever rewrites files runs before any check, so every check reads the commit in its final form. A generator runs after any formatter, so that no formatter changes what the generator writes. A check that reads the nodes runs only on files that have passed the checks on their structure. A tool that changed the commit after the checks would let through what no check had read.

Examples

A project's own guidelines list a formatter. On a commit, the formatter rewrites the files in the commit first, and the generators of the SpecSheriff tools then write their files. Next come the checks that each key is written only once in each object and that each file complies with its JSON Schema. A scan for secrets runs after them, and the other checks of the SpecSheriff guidelines run last, on the final files.

Reason

Each check except the tests runs at the earliest moment at which everything it reads is available, so a mistake is caught and fixed where it is made.

Title

Code and tests that no SpecTag binds

Text

The checks treat code that is outside the commit, and that no SpecTag (§s-8xw4mgvpexyvw5q) binds, as follows:

  • while the specification is a draft, the commit passes without a warning;
  • while the specification is approved and its strict flag (§s-q3pfzyaxvpr2zj2) is off, the commit passes, and a single warning for all such code says that such code exists;
  • while the specification is approved and its strict flag is on, the commit is refused.

Code outside the commit means the system's code that the commit leaves unchanged, tests included. The warning in the second case and the refusal in the third each name the command of the SpecSheriff tools that lists that code by file and symbol.

Reason

Code and tests written before their rules may have no SpecTag that binds them and still work correctly. Refusing every commit while such code exists would stop all work until all of it was bound to rules. So the owners decide when such code is reported, by approving the specification, and when it must be bound, by turning its strict flag on.

Examples

The specification is approved, and its strict flag is off. A commit changes one file, whose symbols all carry SpecTags, while two old files elsewhere carry none. The commit passes, and the checks warn once that no SpecTag binds some code outside the commit, naming the command that lists that code. Were the specification a draft, the same commit would pass with no warning. The most likely mistake is to refuse the commit because of the two old files, or to list their symbols in the warning.

An old function carries a SpecTag that names the section holding the rules it implements. That SpecTag binds nothing, so while the specification is approved and its strict flag is off, a commit that leaves the function unchanged passes with the warning. The most likely mistake is to treat the function as bound because it carries a SpecTag.

Title

Text

Where a section needs terms of its own, they are added to the contracts section. Title

A term defined in a domain

Text

A term is defined in a domain (§s-ypa92gpcj3f5zj8) if at least one node cites it or links to it and every such node is in that domain or in the part of the technical appendix named after it (§s-vj7ercem526zd6v). Before any other node cites such a term or links to it, whoever writes that citation or link moves the term to the contracts section (§s-z6tq6a3btnvvwx7).

Reason

A term that only one domain needs belongs to that domain's subject area, so the contracts section keeps only what the domains share.

Examples

The domain of users defines the term "account", which only its own rules and the part of the technical appendix named after it cite. A rule of the domain of requests then needs the term. Whoever writes that rule moves the term to the contracts section before the rule cites it. The most likely mistake is to define the term again in the domain of requests.
