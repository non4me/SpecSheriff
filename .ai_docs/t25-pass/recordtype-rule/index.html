RecordType: где он хранится и как связан с тестом и кодом

20 ноября 2026 · T25 · к вопросу «является ли RecordType правилом»

RecordType — один узел базовой спецификации, в котором записаны и назначение данных, и их формат. Если считать его правилом, его sid несут код, сгенерированный из него, и хотя бы один тест, как у любого другого правила.

Где хранится RecordType

RecordType — узел базовой спецификации, а не технического приложения. Он стоит в разделе той части системы, где данные этого формата появляются впервые 12.1, согласовано 18 ноября. Фрагменты формата, например адрес, стоят в разделе контрактов, и их может использовать любой раздел.

Узел состоит из двух половин. Это и есть та связка «правило плюс JSON-схема», о которой вы пишете:

  • заголовок и текст — имя формата и то, для чего он нужен 12.2;
  • поле schema — сам формат. Он записан словами JSON Schema 2020-12 ваше решение 19 ноября и несколькими словами словаря SpecSheriff: какое поле идентифицирует запись, какие поля выбирают вариант, откуда приходят значения поля.
{
  "sid": "s-7rq2wd4kmh9vx3p",
  "kind": "RecordType",
  "status": "approved",
  "title": "Request",
  "text": "A request that a user submits to an operator.",
  "identifiedBy": "requestId",
  "schema": {
    "type": "object",
    "properties": {
      "requestId": { "type": "string",
        "description": "Identifies the request." },
      "submittedAt": { "type": "string", "format": "date-time",
        "description": "When the user submitted the request." },
      "state": { "enum": ["open", "closed"],
        "description": "Whether the operator has closed the request." }
    },
    "required": ["requestId", "submittedAt", "state"]
  }
}
НазначениеЧто это за данные и зачем они нужны. Эту половину вы называете правилом базовой спецификации.
ФорматПоля, их типы и границы, гарантировано ли значение и что поле означает. Эту половину вы называете JSON-схемой.

Имя, sid и поля придуманы для примера.

Про отдельный документ

Отдельного документа с JSON-схемами нет: JSON Schema — язык, на котором формат записан внутри узла. Отдельным документом хранится раздел контрактов, если спецификация разделена на домены 11.1.2, и фрагменты формата лежат в нём. Файлы JSON-схем появляются только на выходе генератора, как часть кода системы.

Цепочка от узла к тесту и коду

Так я вижу путь одного RecordType, если он правило. Зелёным отмечено, чей sid несёт каждое звено.

  1. 1

    Узел RecordType

    пишет автор, одобряет владелец

    Правка имени, назначения или формата возвращает узел в черновик, как правка любого правила. Пока узел черновик, сгенерированные файлы остаются такими, какими их дала последняя одобренная формулировка 10.15.

    sid узла: s-7rq2wd4kmh9vx3p
  2. 2

    Сгенерированный код

    пишут инструменты SpecSheriff

    Из одобренной формулировки генерируются типы для TypeScript и Python и RuntimeCheck — JSON-схема, по которой запись проверяется во время работы системы. Каким механизмом выполняется проверка, говорит техническое приложение 12.3. Руками эти файлы никто не правит.

    Для TypeScript и Python инструменты делают так уже сейчас: каждое сгенерированное объявление несёт sid своего RecordType. В сгенерированной JSON-схеме sid станет меткой каждого определения. Это уже запланировано в шаге, который меняет инструменты.

    sid s-7rq2wd4kmh9vx3p на каждом объявлении
  3. 3

    Тест формата

    пишет автор кода, до кода из шага 4

    Проверяет, что часть системы не выдаёт и не сохраняет запись не по формату 12.4: например, заявка без времени подачи не сохраняется. Тест проходит, только если часть системы действительно вызывает RuntimeCheck.

    @spec s-7rq2wd4kmh9vx3p в имени теста
  4. 4

    Код части системы

    пишет автор кода

    Функция, которая сохраняет заявку, вызывает RuntimeCheck перед записью. Она реализует бизнес-правило, например «пользователь подаёт заявку», и несёт SpecTag этого правила. Называть RecordType ей не нужно: код, привязанный к RecordType, уже есть, это сгенерированный код.

    @spec <sid бизнес-правила>
  5. 5

    Проверки при коммите

    выполняют инструменты SpecSheriff
    • сгенерированные файлы совпадают с тем, что даёт одобренный RecordType;
    • у одобренного RecordType есть привязанный код и проходящий тест 9.2;
    • каждый SpecTag называет правило 10.1.26.

Что для этого нужно поменять

  • Расширение RecordType получает одно предложение: RecordType — правило раздела, в котором он объявлен, и ему нужна реализация в коде. Это предложение может стоять только в расширении, потому что SpecSheriff guidelines расширений не называют 1.7.3.
  • Инструменты. Сейчас тест с SpecTag RecordType отклоняется, и тест для RecordType не требуется. Станет наоборот: такой тест разрешён, а у одобренного RecordType обязателен.
  • Цена — по тесту на каждый RecordType. Вариант и фрагмент формата — тоже RecordType, поэтому им тоже нужен тест: например, закрытая заявка без времени закрытия не сохраняется.
