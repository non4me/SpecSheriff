RecordType по JSON Schema

Вариант для вашего решения: как изменятся устройство RecordType и тексты правил, если всё привести к JSON Schema 2020-12. В черновиках ничего не изменено.

Инструменты SpecSheriff уже сейчас генерируют из RecordType схему JSON Schema 2020-12 и проверяют ею файлы узлов. Поэтому почти всё в RecordType совпадает с JSON Schema один к одному. По сути расходится одно устройство — поле типа variant.

Главное

  • По сути меняется одно. Поля варианта переезжают из поля типа variant к полям самой записи данных. В JSON Schema так и устроено: условие if/then добавляет поля в тот же объект. Тип variant, особый признак «гарантировано, когда есть значение» и строка 12.12.4 уходят.
  • Запись узла. Тип поля пишется словами JSON Schema: type, format, enum, items, $ref. Смысл каждого типа остаётся тем же: генератор и сейчас переводит слова RecordType в эти слова один к одному.
  • Своё остаётся своим. Чего в JSON Schema нет — идентификатор записи, выбирающие поля, значения варианта, собранные значения, — остаётся словами SpecSheriff. JSON Schema 2020-12 даёт для этого стандартный механизм — собственный словарь ($vocabulary).
  • Генерация. Вместо oneOf из вариантов и члена «прочее» схема получает пары if/then. Так json-schema.org сам показывает поля, которые зависят от значения другого поля.
  • Проверено. Схема ниже прогнана на Ajv 2020, валидаторе, которым пользуются инструменты: 13 записей из 13 приняты или отклонены как ожидалось. Среди них — выбор варианта по двум полям сразу и ссылка по sid через $anchor.

По JSON Schema: пары if/then

"Notification": {
  "$anchor": "<sid «Уведомления»>",
  "type": "object",
  "properties": {
    "id": { "type": "string" },
    "channel": { "enum": ["email", "sms", "app"] },
    "text": { "type": "string" } },
  "required": ["id", "channel", "text"],

    { "if": { "properties": { "channel": { "const": "sms" } },
              "required": ["channel"] },
      "then": { "$ref": "#/$defs/NotificationBySms" } } ],
  "unevaluatedProperties": false },

"NotificationByEmail": {
  "properties": {
    "address": { "type": "string", "format": "email" } },
  "required": ["address"] },

12.6 · новая редакция

Варианты RecordType

Вариант RecordType объявляет поля, которые запись данных RecordType (§s-7vm323mhry2enx3) содержит из-за значений некоторых полей этого RecordType. Эти поля — поля, которые выбирают вариант RecordType. Их называет сам RecordType или RecordType, который он уточняет. Каждое сочетание их значений, по одному значению каждого поля, имеет свой вариант RecordType, если это сочетание приносит собственные поля, и только тогда.

Вариант RecordType — это RecordType, который:

  • объявлен там же, где RecordType, вариантом которого он является: в том же разделе базовой спецификации или в контрактах (§s-z6tq6a3btnvvwx7);
  • ссылается через связь refines (§s-sn6au3vcr9uy5pm) на этот RecordType;
  • называет значения, которым он соответствует, по одному значению каждого поля, которое выбирает вариант.

Запись данных содержит поля своего варианта рядом с полями своего RecordType. Имя каждого поля варианта отличается от имён полей его RecordType, считая унаследованные.

Обоснование

Когда значения одних полей определяют, какие ещё поля содержит запись данных, сам RecordType описывает не все поля, которых могут ожидать части системы, читающие его записи данных. Остальное описывают его варианты RecordType. Поскольку варианты объявлены там же, где RecordType, эти части системы находят полное описание записей данных там, где ищут сам RecordType (§s-7vm323mhry2enx3).

Примеры
  • RecordType уведомления называет своё поле channel полем, которое выбирает его вариант. Значение email приносит поле address, поэтому вариант RecordType для email объявляет address. Запись данных уведомления по email содержит address рядом с channel и text. Значение app не приносит полей, поэтому варианта RecordType у него нет.
  • В базовой спецификации, разделённой на домены, домен аудита хранит RecordType записи журнала аудита. Значения его поля domain — имена доменов. Записи о заказах содержат ещё номер заказа. Значение orders приходит из домена заказов, а его вариант RecordType объявлен в домене аудита.
Что изменилось
  1. Последний абзац. Было: «Поля своего варианта запись данных содержит в единственном поле типа variant своего RecordType». Стало: «Запись данных содержит поля своего варианта рядом с полями своего RecordType».
  2. Добавлено предложение: «Имя каждого поля варианта отличается от имён полей его RecordType, считая унаследованные». Без него поле варианта могло бы совпасть по имени с полем RecordType, и запись не могла бы содержать оба.
  3. В первый пример добавлено предложение: «Запись данных уведомления по email содержит address рядом с channel и text».

Остальные правила раздела 12

  • 12.1, 12.3, 12.4, 12.5, 12.7–12.11 — без изменений. Гарантированное поле (12.5) и есть required в JSON Schema; отклонение поля, которого RecordType не описывает (пример 12.4), — unevaluatedProperties: false.
  • 12.2 — без изменений. Он говорит «тип поля нейтральными словами». Слова JSON Schema не принадлежат ни одному языку программирования, поэтому остаются нейтральными. Само имя JSON Schema называет только описание инструментов: база руководства не называет технологий (1.21, §s-a4rbry4hsu34hy8).

  • Правило описания инструментов о нейтральных типах: слова JSON Schema 2020-12 и собственный словарь SpecSheriff.
  • Тесты инструментов на варианты; узлы RecordType в saloon переписываются один раз.

Р1

Вариант ссылается на свой RecordType через refines

без изменений

JSON Schema: в схеме ссылку держит RecordType — then: { $ref: вариант }. Инструменты SpecSheriff строят её из входящих связей refines. OpenAPI делает так же, как сейчас SpecSheriff: схема варианта ссылается на базовую через allOf.

Плюсы

  • Новый вариант не меняет одобренный RecordType.
  • У варианта свой sid, своё одобрение и свои тесты.

Минусы

  • Нужна проверка, что вариант ссылается на свой RecordType (12.12.5).
Р2

Вариант называет свои значения (answersTo)

без изменений

JSON Schema: answersTo становится условием if с const для каждого выбирающего поля. Сейчас то же значение записано как const внутри полной копии всех полей.

Плюсы

  • Условие стоит в узле рядом с полями, которые оно приносит.
  • Генерация прямая: одно значение — один const.

Минусы

  • answersTo — своё слово SpecSheriff; в самой схеме оно записано длиннее, через if.
Р3

Поля варианта — рядом с полями RecordType

меняется

JSON Schema: then добавляет свойства в тот же объект. Так json-schema.org показывает формат почтового индекса, который зависит от страны. OpenAPI, TypeScript и serde (внутренняя метка) тоже кладут поля варианта рядом с остальными.

Плюсы

  • Убирает единственное устройство RecordType, которого нет в JSON Schema.
  • Уходят тип variant, признак «гарантировано, когда есть значение», поля «при любом варианте» и строка 12.12.4.
  • Сгенерированные типы TypeScript и Python становятся обычным размеченным объединением, без вложенного объекта.

Минусы

  • Поля варианта и поля RecordType делят одни имена: нужна новая проверка, что имена не совпадают.
  • Пересматриваются согласованные сегодня абзац 12.6 и строка 12.12.4, а также ваше решение от 31 октября о единственном поле типа variant.
  • По записи данных не видно, какие поля принёс вариант: это видно только по узлу варианта.
Р4

Вариант выбирают значения нескольких полей

без изменений

JSON Schema: условие if с несколькими const — обычная запись, проверено на Ajv. На прошлой странице я поставил JSON Schema ◐ — это была ошибка. С JSON Schema как основным ориентиром это решение — уже не отступление от практики.

Плюсы

  • Сочетание полей, например способа оплаты и страны, не требует искусственного поля только для выбора варианта.

Минусы

  • discriminator в OpenAPI, Protobuf и serde выбирают вариант по одному полю. В сгенерированном коде для них сочетание полей выразить труднее.
Р5

Вариант объявлен там же, где его RecordType

без изменений

JSON Schema: варианты — записи $defs в той же схеме. Сама JSON Schema этого не требует: $ref может вести в любую схему.

Плюсы

  • Полное описание записей данных находится там, где ищут сам RecordType.

Минусы

  • Держит только правило 12.6 и проверка 12.12.6, а не сама схема.
Р6

Ссылки только внутри своей части системы и на фрагменты из контрактов

без изменений

JSON Schema: $ref внутри схемы части системы и на общую схему контрактов. Границ частей системы JSON Schema не знает.

Плюсы

  • Граница видна в схеме: кроме контрактов, ссылок наружу нет.

Минусы

  • Держит только правило 12.10 и его проверка.
Р7

Тип поля записан словами JSON Schema

новое

JSON Schema: type, format, enum, items, additionalProperties, $ref, required, description, unevaluatedProperties. OpenAPI 3.1 пользуется теми же словами.

Плюсы

  • Узел и сгенерированная схема записаны одними словами: таблица перевода из email address в format: email не нужна.
  • Эти слова знают и агенты, и разработчики. Узел можно проверить метасхемой JSON Schema.
  • Продолжает ваши решения: границы уже названы, как в JSON Schema, а дата проверяется форматом date JSON Schema.

Минусы

  • Человеку без технической подготовки {"type": "string", "format": "email"} читать труднее, чем email address. Просмотрщику спецификации понадобится показывать типы словами.
  • Все узлы RecordType переписываются: в тестах инструментов и в saloon.
Р8

Чего JSON Schema не выражает — собственным словарём SpecSheriff

новое

JSON Schema 2020-12: собственный словарь, объявленный через $vocabulary, — стандартный способ добавить свои слова. В словарь SpecSheriff входят identifiedBy, identifierOf, chosenBy, answersTo и слово об источнике собранных значений.

Плюсы

  • Всё своё собрано в одном объявленном словаре, а не разбросано по формату узла.

Минусы

  • Обычный валидатор JSON Schema эти слова пропускает: их по-прежнему проверяют инструменты SpecSheriff.
  • Ссылок между записями в JSON Schema нет совсем, поэтому идентификатор остаётся устройством SpecSheriff (12.12.2, 12.12.3).
Р9

Схема генерируется парами if/then

новое

JSON Schema: allOf из пар if/then — запись, которой json-schema.org описывает поля, зависящие от значения другого поля. OpenAPI 3.1 её допускает, но для вариантов чаще пишет oneOf с discriminator.

Плюсы

  • Значению без варианта не нужен член «прочее» с not anyOf: условие не срабатывает, лишние поля отклоняет unevaluatedProperties.
  • Ошибка называет поле: «нет обязательного поля address», а не «не подошёл ни один из трёх вариантов».
  • Вариант в схеме содержит только свои поля, а не полную копию полей RecordType.

Минусы

  • Сама схема не мешает двум парам сработать сразу. Это по-прежнему держит проверка 12.12.9.
  • Нужен валидатор JSON Schema 2019-09 или новее, из-за unevaluatedProperties. Сгенерированная схема и так объявлена как 2020-12.

Что это меняет в работе

  • Согласованные сегодня абзац 12.6 о поле типа variant и строка 12.12.4 пересогласуются: 12.6 — в новой редакции выше, 12.12.4 убирается.
  • Ваше решение от 31 октября в 1.26 заменяется в части «не более одного поля типа variant». Его вторая часть остаётся: две независимые развилки — это две записи данных, у каждой свои выбирающие поля.
  • Строка 12.12.5 не меняется и по-прежнему ждёт вашего решения.
  • Шаг правки инструментов растёт: формат узла, генерация для трёх языков, проверки, правила описания инструментов и тесты. Предварительно это ещё 5–7 часов.
