What a node's status says
A node's status is draft or approved. That of a section and of a domain's header is built from the nodes under it (§s-9kfdycuq34beqvs). What follows holds of every other node. Approved means that one of the node's owners (§s-67vekyup7y8smap) approved its present wording: its title, text and reason, and the values its kind adds beside them, such as the fields of a RecordType. Otherwise the node is a draft. Any change to that wording, an owner's own included, makes the node a draft until one of its owners approves the wording it then holds. So does a withdrawal of its approval, which names whoever made it. Anyone may withdraw the approval of a node outside the SpecSheriff guidelines a project takes (§s-bsya3febm6u64ab), but that of the rule that approves the specification (§s-qzthyh7yqvfhsa2). The status stays as it is through a change to: - the node's links or its metadata; - who its owners are; - what is built into it from other nodes, such as the values gathered beside a field (§s-ju5vcanbjph7mgh); - where it stands.
Why
An approved status claims that one of the node's owners agreed to what it now states. A status that survived a rewrite would certify words nobody approved. A draft node asks for no code (§s-utvqbypzhmgndug) and tells its owners that it waits for their approval. A change of owners changes who reads a part, not what a rule states. An owner leaving, or a node moving, takes back nothing that was agreed. Links, metadata and what is built from other nodes are not what an owner approved, and they change as the specification grows around a rule. A withdrawal gives no agreement in anyone's name: it only makes a node a draft, as a change to its wording by anyone does. So whoever finds an approved rule wrong can keep any further change to its code or its tests from being committed (§s-utvqbypzhmgndug) without waiting for its owners. spec/2.2A link carries its type

Every link names what it means, as one of these types: implements — the linking node is how the linked one is carried out; refines — it states the linked node more precisely, or for a narrower case; constrains — it holds a condition the linked rule depends on; consumes — the domain whose header holds the link uses what the linked section of another domain provides; supersedes — it replaces the linked node, which is archived; exempts — a node of the project's own guidelines takes the linked rule or node of a project's own kind (§s-vsh384ybt4w25a2), or every such node under the linked section, out of the rule that it is implemented (§s-6fw72j65jkqrfpf), for the reason its text gives; cites — the linking node cites the linked one (§s-bpdqd9v72wg7vsz) and no other type says how the two bear on each other, so it holds no link of another type to it; term-relation — the linking term and the linked term are bound, for as long as both exist, in the ratio the link carries; uses — what the linking term names makes use of what the linked term names while taking part in a process, as a user fills in a form while signing up, and the link carries no ratio; a term that only starts a process, as an operator starting an export, uses nothing the process uses. The map shows the structure and the status of each node, and nothing else. The structure is a domain, the parts under it, then the rules, down to the individual rule. It is drawn from the nesting, the titles and the level of each domain alone. A branch opens and closes, so a reader goes to the part they came for while the whole stays in view around it. The branches stand in this order: - the guidelines first; - then contracts; - then a branch for each level of the domains, from the top, holding its domains in the order §s-uw9n84edf7cbe9n gives; - the technical appendix last.
Why
A specification is read one rule at a time and has to be understood as a whole. The two pull against each other. The full text is more than anyone holds at once. An extract loses where the rule sits. A mindmap answers both: the shape of everything, and the detail of whatever is opened. A diagram kept apart from the nodes is a second copy of the specification and disagrees with it silently. So the map is drawn from the nodes at each build rather than kept beside them. The levels and the order of the domains carry how the domains bear on one another. Shown on the map, the statuses tell which parts of the specification wait for their owners while the whole stays in view.

The specification's status is its owners' act
A rule of the project's own guidelines refining this one states that the specification is approved. The specification is approved while that rule is approved, and a draft otherwise. Only the specification's owners approve that rule or withdraw its approval. A commit that makes the specification approved, where before it was a draft, is refused unless every symbol of the system's code outside its tests, and every test, carries a SpecTag. A commit that puts it back to draft is refused unless it records one of the specification's owners withdrawing the approval of that rule.
Why
Whether the specification is approved decides how strictly the checks hold its code and tests (§s-kkbqcb9xrpaepwn, §s-xhcmchcngykvn2k), so its owners decide it, both ways. They must be able to put it back to draft, whatever leads them to it. While the specification changes at its core, as when another version of it is adopted or the system's architecture changes, the code and the tests are secondary. Approved while code or tests carry no SpecTag, it would refuse the next commit for code or tests that commit did not touch. Anyone could put its rule back to draft by an edit of its wording, or remove it. So only a withdrawal by one of the specification's owners puts the specification back.

The parts of the specification are kept under `specs/`: - each domain under `specs/<domain>/`, opening with its header in `specs/<domain>/00-<domain>.json`; - contracts under `specs/contracts/`; - the technical appendix under `specs/tech/`, each of its sections in a file of its own — a domain's in `<domain>.json`, the stack's in `stack.json`, the technical debt's in `debt.json`; - the guidelines under `specs/_guidelines/`. A part divided into one file per section keeps its files in its directory. In `specs/_guidelines/`, a project's own guidelines are kept in `project.json`. In the repository the SpecSheriff guidelines are written in, the base is kept there in `spec.json` and the appendix of the tools in `tools.json`. Every other project reads the base and the appendix of the tools from the plugin of its agent (§s-zh2vcr3xjumppg5, §s-2pdy9gw2jrjvfb4). The schema is kept in `specs/_schema/` of the repository the SpecSheriff guidelines are written in. Every other project reads it from the plugin. The schema is made of these files: - `node.schema.json` for a node and its metadata; - `section-file.schema.json` for the file of a part; - `extension.schema.json`, the schema of an extension. A project's extension of the schema (§s-eferktypcj7njt5) is kept in `specs/_schema/project.schema.json`. It is validated against the schema of an extension and read together with the schema (§s-xzcw3hv4hmxz7h7). Any other file another project keeps under `specs/_schema/` is refused as a copy of the schema. Approvals are kept in `specs/_approvals.jsonl`. The archive of removed nodes is kept in `specs/_archive/<name>.json`. `specs/_viewer/` (the map) and `md-version/` (the readable export) are rebuilt after every change to the specification. Neither is stored in git. The SpecSheriff tools provide the command `sheriff`. In a terminal it is run as `node <tools>/dist/cli.js`, from the tools a plugin keeps on the machine (§s-4mej6ccn7xu3d3p). `<tools>` is the data directory of the plugin for Claude Code, or the `tools/` of the plugin for Codex CLI in Codex's cache. Their plugin for pytest, the package `pytest-specsheriff`, is installed by pip from the branch `release`: `pip install "pytest-specsheriff @ git+https://github.com/non4me/SpecSheriff@release#subdirectory=skills/pytest-specsheriff"`. The settings of the SpecSheriff tools that a project shares are kept in `sheriff.config.json` at the root of the repository. The settings of the reviewer's runs, which each user confirms, are kept in the user's git configuration (§s-xr5xxa9cxf2mq5u). The setting `"writesSpecSheriffGuidelines": true` marks the repository the SpecSheriff guidelines are written in. Among the settings, glob patterns name where the system's code lives and where its tests live. The code and the tests are read for SpecTags, and a file named neither as code nor as tests is read for neither. That is how the repository's configuration, its own tools and their tests are kept out of the system's code by where they live (§s-hheus6f395ynqvc). Among the settings, too, is the command that runs each check and each generator the project's own guidelines add (§s-2fau85dfyyeq66m, §s-km4x4s26kv7pjze). For each of them, the settings also hold the glob patterns naming the files of its code and of its tests (§s-utf4mbt7ref8g9c). The documents are the markdown files the repository keeps outside `specs/`. The tools of the specification are the files of the SpecSheriff tools. A project keeps only the files `sheriff init` writes. The repository the SpecSheriff guidelines are written in keeps them under `skills/`, where the tests are read for the SpecTags they declare. The following are found in `project.json`: - the specification's owners are those its top node names; - the levels the domains stand at are the members of the `TextRule.list` carried by its rule that refines §s-nkyty4dy9x2v2a4; - the rule that approves the specification is its rule that refines §s-qzthyh7yqvfhsa2; - the files kept as fixtures of tests are those named by the glob patterns its rule refining §s-6hha5en226aj8hu lists.

The commands

It then writes the status of each section and domain's header from the nodes under it (§s-9kfdycuq34beqvs). It is run after every change to the specification. At every run, where `project.json` holds no rule refining §s-qzthyh7yqvfhsa2, `sheriff reindex` adds the rule `sheriff init` writes, as a draft (§s-7unxytshhc4md54). A renamed key keeps its place among the node's keys. It renames those kinds also where a field's values are the sids of a kind's nodes, and where the project's extension of the schema adds fields to a kind. A field of type one of whose own list an earlier release wrote empty, which then stood for the values the domains add, takes those values as its source instead. It also renames `specs/_confirmations.jsonl` to `specs/_approvals.jsonl`, and in each of its lines the key `owner` to `by`. Where `specs/_approvals.jsonl` already stands, it appends those lines to it and removes the old file. Then `sheriff reindex` merges, in every file it rewrites, the values an object holds under one key, each into those written before it: two lists into one holding the members of the first and then those of the second that the first does not hold, two objects key by key in the same way with each key where it was first written, and two values JSON Schema holds equal into one. It names every key it merged, with the file and each value's line, and refuses any other two, naming the file, the key and each one's line and value, and then writes no file. `sheriff reindex` also rewrites each test that names its node in the form an earlier release of the SpecSheriff tools read, by a bare sid. A bare sid is a word of the form of a sid that opens the test's name, followed by a space or the name's end, or that stands alone as the argument of its mark. In the files the settings name as the tests of the system's code or of a project's own check or generator, `sheriff reindex` puts `@spec ` before that sid. Each node's list of tests then names the test by its new name, and `sheriff reindex` names each file it rewrites. `sheriff approve` records an approval or its withdrawal (§s-v4qus7raqnwzneb). `sheriff export` writes the readable export in markdown, one file for each file of the specification, each node as §s-k4nqjr96ux7a5m7 says. `sheriff render` writes the map, the mindmap of the specification's structure drawn from its nodes (§s-rpv4fkdqqguptqd). `sheriff guide` prints every node of the guidelines — the base, the appendix of the tools and the project's own — as §s-k4nqjr96ux7a5m7 says, and the figures counted off the model as it prints: how many nodes each part holds and how many of them are approved. It also prints whether the specification is approved. `sheriff show` prints a node, found by its sid or its location, as §s-k4nqjr96ux7a5m7 says. `sheriff model` prints as JSON the model of the specification where it runs: every node as its file holds it, with its location, the part and the file it stands in, and the owners named nearest above it. A project's own check or generator is handed it on its standard input (§s-2fau85dfyyeq66m, §s-km4x4s26kv7pjze). `sheriff todos` prints, as text, every item of the todos of the specification where it runs, the archive left out, and the SpecSheriff guidelines too where the project takes them. The items come the newest first, those of one day in the order the specification reads. Each comes with its date, who its author is, what is to be done, and the sid, location and title of its node (§s-t28j22vbdmmeqnh). `sheriff types` generates, from the RecordTypes, the types and the runtime checks of the system's code, where the technical appendix says they stand, and the files each generator the project's own guidelines add prints, run by the command the settings name for it and handed what `sheriff model` prints on its standard input, printing as JSON each file's path, its content and the sids of the nodes it is written from (§s-km4x4s26kv7pjze). It writes a file only where the file is missing or holds, line endings aside, anything other than what it generates, and names each file it writes. Where the check of generated copies refuses the list of those files or a RecordType (§s-dbk2vyeg8z5jxna), or a project's generator ends with an exit status other than zero, it names each refusal and writes no file. It writes a file only once every node that file is generated from is approved, and names each node it waits for: - the types and runtime checks wait for every RecordType; - a file a project's generator prints waits for the nodes it is written from and for the rule listing that generator.
Why
The reindex rewrites whole the files written by hand, so it keeps everything they hold: two values written under one key are each somebody's intent, kept together where both can stand and refused where keeping one would drop the other, since nothing says which was meant; and every merge is named, because one of them may have been written to replace the other. `sheriff types` runs after every edit an agent makes and at every commit, where the pre-commit hook copies each file it names into the working tree for its author to stage (§s-477gtdrkw34dzxw): the files it names are then exactly those its author has to stage, and a file whose content no edit changed keeps its modification time, so that nothing watching the files takes it for changed. Line endings are set aside because git may check a file out with endings other than those committed, which would make every file differ at every run. Where anything is refused, no file is written, so that nothing a failed run generated reaches the code. Each refusal is named, so that whoever runs it, by hand or through a hook, learns which node or list to change. Each file waits only for the nodes it is generated from, so that a node awaiting approval holds back no file generated without it. Handed the model rather than left to read the files, a project's check or generator finds nodes by their location, finds owners and follows links as the tools do, in whatever language the project writes it; a generator prints its files rather than writing them, so that they are written, compared and held back on the same terms as the types. A project's files are written by the release that wrote them, so a release that writes something in another form rewrites it where the files are next read, and the project rewrites nothing by hand. A test names its node in the form the release of its day reads, so a release that changes that form rewrites the tests as well. The files it rewrites are named, since they are the author's to stage. Under earlier releases a specification without the rule approving it was a draft, and added as a draft the rule keeps it one. Written wherever it is missing, the rule is always there for the owners to approve.

Setting a repository up and taking SpecSheriff out of it
`sheriff init` sets a repository up for the SpecSheriff tools. It writes the git hooks into `.githooks/` (§s-4mej6ccn7xu3d3p); stages with the executable mode, 100755, each hook there that holds what it would write and that git's index does not already hold with that mode, naming each one, or, where it cannot stage a hook, names it and says how to stage it executable; and turns them on. For the agent `--agent` names, `claude` or `codex`, `claude` where the option is not given, `sheriff init` adds the marketplace and the plugin to `.claude/settings.json` as a project declares them (§s-zh2vcr3xjumppg5), keeping every other key there, or writes the agent's hooks for Codex into `.codex/hooks.json` (§s-n76wt2bkqdmh78x), keeping every other hook there. It refuses another name, naming the two it takes. `sheriff init` has git merge the approvals (§s-v4qus7raqnwzneb) by union. Where `git check-attr merge specs/_approvals.jsonl` reports that attribute unspecified, `sheriff init` appends the line `specs/_approvals.jsonl merge=union` to the `.gitattributes` at the repository's root, writing the file where it is missing. The appended line starts a line of its own and ends as the file's lines end. Where git reports `union`, `sheriff init` appends nothing. Where git reports any other state of that attribute, it appends nothing and names that state. Outside a git repository, it appends the line unless the file holds it already, spacing and line endings aside. Where they are missing, `sheriff init` writes a `sheriff.config.json` naming no file as code or tests, and a `specs/_guidelines/project.json`. That `project.json` names the email git is configured with as the specification's owner. It also holds, as a draft, the rule "The specification is approved", refining §s-qzthyh7yqvfhsa2, whose text is "This project's specification is approved." It replaces a hook or a declaration that holds what an earlier release of `sheriff init` wrote, naming each, and no other file that differs from what it would write, naming each one instead; so run again it changes nothing. A hook or a declaration holds what an earlier release wrote where, line endings aside, it equals one of the texts the earlier releases wrote, which the SpecSheriff tools keep. Where the repository's hooks ran from elsewhere before, from `.git/hooks/` or from another folder `core.hooksPath` named, `sheriff init` names each hook found there, git's samples aside, and says that it no longer runs until it is moved into `.githooks/<hook>.d/` (§s-n4m5zvh96yb299p). `sheriff remove` takes out of a repository what `sheriff init` writes outside `specs/`, for both agents: - each git hook, the marketplace and the plugin in `.claude/settings.json` and the agent's hooks for Codex in `.codex/hooks.json`, where each holds what `sheriff init` writes now or wrote in an earlier release; - each line of the `.gitattributes` at the repository's root that is the line `sheriff init` appends there, spacing and line endings aside; - `core.hooksPath` where it names `.githooks`; - a key of `.claude/settings.json` or `.codex/hooks.json` left holding nothing, and either file left holding no key; - `.gitattributes` left holding nothing but blank lines; - `.githooks/`, `.claude/` or `.codex/` left empty; - `sheriff.config.json`, whatever it holds. It leaves each hook and declaration that differs, naming it, and leaves `specs/` as it is, naming it. It stages nothing, and run again it changes nothing. `sheriff remove` names each folder `.githooks/<hook>.d/` it leaves, and says that the project's own tools in it no longer run.
Why
On a system whose files keep an executable bit, git runs a hook only where its file has the bit, and a clone checks a file out with the mode its commit records. Git takes that mode from the file when it stages it where files keep the bit, and records it as not executable where they keep none, as on Windows, where git runs a hook whatever its mode; so a hook set up there would reach the clones unable to run, and nothing on the machine that set it up would show it. A mode reaches the clones only staged and committed, and git stages a mode only with the file's content, so `sheriff init` stages the hooks it holds and nothing else: what else a commit holds stays its author's choice. Claude Code reads its plugin from `.claude/settings.json` and Codex its hooks from `.codex/hooks.json`, so `sheriff init` writes for the agent the project is set up with, and a project moving to another agent runs it again for that one. A hook or a declaration written by an earlier release is the tools' own, so it is replaced; one that differs otherwise was changed by hand and is the project's. Two branches that each append a line to the approvals conflict where they are merged. The approvals keep every approval ever given (§s-v4qus7raqnwzneb), so the lines of both branches belong in the merge. Git's union merge keeps them, wherever the branch merged into holds the line `specs/_approvals.jsonl merge=union`. It suits the approvals, each of whose lines is a whole JSON object. A union merge puts the lines of the branch being merged after those of the branch merged into. So where both branches wrote a line for one node and one wording, the line of the branch being merged decides, whatever the order they were written in. An owner who finds the result wrong approves or withdraws again after the merge. A line removed through git can come back where another branch appended directly after it. So an approval is taken back by a withdrawal, which a merge keeps. `sheriff init` asks git for the approvals' merge attribute, so a setting in any attributes file git reads is found. A project that set it otherwise chose that setting. Git takes, for each attribute, the last line matching a path, so a line appended after the project's would override it. `sheriff init` names the setting, since the approvals then conflict at merges. The rule is written in every project, so that its owners approve the specification by approving the rule, with nothing to write (§s-qzthyh7yqvfhsa2). It is written as a draft, since an approval is an owner's act on reading the rule, which `sheriff init` does not perform for them (§s-67vekyup7y8smap). `sheriff remove` takes out what `sheriff init` writes and no more. A line of `.gitattributes` equal to the one `sheriff init` writes is taken as its own, whoever wrote it, as a hook is. `sheriff.config.json` goes whatever it holds, because a repository holding it is one the plugins act in (§s-zh2vcr3xjumppg5) and its settings serve only the tools; `specs/` stays, being the project's own content. What `sheriff remove` takes out is in git's history, and what a commit holds stays its author's choice, so it stages nothing. Taking up the method moves where git looks for hooks, so a hook the repository ran before stops running unless it is moved, and `sheriff init` names each one rather than moving a file of the project. Taking the method out unsets that place again, so the project's own steps stop running with the checks.

What the export, the guide and `sheriff show` write of a node
`sheriff export` and `sheriff show` write a node with every value its file holds for it. They write each link with its type, its direction, its ratio where it holds one, and the sid, location and title of the node at the other end. `sheriff guide` writes each node of the guidelines as the export does, except its metadata. Each of them writes a value that is not text, other than its links and its children, under its key as JSON, but for two. A rule's list any of whose members is an object (§s-v7vd4ydrwexsgsj) has its other values written as JSON and its members as a table: a column for each property a member holds, the one the list names first and the others in the order they first appear, and a row for each member, a primitive member in the first column alone; a cell holding a list or an object holds it as JSON on one line, a `|` escaped. The values gathered beside a field of type one of are left out of the JSON and written after it as a list under the field's name, each with the sid, location and title of the node it comes from. The export and the guide write a node's children after it, each under a heading one level deeper than its parent's; `sheriff show` writes the node alone.
Why
A person reads the specification in the export, since a structure a schema checks is hard to read (§s-kh8qcd5kxgh9z3j), and a person or an agent reads one node through `sheriff show`. A value either leaves out, such as a RecordType's fields, a rule's list or a decision taken on the node (§s-gqbj8849rf224qa), is one its reader never learns of and works without. A sid alone tells a reader nothing of the node it names. An agent reads the guide whole before it works on the specification, to follow the guidelines: it needs each node as it binds, its links included, since a link may exempt a rule from implementation or narrow it. The metadata serves whoever changes a node, who reads it whole through `sheriff show`; written into the guide, it would only lengthen what every agent reads. JSON is the form the file already holds a value in, so its reader learns no form of its own for it. The export and the guide keep the tree of the file they are written from, while `sheriff show` is asked for one node. Written as JSON, a list of objects spreads each member over lines and repeats every property's name, so its members are hard to compare; a table puts each member on one row and each property down one column. The file names a gathered value's node by its sid alone.

The hooks
Each check lives in a command a git hook calls: `.githooks/pre-commit` runs `sheriff export` and `sheriff render`, then `sheriff validate`, `sheriff binding` and `sheriff citations`, and last `sheriff types`; `.githooks/commit-msg` runs `sheriff message` and then `sheriff review` on the file git hands it; and `.githooks/pre-push` runs the tests of the system's code and of the project's own checks and generators by the command `sheriff.config.json` names as its `testCommand`, as §s-b6qdtghnyha3fhk says. A clone turns them on with `git config core.hooksPath .githooks`, which the `SessionStart` hook of the agent, the plugin's for Claude Code or the project's for Codex (§s-n76wt2bkqdmh78x), runs where `core.hooksPath` is unset, saying so, and reports where it names another directory. The `SessionStart` hook also names each git hook in `.githooks/` that git's index holds without the executable mode and, on a system whose files keep that bit, each whose file lacks it, and says how to make each one executable on every system — `chmod +x <hook>` and `git update-index --chmod=+x <hook>`, then a commit — changing neither the mode of a file nor git's index. The `SessionStart` hook of the plugin for Claude Code writes into the git configuration of the user, by `git config --global`, each setting of the runner `claude` (§s-xr5xxa9cxf2mq5u) the user has given as an option of that plugin (§s-zh2vcr3xjumppg5), wherever the configuration lacks it or holds another value. Where the git configuration lacks a setting of the runner `sheriff review` would take at a commit in the repository (§s-xr5xxa9cxf2mq5u, §s-4mej6ccn7xu3d3p), the `SessionStart` hook of either agent names each such setting, with the default `sheriff review` takes for it, and asks the agent to offer the user each default to confirm or replace and to write with `git config --global` the value the user answers, the default included. It asks so once for each runner on each machine, and marks it asked in the git configuration, as `specsheriff.review.claudeAsked` or `specsheriff.review.codexAsked`; where the mark stands it asks nothing. At a commit, the checks read what is staged, written out to a directory of its own and read there against the repository's history, while the export and the map are written in the working tree, a failure to write them reported and stopping nothing. Whatever the checks found, `sheriff types` then runs in the directory the staged files are written out to; the pre-commit hook copies each file it writes there into the working tree, in place of what stands at the same path, and stages none of them, and what `sheriff types` refuses stops the commit. Where a file differs between them, stands in only one of them, or stands in the working tree without having been added, it refuses the push, naming each such file; otherwise it runs the tests in the working tree. The types and RuntimeChecks generated from the RecordTypes are generated after every edit an agent makes and at every commit, so that they follow the nodes at the first edit or commit after every node they are generated from is approved (§s-kh8qcd5kxgh9z3j), and a person who edits the nodes without an agent has no hook between edits. At a commit they are generated from the staged nodes, because a commit is judged only by what it holds (§s-jau82aq9juv9zzh). What `sheriff types` refuses there is a fault of that commit. The copy it writes is the one that commit has to hold. At a commit `sheriff types` runs after the checks, so that they read what is staged rather than a copy the hook wrote. It runs whatever they found, since the check of the generated copies is among them and refuses exactly the commit whose copies it writes. After an edit it runs before them, so that they read the copies the edited nodes produce rather than report ones about to be replaced. The copy goes to the working tree, since the directory the commit is written out to is gone once the hook ends, and the author stages from the working tree. It replaces whatever stands at that path, since a generated copy is never edited (§s-kh8qcd5kxgh9z3j). What a commit holds is its author's choice, so the hook stages nothing. A commit holding a copy left behind nodes that are all approved still does not pass. The check at the commit comparing each kept generated copy with what the staged nodes produce refuses that commit until its author stages the new copy. A failure to write the export or the map stops no commit, since the commit holds neither, and every check reads the commit being made and never what it does not hold (§s-jau82aq9juv9zzh). A test run judges a commit only where the files it reads are those the commit holds, since every check reads the commit being made and never what it does not hold (§s-jau82aq9juv9zzh). The tests run in the working tree rather than in a copy of the commit, because they need what each checkout installs or builds for itself, which a copy of the commit lacks. The files the working tree ignores are left out of the comparison of the working tree with each commit, because each checkout makes or keeps its own copy of them. So where a commit holds such a file, as a commit of a build's output does, the working tree's copy need not match it. The refusal names the files the push is refused for, because whether each is committed, removed or ignored is for whoever pushes to decide.
tools/7.1.2The schema and a project's extension
Было
The schema and a project's extension
`sheriff validate` validates each file with a JSON Schema validator against the base schema of the SpecSheriff guidelines, composed with the project's extension (§s-eferktypcj7njt5). The extension is validated first, against the schema of an extension. That schema lets an extension add only kinds, fields of an existing kind, and properties of a file or of a link. What the extension adds joins the base schema: - its kinds join the kinds a node may have; - its conditions join those every node is held to; - its properties of a file and of a link join those a file and a link may hold. `sheriff binding` validates each file against the same schema before it checks anything. `sheriff reindex` validates each file once it has merged each key written twice and changed what an earlier release wrote, as §s-f5rz6b7dhxejjts says, and before it computes anything. Where the schema refuses a file, or the schema of an extension refuses the project's extension, each of the two commands names that file or the extension and every refusal in it. It then checks nothing more, and `sheriff reindex` writes no file.

A key written twice is merged first, since a file read without the merge holds only its last value. What an earlier release wrote is changed first, since the schema refuses its old names. What `sheriff reindex` writes itself is left out, since a node written by hand lacks it until the command runs.

`sheriff review` has a runner judge every commit that changes the system's code. A runner is an agent's CLI, started apart from the session that wrote the code (§s-xr5xxa9cxf2mq5u). It also refuses the commit where a changed symbol: - does something no node its SpecTags name states in its text; - carries a SpecTag naming a node it does not implement; - carries the SpecTag that names no node while it implements the system's logic. A finding of the last kind names as its node the rule that every symbol carries a SpecTag (§s-kgbzk2ph9e6jfb4).
Why

A SpecTag is the text `@spec <sid>`, or, on a symbol only, `@spec none` followed by its reason. Why

How an approval is recorded
`sheriff approve <sid>...` appends to `specs/_approvals.jsonl` one line per node: its sid, the fingerprint of its wording and, as `by`, the email git is configured with. It sets the node's status to approved. Where the latest line for the node and that fingerprint is already an approval, it appends nothing and only sets the status. It refuses: - a section and a domain's header; - a node of the SpecSheriff guidelines the project takes; - a node none of whose owners is the one approving, naming its owners; - the rule that approves the specification, unless the one approving is one of the specification's owners (§s-qzthyh7yqvfhsa2). An approval stands for a wording of a node where the latest line for that node and that wording's fingerprint is an approval. The latest line is the one standing last in `specs/_approvals.jsonl`. `sheriff approve --withdraw <sid>...` withdraws the approval of each wording of the node for which one stands, whether the node holds that wording or not. For each such wording it appends a line: the node's sid, that wording's fingerprint, `withdrawn: true` and, as `by`, the email git is configured with. It makes the node a draft. Where no approval stands for any wording of the node, it appends nothing. Anyone may run it. It refuses: - a section and a domain's header; - a node of the SpecSheriff guidelines the project takes; - the rule that approves the specification, unless the one withdrawing is one of the specification's owners (§s-qzthyh7yqvfhsa2). The fingerprint is a SHA-256 hash of one canonical string holding the node's title, text and reason and the values its kind adds beside them, but neither the owners a node names nor what the reindex builds, the keys of an object sorted and a list in its own order. In that string the reason stands under the key `rationale`, the name earlier releases gave it. Earlier releases gave a field of type one of an empty list of its own values where the domains add its values. In that string such a field stands in that form. An owner is named by an email.
Why
One line appended per approval keeps every approval ever given. The lines two branches append merge without a conflict where git merges the approvals by union, as `sheriff init` has it do (§s-7unxytshhc4md54). SHA-256 is a hash every language provides. The email git is configured with is the one a commit names its author by, so an approval and the commit carrying it name the same person. The owners a node names say who reads its wording, not what the wording is, and what the reindex builds is no one's wording. A fingerprint changes with the name and value of every key in its string. A release writing the wording in another form would otherwise make a draft every node approved before it, though no wording changed. A section's and a header's status is built (§s-9kfdycuq34beqvs), so nobody approves them. It refuses the whole patch where: - it refuses one of the patch's files; - it cannot read or apply the patch.
Why
Codex admits no plugin carrying hooks into its public directory, so the hooks are the project's. Codex runs a project's hooks once its user trusts the project and each hook as it stands. A hook holding only the lookup and the call changes only where its lookup does. It is then trusted again. What the scripts do follows the release. A hook that finds no plugin does nothing, so removing the plugin leaves no hook failing in the project. Codex hands an edit as one patch, which may touch several files. The patch is applied whole. So the guard judges each file and refuses the patch whole.

What a RecordType generates
From each RecordType, `sheriff types` writes a type into each file of types and a definition under `$defs` into each file of runtime checks. It takes the nodes in the order the specification reads: its files in the code-point order of their paths, and the nodes of each file in the order they stand. Every type and definition is named by the RecordType's name with the first letter of each word raised and the spaces dropped. Each type carries a SpecTag with the sid of its RecordType, as a symbol of code carries one with the rule it implements (§s-5z5gnu7pahr82xp). A type and a definition hold the fields of every RecordType above the node along its refines links, the topmost first, then the node's own fields, except a variant's own, which stand where the rule on RecordType variants places them (§s-nk8td3ez58gahc4); each field keeps its name and the order its node gives it, and is required where its node says so and optional otherwise. A field of type record refers to the type of that RecordType by its name, and the object of a field of type variant is written out in full. Where the RecordType refuses a field nobody declared, its definition refuses any property its fields do not declare. A name that is not an identifier in the language of its file, or that the file already uses — the names it imports and those its language builds in included — cannot be generated. In TypeScript a type is written `export type <name> = {...}`. In Python a type is written `<name> = TypedDict("<name>", {...})`, every name it uses imported from `typing`, a reference to another type written as a string, an optional field marked `NotRequired`, and the object of a field of type variant given a type of its own, named by the type it stands in followed by the field's name with its first letter raised, and carries a SpecTag with the same sid.
Why
One name in every file lets a reader follow a RecordType from its node to each copy, and a fixed order makes each file come out the same at every run, which the comparison of generated copies needs. The generator writes the SpecTag itself, so that the link from each type to its node is made anew with the type and never kept by hand. A RecordType that refines another holds that one's fields, as the schema of the nodes says, and a field keeps the name its node gives because the code uses that name as it stands. Only a runtime check can refuse an undeclared property; a type in TypeScript or Python cannot. A name the file already uses would break its compilation or hide what it imports. The functional form of `TypedDict` takes any field name, a keyword of Python included; a reference written as a string may name a type written later in the file, or the type itself; and Python can name the object of a field only by a type of its own.

A RecordType its variants refine
A RecordType that variants refine — RecordTypes each answering to values of its choosing fields, the fields whose values choose which variant a RecordType is — is written as the union of its members: in JSON Schema a definition holding `oneOf` the members, in TypeScript a union type, in Python `<name> = Union[...]`. Its members are each variant, referred to by the name of its type, and, where some combination of the choosing fields' values has no variant, a member for those combinations, named by the RecordType's name followed by `Other`: a type and a definition of their own, the type carrying a SpecTag with the RecordType's sid. A variant holds each choosing field, required and fixed to the value it answers to, and its own fields inside the RecordType's field of type variant, beside the fields that field holds, or, where the RecordType has no such field, beside the RecordType's fields; the variant's node decides whether a property nobody declared is refused there and around it. The member for the other combinations holds the RecordType's fields, its choosing fields required where their node says so. Its definition refuses every combination of values a variant answers to; its type gives a choosing field the values no variant answers to where one field chooses, and all its values where several do; the RecordType's node decides whether a property nobody declared is refused. A field of type variant is required where its object holds a field and is not declared otherwise, whether or not variants refine its RecordType.
Why
A union whose members the choosing fields tell apart is how JSON Schema, TypeScript and Python each state that a RecordType's fields depend on its values, and with the choosing fields required in every variant at most one member matches. A value that brings no fields of its own has no variant, as the rule on variants says (§s-z3dnru6qqdf9m6j), so the RecordType itself answers for it, under a name its own name gives and with its own SpecTag. Each member follows its own node on undeclared properties, so that no node's setting overrides another's. A runtime check can refuse every combination of values a variant claims; a type can name only the values each field holds, which is exact where one field chooses. An object with no field in it holds nothing, so the field for it is not declared.
