English
Title

Entries that only an owner of the specification records

Text

For a setting that only an owner of the specification changes (§tools 2.10), sheriff binding accepts a commit's change to the entries in sheriff.config.json (§tools 1) only where both of the following hold:

• after the commit, the first entries for that setting are all those that the commit's parent holds for it, unchanged and in the same order;
• each entry that follows them names an owner of the specification (§1.1.6).

sheriff binding refuses every other change to the entries for a setting that only an owner of the specification changes. The refusal names the setting, each entry concerned and the specification's owners.

sheriff binding reads the entries of the commit's parent in the form to which sheriff reindex would rewrite them (§tools 2.3). For a merge commit, the parent is its first parent. sheriff binding takes the specification's owners from project.json (§tools 1) as the commit leaves it.

sheriff binding makes this check regardless of whether the specification is approved or a draft (§10.1.27, §10.1.27a, §10.1.27b).

Reason

Removing, editing or moving an entry already recorded, or recording an entry in the name of a person who is not an owner, could change a setting that only an owner of the specification changes without an act of an owner (§10.6, §10.7, §1.7.5).

Example

The latest entry for the specification's approval status approves the specification, and the entry before it returned the specification to draft. A person deletes the latest entry by hand, so that the specification would be a draft again. sheriff binding refuses the commit, since the first entries for that setting are no longer those of the commit's parent. The most likely mistake is to check only the added entries, which lets the commit return the specification to draft without an owner's entry.

Заголовок

Записи, которые вносит только ответственный за спецификацию

Текст

Для настройки, которую меняет только ответственный за спецификацию (§tools 2.10), sheriff binding принимает изменение, которое коммит вносит в записи в sheriff.config.json (§tools 1), только если выполнено и то и другое:

• после коммита первыми записями для этой настройки остаются все записи для неё, которые содержит родительский коммит, неизменными и в том же порядке;
• каждая запись, которая следует за ними, называет ответственного за спецификацию (§1.1.6).

Любое другое изменение записей для настройки, которую меняет только ответственный за спецификацию, sheriff binding отвергает. Отказ называет настройку, каждую затронутую запись и ответственных за спецификацию.

Записи родительского коммита sheriff binding читает в том виде, в какой их переписал бы sheriff reindex (§tools 2.3). Для коммита слияния родитель — его первый родитель. Ответственных за спецификацию sheriff binding берёт из project.json (§tools 1) в том виде, в каком его оставляет коммит.

sheriff binding выполняет эту проверку независимо от того, одобрена спецификация или она черновик (§10.1.27, §10.1.27a, §10.1.27b).

Обоснование

Удаление, правка или перестановка уже внесённой записи, как и внесение записи от имени человека, который не является ответственным, могли бы изменить настройку, которую меняет только ответственный за спецификацию, без действия ответственного (§10.6, §10.7, §1.7.5).

Пример

Последняя запись о статусе одобрения спецификации одобряет её, а запись перед ней возвращала спецификацию в черновик. Человек вручную удаляет последнюю запись, чтобы спецификация снова стала черновиком. sheriff binding отвергает коммит, потому что первыми записями для этой настройки больше не являются записи родительского коммита. Самая вероятная ошибка — проверять только добавленные записи: тогда коммит возвращает спецификацию в черновик без записи ответственного.

English
Title

From a draft to an approved specification, and back

Text

sheriff binding holds the specification's passage from a draft to approved and back (§10.6). It reads the rule that approves the specification in project.json.

It takes the specification before a commit as the commit's first parent holds it, read as sheriff reindex would rewrite it (§tools 2). Where the commit has no parent, it takes the specification before the commit as a draft.

While the commit leaves the specification a draft, sheriff binding reports each of these rather than refusing it, where the commit does not change it (§9.5):

• a symbol of the system's code outside its tests that carries no SpecTag;
• a test that carries no SpecTag.

While the commit leaves the specification approved, both are refused.

A commit that puts the specification back to draft passes only where it adds to the approvals a withdrawal of that rule's approval, of whichever wording, by one of the specification's owners as the commit holds them.

tools 7.1.2a (новый, после «How the schema of the specification is composed») · s-mhsb6fjsq5xn6c9 · новый узел описания инструментов · пункт 28
English
Title

The chosen extensions and the installed plugin

Text

A command of the SpecSheriff tools that reads the chosen extensions of the guidelines (§1.7.1, §1.7.5) runs only where the installed SpecSheriff plugin delivers each of them (§10.1.27c). Where the plugin lacks any of them, the command refuses to run. The refusal names each missing extension and the version of the SpecSheriff tools in the plugin. sheriff reindex then leaves every file unchanged.

The commands that read the chosen extensions include sheriff validate, sheriff binding and sheriff reindex, which, as they compose the schema of the specification, add to it the schema of each chosen extension that has one (§tools 7.1.2). The commands that read the chosen extensions also include sheriff guard, which checks an agent's edit before it is made (§tools 7.3.2). The plugin delivers an extension where the extension's file is at the path given for each extension of the guidelines (§tools 1).

Each command that reads the chosen extensions makes this check regardless of whether the specification is approved or a draft (§10.1.27c).

Reason

Without an extension's file, the SpecSheriff tools can neither compose the schema that the extension adds nor run the checks of its table (§1.7.7). A command that ran without the file would accept on one machine what the same command refuses on a machine whose plugin delivers the extension.

Example

A project chooses an extension that a new release of the SpecSheriff plugin delivers. A team member's machine still has an earlier release, which does not deliver it. On that machine, sheriff validate refuses to run, naming the extension and the earlier release's version, so the git hook refuses the commit. The most likely mistake is to compose the schema without the missing extension, which lets the command accept, on that machine, a node that the extension's checks would refuse.

Выбранные расширения и установленный плагин

Текст

Команда инструментов SpecSheriff, которая читает выбранные расширения guidelines (§1.7.1, §1.7.5), выполняется, только если установленный плагин SpecSheriff поставляет каждое из них (§10.1.27c). Если плагину недостаёт хотя бы одного из них, команда отказывается выполняться. Отказ называет каждое недостающее расширение и версию инструментов SpecSheriff в плагине. sheriff reindex при этом оставляет все файлы неизменными.

Среди команд, которые читают выбранные расширения, — sheriff validate, sheriff binding и sheriff reindex, которые, составляя схему спецификации, добавляют в неё схему каждого выбранного расширения, у которого она есть (§tools 7.1.2). Среди команд, которые читают выбранные расширения, есть и sheriff guard, который проверяет правку агента до того, как она сделана (§tools 7.3.2). Плагин поставляет расширение, если файл расширения находится по пути, указанному для каждого расширения guidelines (§tools 1).

Каждая команда, которая читает выбранные расширения, выполняет эту проверку независимо от того, одобрена спецификация или она черновик (§10.1.27c).

Обоснование

Без файла расширения инструменты SpecSheriff не могут ни составить схему, которую добавляет расширение, ни выполнить проверки его таблицы (§1.7.7). Команда, выполненная без этого файла, принимала бы на одной машине то, что та же команда отвергает на машине, где плагин поставляет расширение.

Пример

Проект выбирает расширение, которое поставляет новый выпуск плагина SpecSheriff. На машине одного из участников команды всё ещё стоит более ранний выпуск, который его не поставляет. На этой машине sheriff validate отказывается выполняться и называет расширение и версию более раннего выпуска, поэтому git hook отвергает коммит. Самая вероятная ошибка — составить схему без недостающего расширения: тогда команда на этой машине принимает узел, который отвергли бы проверки расширения.

English
Title

What a commit adds, changes and removes in the code and the tests

Text

The SpecSheriff tools find what a commit adds, changes and removes in the system's code (§9.1), including its tests. They compare each file as the commit leaves it with the same file in the commit's parent. For a merge commit, the parent is its first parent. The first commit of a repository is compared with an empty repository. A file that the commit moves or renames is compared with the file at its earlier path. A line that the commit adds or removes is one that git shows as added or removed when it compares the two versions of the file with the Myers algorithm, git's default, however git is configured on the machine.

A commit changes only the symbols (§spec 1.5.2), files bound as a whole (§tools 8.3, §tools 8.4) and tests (§tools 8.5) that both the commit's parent and the commit hold. It adds each of them that only the commit holds. It removes each of them that only the commit's parent holds.

A commit changes a symbol, a test or a file bound as a whole where its two versions differ (§tools 7.2.1a). A symbol or a test extends from its first line to its last, including its decorators. So a change in a nested symbol also changes each symbol that encloses it.

A symbol or a test in the commit's parent is the same as the one with the same name, nested in symbols with the same names, in the file as the commit leaves it. A test that the commit renames, keeping its SpecTag and changing nothing else in it, also stays the same test (§9.3, §spec 9.4).

A commit also changes each symbol, file bound as a whole and test whose SpecTags it changes (§spec 9.4). A commit changes the SpecTags of a symbol, a file or a test where a SpecTag binds it either in the commit's parent or after the commit, but not in both. Two SpecTags are the same only where their texts are the same, including the text after @spec none (§tools 8.1).

A commit adds an entry of the bindings file (§tools 8.4) where the commit's parent holds no entry for the same file. It changes an entry whose SpecTags differ from those of the same file's entry in the parent.

A commit adds or changes each SpecTag of the following kinds:

• a SpecTag on a line that the commit adds;
• a SpecTag in an entry that the commit adds or changes.

The exception is a SpecTag that binds the same symbol, file or test, with the same text, as in the commit's parent.

A commit leaves unchanged each symbol, file bound as a whole and test that it leaves in the repository and neither adds nor changes.

Reason

The checks of a commit judge code and tests according to whether the commit adds, changes, removes or leaves them unchanged. A single definition of each of these lets every check judge the same code and tests in the same way.

Example 1

A commit deletes the line log(id); inside the function close and changes nothing else in it. The version of close in the commit's parent contains that line, so the two versions produce different syntax trees, and the commit changes close. The most likely mistake is to look only at the lines that the commit adds, which misses a change made by deleting lines.

Example 2

A commit rewords a comment in a stylesheet bound by SpecTags at its start and changes nothing else in it. The SpecSheriff tools parse both versions with the grammar of CSS and leave the comment out of both trees. The trees are the same, so the commit does not change the stylesheet's code. The most likely mistake is to count any change to the text of a file bound as a whole as a change to its code.

Что коммит добавляет, меняет и удаляет в коде и тестах

Текст

Инструменты SpecSheriff находят, что коммит добавляет, меняет и удаляет в коде системы (§9.1), в том числе в его тестах. Они сравнивают каждый файл в том виде, в каком его оставляет коммит, с тем же файлом в родительском коммите. Для коммита слияния родитель — его первый родитель. Первый коммит репозитория сравнивается с пустым репозиторием. Файл, который коммит перемещает или переименовывает, сравнивается с файлом по его прежнему пути. Строка, которую коммит добавляет или удаляет, — это строка, которую git показывает добавленной или удалённой, когда сравнивает две версии файла алгоритмом Майерса, принятым в git по умолчанию, при любых настройках git на машине.

Коммит меняет только те символы (§spec 1.5.2), файлы, привязанные целиком (§tools 8.3, §tools 8.4), и тесты (§tools 8.5), которые есть и в родительском коммите, и в самом коммите. Каждый из них, который есть только в коммите, он добавляет. Каждый, который есть только в родительском коммите, он удаляет.

Коммит меняет символ, тест или файл, привязанный целиком, если две его версии различаются (§tools 7.2.1a). Символ или тест занимает строки от своей первой до последней, включая его декораторы. Поэтому изменение во вложенном символе меняет и каждый символ, в который он вложен.

Символ или тест в родительском коммите — тот, что с тем же именем и вложен в символы с теми же именами, в файле в том виде, в каком его оставляет коммит. Тест, который коммит переименовывает, сохраняя его SpecTag и больше ничего в нём не меняя, тоже остаётся тем же тестом (§9.3, §spec 9.4).

Коммит меняет также каждый символ, файл, привязанный целиком, и тест, SpecTag которых он меняет (§spec 9.4). Коммит меняет SpecTag символа, файла или теста, если SpecTag привязывает его либо в родительском коммите, либо после коммита, но не в обоих случаях. Два SpecTag одинаковы, только если одинаковы их тексты, в том числе текст после @spec none (§tools 8.1).

Коммит добавляет запись файла привязок (§tools 8.4), если в родительском коммите нет записи для того же файла. Он меняет запись, SpecTag которой отличаются от SpecTag записи того же файла в родительском коммите.

Коммит добавляет или меняет каждый SpecTag следующих видов:

• SpecTag на строке, которую коммит добавляет;
• SpecTag в записи, которую коммит добавляет или меняет.

Исключение — SpecTag, который привязывает тот же символ, файл или тест с тем же текстом, что и в родительском коммите.

Коммит оставляет неизменными каждый символ, файл, привязанный целиком, и тест, которые он оставляет в репозитории и не добавляет и не меняет.

Обоснование

Проверки коммита оценивают код и тесты в зависимости от того, добавляет ли их коммит, меняет, удаляет или оставляет неизменными. Единое определение каждого из этих случаев позволяет каждой проверке одинаково оценивать одни и те же код и тесты.

Пример 1

Коммит удаляет строку log(id); внутри функции close и больше ничего в ней не меняет. Версия close в родительском коммите содержит эту строку, поэтому две версии дают разные синтаксические деревья, и коммит меняет close. Самая вероятная ошибка — смотреть только на строки, которые коммит добавляет: тогда изменение, сделанное удалением строк, пропускается.

Пример 2

Коммит меняет формулировку комментария в таблице стилей, привязанной SpecTag в начале файла, и больше ничего в ней не меняет. Инструменты SpecSheriff разбирают обе версии грамматикой CSS и исключают комментарий из обоих деревьев. Деревья одинаковы, поэтому коммит не меняет кода таблицы стилей. Самая вероятная ошибка — считать любое изменение текста файла, привязанного целиком, изменением его кода.

English
Title

How two versions of code are compared

Text

Where the SpecSheriff tools have a grammar for a file's language, they compare two versions of a symbol or a file bound as a whole (§spec 1.5.2), or of a test (§tools 8.5), by their syntax trees. They parse each version with the tree-sitter grammar of that language. Two versions differ where their trees differ once the following are left out of both:

• each comment, other than the file's first line when that line starts with #!;
• in a test, the test's name, other than its SpecTag (§9.3).

A syntax tree holds the kind of each construct of the code, how the constructs nest, and the text of each token, such as an identifier or a literal. So renaming an identifier changes the tree, and so does any edit inside a string literal. A change to whitespace changes the tree only where the grammar makes whitespace part of the syntax, such as the indentation of a line in Python or YAML.

The SpecSheriff tools parse the following files with a grammar:

• a file whose language a description covers (§tools 8.2), with the grammar of its language;
• a file bound as a whole (§spec 1.5.2) whose name ends in .yaml or .yml, in .css, in .sql, in .sh or in .json, with the grammar of YAML, CSS, SQL, Bash or JSON respectively.

Where the grammar finds a syntax error in either version, the two versions differ where their text differs.

In any other file, two versions differ where their text differs.

Reason

A change to the code makes the SpecSheriff tools check that code against its rules again (§spec 9.4). A syntax tree keeps whatever can alter what the code does and drops the whitespace to which the language gives no meaning. So comparing trees treats as changes exactly the edits that can affect what the code does. Where the SpecSheriff tools have no grammar for a file's language, comparing the text treats every edit as a change, so that no change to the code passes unchecked.

Example 1

A commit re-wraps the call send(to, subject, body); onto three lines and adds a comment above it. Both versions produce the same syntax tree, so the commit changes no code. The most likely mistake is to compare the lines, which counts the re-wrapped call as a change.

Example 2

A commit renames the test @spec s-… refuses an empty name to @spec s-… refuses a blank name and changes nothing else in it. With the test's name left out, both versions produce the same tree, so the commit leaves the test unchanged. The most likely mistake is to keep the test's name in the tree, which counts the renamed test as changed.

Example 3

A commit indents the key retries by two more spaces in a YAML file bound as a whole, which nests the key under the key above it. The grammar of YAML makes indentation part of the syntax, so the two versions produce different trees, and the commit changes the file. The most likely mistake is to compare only the tokens, which lets the nested key pass as unchanged.

Как сравниваются две версии кода

Текст

Где у инструментов SpecSheriff есть грамматика языка файла, они сравнивают две версии символа или файла, привязанного целиком (§spec 1.5.2), или теста (§tools 8.5) по их синтаксическим деревьям. Каждую версию они разбирают грамматикой tree-sitter для этого языка. Две версии различаются, если различаются их деревья после того, как из обоих исключено следующее:

• каждый комментарий, кроме первой строки файла, начинающейся с #!;
• в тесте — название теста, кроме его SpecTag (§9.3).

Синтаксическое дерево содержит вид каждой конструкции кода, вложенность конструкций друг в друга и текст каждого токена, например идентификатора или литерала. Поэтому переименование идентификатора меняет дерево, и любая правка внутри строкового литерала тоже. Правка пробельных символов меняет дерево только там, где грамматика делает пробельные символы частью синтаксиса, например отступ строки в Python или YAML.

Грамматикой инструменты SpecSheriff разбирают следующие файлы:

• файл на языке, для которого есть описание (§tools 8.2), — грамматикой этого языка;
• файл, привязанный целиком (§spec 1.5.2), имя которого оканчивается на .yaml или .yml, на .css, на .sql, на .sh или на .json, — грамматикой YAML, CSS, SQL, Bash или JSON соответственно.

Если грамматика находит синтаксическую ошибку хотя бы в одной из двух версий, версии различаются, если различается их текст.

В любом другом файле две версии различаются, если различается их текст.

Обоснование

Изменение кода заставляет инструменты SpecSheriff снова сверить этот код с его правилами (§spec 9.4). Синтаксическое дерево сохраняет всё, что может изменить то, что делает код, и отбрасывает пробельные символы, которым язык не придаёт значения. Поэтому сравнение деревьев засчитывает ровно те правки, которые могут повлиять на то, что делает код. Где у инструментов SpecSheriff нет грамматики языка файла, сравнение текста засчитывает каждую правку, чтобы ни одно изменение кода не прошло без проверки.

Пример 1

Коммит переносит вызов send(to, subject, body); на три строки и добавляет над ним комментарий. Обе версии дают одно и то же синтаксическое дерево, поэтому коммит код не меняет. Самая вероятная ошибка — сравнивать строки: тогда перенесённый вызов засчитывается как изменение.

Пример 2

Коммит переименовывает тест @spec s-… refuses an empty name в @spec s-… refuses a blank name и больше ничего в нём не меняет. Без названия теста обе версии дают одно и то же дерево, поэтому коммит оставляет тест неизменным. Самая вероятная ошибка — оставлять название теста в дереве: тогда переименованный тест засчитывается как изменённый.

Пример 3

Коммит увеличивает на два пробела отступ ключа retries в файле YAML, привязанном целиком, и тем вкладывает этот ключ в ключ выше. Грамматика YAML делает отступ частью синтаксиса, поэтому две версии дают разные деревья, и коммит меняет файл. Самая вероятная ошибка — сравнивать только токены: тогда вложенный ключ проходит как неизменённый.

Title

Which edits change a test or code

Text

A change to a SpecTag (§9.3) is considered a change to the test or the code that the SpecTag binds.

As long as the SpecTag stays the same, none of the following changes the test or the code:

• renaming a test;
• adding, removing or rewording a comment;
• changing whitespace that, in the language of its file, does not affect what the code does.

In a file whose comments and whitespace the checks (§10.1) cannot tell apart from its code, every edit changes the code.

Reason

Tests and code that change are checked again against the rules their SpecTags name. This rule draws the line between an edit to a test or code that can affect that check and one that cannot.

Example

A commit re-indents a block of TypeScript code, adds a comment above it and changes nothing else, so the commit changes no code. By contrast, a commit that indents a key of a YAML file further, which nests the key under the key above it, changes the code.

Title

How code is bound to its rules

Text

The system's code (§9.1) other than tests is bound by SpecTags (§9.3) to the rules it implements. Code that implements no rule has a SpecTag that says so.

A symbol is a named unit of code, such as a function, a class or a member of one, a type, a constant or a component. Whoever writes code binds it to its rules in one of the following ways:

• by a SpecTag directly before each symbol, if the checks (§10.1) can identify the file's symbols;
• by SpecTags in a comment placed as near the start of the file as its format allows, if the checks cannot identify the file's symbols;
• by an entry in the bindings file at the root of the repository, for a file whose format allows no comments.

A SpecTag before a symbol binds that symbol and every symbol nested in it. SpecTags at the start of a file, and an entry in the bindings file, bind the whole file. A change anywhere in a file bound as a whole is a change to the code its SpecTags bind. The only exception is an edit that changes no code (§spec 9.4): an edit to a comment that leaves its SpecTags as they are, or to whitespace that does not affect what the code does.

The formats that allow no comments are JSON and those that a project's own guidelines (§2.3) name as allowing none.

Each entry in the bindings file names an existing file and holds that file's SpecTags.

Reason

Binding each file of the system's code as precisely as its format allows lets the checks immediately find code that has lost its link to the specification.

Example 1

A stylesheet whose symbols the checks cannot identify has its SpecTag in a comment at its start.

Example 2

A JSON file that holds the texts a user interface shows has an entry in the bindings file. The entry names the JSON file and holds its SpecTags.

Title

The code and the tests of a draft rule

Text

sheriff binding refuses a commit that adds, changes or removes (§tools 7.2.1) code or a test bound by a SpecTag (§9.3) that names a draft rule (§10.1.28a). It does so regardless of whether the specification is approved or a draft (§1.3.2).

The refusal names the rule by its file, its sid and its location (§spec 8.5). It also names each symbol (§spec 1.5.2) and each test concerned, with its file and its line, and each other file concerned. Where the commit removes a symbol or a test, its line is read in the commit's parent.

sheriff binding reads the SpecTags both in the commit's parent and as the commit leaves the code and the tests. From the specification as the commit leaves it, sheriff binding takes the approval status of each rule that those SpecTags name. A rule here is a node of one of the kinds that the node on the form of a SpecTag lists (§tools 8.1).

Reason

A draft rule may still be incomplete or wrong, so code or a test written, changed or removed for it would follow a wording that no owner has approved (§1.3.2).

Example

A rule that a function implements is reworded and becomes a draft. Before an owner approves the new wording, a commit deletes the function. sheriff binding refuses the commit and names the rule. The most likely mistake is to read the SpecTags only as the commit leaves the code, which lets the deletion pass, since no SpecTag naming the rule is left.

English
Title

The judgement on a comment that a commit adds or changes

Text

sheriff review reports each finding of the independent reviewer (§spec 1.6.2) on a comment that a commit adds or changes (§spec 10.1.43b) only as a warning. Each such finding names the file, the line and the problem, and also each rule that the comment contradicts.

The reviewer judges the comments in the system's code (§9.1) outside the files generated from the specification (§10.15). In a file whose syntax trees the SpecSheriff tools build (§tools 7.2.1a), the comments are the parts of the file that the SpecSheriff tools treat as comments and leave out of the trees. In any other file, the reviewer itself tells the comments apart from the code.

A commit adds or changes a comment where, with whitespace left out, the comment's text differs from the text of every comment in the same file in the commit's parent (§tools 7.2.1). The reviewer judges the text of a comment, except its SpecTags (§9.3), since a change to a SpecTag is a change to the code (§spec 9.4).

The reviewer judges comments on every commit that adds or changes a comment, including a commit that changes no code. sheriff review gives the reviewer the code that each such comment describes, in addition to what it gives the reviewer in every review (§tools 7.3.4). That code is the following, in full, as the commit leaves it, with its file, its lines and the SpecTags that bind it:

• for a comment in a file bound as a whole (§spec 1.5.2): that file;
• for a comment in a symbol (§spec 1.5.2) or a test, or directly above one (§tools 8.2): the innermost such symbol or test;
• for any other comment: the symbol or the test that follows it, or the whole file where no symbol or test follows it.

The reviewer finds a problem with a comment only where either of the following holds:

• the comment states something that the code it describes does not do;
• the comment contradicts a rule that a SpecTag on that code names.
Reason

A comment that no longer matches its code misleads whoever reads the code next. Only a reader of both the comment and the code can see the mismatch. A comment does not change what the system does, so a problem with a comment warrants a warning, but not a refusal of the commit.

Example

A commit changes only the comment above roundPrice, which now says that the function rounds halves up, while the function rounds them to the nearest even number. sheriff review reports the reviewer's finding as a warning and lets the commit pass. The most likely mistake is to refuse the commit, as sheriff review does for a defect in the code.

Суждение о комментарии, который коммит добавляет или меняет

Текст

sheriff review сообщает каждое замечание независимого рецензента (§spec 1.6.2) о комментарии, который коммит добавляет или меняет (§spec 10.1.43b), только как предупреждение. Каждое такое замечание называет файл, строку и проблему, а также каждое правило, которому комментарий противоречит.

Рецензент оценивает комментарии в коде системы (§9.1) вне файлов, сгенерированных из спецификации (§10.15). В файле, синтаксические деревья которого строят инструменты SpecSheriff (§tools 7.2.1a), комментарии — это те части файла, которые инструменты SpecSheriff считают комментариями и не включают в деревья. В любом другом файле рецензент сам отличает комментарии от кода.

Коммит добавляет или меняет комментарий, если без учёта пробельных символов текст комментария отличается от текста каждого комментария того же файла в родителе коммита (§tools 7.2.1). Рецензент оценивает текст комментария, кроме его SpecTag (§9.3), потому что изменение SpecTag — это изменение кода (§spec 9.4).

Комментарии рецензент оценивает при каждом коммите, который добавляет или меняет комментарий, в том числе при коммите, который не меняет кода. sheriff review передаёт рецензенту код, который описывает каждый такой комментарий, в дополнение к тому, что передаёт ему при каждом ревью (§tools 7.3.4). Этот код — следующее, целиком, в том виде, в каком его оставляет коммит, с его файлом, строками и SpecTag, которые его привязывают:

• для комментария в файле, привязанном целиком (§spec 1.5.2), — этот файл;
• для комментария в символе (§spec 1.5.2) или тесте либо непосредственно над символом или тестом (§tools 8.2) — самый внутренний из таких символов или тестов;
• для любого другого комментария — символ или тест, который идёт после него, или весь файл, если после него нет ни символа, ни теста.

Рецензент находит проблему в комментарии, только если выполнено одно из следующего:

• комментарий говорит то, чего не делает код, который он описывает;
• комментарий противоречит правилу, которое называет SpecTag на этом коде.
Обоснование

Комментарий, который больше не соответствует своему коду, вводит в заблуждение следующего читателя кода. Увидеть несоответствие может только тот, кто читает и комментарий, и код. Комментарий не меняет того, что делает система, поэтому проблема в нём стоит предупреждения, но не отклонения коммита.

Пример

Коммит меняет только комментарий над roundPrice: теперь он говорит, что функция округляет половины вверх, а она округляет их до ближайшего чётного. sheriff review сообщает замечание рецензента как предупреждение и пропускает коммит. Самая вероятная ошибка — отклонить коммит, как sheriff review делает при дефекте в коде.

English
Title

What the independent reviewer judges

Text

In the review of a commit, an independent reviewer judges the following (§spec 10.4):

• for every commit that changes the system's code (§9.1) outside the files generated from the specification (§10.15): whether that code does what the rules named in the commit say and does nothing that they do not say;
• for every commit that adds or changes a comment in the code or in a test outside the files generated from the specification: whether each such comment is consistent with the code that it describes and with the rules that the code implements or that the test is written from;
• for a commit whose message states that a rule's implementation needs no change: whether that statement is true;
• for a commit in which a node of the technical appendix (§1.1.2) is approved, if the node has an implements link (§spec 6.1) to a rule of the base specification (§1.1.4): whether the node refines the rules of the base specification that it implements and contradicts no rule of the base specification.
Reason

No script can decide whether code does only what its rules say, whether a comment agrees with the code and its rules, whether a rule's implementation really needs no change, or whether a node of the technical appendix agrees with the base specification. So these judgements are made by an independent reviewer. Code generated from the specification only restates the specification, so the reviewer has nothing to judge there.

English
Title

What the checks enforce, and when they run

Text

Two things are checked mechanically:

• that the specification conforms to the rules of the guidelines that the main table of checks, or the table of checks of an extension, lists;
• that the specification and the code still agree with each other.

Every check except the review is deterministic.

In the review, an independent reviewer judges the following (§spec 10.4):

• on every commit that changes code: whether that code does what the rules named in the commit say and does nothing that they do not say;
• on a commit whose message states that a rule's implementation needs no change: whether that statement is true;
• on a commit in which a node of the technical appendix (§1.1.2) is approved, if the node has an implements link (§spec 6.1) to a rule of the base specification: whether the node refines the rules of the base specification that it implements and contradicts no rule of the base specification.

The checks run when a commit is made. Where an agent writes the specification, the tests or the code, the checks also run after each of its edits (§10.2). Some of its edits are refused before they are made (§spec 10.3). As long as the specification has the status approved, the tests of the system's code and of a project's own checks and generators must pass before a change reaches the project's shared branch. The project's own guidelines (§2.3) name where the tests run, such as on every push or on a shared server before a merge.

A failed check refuses the change, unless the table that lists the check says otherwise (§10.1).

Reason

Every check but the review is binary, so a refusal requires nobody's judgement. A check that sometimes refuses for a reason nobody can reproduce is bypassed at the first opportunity and never trusted again. The review needs a reviewer, because no script can decide whether code does only what its rules say, whether a rule's implementation really needs no change, or whether a node of the technical appendix agrees with the base specification.

Run after each of an agent's edits, a check finds a mistake where it is made. The order in which the test and the code are written can be seen only edit by edit, since a commit contains the test and the code together.

The tests are not run on a commit, since a test suite takes longer than anyone should wait for a commit. A change not yet shared misleads nobody, so its tests can wait until it is shared. Where they run is the project's choice, since some suites take hours or need what a developer's machine lacks. While the specification is a draft, the work is focused on the specification itself, so no test has to pass.

Example

A project whose tests need a database states in its own guidelines that the tests run on a shared server before a merge. A push from a developer's machine then runs no tests, and the merge waits until the tests pass.

Русский
Заголовок

Что держат проверки и когда они запускаются

Текст

Механически проверяются две вещи:

• что спецификация соответствует тем правилам guidelines, которые перечислены в основной таблице проверок или в таблице проверок расширения;
• что спецификация и код по-прежнему согласованы между собой.

Каждая проверка детерминирована, кроме ревью.

При ревью независимый рецензент судит о следующем (§spec 10.4):

• при каждом коммите, меняющем код, — делает ли этот код то, что говорят названные в коммите правила, и ничего сверх этого;
• при коммите, в сообщении которого сказано, что реализацию правила менять не нужно, — верно ли это утверждение;
• при коммите, в котором одобряется узел технического приложения (§1.1.2), если у узла есть связь implements (§spec 6.1) с правилом базовой спецификации, — уточняет ли узел реализуемые им правила базовой спецификации и не противоречит ли он ни одному правилу базовой спецификации.

Проверки запускаются, когда делается коммит. Там, где спецификацию, тесты или код пишет агент, они запускаются ещё и после каждой его правки (§10.2). Некоторые его правки отклоняются ещё до того, как они сделаны (§spec 10.3). Пока спецификация имеет статус approved, тесты кода системы и собственных проверок и генераторов проекта должны пройти до того, как изменение попадёт в общую ветку проекта. Где запускаются тесты, например при каждом push или на общем сервере перед слиянием, называют собственные guidelines проекта (§2.3).

Непройденная проверка отклоняет изменение, если таблица, в которой она перечислена, не говорит иного (§10.1).

Обоснование

Каждая проверка, кроме ревью, двоична, поэтому отказ ни от кого не требует суждения. Проверку, которая иногда отклоняет по причине, которую никто не может воспроизвести, обходят при первой возможности и больше ей не доверяют. Ревью требует рецензента, потому что скриптом не решить, делает ли код только то, что говорят его правила, действительно ли реализацию правила не нужно менять и согласуется ли узел технического приложения с базовой спецификацией.

Запущенная при каждой правке агента, проверка находит ошибку там, где её сделали. Порядок теста и кода виден только при правках, потому что коммит содержит тест и код вместе.

Тесты не запускаются при коммите, потому что набор тестов идёт дольше, чем стоит ждать коммиту. Изменение, которое ещё не попало в общую ветку, никого не вводит в заблуждение, поэтому его тесты могут подождать до этого момента. Где их запускать, выбирает проект, потому что некоторые наборы тестов идут часами или требуют того, чего нет на машине разработчика. Пока спецификация — черновик, работа сосредоточена на самой спецификации, поэтому ни один тест не обязан проходить.

Пример

Проект, тестам которого нужна база данных, называет в собственных guidelines, что тесты запускаются на общем сервере перед слиянием. Тогда push с машины разработчика тестов не запускает, а слияние ждёт, пока тесты пройдут.

When the tests must pass

Text

As long as the specification has the status approved, the tests of the system's code (§9.1) and of a project's own checks (§10.8) and generators (§10.9) must pass before a change reaches the project's shared branch. The project's own guidelines (§2.3) name where the tests run, such as on every push or on a shared server before a merge.

Reason

The tests are not run on a commit, since a test suite takes longer than anyone should wait for a commit. A change not yet shared misleads nobody, so its tests can wait until it is shared. A project whose tests need a database states in its own guidelines that the tests run on a shared server before a merge. A push from a developer's machine then runs no tests, and the merge waits until the tests pass.

English
Title

The judgement on the code that a commit changes

Text

sheriff review refuses a commit where the independent reviewer (§spec 1.6.2) refuses it for a defect in the code that the commit adds or changes (§spec 10.1.43). Each finding names the rule that it concerns, the file and the line.

The reviewer judges the changed code on every commit that adds or changes the system's code (§9.1), including its tests, outside the files generated from the specification (§10.15). Besides what sheriff review gives the reviewer in every review (§tools 7.3.4), it gives the reviewer the changed code outside the files generated from the specification. That code consists of the following, each in full, as the commit leaves it, with its file, its lines and the SpecTags (§9.3) that bind it:

• each symbol (§spec 1.5.2) whose code the commit adds or changes (§tools 7.2.1);
• each file that the commit adds or changes and that is bound as a whole (§tools 8.3, §tools 8.4);
• each test that the commit adds or changes.

The reviewer refuses the commit where any of the following holds:

• a changed symbol or file whose SpecTags name rules does something that none of those rules states;
• a changed test checks something that the rule its SpecTag names does not state;
• the changed code other than tests leaves out something required by a rule that a SpecTag on that code names, or that the commit's message names outside an Implementation-Needs-No-Change trailer (§tools 9);
• a changed symbol or file carries a SpecTag naming a rule that it does not implement;
• a changed symbol or file carries @spec none (§tools 8.1), but implements the system's logic (§1.2.7);
• a changed symbol or file carries @spec none whose text does not say what the technology that the system is built with requires of it (§tools 8.1).

A finding on code that carries @spec none names the rule on how code is bound to its rules (§spec 1.5.2) as the rule that it concerns.

Reason

A SpecTag shows only which rule a piece of code is meant to implement. Whether the code does only what that rule says, including in the unchanged lines around a change, can be judged only by reading it.

Example

A commit changes one line of the function close, whose SpecTag names a rule saying that an account can be closed only when its balance is zero. An unchanged line of the same function also sends the account holder an email. The reviewer is given the whole function and finds that no rule its SpecTag names says anything about the email. sheriff review refuses the commit, naming the rule and that line. The most likely mistake is to give the reviewer only the changed line, so that the email goes unnoticed.

Суждение о коде, изменённом коммитом

Текст

sheriff review отклоняет коммит, если независимый рецензент (§spec 1.6.2) отклоняет его из-за дефекта в коде, который коммит добавляет или меняет (§spec 10.1.43). Каждое замечание называет правило, которого оно касается, файл и строку.

Рецензент судит изменённый код при каждом коммите, который добавляет или меняет код системы (§9.1), в том числе его тесты, вне файлов, сгенерированных из спецификации (§10.15). Помимо того, что sheriff review передаёт рецензенту при каждом ревью (§tools 7.3.4), он передаёт рецензенту изменённый код вне файлов, сгенерированных из спецификации. Этот код состоит из следующего, каждое целиком в том виде, в каком его оставляет коммит, с его файлом, строками и SpecTag (§9.3), которые его привязывают:

• каждый символ (§spec 1.5.2), код которого коммит добавляет или меняет (§tools 7.2.1);
• каждый файл, привязанный целиком (§tools 8.3, §tools 8.4), который коммит добавляет или меняет;
• каждый тест, который коммит добавляет или меняет.

Рецензент отклоняет коммит, если выполнено что-либо из следующего:

• изменённый символ или файл, SpecTag которого называют правила, делает то, чего не утверждает ни одно из этих правил;
• изменённый тест проверяет то, чего не утверждает правило, которое называет его SpecTag;
• изменённый код помимо тестов упускает то, чего требует правило, которое называет SpecTag на этом коде или которое сообщение коммита называет иначе, чем в trailer Implementation-Needs-No-Change (§tools 9);
• у изменённого символа или файла есть SpecTag, который называет правило, которое этот символ или файл не реализует;
• у изменённого символа или файла есть @spec none (§tools 8.1), но он реализует логику системы (§1.2.7);
• у изменённого символа или файла есть @spec none, текст которого не говорит, чего от него требует технология, на которой построена система (§tools 8.1).

Замечание о коде, у которого есть @spec none, называет правилом, которого оно касается, правило о том, как код привязывается к своим правилам (§spec 1.5.2).

Обоснование

SpecTag показывает только, какое правило должен реализовывать код. Делает ли код только то, что говорит это правило, в том числе в неизменённых строках рядом с изменением, можно узнать, только прочитав его.

Пример

Коммит меняет одну строку функции close, SpecTag которой называет правило: счёт можно закрыть, только если его баланс равен нулю. Неизменённая строка той же функции ещё и отправляет владельцу счёта письмо. Рецензент получает функцию целиком и находит, что о письме не говорит ни одно правило, которое называет её SpecTag. sheriff review отклоняет коммит, называя правило и эту строку. Самая вероятная ошибка — передать рецензенту только изменённую строку: тогда письмо проходит незамеченным.

• a changed symbol or file carries @spec none whose text does not say what the technology that the system is built with requires of it (§tools 8.1).

A finding on code that carries @spec none names the rule on how code is bound to its rules (§spec 1.5.2) as the rule that it concerns.

Reason

A SpecTag shows only which rule a piece of code is meant to implement. Whether the code does only what that rule says, including in the unchanged lines around a change, can be judged only by reading it.

Example

A commit changes one line of the function close, whose SpecTag names a rule saying that an account can be closed only when its balance is zero. An unchanged line of the same function also sends the account holder an email. The reviewer is given the whole function and finds that no rule its SpecTag names says anything about the email. sheriff review refuses the commit, naming the rule and that line. The most likely mistake is to give the reviewer only the changed line, so that the email goes unnoticed.

Title

What the reviewer is given

Text

The SpecSheriff tools give the independent reviewer (§spec 1.6.2) of a commit the following:

• the commit's message;
• the commit's change, excluding the files generated from the specification;
• the wording of each rule or term (§3.3) that the commit's message names;
• the wording of each rule that a SpecTag (§9.3) binds to code or a test that the commit adds or changes, or that is described by a comment that the commit adds or changes;
• for each rule whose implementation, according to the commit's message, needs no change: the rule's wording as it was before the commit and as it is after it, and the tests and the code bound to the rule, directly or through a chain of implements links (§spec 6.1), as they are after it;
• for each node of the technical appendix (§1.1.2) that is approved in the commit and has an implements link to a rule of the base specification (§1.1.4):
◦ the node's wording;
◦ the wording of each rule of the base specification that the node implements, that has a link to or from such a rule, or that is in the same top-level section of the base specification as such a rule.

In this rule, a node's wording is its title, its text, its reason, its examples and the fields its kind adds, as an approval covers them (§1.3.5).

The SpecSheriff tools give the reviewer nothing from the session in which the change was made. They tell the reviewer that each file left out of the change is generated from the specification. The reviewer treats what a rule requires of generated code as implemented by that code.

Reason

The reviewer makes the judgements that no deterministic check can make: whether code does only what its rules say, whether a comment agrees with the code and its rules, whether a rule's implementation really needs no change, and whether an approved node of the technical appendix agrees with the base specification. It can judge only from what it is shown. Shown what each judgement needs, and nothing of what the author of the change meant, it judges by the rules alone.

Рецензент выносит суждения, которых не может вынести ни одна детерминированная проверка: делает ли код только то, что говорят его правила; действительно ли реализацию правила не нужно менять; согласуется ли одобренный узел технического приложения с базовой спецификацией. Решать он может только по тому, что ему показали. Получив то, что нужно для каждого суждения, и ничего о намерениях автора изменения, он судит только по правилам.

English
Title

The review of a commit

Text

sheriff review refuses a commit where the verdict of the independent reviewer (§spec 1.6.2) refuses it. The refusal lists each finding of the verdict (§tools 10.2). Where the commit leaves the specification a draft, sheriff review disregards each finding on a statement that a rule's implementation needs no change (§tools 7.3.4b). In that case, it refuses the commit only where the verdict lists a finding on code or on a node that the commit approves.

sheriff review asks for a verdict only on a commit for which the reviewer must make at least one of the following judgements (§10.2):

• the judgement on the code that the commit adds or changes (§tools 7.3.4a);
• the judgement on each comment that the commit adds or changes (§tools 7.3.4d);
• the judgement on each statement in the commit's message that a rule's implementation needs no change (§tools 7.3.4b);
• the judgement on each node of the technical appendix (§1.1.5) that the commit approves and that implements a rule of the base specification (§1.1.4, §tools 7.3.4c).

Where sheriff review asks for a verdict, it gives the reviewer everything that the rule on what the reviewer is given lists for the commit (§spec 10.4). The files generated from the specification, which sheriff review leaves out of the commit's change, are the files that sheriff types writes (§tools 2.5). sheriff review tells the reviewer which of those files the commit changes.

Reason

Each run of the reviewer is paid for by the user who commits (§tools 10.7), so sheriff review runs the reviewer only on a commit that needs one of the reviewer's judgements.

Example

A commit changes only the wording of a draft rule. It changes no code and no comment in the code, its message contains no statement that a rule's implementation needs no change, and it approves no node. So sheriff review does not run the reviewer, and the commit passes the review. The most likely mistake is to run the reviewer on every commit, which makes the user who commits pay for a run that has nothing to judge.

English
Title

The reviewer's verdict

Text

sheriff review refuses a commit for which the reviewer must make a judgement other than the one on comments (§tools 7.3.4) unless the runner (§tools 10.1) gives a verdict that sheriff review can read (§spec 10.5). Where the commit needs only the judgement on comments (§tools 7.3.4d), sheriff review instead issues a warning that says why it could not read a verdict.

sheriff review gives the runner's CLI the schema of the verdict. The runner's CLI answers with a JSON object that conforms to that schema. The verdict passes or refuses the commit. It lists its findings. Each finding names the sids of the nodes that it concerns and the problem. A finding that concerns code also names the file and, where the problem lies at a line, that line. Each finding also names the judgement that it belongs to (§tools 7.3.4).

sheriff review reads a verdict only from an answer that conforms to the schema of the verdict and that does one of the following:

• passes the commit and lists only findings that belong to the judgement on comments (§tools 7.3.4d), if it lists any;
• refuses the commit and lists at least one finding that belongs to a judgement other than the one on comments.
Reason

A verdict whose meaning sheriff review had to guess, such as a verdict that passes the commit and lists a finding on code, would let sheriff review decide the outcome of the commit in place of the independent reviewer (§spec 1.6.2).

Example

The runner answers with a verdict that passes the commit and lists one finding on code. That answer is not a verdict that sheriff review can read, so sheriff review refuses the commit. The most likely mistake is to pass the commit and drop the finding, which means deciding for the reviewer what it meant.

Title

What sheriff reindex writes

Text

sheriff reindex writes into the files of the specification everything that the SpecSheriff tools compute from the specification, the code and the tests:

• a sid for each node that has none, including a node in a cell of a TableRule (§1.2.2, §8.6);
• the location of each node (§spec 8.5, §tools 7.1.4a);
• the links pointing at each node, rebuilt from the links that the nodes declare (§6.4);
• the list meta.code of each node (§9.7), naming each file, other than a test file, that holds code bound by a SpecTag (§9.3) naming the node, including a file bound as a whole (§tools 8.3, §tools 8.4);
• the list meta.tests of each node, naming each test that declares a SpecTag naming the node (§tools 8.5), by its file and its name;
• the approval status of each section, derived from every node under it other than a section, including the nodes in the cells of a TableRule (§1.3.8);
• where the project has chosen the Domains extension (§11), the approval status of the header of each domain, derived from every node of the domain other than its sections and the header itself, including the nodes in the cells of a TableRule (§domains 11.1.4a);
• where the project has chosen the Domains extension, the index of the sections in the header of each domain that has sections (§11.1.4);
• where the project has chosen the RecordType extension (§12), the values gathered for each field that has an enum whose values come from elsewhere in the specification, in the field's x-enumSource.gathered (§12.9).

In the files that the repository keeps, an approved node whose approval status is set by approvals stays approved while an approval of its current wording stands (§tools 11). sheriff reindex makes each remaining such node a draft and names it.

sheriff reindex writes only the files that the repository keeps. It writes a file only when the text it would write differs from the file's text. It names each file that it writes.

sheriff reindex writes each file as JSON.stringify writes the file's data with an indent of two spaces, with a line feed at the end, with each node's location and sid first, and with all the other keys in the order in which the file already has them.

Reason

The SpecSheriff tools themselves write whatever they can compute from the specification, the code and the tests, so that it always agrees with its sources and nobody spends effort writing it. Because it is rebuilt in full on every run, it is correct regardless of what an earlier run left behind (§10.13).

Title

A list and its declaration

Text

sheriff binding accepts a TextRule.list (§5.1) only where each of the following holds (§10.1.35):

• where the list has a TextRule.list.jsonSchema, each of its values is valid, under JSON Schema 2020-12, against the schema at the place to which that property points;
• where the schema at that place holds the keyword enum, directly or through $ref, each value of that enum is one of the list's values;
• where the list has a TextRule.list.valueList, the symbol (§spec 1.5.2) to which that property points declares exactly the list's values.

sheriff binding refuses every other TextRule.list, naming the node by its file, its sid and its location (§spec 8.5), and naming each value concerned. Where the file to which the list points, the place in it or the symbol cannot be found, the refusal names the one that cannot be found.

Each member of a list gives one of the list's values. The value of a member that is an object is the value of the member's property that TextRule.list.property names. sheriff binding checks a list only where each of its members that is an object holds that property, which the check of an object in a list requires (§tools 7.1.19).

A symbol declares the text of each string literal within its lines, as the SpecSheriff tools read a file whose language a description covers (§tools 8.2). A value of the list matches such a literal where the value, written as text, is the literal's text.

sheriff binding checks the list of each node of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). sheriff binding makes this check regardless of whether the specification is approved or a draft (§10.1.35).

Reason

A rule's list and the schema or the code that declares the same values are written separately, so either can gain or lose a value unnoticed. Comparing them at every commit keeps the values that the system accepts in line with those that the rule states.

Example

A rule lists the states of a request: open, done and cancelled. The rule's TextRule.list.jsonSchema points to #/properties/state in schema/request.schema.json, and the schema at that place holds "enum": ["open", "done", "cancelled", "held"]. sheriff binding refuses the list and names held, a value of the enum that the list does not hold. The most likely mistake is to check only that each value of the list is valid against the schema. All three are, so a state that the schema accepts and the rule does not state would pass.

Текст

sheriff binding принимает TextRule.list (§5.1), только если выполнено каждое из следующего (§10.1.35):

• если у списка есть TextRule.list.jsonSchema, каждое его значение корректно, по JSON Schema 2020-12, относительно схемы в том месте, на которое указывает это свойство;

Каждый элемент списка даёт одно из значений списка. Значение элемента, который является объектом, — значение того его свойства, которое называет TextRule.list.property. sheriff binding проверяет список, только если каждый его элемент, который является объектом, содержит это свойство, чего требует проверка объекта в списке (§tools 7.1.19).

Символ объявляет текст каждого строкового литерала в своих строках, как инструменты SpecSheriff читают файл на языке, для которого есть описание (§tools 8.2). Значение списка совпадает с таким литералом, если значение, записанное как текст, — текст этого литерала.

Список правила и схема или код, которые объявляют те же значения, пишутся отдельно, поэтому в любом из них значение может незаметно появиться или пропасть. Сравнение при каждом коммите удерживает значения, которые принимает система, в соответствии с теми, что утверждает правило.

Title

The list of a project's own kinds of node

Text

sheriff binding accepts the kinds of node that the project's extension of the schema adds in its field kinds (§5.2) only where each of the following holds (§spec 8.4, §spec 10.1.35a):

• taken together, the members of the TextRule.list (§5.1) of the rules in the project's own guidelines (§2.3) that refine the rule on a project's own kinds of node (§8.3) include a member for each of those kinds;
• each member of the TextRule.list of those rules gives its kind the same needsCode as the field kinds gives it;
• each member of the TextRule.list of those rules names one of those kinds.

sheriff binding refuses a commit after which a kind or a member fails one of the conditions above. The refusal names each such kind or member. For a member, it also names the rule that lists the member, by that rule's file, sid and location (§spec 8.5).

A member names a kind by the property that TextRule.list.property names (§spec 8.4). It gives the kind's needsCode by its property needsCode. sheriff binding compares the kinds with the members only where each member that is an object holds the property that TextRule.list.property names, which the check of an object in a list requires (§tools 7.1.19). sheriff binding makes this check regardless of whether the specification is approved or a draft (§spec 10.1.35a).

Reason

A project's own kind of node is declared in the extension of the schema, which nobody approves, but listed in a rule, which an owner approves (§spec 8.4). Comparing the two keeps the declaration of each kind, including whether its nodes require an implementation in code, in line with what an owner has approved.

Example

The project's extension of the schema adds the kind procedure with needsCode: true, and the rule that lists the project's own kinds lists procedure with needsCode: false. sheriff binding refuses the commit and names procedure. The most likely mistake is to compare only the names of the kinds. The commit would then pass, although the rule says that the nodes of the kind procedure require no code and the schema says that they do.

Title

How a project's own kind of node is declared and checked

Text

A project adds a new kind of node to its JSON Schema, in the field kinds (§5.2). Through its schema, a new kind of node may add fields of its own, beyond those the schema of the SpecSheriff guidelines sets for every node. A kind's needsCode says whether its nodes require an implementation in code.

A rule in the project's own guidelines refines the rule on a project's own kinds of node (§8.3). That rule's TextRule.list.members (§5.1) holds each added kind of node with its needsCode. That rule's TextRule.list.property names the key holding a kind's name.

At each commit, a check verifies that the JSON Schema and the project's own guidelines agree on the name and needsCode of each new kind of node (§10.1).

Reason

Only the project knows whether the nodes of a kind it adds are carried out by code, by tools or by people. Nobody approves an extension of the schema, so this rule subjects each such kind, and whether its nodes require an implementation in code, to an owner's approval.

Example

A project adds the kind procedure for the steps that an operator carries out by hand. Its extension of the schema declares "procedure": {"needsCode": false, "schema": {}} in the field kinds. The rule of the project's own guidelines that refines the rule on a project's own kinds of node has TextRule.list.property set to name, and its TextRule.list.members holds {"name": "procedure", "needsCode": false}. The most likely mistake is to declare the kind only in the extension of the schema, which nobody approves.

Как собственный тип узлов объявляется и проверяется

Текст

Проект добавляет новый тип узлов в свою JSON-схему, в поле kinds (§5.2). Посредством schema новый тип узла может добавить собственные поля, помимо общих для всех узлов, перечисленных в схеме SpecSheriff guidelines. needsCode типа узлов говорит, требуется ли его узлам имплементация кода.

Правило в собственных guidelines проекта уточняет правило о собственных типах узлов (§8.3). TextRule.list.members (§5.1) этого правила содержит каждый добавленный тип узла с его needsCode. TextRule.list.property этого правила называет ключ с именем типа узла.

При каждом коммите проверка сверяет согласованность новых типов узлов по имени и needsCode между JSON-схемой и собственными guidelines проекта (§10.1).

Обоснование

Только проект знает, выполняются ли узлы типа, который он добавляет, кодом, инструментами или людьми. Расширение схемы никто не одобряет, поэтому по этому правилу каждый такой тип и то, требуется ли его узлам имплементация в коде, одобряет ответственный.

Пример

Проект добавляет тип узлов procedure для шагов, которые оператор выполняет вручную. Его расширение схемы объявляет "procedure": {"needsCode": false, "schema": {}} в поле kinds. У правила собственных guidelines проекта, которое уточняет правило о собственных типах узлов, TextRule.list.property — name, а его TextRule.list.members содержит {"name": "procedure", "needsCode": false}. Самая вероятная ошибка — объявить тип только в расширении схемы, которое никто не одобряет.

Title

How a project's own kind of node is declared and checked

Text

A project adds a new kind of node to its JSON Schema, in the field kinds (§5.2).

Through its schema, a new kind of node may add fields of its own, beyond those the schema of the SpecSheriff guidelines sets for every node.

A kind's needsCode says whether its nodes require an implementation in code.

A rule in the project's own guidelines refines the rule on a project's own kinds of node (§8.3). That rule's TextRule.list.members holds each added kind of node with its needsCode. That rule's TextRule.list.property names the key holding a kind's name. That rule's TextRule.list.declaredIn refers to the field kinds of the JSON Schema.

At each commit, a check verifies that the JSON Schema and the project's own guidelines agree on the name and needsCode of each new kind of node (§10.1).

Reason

Only the project knows whether the nodes of a kind it adds are carried out by code, by tools or by people. Nobody approves an extension of the schema, so a rule lists those kinds.

Title

What sheriff reindex changes in what an earlier release wrote

Text

sheriff reindex rewrites whatever an earlier release of the SpecSheriff tools wrote or read differently from the release that sheriff reindex belongs to. It does so after it has merged the duplicate keys (§tools 2.4), and before it validates the files. In every file of the specification and of its archive, it makes the following changes:

• a node's key id becomes location;
• a node's key rationale becomes reason;
• the kinds of node record and recordType become RecordType;
• the kind of node rule becomes TextRule;
• the kind of node domain becomes header;
• a node's status "" becomes draft;
• a node's status checked becomes approved;
• a node's key owner, which holds an email address, becomes owners, which holds a list that contains that email address;
• a RecordType's fields and unknown become its schema (§12.2), as follows:
◦ each field becomes a property whose schema is the one given for the field's neutral type (§tools 20);
◦ the field's text becomes the property's description;
◦ each field that the RecordType marks as required is listed in the schema's required;
◦ a field that is required only "where it holds a value" becomes an optional property;
◦ unknown: "refused" becomes additionalProperties: false;
• the source of a field's values becomes the field's x-enumSource (§12.7);
• TextRule.list.declaredIn is removed where it points to the field kinds of the project's extension of the schema (§5.2);
• TextRule.list.declaredIn becomes TextRule.list.jsonSchema where it points to any other place in a JSON Schema;
• TextRule.list.declaredIn becomes TextRule.list.valueList where it names a declaration in code;
• a link of the type supersedes is removed (§spec 6.1);
• a node of the archive loses its sid and every link that points to it (§2.6, §6.4).

A renamed key keeps its place among the node's keys. A kind of node is also renamed where a field's values are the sids of that kind's nodes, and where the project's extension of the schema declares fields for that kind.

A bare sid is a word that has the form of a sid and occurs in one of these places:

• it opens a test's name, followed by a space or by the end of the name;
• it is the only argument of the test's mark.

sheriff reindex also makes the following changes:

• specs/_confirmations.jsonl becomes specs/_approvals.jsonl;
• the key owner in each line of specs/_confirmations.jsonl becomes by;
• where specs/_approvals.jsonl already exists, the lines of specs/_confirmations.jsonl, with that key renamed, are appended to it, and specs/_confirmations.jsonl is removed;
• until sheriff.config.json holds an entry that sets the specification's approval status, an approved rule of project.json that refines the rule on that status (§10.6) is replaced by an entry that approves the specification;
• that entry names the owner who last approved that rule;
• that rule is moved to the archive (§2.6), with the reason "Replaced by the entry in sheriff.config.json that records the specification's approval status";
• the key writesSpecSheriffGuidelines is removed from sheriff.config.json (§tools 1) before the SpecSheriff tools validate that file;
• in each file that sheriff.config.json names as tests of the system's code or of a project's own check or generator, @spec is inserted before each bare sid.

sheriff reindex leaves unchanged a RecordType that holds a field of type variant, a field whose values come from the source domains, or a field whose own list of values is empty, and names that RecordType and each such field.

Where a node of the specification is of a kind, or holds a link of a type, that an extension of the guidelines adds, and the project has yet to choose that extension (§1.7.5), sheriff reindex names that extension.

A renamed key and a renamed kind of node leave a node's fingerprint unchanged (§tools 11). sheriff reindex names each file that it changes in this way, including the files of the specification.

Reason

Each file and each test of a project is written in the form of the release of the SpecSheriff tools that last wrote or read it. A release that writes or reads them differently rewrites them, so that nobody has to rewrite a project by hand and no approval is lost because of a rename.

Что sheriff reindex меняет в записанном прежним выпуском

Текст

sheriff reindex переписывает всё, что прежний выпуск инструментов SpecSheriff писал или читал иначе, чем его собственный выпуск. Он делает это после того, как объединил ключи, записанные дважды (§tools 2.4), и до того, как проверяет файлы. В каждом файле спецификации и её архива он вносит следующие изменения:

• ключ узла id становится location;
• ключ узла rationale становится reason;
• типы узлов record и recordType становятся RecordType;
• тип узлов rule становится TextRule;
• тип узлов domain становится header;
• статус узла "" становится draft;
• статус узла checked становится approved;
• ключ узла owner с адресом почты становится owners со списком из этого адреса;
• fields и unknown у RecordType становятся его schema (§12.2) так:
◦ каждое поле становится свойством со схемой, которую даёт нейтральный тип поля (§tools 20);
◦ text поля становится description свойства;
◦ каждое поле, которое RecordType отмечает обязательным, называется в required схемы;
◦ поле, обязательное «где в нём есть значение», становится необязательным свойством;
◦ unknown: "refused" становится additionalProperties: false;
• источник значений поля становится его x-enumSource (§12.7);
• TextRule.list.declaredIn удаляется, если указывает на поле kinds расширения схемы проекта (§5.2);
• TextRule.list.declaredIn становится TextRule.list.jsonSchema, если указывает в другое место JSON Schema;
• TextRule.list.declaredIn становится TextRule.list.valueList, если называет объявление в коде;
• связь типа supersedes удаляется (§spec 6.1);
• узел архива теряет свой sid и все связи, указывающие на него (§2.6, §6.4).

Переименованный ключ сохраняет своё место среди ключей узла. Тип узла переименовывается и там, где значения поля — sid узлов этого типа, и там, где расширение схемы проекта задаёт fields для этого типа.

Голый sid — это слово в виде sid, которое стоит в одном из этих мест:

• оно открывает имя теста, и за ним идёт пробел или конец имени;
• оно — единственный аргумент метки теста.

sheriff reindex также вносит следующие изменения:

• specs/_confirmations.jsonl становится specs/_approvals.jsonl;
• ключ owner каждой строки specs/_confirmations.jsonl становится by;
• если specs/_approvals.jsonl уже есть, строки specs/_confirmations.jsonl, с переименованным ключом, дописываются в него, а specs/_confirmations.jsonl удаляется;
• пока в sheriff.config.json нет записи, задающей статус одобрения спецификации, одобренное правило project.json, которое уточняет правило об этом статусе (§10.6), уступает место записи, которая одобряет спецификацию;
• эта запись называет ответственного, который последним одобрил это правило;
• это правило уходит в архив (§2.6) с причиной "Replaced by the entry in sheriff.config.json that records the specification's approval status";
• ключ writesSpecSheriffGuidelines удаляется из sheriff.config.json (§tools 1) до того, как инструменты SpecSheriff проверяют этот файл;
• в каждом файле, который sheriff.config.json называет тестами кода системы или собственной проверки или генератора проекта, перед каждым голым sid ставится @spec .

RecordType, в котором есть поле типа variant, поле, значения которого брались из источника domains, или поле с пустым собственным списком значений, sheriff reindex оставляет в прежнем виде и называет этот RecordType и каждое такое поле.

Если узел спецификации — того типа или со связью того типа, которые добавляет расширение guidelines, а проекту ещё предстоит выбрать это расширение (§1.7.5), sheriff reindex называет это расширение.

Переименованный ключ и переименованный тип узла оставляют отпечаток узла прежним (§tools 11). sheriff reindex называет каждый файл, который так меняет, в том числе файлы спецификации.

Обоснование

Каждый файл и каждый тест проекта следует выпуску инструментов SpecSheriff, который последним его записал или прочитал. Выпуск, который пишет или читает их иначе, переписывает их сам, чтобы никто не переписывал проект вручную и ни одно одобрение не терялось из-за переименования.

Title

An object in a list

Text

sheriff validate accepts a member of a TextRule.list (§5.1) that is an object only where TextRule.list.property names a property and the member holds that property (§10.1.36). It refuses any other such member. The refusal names the node by its file, its sid and its location (§spec 8.5), the member's position in the list and, where the list names one, the property.

sheriff validate checks each node of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). It makes this check regardless of whether the specification is approved or a draft (§10.1.36).

Reason

The value of a member that is an object is the value of the property that TextRule.list.property names. sheriff binding compares that value with the schema or the symbol to which the list points (§tools 7.2.6), so a member without that property has no value to compare.

Example

A rule lists the roles of a user as objects, and its TextRule.list.property is name. One member is {"title": "operator"}. sheriff validate refuses that member and names name. The most likely mistake is to take the member's only property as its value.

Значение элемента, который является объектом, — значение того свойства, которое называет TextRule.list.property. sheriff binding сравнивает это значение со схемой или символом, на которые указывает список (§tools 7.2.6), поэтому у элемента без этого свойства нет значения для сравнения.
