### base-questions.md · 2.3 Rule 10.12, "The order in which tools and checks run on a commit and on a push"
TRANSLATION: Правило 10.12, «Порядок, в котором инструменты и проверки запускаются при коммите и при push».

При коммите и при push собственные инструменты проекта, инструменты SpecSheriff и проверки запускаются следующими шагами:
1. инструменты, которые переписывают файлы: сначала те собственные инструменты проекта этого рода, которые перечисляют его собственные guidelines (§s-u7tw6m8npxmv5tu), например форматтеры, а затем генераторы — и инструментов SpecSheriff, и собственные генераторы проекта (§s-km4x4s26kv7pjze);
2. собственные проверки проекта (§s-2fau85dfyyeq66m) и остальные собственные инструменты проекта, каждый из которых оставляет файлы такими, какими они были, кроме тех, которые git игнорирует;
3. проверки SpecSheriff guidelines (§s-jau82aq9juv9zzh).

После первого шага ничто не меняет содержимое коммита. Каждый шаг выполняется независимо от того, что нашли предыдущие. Коммит или push проходит, только если каждая проверка пройдена и ни один инструмент не завершился с ошибкой.

При коммите, в порядке исключения из шагов выше, после первого шага и до любой другой проверки выполняются следующие проверки:
- проверка того, что в каждом объекте (§s-d5cgda5bdsn7bzy) файла спецификации, её архива (§s-f2b5zvc565s242f) или её схемы (§s-eferktypcj7njt5) каждый ключ записан только один раз;
- проверка того, что каждый файл спецификации соответствует своей JSON Schema (§s-emrfpzw2d5bgb6x).

Собственные проверки проекта и остальные проверки SpecSheriff guidelines выполняются только после того, как эти проверки пройдены.

Там, где инструменты SpecSheriff не могут запуститься, собственные инструменты проекта всё равно запускаются. Коммит или push тогда проходит, если ни один из них не завершился с ошибкой. Тому, кто делает коммит или push, сообщается, что ни одна проверка SpecSheriff не выполнялась.

**Обоснование:** Проект может запускать при коммите или push собственные инструменты, например сканирование, которое проверяет, что ничто внутреннее не попадает в публичный репозиторий. Переход на SpecSheriff не должен их останавливать, даже там, где инструменты SpecSheriff не могут запуститься, например на машине без плагина SpecSheriff. Команда, которой нужно, чтобы проверки git-хуков распространялись на всех, запускает их в CI.

Порядок позволяет каждой проверке полагаться на то, что она читает: на файлы в окончательном виде, а там, где она читает узлы, — на узлы, структура которых прошла проверки структуры.

Следующим запускается поиск секретов, один из собственных инструментов проекта для хука pre-commit. За ним идут проверки того, что каждый ключ записан в каждом объекте только один раз и что каждый файл соответствует своей JSON Schema, а остальные проверки SpecSheriff guidelines выполняются последними, на окончательных файлах.
TWO READINGS:
- "each of which leaves the files as they were": (1) описание — так названы те инструменты и проверки, которые файлов не меняют; (2) требование — на этом шаге менять файлы запрещено. **Заголовок:** Код и тесты, которые не привязывает ни один SpecTag

С кодом, который находится за пределами коммита и который не привязывает ни один SpecTag (§s-8xw4mgvpexyvw5q), проверки поступают так:
- пока спецификация — черновик, коммит проходит без предупреждения;
- пока спецификация одобрена и её флаг `strict` (§s-q3pfzyaxvpr2zj2) выключен, коммит проходит, и одно предупреждение на весь такой код говорит, что такой код есть;
- пока спецификация одобрена и её флаг `strict` включён, коммит отклоняется.

Код за пределами коммита — это код системы, который коммит оставляет без изменений, включая тесты. Предупреждение во втором случае и отказ в третьем называют команду инструментов SpecSheriff, которая перечисляет этот код по файлам и символам.

**Обоснование:** У кода и тестов, написанных раньше своих правил, может не быть SpecTag, который их привязывает, и при этом они работают правильно. Отклонять каждый коммит, пока такой код существует, значило бы остановить всю работу, пока весь он не будет привязан к правилам. Поэтому ответственные решают, когда о таком коде сообщается, — одобряя спецификацию, и когда он обязан быть привязан, — включая её флаг `strict`.

**Примеры:**
- Спецификация одобрена, её флаг `strict` выключен. Коммит меняет один файл, у всех символов которого есть SpecTag, а в двух старых файлах в другом месте их нет. Коммит проходит, и проверки один раз предупреждают, что какой-то код за пределами коммита не привязывает ни один SpecTag, называя команду, которая этот код перечисляет. Будь спецификация черновиком, тот же коммит прошёл бы без предупреждения. Самая вероятная ошибка — отклонить коммит из-за двух старых файлов или перечислить их символы в предупреждении.
- У старой функции есть SpecTag, который называет раздел с правилами, которые она реализует. Этот SpecTag ничего не привязывает, поэтому, пока спецификация одобрена и её флаг `strict` выключен, коммит, оставляющий функцию без изменений, проходит с предупреждением. Самая вероятная ошибка — считать функцию привязанной, потому что у неё есть SpecTag.
TWO READINGS:
- "the same rename": «то же» — что и где, в абзаце не названо; подразумевается замена "carries no SpecTag" на "that no SpecTag binds".
- "until all of it was bound to rules": "it" — (1) такой код (вероятнее); (2) вся работа.
- "the rules it implements": "it" — (1) функция (вероятнее); (2) раздел.
- "its `strict` flag is on, the commit is refused": заголовок правила говорит о «коде и тестах», а первая фраза текста — только о "code"; тесты вводятся лишь фразой "tests included". Читатель первой фразы может решить, что тесты не охвачены.
LANGUAGE:
