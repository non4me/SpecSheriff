English
Title

Domains that use one another in a cycle

Text

Where the project has chosen the Domains extension (§11), sheriff validate refuses a change after which domains use one another in a cycle (§11.3.4). The refusal names the domains of one such cycle, in the order in which each uses the next.

One domain uses another where the header of the first (§11.1.3) has a consumes link to a section of the second. Domains use one another in a cycle where a chain of domains, each of which uses the next, leads back to the domain that it starts from.

sheriff validate makes this check regardless of whether the specification is approved or a draft (§11.3.4).

Reason

Only the consumes links of the domains' headers state which domain uses which (§11.1.3). A node that relies on what another domain states has a link, of whatever type, to the node of that domain that states it (§11.1.5). So a check that followed links of every type would refuse changes after which no domains use one another in a cycle.

Example

The header of the domain requests has a consumes link to a section of the domain users. The header of users has such a link to a section of requests. sheriff validate refuses the change and names requests and users. In another project, only the header of requests has a consumes link to a section of users, and a rule of users cites a rule of requests. There sheriff validate accepts the change. The most likely mistake is to treat that citation as a use of requests by users.

English
Title

Sections of the technical appendix matched to the domains

Text

Where the project has chosen the Domains extension (§11), sheriff validate accepts a JSON file under specs/tech/ only where it is one of the following (§tools 1, §11.3.5):

• specs/tech/stack.json or specs/tech/debt.json;
• a file named after a domain, specs/tech/<domain>.json, where <domain> is the name of a domain.

sheriff validate refuses any other JSON file under specs/tech/, and names that file.

In a file named after a domain, sheriff validate accepts each section below the file's first top-level node only where the titles that lead to it also lead to a section of that domain (§11.3.5). The titles that lead to a section are those of the sections that hold it, from the top down, followed by the section's own title. sheriff validate refuses any other section below the file's first top-level node, naming it by its file, its sid and its location (§spec 8.5), and giving its title.

The first top-level node of a file named after a domain represents the domain itself, so the titles that lead to a section of that file start below that node. Each further top-level node of the file is treated as a node under the first, as in the computation of locations (§tools 7.1.4a). In the domain, the titles that lead to a section start with the title of a section that is a top-level node of one of the domain's files or a child of the domain's header (§11.1.3).

sheriff validate makes this check regardless of whether the specification is approved or a draft (§11.3.5).

Reason

To find how a rule of a domain is implemented, a reader looks in the file of the technical appendix named after that domain. There the reader follows the same titles that lead to the rule in the domain (§4.1). A section of that file that matches no section of the domain holds an implementation that the reader will not find.

Example

The domain requests has a section titled “Intake”, which holds a section titled “Validation”. In specs/tech/requests.json, the file's first top-level node holds a section titled “Intake”, which holds a section titled “Validation”, and sheriff validate accepts both. Another section titled “Validation” is directly under the file's first top-level node, and sheriff validate refuses it. The most likely mistake is to accept that section because the domain has a section titled “Validation”, although the domain's section is under “Intake”.

Чтобы найти, как реализовано правило домена, читатель смотрит в файл технического приложения, названный по этому домену. Там читатель идёт по тем же названиям, которые ведут к правилу в домене (§4.1). Раздел этого файла, который не совпадает ни с одним разделом домена, содержит реализацию, которую читатель не найдёт.

Пример

У домена requests есть раздел «Intake», который содержит раздел «Validation». Ещё один раздел «Validation» находится прямо под первым узлом верхнего уровня файла, и sheriff validate его отвергает. Самая вероятная ошибка — принять этот раздел потому, что в домене есть раздел «Validation», хотя раздел домена находится под «Intake».

Where the project has chosen the Domains extension (§11), sheriff validate accepts a domain's header (§11.1.3) that contains a level only where the project's own guidelines (§2.3) list that level (§11.2.1, §11.3.6). A header contains a level as the value of its property level.

sheriff validate refuses any other header that contains a level, naming the header by its file, its sid and its location (§spec 8.5), and naming the level. A header that contains no level passes this check.

As with every list in the project's own guidelines, the SpecSheriff tools read the levels in the last approved wording (§tools 2.5) of each rule that lists them (§tools 3). So a level that only a draft wording adds is accepted only after that wording is approved.

sheriff validate makes this check regardless of whether the specification is approved or a draft (§11.3.6).

Reason

The diagram of the domains places each domain in the row of its level (§11.2.2). The order of the levels in the list of levels sets the order of the rows (§11.2.1). So a level outside that list has no row.

Example

An approved rule in project.json refines the rule about a domain's level and lists the levels core and edge. sheriff validate accepts each header that contains core or edge, and each header that contains no level. Title

An identifier followed to its end

Text

Where the project has chosen the RecordType extension (§12), sheriff validate accepts a field with identifierOf (§12.12.2) only where both of the following hold:

• its identifierOf names a RecordType (§12.1) that names, in its identifiedBy, one of its fields as the field that identifies its data records (§12.2);
• the chain of identifiers that starts at the field ends in a field without identifierOf (§12.12.3).

sheriff validate refuses any other field with identifierOf, naming the RecordType that holds it by its file, its sid and its location (§spec 8.5). The refusal also names the field and each condition that the field fails. It names the field by the JSON Pointer to the field's schema within the RecordType's schema, such as /properties/accounts/items.

The chain of identifiers that starts at a field goes to the field that identifies the data records of the RecordType that the field's identifierOf names. Where that field has identifierOf too, the chain goes on in the same way. A chain has no end if it comes back to a field that is already in it.

A RecordType's fields here are those that it declares in its schema (§12.2) and those that it takes through refines (§spec 6.1) from another RecordType. sheriff validate makes this check wherever a RecordType's schema holds identifierOf, at any depth, such as in the schema of the members of a list.

sheriff validate makes this check regardless of whether the specification is approved or a draft (§12.12.2, §12.12.3).

Reason

A field with identifierOf takes its type from the field at the end of its chain of identifiers (§12.2, §12.12.3). The types and RuntimeChecks generated from the RecordType that holds the field (§12.3) can therefore give the field a type only where that chain has an end.

Example

The RecordType statement has a field accountId whose identifierOf names the RecordType account. The identifiedBy of the RecordType account names its field number, of type string. The chain that starts at accountId ends at number, and sheriff validate accepts the field. The RecordTypes left and right are each identified by a field whose identifierOf names the other RecordType, so the chains that start at those fields never end. sheriff validate refuses both fields. The most likely mistake is to follow only the first step of each chain and so accept both fields.

Title

What a RecordType variant must agree with

Text

Where the project has chosen the RecordType extension (§12), sheriff validate checks each RecordType variant (§12.6) against its RecordType (§12.1).

sheriff validate treats as a RecordType variant each RecordType that names, in its answersTo, the values that it corresponds to. A RecordType variant's RecordType is the RecordType that has fields that select a variant and to which the RecordType variant has a refines link (§spec 6.1). The fields that select a variant of a RecordType are those that the RecordType names in its chosenBy. Where it has no chosenBy, they are those named in the chosenBy of the RecordType that has a chosenBy and that it reaches through the fewest refines links.

The fields that a RecordType declares are the properties of its schema (§12.2). The names of fields are compared character for character. Where no section holds a RecordType, the part of the specification that its location names (§spec 8.5) is treated as its nearest section.

sheriff validate accepts a RecordType variant only where all of the following hold:

• it has a refines link to exactly one RecordType that has fields that select a variant (§12.12.4);
• it is declared in the same section of the base specification (§1.1.4) as its RecordType (§12.12.5): the nearest section that holds the RecordType variant is the nearest section that holds its RecordType;
• it declares at least one field (§12.12.6);
• the name of each field that it declares differs from the name of every field that its RecordType declares or takes through refines from another RecordType (§12.12.7);
• the fields that its answersTo names are exactly the fields that select a variant of its RecordType (§12.12.8);
• each value that its answersTo names for a field is one of that field's values, as the SpecSheriff tools collect them (§tools 7.1.18, §12.12.9);
• its answersTo differs from the answersTo of every other RecordType variant of its RecordType (§12.12.10).

sheriff validate refuses any other RecordType variant, naming it by its file, its sid and its location (§spec 8.5). The refusal also says which of the conditions above the RecordType variant fails. Where the RecordType variant fails the last condition, the refusal also names each of the other RecordType variants of its RecordType that have the same answersTo as it does.

When sheriff validate validates the files against the schema of the specification, it refuses a RecordType variant whose answersTo gives a field more than one value (§tools 7.1.2, §12.12.8).

Where a RecordType variant fails the first condition, sheriff validate checks it further only against the third condition, since each of the other conditions compares the RecordType variant with its RecordType.

Where a RecordType has no chosenBy, the RecordTypes that have a chosenBy and that it reaches through the fewest refines links can name different fields in their chosenBy. Where they name different fields, sheriff validate refuses every RecordType variant that refines the RecordType that has no chosenBy, since each such RecordType variant fails the first condition. The refusal names each of those RecordTypes with a chosenBy.

sheriff validate makes these checks regardless of whether the specification is approved or a draft (§12.12.4, §12.12.5, §12.12.6, §12.12.7, §12.12.8, §12.12.9, §12.12.10).

Reason

A data record holds the fields of its RecordType together with those of the RecordType variant that corresponds to the data record's values (§12.6). Only where every RecordType variant agrees with its RecordType does each data record have one set of fields that the types and RuntimeChecks generated from the RecordType can describe (§12.3).

Example

The RecordType notification names channel in its chosenBy, and the values of channel are email and app. It refines message, a fragment of a format that declares the field text. A RecordType variant in the same section as notification refines notification, names email as the value of channel in its answersTo and declares address, and sheriff validate accepts it. Another RecordType variant of notification names sms as the value of channel in its answersTo and declares text. sheriff validate refuses it, since sms is not a value of channel and notification takes text from message. The most likely mistake is to compare the names of a RecordType variant's fields only with those that notification declares in its own schema, which overlooks text.

С чем должен согласовываться вариант RecordType

Текст

Если проект выбрал расширение RecordType (§12), sheriff validate сверяет каждый вариант RecordType (§12.6) с его RecordType (§12.1).

Вариантом RecordType sheriff validate считает каждый RecordType, который называет в своём answersTo значения, которым он соответствует. RecordType варианта RecordType — это RecordType, у которого есть поля, выбирающие вариант, и с которым у варианта RecordType есть связь refines (§spec 6.1). Поля, которые выбирают вариант RecordType, — те, что RecordType называет в своём chosenBy. Если у него нет chosenBy, это поля из chosenBy того RecordType с chosenBy, к которому от него ведёт наименьшее число связей refines.

Поля, которые объявляет RecordType, — это свойства его schema (§12.2). Имена полей сравниваются посимвольно. Если RecordType не содержится ни в одном разделе, его ближайшим разделом считается часть спецификации, которую называет его расположение (§spec 8.5).

sheriff validate принимает вариант RecordType, только если выполнено всё следующее:

• у него есть связь refines ровно с одним RecordType, у которого есть поля, выбирающие вариант (§12.12.4);
• он объявлен в том же разделе базовой спецификации (§1.1.4), что и его RecordType (§12.12.5): ближайший раздел, который содержит вариант RecordType, — это ближайший раздел, который содержит его RecordType;
• он объявляет хотя бы одно поле (§12.12.6);
• имя каждого поля, которое он объявляет, отличается от имени любого поля, которое его RecordType объявляет или берёт через refines из другого RecordType (§12.12.7);
• поля, которые называет его answersTo, — ровно те поля, которые выбирают вариант его RecordType (§12.12.8);
• каждое значение, которое его answersTo называет для поля, — одно из значений этого поля, которые собирают инструменты SpecSheriff (§tools 7.1.18, §12.12.9);
• его answersTo отличается от answersTo любого другого варианта RecordType его RecordType (§12.12.10).

Любой другой вариант RecordType sheriff validate отвергает, называя его файл, sid и расположение (§spec 8.5). Отказ также говорит, какие из условий выше вариант RecordType не выполняет. Если вариант RecordType не выполняет последнего условия, отказ называет также каждый из других вариантов его RecordType, у которых тот же answersTo, что у него.

Когда sheriff validate проверяет файлы на соответствие схеме спецификации, он отвергает вариант RecordType, у которого answersTo даёт полю больше одного значения (§tools 7.1.2, §12.12.8).

Если вариант RecordType не выполняет первого условия, дальше sheriff validate проверяет его только по третьему, потому что каждое из других условий сравнивает вариант RecordType с его RecordType.

Если у RecordType нет chosenBy, RecordType, у которых есть chosenBy и к которым от него ведёт наименьшее число связей refines, могут называть в своих chosenBy разные поля. Если они называют разные поля, sheriff validate отвергает каждый вариант RecordType, который уточняет RecordType, у которого нет chosenBy, потому что каждый такой вариант не выполняет первого условия. Отказ называет каждый из этих RecordType с chosenBy.

sheriff validate выполняет эти проверки независимо от того, одобрена спецификация или она черновик (§12.12.4, §12.12.5, §12.12.6, §12.12.7, §12.12.8, §12.12.9, §12.12.10).

Обоснование

Запись данных содержит поля своего RecordType вместе с полями того варианта RecordType, который соответствует значениям этой записи данных (§12.6). Только если каждый вариант RecordType согласуется со своим RecordType, у каждой записи данных один набор полей, который могут описать типы и RuntimeCheck, сгенерированные из RecordType (§12.3).

Пример

RecordType notification называет channel в своём chosenBy, и значения channel — email и app. Он уточняет message — фрагмент формата, который объявляет поле text. Вариант RecordType в том же разделе, что и notification, уточняет notification, называет в своём answersTo для channel значение email и объявляет address, и sheriff validate его принимает. Другой вариант RecordType notification называет в своём answersTo для channel значение sms и объявляет text. sheriff validate отвергает его, потому что sms — не значение channel, а notification берёт text из message. Самая вероятная ошибка — сравнивать имена полей варианта RecordType только с теми, которые notification объявляет в своём собственном schema: так text будет пропущено.

English
Title

Where the values of a field with enum are collected from

Text

Where the project has chosen the RecordType extension (§12), the SpecSheriff tools collect the values of a field with enum (§12.7) from its source, which is exactly one of the following:

• its own list, where the field's schema holds enum: the members of that enum, in their order;
• the names of the parts of the base specification (§12.11, §1.1.4), where the field's x-enumSource.from is parts;
• the sids of the nodes of a project's own kind (§12.8), where the field's x-enumSource.from is kind: the sid of each node of the base specification whose kind the field's x-enumSource.kind names, including a node in a cell of a TableRule (§8.6).

Where the project has chosen the Domains extension (§11), the parts of the base specification are the domains and the contracts section (§3.1). The name of each such part is the name of its folder under specs/ (§tools 1), such as contracts or requests.

Otherwise, the parts of the base specification are the contracts section and the sections whose location (§spec 8.5) is base/ followed by a single number. The contracts section is named contracts, after its folder. The name of each of the other parts is its title.

sheriff reindex writes each value collected from the names of the parts or from the sids into the field's x-enumSource.gathered (§12.9, §tools 2.2), together with the sid of the node that the value comes from:

• for a domain's name, the domain's header (§11.1.3);
• for the name contracts, the first top-level node of the first file of specs/contracts/ in the code-point order of the files' paths;
• for the title of a section, that section;
• for a sid, the node whose sid it is.

sheriff reindex writes the values in the order of the nodes that they come from: their files in the code-point order of the files' paths, and the nodes of one file in the order in which the computation of locations goes through them (§tools 7.1.4a).

The SpecSheriff tools collect the values of a field with enum at any depth within a RecordType's schema (§12.2), such as in the schema of the members of a list.

Reason

A field's values are used by sheriff reindex, sheriff validate, the check of RecordType variants and sheriff types (§tools 2.2, §tools 7.1.9, §tools 7.1.16, §tools 2.5). Collected in a single way, they are the same for each of these uses and on every machine.

Example 1

In a project that has chosen the Domains extension, the RecordType of an audit log entry has a field part whose x-enumSource.from is parts. The base specification is kept in specs/contracts/, specs/requests/ and specs/users/. sheriff reindex writes contracts, requests and users into the field's x-enumSource.gathered. With contracts it writes the sid of the first top-level node of the first file of specs/contracts/. With each domain's name it writes the sid of that domain's header. The most likely mistake is to leave out contracts, which is a part of the base specification although it is not a domain.

Example 2

In a project without the Domains extension, specs/base/ holds the top-level sections titled “Requests” and “Users”, and specs/contracts/ holds the section titled “Contracts”. The RecordType of an audit log entry has a field part whose x-enumSource.from is parts. The values of that field are “Requests”, “Users” and contracts, each with the sid of the node that it comes from. The most likely mistake is to use the title “Contracts” as a value in place of contracts.

Заголовок

Откуда собираются значения поля с enum

Текст

Если проект выбрал расширение RecordType (§12), инструменты SpecSheriff собирают значения поля с enum (§12.7) из его источника — ровно одного из следующих:

• его собственный перечень, если схема поля содержит enum: элементы этого enum в их порядке;
• имена частей базовой спецификации (§12.11, §1.1.4), если x-enumSource.from поля — parts;
• sid узлов собственного типа в проекте (§12.8), если x-enumSource.from поля — kind: sid каждого узла базовой спецификации, тип которого называет x-enumSource.kind поля, в том числе узла в ячейке TableRule (§8.6).

Если проект выбрал расширение Domains (§11), части базовой спецификации — это домены и контракты (§3.1). Имя каждой такой части — имя её папки в specs/ (§tools 1), например contracts или requests.

Иначе части базовой спецификации — это контракты и разделы, расположение которых (§spec 8.5) — base/ и одно число. Контракты называются contracts, по имени их папки. Каждая из остальных частей называется по своему названию.

sheriff reindex записывает каждое значение, собранное из имён частей или из sid, в x-enumSource.gathered поля (§12.9, §tools 2.2) вместе с sid узла, из которого это значение приходит:

• для имени домена — заголовка домена (§11.1.3);
• для имени contracts — первого узла верхнего уровня первого файла specs/contracts/ в порядке кодовых точек путей файлов;
• для названия раздела — этого раздела;
• для sid — узла, чей это sid.

Значения sheriff reindex записывает в порядке узлов, из которых они приходят: их файлы — в порядке кодовых точек путей файлов, а узлы одного файла — в том порядке, в каком их проходит вычисление расположения (§tools 7.1.4a).

Значения поля с enum инструменты SpecSheriff собирают на любой глубине schema RecordType (§12.2), например в схеме элементов списка.

Обоснование

Значения поля используют sheriff reindex, sheriff validate, проверка вариантов RecordType и sheriff types (§tools 2.2, §tools 7.1.9, §tools 7.1.16, §tools 2.5). Собранные одним способом, они одинаковы для каждого из этих применений и на каждой машине.

Пример 1

В проекте, который выбрал расширение Domains, у RecordType записи журнала аудита есть поле part, x-enumSource.from которого — parts. Базовая спецификация хранится в specs/contracts/, specs/requests/ и specs/users/. sheriff reindex записывает contracts, requests и users в x-enumSource.gathered этого поля. Вместе с contracts он записывает sid первого узла верхнего уровня первого файла specs/contracts/. Вместе с именем каждого домена он записывает sid заголовка этого домена. Самая вероятная ошибка — пропустить contracts: это часть базовой спецификации, хотя и не домен.

Пример 2

В проекте без расширения Domains в specs/base/ находятся разделы верхнего уровня «Requests» и «Users», а в specs/contracts/ — раздел «Contracts». У RecordType записи журнала аудита есть поле part, x-enumSource.from которого — parts. Значения этого поля — «Requests», «Users» и contracts, каждое вместе с sid узла, из которого оно приходит. Самая вероятная ошибка — использовать как значение название «Contracts» вместо contracts.

Title

Fields with enum that sheriff validate accepts

Text

Where the project has chosen the RecordType extension (§12), sheriff validate accepts a field with enum (§12.7) only where both of the following hold:

• its source gives it at least one value when the SpecSheriff tools collect its values (§tools 7.1.18, §12.12.12);
• where its x-enumSource.from is kind, its x-enumSource.kind names one of the kinds of node that the project's extension of the schema adds in its field kinds (§5.2, §12.12.13).

sheriff validate refuses any other field with enum, naming the RecordType that holds it by its file, its sid and its location (§spec 8.5). The refusal also names the field, each condition that the field fails and, where the field fails the condition on the kind, the kind. It names the field by the JSON Pointer to the field's schema within the RecordType's schema, such as /properties/accounts/items.

When sheriff validate validates the files against the schema of the specification, it refuses a field whose own enum holds a value more than once (§tools 7.1.2, §12.12.11). The schema of the RecordType extension requires each enum within a RecordType's schema (§12.2) to hold each value only once.

sheriff validate checks each field with enum at any depth within the schema of each RecordType in the files that the repository keeps. It makes these checks regardless of whether the specification is approved or a draft (§12.12.11, §12.12.12, §12.12.13).

Reason

The types and RuntimeChecks of a field are generated from its values (§12.3). So, if sheriff validate accepted a field that has no values, or whose values break the rules about their source (§12.7, §12.8), the types and RuntimeChecks generated from that field's values would inherit the field's defect.

Example

The RecordType of a job log entry has a field step whose x-enumSource.from is kind and whose x-enumSource.kind is TextRule. sheriff validate refuses the field and names TextRule. Once x-enumSource.kind names jobStep, a kind that the project's extension of the schema adds, and the base specification holds a node of that kind, the field passes. The most likely mistake is to accept TextRule because the schema of the SpecSheriff guidelines defines it.

English
Title

A RecordType that refers to a RecordType outside its part of the system

Text

Where the project has chosen the RecordType extension (§12), sheriff validate stays silent about a reference from one RecordType (§12.1) to another only in the following cases (§12.10):

• from a RecordType outside the contracts section (§3.1), to a RecordType of its own part of the system or to a fragment of a format (§12.1, §12.12.15);
• from a fragment of a format, to another fragment of a format (§12.12.16).

sheriff validate reports each RecordType that holds any other reference, naming that RecordType and each RecordType that it refers to by such a reference, each by its sid (§12.12.15, §12.12.16). The change still passes.

A RecordType refers to another RecordType in either of these ways:

• its schema (§12.2) holds, at any depth, a $ref that points to that RecordType or an identifierOf that names it (§12.12.2);
• it has a refines link (§spec 6.1) to that RecordType.

A fragment of a format is a RecordType in the contracts section. Where the project has chosen the Domains extension (§11), the part of the system that a RecordType belongs to is the domain whose files hold the RecordType. Otherwise, it is the section of specs/base/ that holds the RecordType and whose location (§spec 8.5) is base/ followed by a single number. The RecordTypes in specs/base/ that no such section holds are treated as together forming one part of the system.

sheriff validate makes this check regardless of whether the specification is approved or a draft (§12.12.15, §12.12.16).

Reason

A RecordType can refer to another RecordType at any depth of its schema and through its refines links. So only a check that reads a RecordType's whole schema and all its refines links finds each reference that breaks the rule on what a RecordType may refer to (§12.10).

Example

In the domain requests, the RecordType of a request has a field deliveryAddress with a $ref to address, a fragment of a format. It also has a field user whose identifierOf names the RecordType of a user in the domain users. sheriff validate reports that RecordType, naming it and the RecordType of a user, each by its sid, and lets the change pass. The most likely mistake is to leave the reference in the field user unreported because that field holds only an identifier. A field user that holds only a user's identifier, with no reference to the RecordType of a user, has the type string and no identifierOf.
