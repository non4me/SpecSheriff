English
Title

A location that differs from the computed one

Text

sheriff validate refuses each node whose location (§spec 8.5) is missing or differs from the one computed for it (§tools 7.1.4a, §10.1.5). The refusal names the node's file and sid, the location that the file holds and the computed location.

sheriff validate checks each node of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6).

Reason

A location tells a reader where a node is only while it is the computed one. sheriff reindex writes every location after each edit that an agent makes (§tools 6). So a location that differs from the computed one was left behind by a change that no run of sheriff reindex has followed yet, such as an edit made without an agent.

Расположение, которое отличается от вычисленного

Обоснование

Расположение говорит читателю, где находится узел, только пока оно совпадает с вычисленным. sheriff reindex пишет каждое расположение после каждой правки, которую делает агент (§tools 6). Как вычисляется расположение узла · How a node's location is computed
tools 7.1.4a (новый, после «Locations computed anew») · s-ygg5kpcxgzq3m7w · новый узел описания инструментов · пункт 9
English
Title

How a node's location is computed

Text

The SpecSheriff tools compute a node's location (§spec 8.5) from the path of its file and where the node is in the specification. They compute it for each node of the specification in the files that the repository keeps.

In a file of the guidelines, of the appendix of the tools (§2.1) or of the technical appendix (§1.1.5), the first top-level node of the file takes as its location the file's path under specs/, without .json (§tools 1). Such locations include _guidelines/spec, _guidelines/extensions/domains and tech/stack. Where the project has chosen the Domains extension (§11), a domain's header (§11.1.3) takes the domain's name as its location. Every other node's location is one of the following, followed by a slash and the node's place:

• in a file of the guidelines, of the appendix of the tools or of the technical appendix, the location of the first top-level node of that file, as in _guidelines/spec/1.3.4;
• in the base specification (§1.1.4), the name of the folder under specs/ that holds the node's file, as in base/3.2, contracts/1 or requests/2.

Every node is numbered except the following:

• a term (§3.3), whose place is the term's name;
• the first top-level node of a file of the guidelines, of the appendix of the tools or of the technical appendix;
• a domain's header.

A numbered node's place is its position among the numbered nodes under its parent, counted from one. Where the parent is numbered too, the parent's place and a dot come before that position, as in 3.2.

The SpecSheriff tools go through the numbered nodes under a node in the order of the node's children. Under a TableRule (§8.6), the nodes in its cells come after its children, row by row through its groups and, within a row, column by column.

In a folder of the base specification, the top-level nodes of its files and the children of a domain's header are treated as nodes under one parent. The SpecSheriff tools go through them file by file, in the code-point order of the files' paths. The top-level nodes of one file come in the order in which the file lists them. The children of a domain's header take the header's position in that order.

In a file of the guidelines, of the appendix of the tools or of the technical appendix, each further top-level node of the file is numbered under the location of the first node, after that node's children.

Reason

sheriff reindex writes the locations that sheriff validate checks (§tools 2.2, §tools 7.1.4). Both commands therefore need one computation that gives every node a location of its own that is the same on every machine.

Example

A domain named requests is kept in three files: specs/requests/00-requests.json holds its header, specs/requests/intake.json holds one section, and specs/requests/review.json holds another. The header's location is requests, and the sections' locations are requests/1 and requests/2. The fourth node of the second section is a TableRule, requests/2.4, each of whose rows holds one node, so the node in its third row is requests/2.4.3. The most likely mistake is to number each file from one, which gives both sections the location requests/1.

Как вычисляется расположение узла

Текст

Инструменты SpecSheriff вычисляют расположение узла (§spec 8.5) по пути к его файлу и по тому, где узел находится в спецификации. Они вычисляют его для каждого узла спецификации в файлах, которые хранит репозиторий.

В файле guidelines, описания инструментов (§2.1) или технического приложения (§1.1.5) первый узел на вершине файла получает расположением путь к файлу внутри specs/ без .json (§tools 1). Среди таких расположений — _guidelines/spec, _guidelines/extensions/domains и tech/stack. Если проект выбрал расширение Domains (§11), заголовок домена (§11.1.3) получает расположением имя домена. Расположение любого другого узла — одно из следующего, затем косая черта и место узла:

• в файле guidelines, описания инструментов или технического приложения — расположение первого узла на вершине этого файла, как в _guidelines/spec/1.3.4;
• в базовой спецификации (§1.1.4) — имя папки внутри specs/, в которой лежит файл узла, как в base/3.2, contracts/1 или requests/2.

Нумеруется каждый узел, кроме следующих:

• термина (§3.3), место которого — имя термина;
• первого узла на вершине файла guidelines, описания инструментов или технического приложения;
• заголовка домена.

Место пронумерованного узла — его порядковый номер среди пронумерованных узлов под его родителем, считая с единицы. Если родитель тоже пронумерован, перед этим номером стоят место родителя и точка, как в 3.2.

Пронумерованные узлы под узлом инструменты SpecSheriff обходят в порядке его дочерних узлов. Под TableRule (§8.6) после его дочерних узлов идут узлы в его ячейках: строка за строкой по всем его группам, а внутри строки — столбец за столбцом.

В папке базовой спецификации узлы на вершине её файлов и дочерние узлы заголовка домена считаются узлами под одним родителем. Инструменты SpecSheriff обходят их файл за файлом, в порядке кодовых точек путей к файлам. Узлы на вершине одного файла идут в том порядке, в каком их перечисляет файл. Дочерние узлы заголовка домена занимают в этом порядке позицию заголовка.

В файле guidelines, описания инструментов или технического приложения каждый следующий узел на вершине файла нумеруется под расположением первого узла, после его дочерних узлов.

Обоснование

sheriff reindex записывает расположения, которые проверяет sheriff validate (§tools 2.2, §tools 7.1.4). Поэтому обеим командам нужно одно вычисление, которое даёт каждому узлу собственное расположение, одно и то же на любой машине.

Пример

Домен requests хранится в трёх файлах: в specs/requests/00-requests.json — его заголовок, в specs/requests/intake.json — один раздел, в specs/requests/review.json — другой. Расположение заголовка — requests, разделов — requests/1 и requests/2. Четвёртый узел второго раздела — TableRule requests/2.4, в каждой строке которого по одному узлу, поэтому узел в его третьей строке — requests/2.4.3. Самая вероятная ошибка — нумеровать каждый файл с единицы: тогда оба раздела получают расположение requests/1.

Title

A node's location

Text

A node's location names where it is in the specification: the part it is in, followed by its place there. A node's place is its number among the nodes under the same parent. The following nodes take no number:

• a term (§3.3), whose place is the term's name;
• the first top-level node of a file of the guidelines, of the appendix of the tools (§2.1) or of the technical appendix (§1.1.5), which takes as its location the part's name followed by the file's name;
• a node of a kind that an extension of the guidelines (§1.7.1) defines and that a part of the base specification (§1.1.4) opens with, which takes the part's name alone as its location.

In each file of the guidelines, of the appendix of the tools or of the technical appendix, the nodes are numbered under the location of the file's first top-level node. The nodes under a node whose location is the part's name alone are numbered together with the other top-level nodes of the part.

The location is computed from where the node is and is never written by hand.

Reason

A location is computed from where a node is, so it always shows a reader where to find the node.

Example

A rule kept in specs/_guidelines/spec.json as the fifth node of the file's eighth section is at _guidelines/spec/8.5. Where an extension makes a part requests open with a header, the header is at requests, and the part's first section, kept in another of its files, is at requests/1. The most likely mistake is to number the header, which would put that section at requests/2.

Title

What sheriff reindex writes

Text

sheriff reindex writes into the files of the specification everything that the SpecSheriff tools compute from the specification, the code and the tests:

• a sid for each node that has none, including a node in a cell of a TableRule (§1.2.2, §8.6);
• the location of each node (§spec 8.5, §tools 7.1.4a);
• the links pointing at each node, rebuilt from the links that the nodes declare (§6.4);
• the lists meta.code and meta.tests of each node, built from the SpecTags that bind code and tests to the node (§9.7): meta.code names each code file that holds a symbol bound by such a SpecTag, and meta.tests names each such test by its file and its name;
• the approval status of each section, derived from every node under it other than a section, including the nodes in the cells of a TableRule (§1.3.8);
• where the project has chosen the Domains extension (§11), the approval status of the header of each domain, derived from every node of the domain other than its sections and the header itself, including the nodes in the cells of a TableRule (§domains 11.1.4a);
• where the project has chosen the Domains extension, the index of the sections in the header of each domain that has sections (§11.1.4);
• where the project has chosen the RecordType extension (§12), the values gathered for each field that has an enum whose values come from elsewhere in the specification, in the field's x-enumSource.gathered (§12.9).

In the files that the repository keeps, an approved node whose approval status is set by approvals stays approved while an approval of its current wording stands (§tools 11). sheriff reindex makes each remaining such node a draft and names it.

sheriff reindex writes only the files that the repository keeps. It writes a file only when the text it would write differs from the file's text. It names each file that it writes.

sheriff reindex writes each file as JSON.stringify writes the file's data with an indent of two spaces, with a line feed at the end, with each node's location and sid first, and with all the other keys in the order in which the file already has them.

Reason

The SpecSheriff tools themselves write whatever they can compute from the specification, the code and the tests, so that it always agrees with its sources and nobody spends effort writing it. Because it is rebuilt in full on every run, it is correct regardless of what an earlier run left behind (§10.13).

Text

sheriff validate accepts an approval (§tools 11) that a commit adds to specs/_approvals.jsonl only where both of the following hold:

The most likely mistake is to judge the approval against the owners named in the commit's parent, which would refuse that second commit.

Title

The approval status of a domain's header

Text

The SpecSheriff tools derive the approval status (§1.3.1) of a domain's header (§11.1.3) in the same way as they derive a section's (§1.3.8). The header is approved while every node of the domain other than its sections and the header itself is approved, in whichever of the domain's documents (§11.1.2) the node is kept. Nobody approves a header.

Reason

A header, like a section, requires nothing, so it leaves an owner nothing to agree to. Its approval status shows at a glance whether the whole domain is approved, which helps where only the headers are visible.

Example

A domain is kept in two documents: the first holds its header and a section under it, and the second holds another section, one rule of which is a draft. The header's approval status is draft. Once that rule is approved, the header becomes approved too, though nobody approved the header. The most likely mistake is to derive the header's approval status only from the nodes under the header, and so to show the header as approved while a rule in the second document is still a draft.

English
Title

An agent's edit is checked before it is made

Text

Before an agent's edit is made, the SpecSheriff tools refuse it if it would do any of the following:

• leave a node approved with a wording for which no approval stands (§1.3.5), unless the node is a section or any other node whose approval status (§1.3.1) is derived from other nodes;
• change the code written for a rule, including a rule of a project's own kind (§8.3), while no test has that rule's SpecTag (§9.3, §1.4.1);
• change the approvals, or the entries that set the specification's approval status (§10.6) or its strict flag (§10.7), or the record of the extensions that the project has chosen (§1.7.5), other than through the procedures that record or withdraw them.

The refusal before an edit applies only to an edit whose request names the files it writes to and what it writes to them. A shell command names neither.

Reason

A check that runs later sees only the result: the approvals, which it takes as given, and a commit that contains a test together with the code it tests. So only a check made before an edit can keep an agent from making a decision that only the owners may make, or from writing code before its test.

English
Title

Values built from other nodes

Text

sheriff validate refuses each node in which a value built from other nodes differs from the value that sheriff reindex would write (§tools 2.2). sheriff validate computes the following values:

• the links pointing at each node (§6.4, §10.1.16), compared without regard to their order;
• the approval status of each section (§1.3.8, §10.1.10);
• where the project has chosen the Domains extension (§11), the approval status of the header of each domain (§domains 11.1.4a, §domains 11.3.2a);
• where the project has chosen the Domains extension, the index of the sections in the header of each domain (§11.1.4, §11.3.2);
• where the project has chosen the RecordType extension (§12), the values gathered for each field that has an enum (§12.9, §12.12.14).

sheriff validate checks each node of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). The refusal names the node by its file, its sid and its location in the specification (§spec 8.5), and names the value that differs.

Reason

After an edit to one node, a value built from it stays out of date until sheriff reindex runs. Computing every such value again reveals a commit that holds an out-of-date value or a value written by hand.

Example

A section holds a TableRule, one cell of which holds a draft node, and every other node under the section is approved. sheriff validate computes the section's approval status as draft, and refuses the section if its file marks it approved. The most likely mistake is to count only the nodes in a node's children, which leaves out the node in the cell.

Title

The target of a link

Text

sheriff validate accepts a link only where its target is the sid of a node of the model of the specification (§tools 2.7, §10.1.12). It refuses any other link declared by a node of the specification in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). Reason

Only a link whose target is a node of the specification can be followed. Only such a link appears among the links pointing at its target (§6.4).

Example

A rule still has a refines link to a rule that a later commit removed and archived. sheriff validate refuses the link, since no node of the specification holds the removed rule's sid any longer. The most likely mistake is to look for the target only among the nodes in the files that the repository keeps. That mistake would refuse a refines link from a rule of a project's own guidelines to a rule of the SpecSheriff guidelines, which the project takes from the SpecSheriff plugin. sheriff validate accepts that link.

Text

English
Title

What a link is

Text

A link is a directed relation from one node to another. Every link states its meaning through its type. The types of link are:

• implements — the linking node states how the linked one is implemented.
• refines — the linking node states more precisely what the linked node states, states it for a narrower case, or extends the linked node. A node extends another when it adds a requirement on something that the other leaves open within its own subject, such as a value that the other leaves to each project. The linking node leaves every requirement of the linked node in force.
• constrains — the linking node states a condition the linked rule depends on.
• exempts — the linking node exempts the linked rule, or every rule under the linked section, from being implemented (§9.8).
• checks — the linking node is a check, and it verifies that the linked rule is followed. Such a link is written by hand.
• cites — the linking node cites the linked one (§6.3), and no other type says how the two relate to each other. So the linking node has no link of another type to the linked one.
• term-relation — the linking term (§3.3) and the linked term are bound, for as long as both exist, in the ratio the link carries (§6.6).
• uses — what the linking term names makes use of what the linked term names while taking part in a process. The link carries no ratio. A term that only starts a process, such as an operator who starts an export, uses nothing the process uses.

An extension of the guidelines (§1.7.1) or a project's own guidelines (§2.3) may define further types of link. Each such type states its meaning and contradicts no rule of the SpecSheriff guidelines.

Reason

A link without a type records only that somebody thought of two nodes together. No check can evaluate it. No diagram can show it. A type named without its meaning is the same guess, one step removed.

Example 1

uses: a user fills in a form while signing up.

Example 2

refines, extending a rule: a rule of a project's own guidelines lists the fixtures of the tests of a check that reads citations, a list that the rule it refines leaves to each project. The most likely mistake is an implements link from the project's rule: that rule does not state how the rule it refines is implemented.

Title

Copies of the files that the SpecSheriff plugin delivers

Text

sheriff validate refuses each copy of a file that is common to every project and comes with the SpecSheriff tools in the SpecSheriff plugin (§tools 1, §10.1.25). It accepts such a file only in the repository where the SpecSheriff guidelines are written (§tools 1).

A copy is any of the following files that the repository keeps:

• specs/_guidelines/spec.json and specs/_guidelines/tools.json;
• each file in specs/_guidelines/extensions/;
• each file in specs/_schema/ or in a folder under it, other than specs/_schema/project.schema.json.

The refusal names each copy. As long as the repository keeps a copy, sheriff validate runs only the check for copies.

Reason

In a project, the SpecSheriff tools read the files common to every project from the SpecSheriff plugin (§tools 1). A copy in the project's repository is read by people and agents, but not by any of the SpecSheriff tools. So it falls behind the plugin's files unnoticed.

Example

A project copies node.schema.json into specs/_schema/ to read it beside its own extension of the schema. sheriff validate refuses the copy and names it. It accepts specs/_schema/project.schema.json, the project's own extension of the schema.
