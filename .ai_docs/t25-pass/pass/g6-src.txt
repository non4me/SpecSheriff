A SpecTag is the text `@spec <sid>`, or `@spec none` followed by its reason. The form `@spec none` stands on a symbol only.

A symbol carries its SpecTag as a line of the comment directly above it, above its decorators where it has any. That comment is:

- in TypeScript and JavaScript, the symbol's doc comment;
- in Python, a comment line.

A symbol implementing several rules carries several SpecTags. A test carries its SpecTag in its name or in a mark on it (§s-zrsc6asgmhv8tnc).

A symbol that implements no rule says so with `@spec none`, followed by the reason it carries none. Where such a symbol stands first in a run of re-exports, with no blank line between them, it says so for the whole run.

On a symbol, only the delimiters of the comment may share a SpecTag's line, so that a scan finds a SpecTag's text in any language.

Which symbol a SpecTag stands on is found by parsing the file with tree-sitter and the grammar of the file's language. The parser is used alone, with no program and no type checker.

A description of each language names what counts in it as a declaration and as a test. TypeScript, JavaScript and Python are described.
@reason
A comment above a symbol is where an editor shows a SpecTag and where a reader of the symbol is already looking.

A scan finds a SpecTag but cannot see what it is attached to, so a SpecTag standing over nothing would pass it. The parser sees the symbol under the comment. Used alone, the parser answers the same for the same file every time. Alone, it is also cheap enough to run at every commit.

One parser with a grammar per language makes a further language a description rather than new code.
@doubts
@split
The SpecTag's form and where a symbol and a test carry it; how the tools find a SpecTag and the symbol under it (the scan, tree-sitter alone, a description per language).

The list of those files is defined in the rule that describes how the system generates its types and RuntimeChecks from its RecordTypes, as the rule on data structures requires (§s-e877bnfa559tvk9). That rule stands in the section of the technical appendix that describes the technologies the whole system is built with, the stack. Each path in the list is taken from the root of the repository.

A file's extension says what is written into it:

- `.ts`, the types in TypeScript;
- `.py`, the types in Python;
- `.json`, the RuntimeChecks in JSON Schema of draft 2020-12.

Those RuntimeChecks are run by the JSON Schema validator the technical appendix names. That validator asserts `format` rather than taking it as a note.

`sheriff binding` reads a file of types as the system's code even where the glob patterns naming where that code lives do not reach it.
@reason
Which files the generated types go to is a choice covering the whole system. Such choices are described in the stack section (§s-vj7ercem526zd6v). Defined as a list in one rule, those files are read by the tools rather than looked for in prose. The tools read the levels of the domains in the same way, from a list in the project's own guidelines.

The extension already says what a file holds. A validator taking `format` as a mere note would pass an instant that is no instant.

A project with no code yet has nowhere to write the types. Read as code, a file of types has its SpecTags read, so that each RecordType's `meta.code` names the types generated from it.

@text
From each RecordType, `sheriff types` writes a type into each file of types and a definition under `$defs` into each file of RuntimeChecks. It takes the nodes in the order the specification reads:

- its files in the code-point order of their paths;
- the nodes of each file in the order they stand.

Every type and definition is named by the RecordType's name with the first letter of each word raised and the spaces dropped. Each type carries a SpecTag with the sid of its RecordType, as a symbol of code carries one with the rule it implements (§s-5z5gnu7pahr82xp).

A type and a definition hold, in this order:

- the fields of every RecordType above the node along its `refines` links, the topmost first;
- the node's own fields.

A variant's own fields stand instead where the rule on RecordType variants places them (§s-nk8td3ez58gahc4).

Each field keeps its name and the order its node gives it. It is required where its node says so and optional otherwise.

A field of type `record` refers to the type of that RecordType by its name. The object of a field of type `variant` is written out in full. Where the RecordType refuses a field nobody declared, its definition refuses any property its fields do not declare.

A name cannot be generated where:

- it is not an identifier in the language of its file;
- the file already uses it, the names the file imports and those its language builds in included.

In TypeScript a type is written `export type <name> = {...}`.

In Python:

- a type is written `<name> = TypedDict("<name>", {...})`;
- every name a type uses is imported from `typing`;
- a reference to another type is written as a string;
- an optional field is marked `NotRequired`;
- the object of a field of type `variant` is given a type of its own.

That type of its own is named by the type it stands in followed by the field's name with its first letter raised. It carries a SpecTag with the same sid.
@reason
One name in every file lets a reader follow a RecordType from its node to each copy. A fixed order makes each file come out the same at every run, which the comparison of generated copies needs. The generator writes the SpecTag itself, so that the binding of each type to its node is made anew with the type and never kept by hand.

A RecordType that refines another holds that one's fields, as the schema of the nodes says. A field keeps the name its node gives because the code uses that name as it stands.

Only a RuntimeCheck can refuse an undeclared property. A type in TypeScript or Python cannot.

A name the file already uses would break its compilation or hide what it imports.

The functional form of `TypedDict` takes any field name, a keyword of Python included. A reference written as a string may name a type written later in the file, or the type itself. Python can name the object of a field only by a type of its own.

@text
A RecordType that variants refine is written as the union of its members. Its variants are RecordTypes each answering to values of its choosing fields. The choosing fields are the fields whose values choose which variant a RecordType is.

The union is written:

- in JSON Schema, as a definition holding `oneOf` the members;
- in TypeScript, as a union type;
- in Python, as `<name> = Union[...]`.

Its members are:

- each variant, referred to by the name of its type;
- where some combination of the choosing fields' values has no variant, a member for those combinations.

The member for those combinations is named by the RecordType's name followed by `Other`. It has a type and a definition of its own. The type carries a SpecTag with the RecordType's sid.

A variant holds each choosing field, required and fixed to the value it answers to. It holds its own fields:

- inside the RecordType's field of type `variant`, beside the fields that field holds;
- where the RecordType has no such field, beside the RecordType's fields.

The variant's node decides whether a property nobody declared is refused there and around it.

The member for the other combinations holds the RecordType's fields, its choosing fields required where their node says so. Its definition refuses every combination of values a variant answers to. Its type gives a choosing field:

- where one field chooses, the values no variant answers to;
- where several fields choose, all its values.

The RecordType's node decides whether a property nobody declared is refused.

A field of type `variant` is required where its object holds a field and is not declared otherwise, whether or not variants refine its RecordType.
@reason
A union whose members the choosing fields tell apart is how JSON Schema, TypeScript and Python each state that a RecordType's fields depend on its values. With the choosing fields required in every variant, at most one member matches.

A value that brings no fields of its own has no variant, as the rule on variants says (§s-z3dnru6qqdf9m6j). So the RecordType itself answers for it, under a name its own name gives and with its own SpecTag.

Each member follows its own node on undeclared properties, so that no node's setting overrides another's. A RuntimeCheck can refuse every combination of values a variant claims. A type can name only the values each field holds, which is exact where one field chooses.

An object with no field in it holds nothing, so the field for it is not declared.
