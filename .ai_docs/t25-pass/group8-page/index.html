Title

The hooks

Text

The following hooks run the SpecSheriff tools, and with them the checks before and after an agent's edit, on a commit and on a push (§10.2):

• the git hooks, which sheriff init writes into .githooks/ (§tools 3), and each of which runs the SpecSheriff tools that a plugin keeps on the machine (§tools 12):
◦ pre-commit, which runs the project's own tools for that hook (§tools 13), sheriff types (§tools 2.5) and the checks (§tools 6a);
◦ commit-msg, which runs the project's own tools for that hook (§tools 13), then sheriff commit-message, and then, only after sheriff commit-message has passed, sheriff review (§tools 7);
◦ pre-push, which runs the project's own tools for that hook (§tools 13), then compares the working tree with each commit that the tests judge (§tools 6b), and runs the tests (§tools 7.3.5) only where that comparison gives it no reason to refuse the push.
• the agent's hooks, which the plugin for Claude Code declares (§tools 14) and which sheriff init --agent codex writes into the project for Codex CLI (§tools 16):
◦ when a session starts, a hook that turns the git hooks on (§tools 6c), updates the copy of the SpecSheriff tools that the plugin for Claude Code keeps, names each hook that holds what an earlier release of sheriff init wrote (§tools 12), and has the agent ask the user for the settings of each runner (§tools 10.7, §tools 6d);
◦ before an edit made with the file-editing tools, a hook that runs sheriff guard (§tools 7.3.2);
◦ after such an edit or a shell command, a hook that writes what is generated from the nodes and runs the checks (§tools 6e).

On a commit, the pre-commit hook and the commit-msg hook each write out what is staged to a directory of their own. Each of them runs its checks there, with that directory as git's working tree, against the repository's history.

Each check run by the pre-commit hook, the commit-msg hook or the agent's hook after an edit reads the commit being made. On a commit, the commit being made is what is staged. After an edit, it is the working tree's difference from the last commit. Besides that commit, such a check reads only the following:

• the SpecSheriff guidelines and the extensions of the guidelines that the project has chosen (§1.7.5), with the schema of the guidelines and that of each such extension that has one, as they are delivered with the SpecSheriff tools that run the check (§2.5);
• the settings of the reviewer's runner in the git configuration of the user who commits, for the review (§tools 10.7);
• the repository's history and the commit message, where the node on how the check is made (§tools 7) says so.
Reason

A check reads the commit being made, because judging anything else would pass or refuse what is not being committed. The hooks that the repository keeps and those that the plugin for Claude Code declares run each check at the moment set for it in every clone, whoever makes the change (§10.2).

Example

A developer stages a change to rule R and leaves a second change to R unstaged. On the commit, sheriff validate reads R as it is staged. The most likely mistake is to run the checks on the working tree, so that they judge the second change, which the commit does not hold.

Todo

The export and the map catch up with a change that reaches the working tree through git — a pull, a merge, a checkout — only at the next edit an agent makes or the next commit. Post-merge and post-checkout hooks running sheriff markdown and sheriff map would remove that delay.

Хуки

Текст

Инструменты SpecSheriff, а с ними и проверки до и после правки агента, при коммите и при push (§10.2), запускают следующие хуки:

• git-хуки, которые sheriff init записывает в .githooks/ (§tools 3) и каждый из которых запускает инструменты SpecSheriff, которые плагин хранит на машине (§tools 12):
◦ pre-commit, который запускает собственные инструменты проекта для этого хука (§tools 13), sheriff types (§tools 2.5) и проверки (§tools 6a);
◦ commit-msg, который запускает собственные инструменты проекта для этого хука (§tools 13), затем sheriff commit-message, а затем, только после того как проверка sheriff commit-message пройдена, — sheriff review (§tools 7);
◦ pre-push, который запускает собственные инструменты проекта для этого хука (§tools 13), затем сравнивает рабочее дерево с каждым коммитом, который оценивают тесты (§tools 6b), и запускает тесты (§tools 7.3.5), только если это сравнение не даёт ему причины отвергнуть push.
• хуки агента, которые объявляет плагин для Claude Code (§tools 14) и которые sheriff init --agent codex записывает в проект для Codex CLI (§tools 16):
◦ при начале сессии — хук, который включает git-хуки (§tools 6c), обновляет копию инструментов SpecSheriff, которую хранит плагин для Claude Code, называет каждый хук, который содержит то, что записал более ранний выпуск sheriff init (§tools 12), и через агента запрашивает у пользователя настройки каждого runner (§tools 10.7, §tools 6d);
◦ перед правкой, сделанной инструментами редактирования файлов, — хук, который запускает sheriff guard (§tools 7.3.2);
◦ после такой правки или команды оболочки — хук, который записывает то, что порождается из узлов, и запускает проверки (§tools 6e).

При коммите хук pre-commit и хук commit-msg каждый выписывают то, что находится в стейджинге, в отдельный каталог. Каждый из них запускает там свои проверки, сделав этот каталог рабочим деревом git и сверяясь с историей репозитория.

Каждая проверка, которую запускает хук pre-commit, хук commit-msg или хук агента после правки, читает создаваемый коммит. При коммите этот коммит — то, что находится в стейджинге. После правки — отличие рабочего дерева от последнего коммита. Кроме этого коммита, такая проверка читает только следующее:

• SpecSheriff guidelines и выбранные проектом расширения guidelines (§1.7.5) вместе со схемой guidelines и схемой каждого такого расширения, у которого она есть, в том виде, в каком они поставляются с инструментами SpecSheriff, которые выполняют проверку (§2.5);
• настройки runner рецензента в конфигурации git пользователя, который делает коммит, — для ревью (§tools 10.7);
• историю репозитория и сообщение коммита — там, где это говорит узел о том, как выполняется проверка (§tools 7).
Обоснование

Проверка читает создаваемый коммит, потому что, оценивая что-либо другое, она пропускала бы или отвергала то, что в коммит не входит. Хуки, которые хранит репозиторий, и хуки, которые объявляет плагин для Claude Code, запускают каждую проверку в назначенный для неё момент в каждом клоне, кто бы ни вносил изменение (§10.2).

Пример

Разработчик добавляет в стейджинг одно изменение правила R, а второе изменение R оставляет вне стейджинга. При коммите sheriff validate читает R в том виде, в каком оно находится в стейджинге. Самая вероятная ошибка — запускать проверки на рабочем дереве: тогда они оценивают второе изменение, которого коммит не содержит.

Отложено (todo)

Экспорт и карта догоняют изменение, которое приходит в рабочее дерево через git — pull, merge, checkout, — только при следующей правке агента или следующем коммите. Хуки post-merge и post-checkout, которые запускают sheriff markdown и sheriff map, убрали бы эту задержку.

Title

The hooks

Text

Each check lives in a command a git hook calls:

• .githooks/pre-commit runs sheriff export and sheriff render, then sheriff validate, sheriff binding and sheriff citations, and last sheriff types;
• .githooks/commit-msg runs sheriff message and then sheriff review on the file git hands it;
• .githooks/pre-push runs the tests of the system's code and of the project's own checks and generators, by the command sheriff.config.json names as its testCommand, as §tools 7.3.5 says.

A clone turns the git hooks on with git config core.hooksPath .githooks. The SessionStart hook of the agent, the plugin's for Claude Code or the project's for Codex (§tools 16), runs that command where core.hooksPath is unset, saying so. It reports where core.hooksPath names another directory.

The SessionStart hook also names each git hook in .githooks/ in one of these cases:

• git's index holds it without the executable mode;
• on a system whose files keep the executable bit, its file lacks the bit.

It says how to make each one executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It changes neither the mode of a file nor git's index.

The SessionStart hook of the plugin for Claude Code writes into the user's git configuration, by git config --global, each setting of the runner claude (§tools 10.1) the user has given as an option of that plugin (§tools 14). It writes a setting wherever the configuration lacks it or holds another value.

Where the git configuration lacks a setting of the runner sheriff review would take at a commit in the repository (§tools 10.1, §tools 12), the SessionStart hook of either agent names each such setting. With each, it names the default sheriff review takes for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value the user answers, the default included.

It asks so once for each runner on each machine, and marks it asked in the git configuration, as specsheriff.review.claudeAsked or specsheriff.review.codexAsked. Where the mark stands, it asks nothing.

At a commit, the checks read what is staged. What is staged is written out to a directory of its own and read there against the repository's history. The export and the map are written in the working tree. A failure to write them is reported and stops nothing.

Whatever the checks found, sheriff types then runs in the directory the staged files are written out to. The pre-commit hook copies each file sheriff types writes there into the working tree, in place of what stands at the same path. The hook stages none of them. What sheriff types refuses stops the commit.

Before a push that runs the tests (§tools 7.3.5), the pre-push hook compares the working tree with the commit each ref the push creates or updates names, directly or through a tag. It leaves aside the files the working tree ignores. It refuses the push where a file is in one of these cases, naming each such file:

• it differs between the working tree and the commit;
• it stands in only one of them;
• it stands in the working tree without having been added.

Otherwise it runs the tests in the working tree.

The agent's hooks are Claude Code's, which the plugin for Claude Code declares (§tools 14), and Codex's, which sheriff init writes into the project (§tools 16). Before an edit made with the file tools or with apply_patch, sheriff guard judges it.

After such an edit or a shell command (Claude Code's Bash or PowerShell), the checks run over the working tree where one of the following holds:

• the last commit or the working tree, the files it ignores left aside, differs from what the hook noted in the clone's git directory once the checks last ran;
• nothing is noted.

The checks read the working tree's difference from the last commit as the commit. They run in this order:

• first, where a file under specs/, sheriff.config.json or a file the settings name as the code of a project's own generator differs, sheriff reindex, sheriff export, sheriff render and sheriff types;
• then sheriff validate, sheriff binding and sheriff citations.

What they refuse is reported to the agent. So is each node that sheriff reindex made a draft, a section and a domain's header left out (§1.3.8).

An edit made through the shell is not judged before it is made. Nor is a file sheriff types writes after an edit. The checks after them and at the commit still read them.

Хуки

Текст

Каждая проверка находится в команде, которую вызывает git-хук:

• .githooks/pre-commit запускает sheriff export и sheriff render, затем sheriff validate, sheriff binding и sheriff citations и последним — sheriff types;
• .githooks/commit-msg запускает sheriff message, а затем sheriff review на файле, который ему передаёт git;
• .githooks/pre-push запускает тесты кода системы и собственных проверок и генераторов проекта командой, которую sheriff.config.json называет своим testCommand, как говорит §tools 7.3.5.

Клон включает git-хуки командой git config core.hooksPath .githooks. Хук агента SessionStart — хук плагина для Claude Code или хук проекта для Codex (§tools 16) — выполняет эту команду, если core.hooksPath не задан, и сообщает об этом. Если core.hooksPath называет другой каталог, он сообщает об этом.

Хук SessionStart также называет каждый git-хук в .githooks/ в одном из этих случаев:

• индекс git хранит его без исполняемого режима;
• в системе, где у файлов есть бит исполнения, у его файла этого бита нет.

Он сообщает, как сделать каждый из них исполняемым в любой системе: chmod +x <hook> и git update-index --chmod=+x <hook>, затем коммит. Он не меняет ни режим файла, ни индекс git.

Хук SessionStart плагина для Claude Code записывает в конфигурацию git пользователя командой git config --global каждую настройку runner claude (§tools 10.1), которую пользователь задал как параметр этого плагина (§tools 14). Он записывает настройку везде, где её в конфигурации нет или там другое значение.

Если в конфигурации git нет настройки runner, которого sheriff review взял бы при коммите в этом репозитории (§tools 10.1, §tools 12), хук SessionStart любого из агентов называет каждую такую настройку. Вместе с каждой он называет значение по умолчанию, которое для неё берёт sheriff review. Он просит агента:

• предложить пользователю подтвердить или заменить каждое значение по умолчанию;
• записать командой git config --global значение, которое ответит пользователь, в том числе значение по умолчанию.

Он просит об этом один раз для каждого runner на каждой машине и отмечает это в конфигурации git как specsheriff.review.claudeAsked или specsheriff.review.codexAsked. Если отметка стоит, он ни о чём не просит.

При коммите проверки читают то, что находится в стейджинге. То, что в стейджинге, выписывается в отдельный каталог и читается там, сверяясь с историей репозитория. Экспорт и карта пишутся в рабочем дереве. О неудаче при их записи сообщается, и она ничего не останавливает.

Что бы ни нашли проверки, затем в каталоге, куда выписаны файлы из стейджинга, запускается sheriff types. Хук pre-commit копирует каждый файл, который sheriff types там пишет, в рабочее дерево, на место того, что лежит по тому же пути. Хук ни один из них не добавляет в стейджинг. То, что отвергает sheriff types, останавливает коммит.

Перед push, при котором запускаются тесты (§tools 7.3.5), хук pre-push сравнивает рабочее дерево с коммитом, который называет каждый ref, создаваемый или обновляемый push, напрямую или через тег. Файлы, которые рабочее дерево игнорирует, он не учитывает. Он отвергает push, если какой-либо файл находится в одном из этих случаев, и называет каждый такой файл:

• он отличается в рабочем дереве и в коммите;
• он есть только в одном из них;
• он есть в рабочем дереве, но не был добавлен.

Иначе он запускает тесты в рабочем дереве.

Хуки агента — это хуки Claude Code, которые объявляет плагин для Claude Code (§tools 14), и хуки Codex, которые sheriff init записывает в проект (§tools 16). Перед правкой, сделанной инструментами работы с файлами или apply_patch, её оценивает sheriff guard.

После такой правки или команды оболочки (Bash или PowerShell в Claude Code) проверки выполняются над рабочим деревом, если выполняется одно из следующего:

• последний коммит или рабочее дерево, кроме файлов, которые оно игнорирует, отличается от того, что хук отметил в каталоге git клона, когда проверки выполнялись в последний раз;
• ничего не отмечено.

Отличие рабочего дерева от последнего коммита проверки читают как коммит. Они выполняются в таком порядке:

• сначала, если отличается файл внутри specs/, sheriff.config.json или файл, который настройки называют кодом собственного генератора проекта, — sheriff reindex, sheriff export, sheriff render и sheriff types;
• затем sheriff validate, sheriff binding и sheriff citations.

О том, что они отвергают, сообщается агенту. Так же сообщается о каждом узле, который sheriff reindex сделал черновиком, кроме раздела и заголовка домена (§1.3.8).

Правка, сделанная через оболочку, до того как она сделана, не оценивается. Не оценивается и файл, который sheriff types пишет после правки. Проверки после них и при коммите их всё равно читают.

Title

The pre-commit hook

Text

The pre-commit hook runs the following, in this order (§10.12):

• the project's own tools for that hook that the project's own guidelines (§2.3) list as tools that rewrite files (§tools 3, §tools 13);
• sheriff types (§tools 2.5), run on the files as they are staged;
• the project's other tools for that hook (§tools 13);
• sheriff validate (§tools 7.1), which first checks for a key written more than once (§tools 7.1.1) and validates the files of the specification against their schema (§tools 7.1.2), and runs the project's own checks (§10.8, §tools 7.1.23) only after both have passed;
• sheriff binding (§tools 7.2) and sheriff citations (§tools 7.3), only after the check for a key written more than once and the validation against the schema have passed;
• where the project has chosen the Views extension (§13), sheriff markdown (§tools 5a) and sheriff map (§tools 4), in the working tree.

The hook writes out what is staged to a directory of its own (§tools 6) once the project's tools that rewrite files have run. The checks run in that directory.

For each file that sheriff types writes, the hook writes that file into the working tree, not into that directory, replacing whatever is at the same path. The checks therefore read each such file as it is staged. The hook tells the author to stage each such file. The hook itself leaves git's index as it is.

A failure of sheriff markdown or sheriff map to write its files is reported, and the hook judges the commit by its other steps alone.

Reason

On every commit, each check judges the commit in its final form (§10.12). So the tools that rewrite files run before the checks, and what the hook generates waits in the working tree until the author stages it, since what a commit holds is its author's choice.

Example

A developer edits a RecordType, an owner approves the new wording, and the developer stages the specification and commits. sheriff types generates the RecordType's new types from the staged nodes, and the hook writes them into the working tree and names them. sheriff binding refuses the commit, since the staged types differ from what the approved wording produces (§tools 7.2.8). The developer stages the new types and commits again. The most likely mistake is to let the checks read the types that sheriff types has just written, so that the commit passes with the old types staged.

Хук pre-commit

Текст

Хук pre-commit выполняет следующее в таком порядке (§10.12):

• собственные инструменты проекта для этого хука, которые собственные guidelines проекта (§2.3) перечисляют как инструменты, переписывающие файлы (§tools 3, §tools 13);
• sheriff types (§tools 2.5), запущенный на файлах в том виде, в каком они находятся в стейджинге;
• остальные собственные инструменты проекта для этого хука (§tools 13);
• sheriff validate (§tools 7.1), который сначала проверяет, нет ли ключа, записанного больше одного раза (§tools 7.1.1), и проверяет файлы спецификации по их схеме (§tools 7.1.2), а собственные проверки проекта (§10.8, §tools 7.1.23) запускает только после того, как обе проверки пройдены;
• sheriff binding (§tools 7.2) и sheriff citations (§tools 7.3) — только после того, как пройдены проверка ключа, записанного больше одного раза, и проверка по схеме;
• если проект выбрал расширение Views (§13), — sheriff markdown (§tools 5a) и sheriff map (§tools 4) в рабочем дереве.

Хук выписывает то, что находится в стейджинге, в отдельный каталог (§tools 6) после того, как отработали собственные инструменты проекта, переписывающие файлы. Проверки выполняются в этом каталоге.

Каждый файл, который записывает sheriff types, хук записывает не в этот каталог, а в рабочее дерево, заменяя то, что лежит по тому же пути. Поэтому проверки читают каждый такой файл в том виде, в каком он находится в стейджинге. Хук говорит автору добавить каждый такой файл в стейджинг. Сам хук оставляет индекс git как есть.

Если sheriff markdown или sheriff map не может записать свои файлы, об этом сообщается, и хук оценивает коммит только по остальным своим шагам.

Обоснование

При каждом коммите каждая проверка оценивает коммит в его окончательном виде (§10.12). Поэтому инструменты, переписывающие файлы, выполняются до проверок, а то, что порождает хук, ждёт в рабочем дереве, пока автор не добавит это в стейджинг: что содержит коммит, решает его автор.

Пример

Разработчик меняет RecordType, ответственный одобряет новую формулировку, а разработчик добавляет спецификацию в стейджинг и делает коммит. sheriff types порождает новые типы этого RecordType из узлов в стейджинге, а хук записывает их в рабочее дерево и называет их. sheriff binding отвергает коммит, потому что типы в стейджинге отличаются от того, что даёт одобренная формулировка (§tools 7.2.8). Разработчик добавляет новые типы в стейджинг и снова делает коммит. Самая вероятная ошибка — дать проверкам читать типы, которые только что записал sheriff types: тогда коммит проходит со старыми типами в стейджинге.

The hooks

Text

Each check lives in a command a git hook calls:

• .githooks/pre-commit runs sheriff export and sheriff render, then sheriff validate, sheriff binding and sheriff citations, and last sheriff types;
• .githooks/commit-msg runs sheriff message and then sheriff review on the file git hands it;
• .githooks/pre-push runs the tests of the system's code and of the project's own checks and generators, by the command sheriff.config.json names as its testCommand, as §tools 7.3.5 says.

A clone turns the git hooks on with git config core.hooksPath .githooks. The SessionStart hook of the agent, the plugin's for Claude Code or the project's for Codex (§tools 16), runs that command where core.hooksPath is unset, saying so. It reports where core.hooksPath names another directory.

The SessionStart hook also names each git hook in .githooks/ in one of these cases:

• git's index holds it without the executable mode;
• on a system whose files keep the executable bit, its file lacks the bit.

It says how to make each one executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It changes neither the mode of a file nor git's index.

The SessionStart hook of the plugin for Claude Code writes into the user's git configuration, by git config --global, each setting of the runner claude (§tools 10.1) the user has given as an option of that plugin (§tools 14). It writes a setting wherever the configuration lacks it or holds another value.

Where the git configuration lacks a setting of the runner sheriff review would take at a commit in the repository (§tools 10.1, §tools 12), the SessionStart hook of either agent names each such setting. With each, it names the default sheriff review takes for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value the user answers, the default included.

It asks so once for each runner on each machine, and marks it asked in the git configuration, as specsheriff.review.claudeAsked or specsheriff.review.codexAsked. Where the mark stands, it asks nothing.

At a commit, the checks read what is staged. What is staged is written out to a directory of its own and read there against the repository's history. The export and the map are written in the working tree. A failure to write them is reported and stops nothing.

Whatever the checks found, sheriff types then runs in the directory the staged files are written out to. The pre-commit hook copies each file sheriff types writes there into the working tree, in place of what stands at the same path. The hook stages none of them. What sheriff types refuses stops the commit.

Before a push that runs the tests (§tools 7.3.5), the pre-push hook compares the working tree with the commit each ref the push creates or updates names, directly or through a tag. It leaves aside the files the working tree ignores. It refuses the push where a file is in one of these cases, naming each such file:

• it differs between the working tree and the commit;
• it stands in only one of them;
• it stands in the working tree without having been added.

Otherwise it runs the tests in the working tree.

The agent's hooks are Claude Code's, which the plugin for Claude Code declares (§tools 14), and Codex's, which sheriff init writes into the project (§tools 16). Before an edit made with the file tools or with apply_patch, sheriff guard judges it.

After such an edit or a shell command (Claude Code's Bash or PowerShell), the checks run over the working tree where one of the following holds:

• the last commit or the working tree, the files it ignores left aside, differs from what the hook noted in the clone's git directory once the checks last ran;
• nothing is noted.

The checks read the working tree's difference from the last commit as the commit. They run in this order:

• first, where a file under specs/, sheriff.config.json or a file the settings name as the code of a project's own generator differs, sheriff reindex, sheriff export, sheriff render and sheriff types;
• then sheriff validate, sheriff binding and sheriff citations.

What they refuse is reported to the agent. So is each node that sheriff reindex made a draft, a section and a domain's header left out (§1.3.8).

An edit made through the shell is not judged before it is made. Nor is a file sheriff types writes after an edit. The checks after them and at the commit still read them.

Хуки

Текст

Каждая проверка находится в команде, которую вызывает git-хук:

• .githooks/pre-commit запускает sheriff export и sheriff render, затем sheriff validate, sheriff binding и sheriff citations и последним — sheriff types;
• .githooks/commit-msg запускает sheriff message, а затем sheriff review на файле, который ему передаёт git;
• .githooks/pre-push запускает тесты кода системы и собственных проверок и генераторов проекта командой, которую sheriff.config.json называет своим testCommand, как говорит §tools 7.3.5.

Клон включает git-хуки командой git config core.hooksPath .githooks. Хук агента SessionStart — хук плагина для Claude Code или хук проекта для Codex (§tools 16) — выполняет эту команду, если core.hooksPath не задан, и сообщает об этом. Если core.hooksPath называет другой каталог, он сообщает об этом.

Хук SessionStart также называет каждый git-хук в .githooks/ в одном из этих случаев:

• индекс git хранит его без исполняемого режима;
• в системе, где у файлов есть бит исполнения, у его файла этого бита нет.

Он сообщает, как сделать каждый из них исполняемым в любой системе: chmod +x <hook> и git update-index --chmod=+x <hook>, затем коммит. Он не меняет ни режим файла, ни индекс git.

Хук SessionStart плагина для Claude Code записывает в конфигурацию git пользователя командой git config --global каждую настройку runner claude (§tools 10.1), которую пользователь задал как параметр этого плагина (§tools 14). Он записывает настройку везде, где её в конфигурации нет или там другое значение.

Если в конфигурации git нет настройки runner, которого sheriff review взял бы при коммите в этом репозитории (§tools 10.1, §tools 12), хук SessionStart любого из агентов называет каждую такую настройку. Вместе с каждой он называет значение по умолчанию, которое для неё берёт sheriff review. Он просит агента:

• предложить пользователю подтвердить или заменить каждое значение по умолчанию;
• записать командой git config --global значение, которое ответит пользователь, в том числе значение по умолчанию.

Он просит об этом один раз для каждого runner на каждой машине и отмечает это в конфигурации git как specsheriff.review.claudeAsked или specsheriff.review.codexAsked. Если отметка стоит, он ни о чём не просит.

При коммите проверки читают то, что находится в стейджинге. То, что в стейджинге, выписывается в отдельный каталог и читается там, сверяясь с историей репозитория. Экспорт и карта пишутся в рабочем дереве. О неудаче при их записи сообщается, и она ничего не останавливает.

Что бы ни нашли проверки, затем в каталоге, куда выписаны файлы из стейджинга, запускается sheriff types. Хук pre-commit копирует каждый файл, который sheriff types там пишет, в рабочее дерево, на место того, что лежит по тому же пути. Хук ни один из них не добавляет в стейджинг. То, что отвергает sheriff types, останавливает коммит.

Перед push, при котором запускаются тесты (§tools 7.3.5), хук pre-push сравнивает рабочее дерево с коммитом, который называет каждый ref, создаваемый или обновляемый push, напрямую или через тег. Файлы, которые рабочее дерево игнорирует, он не учитывает. Он отвергает push, если какой-либо файл находится в одном из этих случаев, и называет каждый такой файл:

• он отличается в рабочем дереве и в коммите;
• он есть только в одном из них;
• он есть в рабочем дереве, но не был добавлен.

Иначе он запускает тесты в рабочем дереве.

Хуки агента — это хуки Claude Code, которые объявляет плагин для Claude Code (§tools 14), и хуки Codex, которые sheriff init записывает в проект (§tools 16). Перед правкой, сделанной инструментами работы с файлами или apply_patch, её оценивает sheriff guard.

После такой правки или команды оболочки (Bash или PowerShell в Claude Code) проверки выполняются над рабочим деревом, если выполняется одно из следующего:

• последний коммит или рабочее дерево, кроме файлов, которые оно игнорирует, отличается от того, что хук отметил в каталоге git клона, когда проверки выполнялись в последний раз;
• ничего не отмечено.

Отличие рабочего дерева от последнего коммита проверки читают как коммит. Они выполняются в таком порядке:

• сначала, если отличается файл внутри specs/, sheriff.config.json или файл, который настройки называют кодом собственного генератора проекта, — sheriff reindex, sheriff export, sheriff render и sheriff types;
• затем sheriff validate, sheriff binding и sheriff citations.

О том, что они отвергают, сообщается агенту. Так же сообщается о каждом узле, который sheriff reindex сделал черновиком, кроме раздела и заголовка домена (§1.3.8).

Правка, сделанная через оболочку, до того как она сделана, не оценивается. Не оценивается и файл, который sheriff types пишет после правки. Проверки после них и при коммите их всё равно читают.

English
Title

The working tree compared with what a push sends

Text

Before a push for which the tests are to run (§tools 7.3.5), the pre-push hook compares the working tree with each commit that the tests judge: each commit that is pointed to, directly or through a tag, by a ref that the push creates or updates, and that meets the conditions under which the tests run.

The hook refuses the push where either of the following holds for a file, and names each such file:

• the file differs between the working tree and such a commit;
• the file is in only one of the two, even where it is a file in the working tree that git does not track.

The hook leaves out the files that git ignores. Where it refuses nothing, it runs the tests in the working tree.

Reason

The tests run in the working tree, which holds what each clone installs or builds for itself, so they judge a pushed commit only where the working tree holds what that commit holds.

Example

A developer commits a change and leaves an edit to src/a.ts uncommitted. The specification is approved, and the project's own guidelines name a push as the moment at which the tests run. The pre-push hook refuses the push and names src/a.ts. The most likely mistake is to run the tests in the working tree as it is, so that they pass or fail because of an edit that the pushed commit does not hold.

Заголовок

Сравнение рабочего дерева с тем, что отправляет push

Текст

Перед push, для которого должны выполняться тесты (§tools 7.3.5), хук pre-push сравнивает рабочее дерево с каждым коммитом, который оценивают тесты: с каждым коммитом, на который напрямую или через тег указывает ref, создаваемый или обновляемый этим push, если этот коммит удовлетворяет условиям запуска тестов.

Хук отвергает push, если для какого-либо файла выполняется одно из следующих условий, и называет каждый такой файл:

• файл отличается в рабочем дереве и в таком коммите;
• файл есть только в одном из двух, даже если это файл в рабочем дереве, который git не отслеживает.

Хук не учитывает файлы, которые git игнорирует. Если он ничего не отверг, он запускает тесты в рабочем дереве.

Обоснование

Тесты выполняются в рабочем дереве, где есть то, что каждый клон устанавливает или собирает для себя, поэтому они оценивают отправленный коммит, только если рабочее дерево содержит то же, что этот коммит.

Пример

Разработчик делает коммит изменения, а правку src/a.ts оставляет вне коммита. Спецификация одобрена, и собственные guidelines проекта называют push моментом запуска тестов. Хук pre-push отвергает push и называет src/a.ts. Самая вероятная ошибка — запускать тесты в рабочем дереве как есть: тогда они проходят или падают из-за правки, которой нет в отправленном коммите.

English
Title

The hooks

Text

Each check lives in a command a git hook calls:

• .githooks/pre-commit runs sheriff export and sheriff render, then sheriff validate, sheriff binding and sheriff citations, and last sheriff types;
• .githooks/commit-msg runs sheriff message and then sheriff review on the file git hands it;
• .githooks/pre-push runs the tests of the system's code and of the project's own checks and generators, by the command sheriff.config.json names as its testCommand, as §tools 7.3.5 says.

A clone turns the git hooks on with git config core.hooksPath .githooks. The SessionStart hook of the agent, the plugin's for Claude Code or the project's for Codex (§tools 16), runs that command where core.hooksPath is unset, saying so. It reports where core.hooksPath names another directory.

The SessionStart hook also names each git hook in .githooks/ in one of these cases:

• git's index holds it without the executable mode;
• on a system whose files keep the executable bit, its file lacks the bit.

It says how to make each one executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It changes neither the mode of a file nor git's index.

The SessionStart hook of the plugin for Claude Code writes into the user's git configuration, by git config --global, each setting of the runner claude (§tools 10.1) the user has given as an option of that plugin (§tools 14). It writes a setting wherever the configuration lacks it or holds another value.

Where the git configuration lacks a setting of the runner sheriff review would take at a commit in the repository (§tools 10.1, §tools 12), the SessionStart hook of either agent names each such setting. With each, it names the default sheriff review takes for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value the user answers, the default included.

It asks so once for each runner on each machine, and marks it asked in the git configuration, as specsheriff.review.claudeAsked or specsheriff.review.codexAsked. Where the mark stands, it asks nothing.

Title

Turning the git hooks on when a session starts

Text

In a repository whose root holds sheriff.config.json, the agent's hook that runs when a session starts (§tools 6) does the following with git's core.hooksPath:

• where it is unset, the hook sets it to .githooks in the repository's git configuration and says so;
• where it points to a different directory, the hook says that the git hooks that sheriff init writes (§tools 3) do not run.

The hook also names each git hook in .githooks/ that git's index holds, in either of the following cases:

• git's index holds that git hook without the executable mode;
• on a file system that keeps the executable bit, the git hook's file lacks that bit.

For each such git hook, the agent's hook says how to make the git hook executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It leaves the mode of each file and git's index as they are. It leaves out the project's own tools in .githooks/<hook>.d/ (§tools 13).

Reason

In a clone where git does not run the git hooks, no check runs on a commit. A git hook that git does not run cannot report that it was skipped, while the hook that runs when a session starts runs in every clone. The hook that runs when a session starts leaves it to the author of the next commit to record a git hook's mode, since what a commit holds is its author's choice.

Example

A repository set up on Windows has its git hooks committed without the executable mode. A developer clones it on Linux and starts a session. The hook that runs when a session starts names each git hook and says how to make it executable. The most likely mistake is to make the git hooks executable in the working tree without saying so, which leaves the index as it was, so that each of the other clones still gets git hooks that git skips.

Что бы ни нашли проверки, затем в каталоге, куда выписаны файлы из стейджинга, запускается sheriff types. Хук pre-commit копирует каждый файл, который sheriff types там пишет, в рабочее дерево, на место того, что лежит по тому же пути. Хук ни один из них не добавляет в стейджинг. То, что отвергает sheriff types, останавливает коммит.

Перед push, при котором запускаются тесты (§tools 7.3.5), хук pre-push сравнивает рабочее дерево с коммитом, который называет каждый ref, создаваемый или обновляемый push, напрямую или через тег. Файлы, которые рабочее дерево игнорирует, он не учитывает. Он отвергает push, если какой-либо файл находится в одном из этих случаев, и называет каждый такой файл:

• он отличается в рабочем дереве и в коммите;
• он есть только в одном из них;
• он есть в рабочем дереве, но не был добавлен.

Иначе он запускает тесты в рабочем дереве.

Хуки агента — это хуки Claude Code, которые объявляет плагин для Claude Code (§tools 14), и хуки Codex, которые sheriff init записывает в проект (§tools 16). Перед правкой, сделанной инструментами работы с файлами или apply_patch, её оценивает sheriff guard.

После такой правки или команды оболочки (Bash или PowerShell в Claude Code) проверки выполняются над рабочим деревом, если выполняется одно из следующего:

• последний коммит или рабочее дерево, кроме файлов, которые оно игнорирует, отличается от того, что хук отметил в каталоге git клона, когда проверки выполнялись в последний раз;
• ничего не отмечено.

Отличие рабочего дерева от последнего коммита проверки читают как коммит. Они выполняются в таком порядке:

• сначала, если отличается файл внутри specs/, sheriff.config.json или файл, который настройки называют кодом собственного генератора проекта, — sheriff reindex, sheriff export, sheriff render и sheriff types;
• затем sheriff validate, sheriff binding и sheriff citations.

О том, что они отвергают, сообщается агенту. Так же сообщается о каждом узле, который sheriff reindex сделал черновиком, кроме раздела и заголовка домена (§1.3.8).

Правка, сделанная через оболочку, до того как она сделана, не оценивается. Не оценивается и файл, который sheriff types пишет после правки. Проверки после них и при коммите их всё равно читают.

Title

The settings of each runner when a session starts

Text

In Claude Code, the hook that runs when a session starts writes into the user's git configuration, with git config --global, each setting of the runner claude (§tools 10.7) that the user has given as an option of the plugin for Claude Code (§tools 14). It does so in any repository, whenever the configuration lacks the setting or holds a different value.

Then, in a repository whose root holds sheriff.config.json, the agent's hook that runs when a session starts (§tools 6), in Claude Code or in Codex CLI, names each setting of the runner that sheriff review would run on a commit there (§tools 10.1), where the user's git configuration lacks that setting.

That runner is the one that review.runner in sheriff.config.json names, or otherwise the runner of the SpecSheriff plugin whose tools the git hooks would use there (§tools 12). With each setting, the hook names the default that sheriff review uses for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value that the user gives in reply, even where that value is the default.

The hook makes this request once for each runner on each machine. After making it, the hook sets specsheriff.review.claudeAsked or specsheriff.review.codexAsked to true in the user's git configuration. The hook stops making the request about a runner once that runner's key is true.

Reason

A run of the reviewer is paid for by the user who commits, so the user who commits chooses the settings of each runner (§tools 10.7), once, as soon as an agent can ask. The git hooks run the reviewer outside the agent, so they read those settings from the user's git configuration, where the hook that runs when a session starts also writes the options that Claude Code asked the user for.

Example

A user installs the plugin for Codex CLI and opens a repository that sheriff init --agent codex has set up. The hook that runs when a session starts names specsheriff.review.codexModel and specsheriff.review.codexEffort with their defaults, and the agent asks the user about them. The user confirms the effort and names a model, and the agent writes both. The most likely mistake is to write the defaults without asking, so that the user pays for settings that the user never chose.

Title

The hooks

Text

Each check lives in a command a git hook calls:

• .githooks/pre-commit runs sheriff export and sheriff render, then sheriff validate, sheriff binding and sheriff citations, and last sheriff types;
• .githooks/commit-msg runs sheriff message and then sheriff review on the file git hands it;
• .githooks/pre-push runs the tests of the system's code and of the project's own checks and generators, by the command sheriff.config.json names as its testCommand, as §tools 7.3.5 says.

A clone turns the git hooks on with git config core.hooksPath .githooks. The SessionStart hook of the agent, the plugin's for Claude Code or the project's for Codex (§tools 16), runs that command where core.hooksPath is unset, saying so. It reports where core.hooksPath names another directory.

The SessionStart hook also names each git hook in .githooks/ in one of these cases:

• git's index holds it without the executable mode;
• on a system whose files keep the executable bit, its file lacks the bit.

It says how to make each one executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It changes neither the mode of a file nor git's index.

The SessionStart hook of the plugin for Claude Code writes into the user's git configuration, by git config --global, each setting of the runner claude (§tools 10.1) the user has given as an option of that plugin (§tools 14). It writes a setting wherever the configuration lacks it or holds another value.

Where the git configuration lacks a setting of the runner sheriff review would take at a commit in the repository (§tools 10.1, §tools 12), the SessionStart hook of either agent names each such setting. With each, it names the default sheriff review takes for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value the user answers, the default included.

It asks so once for each runner on each machine, and marks it asked in the git configuration, as specsheriff.review.claudeAsked or specsheriff.review.codexAsked. Where the mark stands, it asks nothing.

At a commit, the checks read what is staged. What is staged is written out to a directory of its own and read there against the repository's history. The export and the map are written in the working tree. A failure to write them is reported and stops nothing.

Whatever the checks found, sheriff types then runs in the directory the staged files are written out to. The pre-commit hook copies each file sheriff types writes there into the working tree, in place of what stands at the same path. The hook stages none of them. What sheriff types refuses stops the commit.

Before a push that runs the tests (§tools 7.3.5), the pre-push hook compares the working tree with the commit each ref the push creates or updates names, directly or through a tag. It leaves aside the files the working tree ignores. It refuses the push where a file is in one of these cases, naming each such file:

• it differs between the working tree and the commit;
• it stands in only one of them;
• it stands in the working tree without having been added.

Otherwise it runs the tests in the working tree.

The agent's hooks are Claude Code's, which the plugin for Claude Code declares (§tools 14), and Codex's, which sheriff init writes into the project (§tools 16). Before an edit made with the file tools or with apply_patch, sheriff guard judges it.

After such an edit or a shell command (Claude Code's Bash or PowerShell), the checks run over the working tree where one of the following holds:

• the last commit or the working tree, the files it ignores left aside, differs from what the hook noted in the clone's git directory once the checks last ran;
• nothing is noted.

The checks read the working tree's difference from the last commit as the commit. They run in this order:

• first, where a file under specs/, sheriff.config.json or a file the settings name as the code of a project's own generator differs, sheriff reindex, sheriff export, sheriff render and sheriff types;
• then sheriff validate, sheriff binding and sheriff citations.

What they refuse is reported to the agent. So is each node that sheriff reindex made a draft, a section and a domain's header left out (§1.3.8).

An edit made through the shell is not judged before it is made. Nor is a file sheriff types writes after an edit. The checks after them and at the commit still read them.

English
Title

The agent's hook after an edit

Text

After an agent's edit made with the file-editing tools, or after a shell command that the agent runs, the agent's hook (§tools 6) runs the SpecSheriff tools where either of the following holds:

• the last commit or the working tree, other than the files that git ignores, differs from what the hook last recorded in the clone's git directory;
• nothing is recorded.

Where nothing is recorded, the hook treats every file as one that differs.

Where the hook runs the SpecSheriff tools, it runs the following, in this order:

• sheriff reindex (§tools 2.2), where the files that differ include sheriff.config.json, a file under specs/, or a file that the SpecSheriff tools read to find SpecTags (§9.3);
• sheriff markdown (§tools 5a) and sheriff map (§tools 4), where the project has chosen the Views extension (§13), and the files that differ include sheriff.config.json or a file under specs/, or sheriff reindex has written a file;
• sheriff types (§tools 2.5), where the files that differ include sheriff.config.json, a file under specs/ or the code of a project's own generator (§10.9), or where sheriff reindex has written a file;
• sheriff validate (§tools 7.1), sheriff binding (§tools 7.2) and sheriff citations (§tools 7.3).

Where sheriff reindex refuses anything, for example a key written more than once whose values it cannot merge (§tools 2.4) or a file that does not conform to its schema (§tools 7.1.2), the hook stops after it. It then records the last commit and the working tree as they are at that moment.

The hook hands the agent the refusals of sheriff reindex, of sheriff types and of the checks, and names each node that sheriff reindex makes a draft. It hands them to Claude Code by exiting with code 2 and writing them to its standard error. It hands them to Codex in the answer that the agent's hooks for Codex CLI write (§tools 16).

A failure of sheriff markdown or sheriff map to write its files is reported to the agent, and the hook goes on to the next step.

Once the checks have finished, whether or not they refuse anything, the hook records the last commit and the working tree as they were when sheriff validate began. So a file changed while the checks run is checked at the next run.

Reason

The checks run where the agent works, so that a mistake is found at the edit that introduces it (§10.2). They run only where something has changed since they last ran, so that a session that only reads the repository through the shell is not held up.

Example

An agent that has written the test of rule R adds the SpecTag of R to a function in a new file, src/order.ts. The hook runs sheriff reindex, which adds src/order.ts to the meta.code of R, and the checks then accept that list. The most likely mistake is to run sheriff reindex only where a file under specs/ has changed, so that sheriff binding refuses the meta.code of R after an edit to code alone (§tools 7.2.5).

Хук агента после правки

Текст

После правки агента, сделанной инструментами редактирования файлов, или после команды оболочки, которую запускает агент, хук агента (§tools 6) запускает инструменты SpecSheriff, если выполняется одно из следующего:

• последний коммит или рабочее дерево, кроме файлов, которые git игнорирует, отличается от того, что хук в последний раз записал в каталоге git клона;
• ничего не записано.

Если ничего не записано, хук считает отличающимся каждый файл.

Если хук запускает инструменты SpecSheriff, он выполняет следующее в таком порядке:

• sheriff reindex (§tools 2.2), если среди отличающихся файлов есть sheriff.config.json, файл внутри specs/ или файл, который инструменты SpecSheriff читают, чтобы найти SpecTag (§9.3);
• sheriff markdown (§tools 5a) и sheriff map (§tools 4), если проект выбрал расширение Views (§13) и либо среди отличающихся файлов есть sheriff.config.json или файл внутри specs/, либо sheriff reindex записал какой-либо файл;
• sheriff types (§tools 2.5), если среди отличающихся файлов есть sheriff.config.json, файл внутри specs/ или код собственного генератора проекта (§10.9) либо sheriff reindex записал какой-либо файл;
• sheriff validate (§tools 7.1), sheriff binding (§tools 7.2) и sheriff citations (§tools 7.3).

Если sheriff reindex что-либо отвергает, например ключ, записанный больше одного раза, значения которого он не может объединить (§tools 2.4), или файл, который не соответствует своей схеме (§tools 7.1.2), хук на нём останавливается. Затем он записывает последний коммит и рабочее дерево такими, какие они в этот момент.

Хук передаёт агенту отказы sheriff reindex, sheriff types и проверок и называет каждый узел, который sheriff reindex делает черновиком. Claude Code он передаёт это, завершаясь с кодом 2 и записывая это в свой стандартный поток ошибок. Codex он передаёт это в ответе, который пишут хуки агента для Codex CLI (§tools 16).

Если sheriff markdown или sheriff map не может записать свои файлы, об этом сообщается агенту, и хук переходит к следующему шагу.

Когда проверки закончились, отвергли они что-либо или нет, хук записывает последний коммит и рабочее дерево такими, какими они были, когда начал работу sheriff validate. Поэтому файл, изменённый, пока выполнялись проверки, проверяется при следующем запуске.

Обоснование

Проверки выполняются там, где работает агент, чтобы ошибка находилась при той правке, которая её вносит (§10.2). Они выполняются, только если что-то изменилось с прошлого раза, чтобы сессия, которая лишь читает репозиторий через оболочку, не задерживалась.

Пример

Агент, который уже написал тест правила R, добавляет SpecTag правила R к функции в новом файле src/order.ts. Хук запускает sheriff reindex, который добавляет src/order.ts в meta.code правила R, и затем проверки этот список принимают. Самая вероятная ошибка — запускать sheriff reindex, только если изменился файл внутри specs/: тогда после правки одного кода sheriff binding отвергает meta.code правила R (§tools 7.2.5).

Title

The hooks

Text

Each check lives in a command a git hook calls:

• .githooks/pre-commit runs sheriff export and sheriff render, then sheriff validate, sheriff binding and sheriff citations, and last sheriff types;
• .githooks/commit-msg runs sheriff message and then sheriff review on the file git hands it;
• .githooks/pre-push runs the tests of the system's code and of the project's own checks and generators, by the command sheriff.config.json names as its testCommand, as §tools 7.3.5 says.

A clone turns the git hooks on with git config core.hooksPath .githooks. The SessionStart hook of the agent, the plugin's for Claude Code or the project's for Codex (§tools 16), runs that command where core.hooksPath is unset, saying so. It reports where core.hooksPath names another directory.

The SessionStart hook also names each git hook in .githooks/ in one of these cases:

• git's index holds it without the executable mode;
• on a system whose files keep the executable bit, its file lacks the bit.

It says how to make each one executable on every system: chmod +x <hook> and git update-index --chmod=+x <hook>, then a commit. It changes neither the mode of a file nor git's index.

The SessionStart hook of the plugin for Claude Code writes into the user's git configuration, by git config --global, each setting of the runner claude (§tools 10.1) the user has given as an option of that plugin (§tools 14). It writes a setting wherever the configuration lacks it or holds another value.

Where the git configuration lacks a setting of the runner sheriff review would take at a commit in the repository (§tools 10.1, §tools 12), the SessionStart hook of either agent names each such setting. With each, it names the default sheriff review takes for it. It asks the agent to do the following:

• to offer the user each default to confirm or replace;
• to write with git config --global the value the user answers, the default included.

It asks so once for each runner on each machine, and marks it asked in the git configuration, as specsheriff.review.claudeAsked or specsheriff.review.codexAsked. Where the mark stands, it asks nothing.

At a commit, the checks read what is staged. What is staged is written out to a directory of its own and read there against the repository's history. The export and the map are written in the working tree. A failure to write them is reported and stops nothing.

Whatever the checks found, sheriff types then runs in the directory the staged files are written out to. The pre-commit hook copies each file sheriff types writes there into the working tree, in place of what stands at the same path. The hook stages none of them. What sheriff types refuses stops the commit.

Before a push that runs the tests (§tools 7.3.5), the pre-push hook compares the working tree with the commit each ref the push creates or updates names, directly or through a tag. It leaves aside the files the working tree ignores. It refuses the push where a file is in one of these cases, naming each such file:

• it differs between the working tree and the commit;
• it stands in only one of them;
• it stands in the working tree without having been added.

Otherwise it runs the tests in the working tree.

The agent's hooks are Claude Code's, which the plugin for Claude Code declares (§tools 14), and Codex's, which sheriff init writes into the project (§tools 16). Before an edit made with the file tools or with apply_patch, sheriff guard judges it.

After such an edit or a shell command (Claude Code's Bash or PowerShell), the checks run over the working tree where one of the following holds:

• the last commit or the working tree, the files it ignores left aside, differs from what the hook noted in the clone's git directory once the checks last ran;
• nothing is noted.

The checks read the working tree's difference from the last commit as the commit. They run in this order:

• first, where a file under specs/, sheriff.config.json or a file the settings name as the code of a project's own generator differs, sheriff reindex, sheriff export, sheriff render and sheriff types;
• then sheriff validate, sheriff binding and sheriff citations.

What they refuse is reported to the agent. So is each node that sheriff reindex made a draft, a section and a domain's header left out (§1.3.8).

An edit made through the shell is not judged before it is made. Nor is a file sheriff types writes after an edit. The checks after them and at the commit still read them.

Хуки

Текст

Каждая проверка находится в команде, которую вызывает git-хук:

• .githooks/pre-commit запускает sheriff export и sheriff render, затем sheriff validate, sheriff binding и sheriff citations и последним — sheriff types;
• .githooks/commit-msg запускает sheriff message, а затем sheriff review на файле, который ему передаёт git;
• .githooks/pre-push запускает тесты кода системы и собственных проверок и генераторов проекта командой, которую sheriff.config.json называет своим testCommand, как говорит §tools 7.3.5.

Клон включает git-хуки командой git config core.hooksPath .githooks. Хук агента SessionStart — хук плагина для Claude Code или хук проекта для Codex (§tools 16) — выполняет эту команду, если core.hooksPath не задан, и сообщает об этом. Если core.hooksPath называет другой каталог, он сообщает об этом.

Хук SessionStart также называет каждый git-хук в .githooks/ в одном из этих случаев:

• индекс git хранит его без исполняемого режима;
• в системе, где у файлов есть бит исполнения, у его файла этого бита нет.

Он сообщает, как сделать каждый из них исполняемым в любой системе: chmod +x <hook> и git update-index --chmod=+x <hook>, затем коммит. Он не меняет ни режим файла, ни индекс git.

Хук SessionStart плагина для Claude Code записывает в конфигурацию git пользователя командой git config --global каждую настройку runner claude (§tools 10.1), которую пользователь задал как параметр этого плагина (§tools 14). Он записывает настройку везде, где её в конфигурации нет или там другое значение.

Если в конфигурации git нет настройки runner, которого sheriff review взял бы при коммите в этом репозитории (§tools 10.1, §tools 12), хук SessionStart любого из агентов называет каждую такую настройку. Вместе с каждой он называет значение по умолчанию, которое для неё берёт sheriff review. Он просит агента:

• предложить пользователю подтвердить или заменить каждое значение по умолчанию;
• записать командой git config --global значение, которое ответит пользователь, в том числе значение по умолчанию.

Он просит об этом один раз для каждого runner на каждой машине и отмечает это в конфигурации git как specsheriff.review.claudeAsked или specsheriff.review.codexAsked. Если отметка стоит, он ни о чём не просит.

При коммите проверки читают то, что находится в стейджинге. То, что в стейджинге, выписывается в отдельный каталог и читается там, сверяясь с историей репозитория. Экспорт и карта пишутся в рабочем дереве. О неудаче при их записи сообщается, и она ничего не останавливает.

Что бы ни нашли проверки, затем в каталоге, куда выписаны файлы из стейджинга, запускается sheriff types. Хук pre-commit копирует каждый файл, который sheriff types там пишет, в рабочее дерево, на место того, что лежит по тому же пути. Хук ни один из них не добавляет в стейджинг. То, что отвергает sheriff types, останавливает коммит.

Перед push, при котором запускаются тесты (§tools 7.3.5), хук pre-push сравнивает рабочее дерево с коммитом, который называет каждый ref, создаваемый или обновляемый push, напрямую или через тег. Файлы, которые рабочее дерево игнорирует, он не учитывает. Он отвергает push, если какой-либо файл находится в одном из этих случаев, и называет каждый такой файл:

• он отличается в рабочем дереве и в коммите;
• он есть только в одном из них;
• он есть в рабочем дереве, но не был добавлен.

Иначе он запускает тесты в рабочем дереве.

Хуки агента — это хуки Claude Code, которые объявляет плагин для Claude Code (§tools 14), и хуки Codex, которые sheriff init записывает в проект (§tools 16). Перед правкой, сделанной инструментами работы с файлами или apply_patch, её оценивает sheriff guard.

После такой правки или команды оболочки (Bash или PowerShell в Claude Code) проверки выполняются над рабочим деревом, если выполняется одно из следующего:

• последний коммит или рабочее дерево, кроме файлов, которые оно игнорирует, отличается от того, что хук отметил в каталоге git клона, когда проверки выполнялись в последний раз;
• ничего не отмечено.

Отличие рабочего дерева от последнего коммита проверки читают как коммит. Они выполняются в таком порядке:

• сначала, если отличается файл внутри specs/, sheriff.config.json или файл, который настройки называют кодом собственного генератора проекта, — sheriff reindex, sheriff export, sheriff render и sheriff types;
• затем sheriff validate, sheriff binding и sheriff citations.

О том, что они отвергают, сообщается агенту. Так же сообщается о каждом узле, который sheriff reindex сделал черновиком, кроме раздела и заголовка домена (§1.3.8).

Правка, сделанная через оболочку, до того как она сделана, не оценивается. Не оценивается и файл, который sheriff types пишет после правки. Проверки после них и при коммите их всё равно читают.

English
Title

An edit judged before it is made

Text

sheriff guard refuses each of the following edits by an agent (§10.3), regardless of whether the specification is approved or a draft:

• an edit after which a node that it adds, or a node whose wording (§1.3.5) or approval status (§1.3.1) it changes, has the status approved while no approval of that node's wording is in force (§tools 11.1);
• an edit that adds or changes code bound to a rule (§1.5.2, §tools 8.1), other than tests, while no test of the system's code (§9.1) declares that rule's SpecTag (§tools 8.5);
• an edit to specs/_approvals.jsonl, whatever it changes;
• an edit that adds, changes or removes an entry in one of the lists approvalStatus, strict and extensions of sheriff.config.json (§tools 2.10a).

The refusal names each such node by its file, its sid and its location (§8.5), and each such rule by its sid and its location. Where a test names such a rule only by a bare sid (§tools 2.3), the refusal also names sheriff reindex, which writes the test's SpecTag.

For an edit to specs/_approvals.jsonl, the refusal names sheriff approve, which records approvals and their withdrawals (§tools 11.3, §tools 11.4). For an edit to an entry of approvalStatus, strict or extensions, it names that list and sheriff settings (§tools 2.10).

While the installed SpecSheriff plugin lacks an extension of the guidelines that the project has chosen, sheriff guard refuses every edit, and names each missing extension and the version of the SpecSheriff tools in the plugin (§tools 7.1.2a).

sheriff guard judges an edit made with Claude Code's Write, Edit or MultiEdit, and a patch that Codex's apply_patch applies (§tools 16). It reads the edit, as the agent's harness describes it, from its standard input. It builds in memory each file as the edit would leave it. Where an edit made with Edit or MultiEdit would not apply, for example where it names text that the file does not contain, sheriff guard lets the tool refuse it.

sheriff guard judges the nodes in the files that the repository keeps, including a node in a cell of a TableRule (§8.6). It leaves out each node whose approval status is derived from other nodes, such as a section (§1.3.8). A file of the specification that would be invalid JSON after the edit is left to the checks that run after the edit (§tools 6e).

sheriff guard finds the code that an edit adds or changes in the same way as the SpecSheriff tools find what a commit adds or changes (§tools 7.2.1), comparing each file as it is with the file as the edit would leave it. Among the tests of the working tree as the edit would leave it, it looks for a test that declares the SpecTag of the rule to which that code is bound.

sheriff guard reads the lists approvalStatus, strict and extensions from sheriff.config.json as it is and as the edit would leave it. Where sheriff.config.json is missing or is not valid JSON, sheriff guard treats each of those lists as empty.

Where it refuses an edit, sheriff guard writes the refusal to its standard error and exits with code 2.

Reason

sheriff guard judges each file as the edit would leave it, so that an edit that the rule on an agent's edit forbids is refused before anything is written (§10.3). It judges only the nodes and the code that the edit adds or changes, so that a node or code that the edit leaves as it was never holds up the edit.

Example

An owner asks the agent to approve the specification, and the agent tries to add an entry to approvalStatus in sheriff.config.json with a file-editing tool. sheriff guard refuses the edit and names approvalStatus and sheriff settings, and the agent runs sheriff settings status approved. The most likely mistake is to judge only the files under specs/, so that the entry is written without sheriff settings, which checks that whoever records it is an owner.

Текст

sheriff guard отвергает каждую из следующих правок агента (§10.3) независимо от того, одобрена спецификация или является черновиком:

• правку, после которой узел, который она добавляет, или узел, формулировку (§1.3.5) или статус одобрения (§1.3.1) которого она меняет, имеет статус approved, тогда как ни одно одобрение формулировки этого узла не действует (§tools 11.1);
• правку, которая добавляет или меняет код, привязанный к правилу (§1.5.2, §tools 8.1), кроме тестов, тогда как ни у одного теста кода системы (§9.1) нет SpecTag этого правила (§tools 8.5);
• правку specs/_approvals.jsonl, что бы она ни меняла;
• правку, которая добавляет, меняет или удаляет запись в одном из списков approvalStatus, strict и extensions файла sheriff.config.json (§tools 2.10a).

Отказ называет каждый такой узел по его файлу, sid и расположению (§8.5), а каждое такое правило — по sid и расположению. Если тест называет такое правило только голым sid (§tools 2.3), отказ называет ещё и sheriff reindex, который записывает SpecTag теста.

Для правки specs/_approvals.jsonl отказ называет sheriff approve, который записывает одобрения и их отзывы (§tools 11.3, §tools 11.4). Для правки записи в approvalStatus, strict или extensions он называет этот список и sheriff settings (§tools 2.10).

Пока в установленном плагине SpecSheriff нет расширения guidelines, которое выбрал проект, sheriff guard отвергает любую правку и называет каждое недостающее расширение и версию инструментов SpecSheriff в плагине (§tools 7.1.2a).

sheriff guard оценивает правку, сделанную инструментами Claude Code Write, Edit или MultiEdit, и патч, который применяет инструмент Codex apply_patch (§tools 16). Правку он читает со своего стандартного ввода в том виде, в каком её описывает среда агента. Каждый файл он строит в памяти таким, каким его оставит правка. Если правку, сделанную Edit или MultiEdit, нельзя применить, например когда она называет текст, которого в файле нет, sheriff guard оставляет отказ инструменту.

sheriff guard оценивает узлы в файлах, которые хранит репозиторий, в том числе узел в ячейке TableRule (§8.6). Он не оценивает узел, статус одобрения которого выводится из других узлов, например раздел (§1.3.8). Файл спецификации, который после правки будет некорректным JSON, он оставляет проверкам после правки (§tools 6e).

Код, который правка добавляет или меняет, sheriff guard находит так же, как инструменты SpecSheriff находят то, что добавляет или меняет коммит (§tools 7.2.1), сравнивая каждый файл в нынешнем виде с файлом таким, каким его оставит правка. Тест, у которого есть SpecTag правила, к которому привязан этот код, он ищет среди тестов рабочего дерева в том виде, в каком его оставит правка.

Списки approvalStatus, strict и extensions sheriff guard читает из sheriff.config.json в нынешнем виде и в том виде, в каком его оставит правка. sheriff.config.json, которого нет или который не является корректным JSON, читается так, будто каждый из этих списков пуст.

Отвергая правку, sheriff guard записывает отказ в свой стандартный поток ошибок и завершается с кодом 2.

Обоснование

sheriff guard оценивает каждый файл таким, каким его оставит правка, чтобы правка, которую запрещает правило о правке агента, отвергалась до того, как что-либо записано (§10.3). Он оценивает только те узлы и тот код, которые правка добавляет или меняет, чтобы правку никогда не задерживали узел или код, которые она оставляет как были.

Пример

Ответственный просит агента одобрить спецификацию, и агент пытается добавить запись в approvalStatus в sheriff.config.json инструментом редактирования файлов. sheriff guard отвергает правку и называет approvalStatus и sheriff settings, и агент запускает sheriff settings status approved. Самая вероятная ошибка — оценивать только файлы внутри specs/: тогда запись появляется в обход sheriff settings, который проверяет, что её делает ответственный.

The agent's hooks for Codex CLI

Text

The agent's hooks for Codex are in the project's .codex/hooks.json, where sheriff init --agent codex writes them (§tools 3). They are the following:

• one that runs when a session starts;
• one that runs before an edit made with apply_patch;
• one that runs after such an edit or a shell command.

Each hook does only two things: it looks for the plugin for Codex CLI (§tools 15) in Codex's cache (§tools 12), and it calls the plugin's script for that hook, hooks/session-start.sh, hooks/guard.sh or hooks/after-edit.sh, only where it finds the plugin.

Each script runs what the list of the hooks specifies for its hook (§tools 6) only in a repository whose root holds sheriff.config.json.

Where the file agent in the folder of the plugin's SpecSheriff tools (§tools 10.1) contains codex, the scripts answer Codex with JSON written to their standard output and exit with code 0:

• before an edit that sheriff guard (§tools 7.3.2) refuses: {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": <the refusal>}};
• after an edit or a shell command for which the hook has something to hand the agent (§tools 6e): {"decision": "block", "reason": <what it hands the agent>}.

Before an edit, sheriff guard does the following:

• it takes from the patch the path of each file that the patch adds, updates, deletes or moves, and the new path of each moved file, each relative to the session's working directory, and reads from disk each of those files that exists;
• it applies the patch to those files in memory, treating a moved file as deleted at its old path and added at its new one;
• it judges each of those files as it judges an edit made with the file-editing tools (§tools 7.3.2).

sheriff guard refuses the whole patch in either of the following cases:

• it refuses one of the patch's files;
• it cannot read or apply the patch.
Reason

The agent's hooks for Codex hold an agent working in Codex to the same checks, before and after each edit, as an agent in Claude Code. Codex's public plugin directory admits no plugin that contains hooks, so the agent's hooks for Codex are in the project. Codex runs a project's hook only after its user has trusted the hook as it is written. So a hook that only finds the plugin and calls its scripts does not have to be trusted again when a release of the plugin changes what the scripts do.

Example

A patch adds src/new.ts and changes specs/_approvals.jsonl. sheriff guard refuses the patch, and hooks/guard.sh writes the denial as JSON with the refusal in permissionDecisionReason, so Codex applies no part of the patch. The most likely mistake is to write the refusal to standard output as plain text, which Codex ignores before a tool call, so that the patch is applied.

English
Title

A git hook runs the SpecSheriff tools that a plugin keeps on the machine

Text

When a session starts, the plugin for Claude Code (§tools 14) copies the SpecSheriff tools that it holds into its data directory, unless its data directory already holds a copy of the same release. The data directory is <plugins>/data/specsheriff-specsheriff-marketplace/. <plugins> is CLAUDE_CODE_PLUGIN_CACHE_DIR where that variable is set, and ~/.claude/plugins otherwise.

The plugin for Codex CLI (§tools 15) keeps its SpecSheriff tools only in its directory in Codex's cache, <Codex home>/plugins/cache/specsheriff-marketplace/specsheriff/<version>/tools/. <Codex home> is CODEX_HOME where that variable is set, and ~/.codex otherwise.

~ is the user's home directory, which on Windows is the user's profile directory.

Each git hook that sheriff init writes (§tools 3) does the following:

• it looks for the SpecSheriff tools of each plugin;
• where the SpecSheriff tools can run, it calls the script for that hook in their hooks/;
• where the SpecSheriff tools cannot run, it runs the project's own tools for that hook (§tools 13).

Where the hook finds the SpecSheriff tools of both plugins, it takes those whose release file begins with the higher version, the versions being compared as semantic versions. Where their versions are equal, it takes either set.

The script for the hook runs what the list of the hooks specifies for that hook (§tools 6), including the project's own tools for that hook.

The SpecSheriff tools cannot run where the hook finds the tools of neither plugin, or where Node.js is missing or older than the version that the engines field of their package.json names. In either case, the hook lets the commit or the push through unless one of the project's own tools fails (§10.12). The pre-commit and pre-push hooks then say that the SpecSheriff tools ran no check, and why: either no plugin's SpecSheriff tools are on the machine, or Node.js is missing or older than that version, which the hooks name.

The hook that runs when a session starts (§tools 6) names each of the following hooks that holds what an earlier release of sheriff init wrote:

• each git hook in .githooks/;
• each of the agent's hooks for Codex in .codex/hooks.json.

For each such hook, it says that running sheriff init again replaces that hook.

Reason

A git hook written once into a project finds the SpecSheriff tools wherever a machine keeps them and whichever plugin they come from, so that the checks keep up with each release of the plugin without any change to the project. Where those tools cannot run, the project's own tools keep guarding the commit and the push, as the rule on the order of tools and checks requires (§10.12).

Example

A user has both plugins: the plugin for Claude Code at release 0.7.0 and the plugin for Codex CLI at release 0.6.0. Each git hook runs the SpecSheriff tools of 0.7.0 from the data directory of the plugin for Claude Code, even when the commit is made from Codex. The most likely mistake is to take the tools of the agent that is running, so that a commit made from Codex is checked by the earlier release.

Git-хук, однажды записанный в проект, находит инструменты SpecSheriff, где бы машина их ни хранила и из какого бы плагина они ни были, чтобы проверки не отставали от каждого выпуска плагина без изменений в проекте. Если эти инструменты выполняться не могут, коммит и push по-прежнему охраняют собственные инструменты проекта, как требует правило о порядке инструментов и проверок (§10.12).

Title

The project's own tools in a git hook

Text

A project's own tools for a git hook are the files directly in .githooks/<hook>.d/ whose first line names their interpreter. Each git hook that sheriff init writes (§tools 3) runs only those files, and names any other file in that directory.

A first line names an interpreter where it starts with #!, followed by a path and at most one argument. A carriage return that ends the line is ignored.

Where the hook runs the SpecSheriff tools (§tools 12), it runs the project's own tools at the points set by the order of that hook's steps (§tools 6, §10.12):

• first, those that the project's own guidelines list as tools that rewrite files (§tools 3), in the order of that list;
• later, the other tools, in the byte order of their names.

Where a path in the project's list of tools that rewrite files points into the hook's own folder, .githooks/<hook>.d/, and the hook runs nothing for that path, the hook names the path.

Where the SpecSheriff tools cannot run (§tools 12), the hook runs all of the project's own tools for that hook in the byte order of their names.

The hook runs each of the project's own tools as follows:

• from the root of the working tree, with the interpreter that the tool's first line names, in the environment that git gives the hook, so that the tool reads the working tree and git's index;
• with the arguments that git hands the hook, and with a copy of the standard input that git hands the hook.

Each of the project's own tools runs even where another of them has failed. The hook fails where one of them exits with a code other than zero.

Where the hook runs the SpecSheriff tools, it also refuses the commit or the push if one of the project's own tools that run after the tools that rewrite files does any of the following, regardless of whether the specification is approved or a draft (§10.1.37b):

• adds, changes or removes a file of the working tree, other than a file that git ignores;
• changes what is staged;
• changes the commit message.

The hook names each tool that makes it fail, and each file that such a tool added, changed or removed.

A project's own tools for a git hook are among the repository's own tools (§9.1).

Reason

A project's own tools check what the checks of the SpecSheriff tools do not check, for example by scanning for secrets, so they run on every machine, whether or not the SpecSheriff tools can run there. They run at the points that the rule on the order of tools and checks sets (§10.12), so that none of them changes what a check has read. A tool is recognised by its first line rather than by the executable bit, since a file committed from a system without that bit loses it.

Example

.githooks/pre-commit.d/ holds scan and tidy, and the project's own guidelines list pre-commit.d/tidy as a tool that rewrites files. On a commit, tidy runs first and stages the files that it rewrites. scan runs after sheriff types, and the hook refuses the commit where scan changes any file that git does not ignore. The most likely mistake is to run both in the byte order of their names, so that scan reads the files before tidy has rewritten them.

Собственные инструменты проекта в git-хуке

Текст

Собственные инструменты проекта для git-хука — это файлы непосредственно в .githooks/<hook>.d/, первая строка которых называет их интерпретатор. Каждый git-хук, который записывает sheriff init (§tools 3), запускает только эти файлы и называет любой другой файл в этой папке.

Первая строка называет интерпретатор, если она начинается с #!, за которым идут путь и не больше одного аргумента. Возврат каретки в конце строки игнорируется.

Если хук запускает инструменты SpecSheriff (§tools 12), он запускает собственные инструменты проекта в тех местах, которые задаёт порядок шагов этого хука (§tools 6, §10.12):

• сначала — инструменты, которые собственные guidelines проекта перечисляют как инструменты, переписывающие файлы (§tools 3), в порядке этого перечня;
• позже — остальные инструменты в порядке байтов их имён.

Если путь из перечня инструментов проекта, переписывающих файлы, ведёт в собственную папку хука .githooks/<hook>.d/ и хук ничего для этого пути не запускает, хук называет этот путь.

Если инструменты SpecSheriff выполняться не могут (§tools 12), хук запускает все собственные инструменты проекта для этого хука в порядке байтов их имён.

Хук запускает каждый собственный инструмент проекта так:

• из корня рабочего дерева, интерпретатором, который назван в первой строке инструмента, в окружении, которое git даёт хуку, чтобы инструмент читал рабочее дерево и индекс git;
• с аргументами, которые git передаёт хуку, и с копией стандартного ввода, который git передаёт хуку.

Каждый собственный инструмент проекта выполняется, даже если другой из них завершился неудачей. Хук завершается неудачей, если один из них завершился с кодом, отличным от нуля.

Если хук запускает инструменты SpecSheriff, он также отвергает коммит или push, независимо от того, одобрена спецификация или является черновиком, если один из собственных инструментов проекта, которые выполняются после инструментов, переписывающих файлы, делает что-либо из следующего (§10.1.37b):

• добавляет, меняет или удаляет файл рабочего дерева, кроме файла, который git игнорирует;
• меняет то, что находится в стейджинге;
• меняет сообщение коммита.

Хук называет каждый инструмент, из-за которого он завершился неудачей, и каждый файл, который такой инструмент добавил, изменил или удалил.

Собственные инструменты проекта для git-хука относятся к собственным инструментам репозитория (§9.1).

Обоснование

Собственные инструменты проекта проверяют то, чего не проверяют проверки инструментов SpecSheriff, например ищут секреты, поэтому они выполняются на каждой машине, могут там выполняться инструменты SpecSheriff или нет. Они выполняются в тех местах, которые задаёт правило о порядке инструментов и проверок (§10.12), чтобы ни один из них не менял того, что уже прочитала проверка. Инструмент распознаётся по первой строке, а не по биту исполнения, потому что файл, закоммиченный из системы без этого бита, его теряет.

Пример

В .githooks/pre-commit.d/ лежат scan и tidy, и собственные guidelines проекта перечисляют pre-commit.d/tidy как инструмент, переписывающий файлы. При коммите tidy выполняется первым и добавляет в стейджинг файлы, которые переписывает. scan выполняется после sheriff types, и хук отвергает коммит, если scan меняет какой-либо файл, который git не игнорирует. Самая вероятная ошибка — запускать оба в порядке байтов их имён: тогда scan читает файлы до того, как tidy их переписал.

Title

The plugin for Claude Code

Text

The plugin for Claude Code, specsheriff, holds the following:

• the skills of the SpecSheriff plugins (§tools 15a);
• the SpecSheriff tools, with each file common to every project, such as the SpecSheriff guidelines, each extension of the guidelines (§1.7.1) and the appendix of the tools (§2.1), at its path in the folder of the SpecSheriff tools (§tools 1);
• the scripts of the agent's hooks (§tools 6).

The plugin declares the following hooks of the agent to Claude Code:

• the hook that runs when a session starts;
• the hook that runs before an edit made with Write, Edit or MultiEdit;
• the hook that runs after such an edit or after a shell command run with Bash or PowerShell.

The plugin declares each setting of the runner claude (§tools 10.7) as one of its options. Claude Code asks the user for those options when it enables the plugin. Each option names the default of its setting only in its description, so that a value that Claude Code holds for the option is one that the user gave.

In a repository without sheriff.config.json at its root, the plugin's hooks do only the following:

• keep the plugin's copy of the SpecSheriff tools up to date (§tools 12);
• write the settings that the user gave as the plugin's options (§tools 6d).

The marketplace specsheriff-marketplace lists the plugin by the relative path of its directory, in .claude-plugin/marketplace.json at the root of the repository where the SpecSheriff guidelines are written. A project declares both in .claude/settings.json (§tools 3):

• the marketplace under extraKnownMarketplaces, with the branch release of that repository as its source and with autoUpdate on;
• the plugin under enabledPlugins.

Each machine runs the release that its copy of the plugin holds, until Claude Code updates that copy.

The plugin's skills and the agent's hooks run sheriff from the SpecSheriff tools in the plugin, as node "${CLAUDE_PLUGIN_ROOT}/tools/dist/cli.js".

Reason

An agent can use a skill only where the skill is installed. Claude Code installs, updates and enables a plugin that a project declares. So the plugin brings the skills, the SpecSheriff guidelines with their extensions and the SpecSheriff tools, all from the same release, to the agent in every clone. Of all this, the project keeps only the declaration of the plugin and the calls to the plugin's tools.

Example

A project chooses the RecordType extension. On every machine where Claude Code has updated the plugin to a release that delivers that extension, the SpecSheriff tools find the extension at guidelines/extensions/recordtype.json in their own folder. The most likely mistake is to keep a copy of the extension in specs/_guidelines/extensions/, which sheriff validate refuses (§tools 7.1.20).

Title

The plugin for Codex CLI

Text

The plugin for Codex CLI, specsheriff, holds the skills of the SpecSheriff plugins (§tools 15a). It holds the SpecSheriff tools, with the files common to every project (§tools 1), and the scripts of the agent's hooks (§tools 6), as the plugin for Claude Code does (§tools 14).

The agent's hooks for Codex are in the project, not in the plugin (§tools 16). They call the scripts that the plugin holds.

The marketplace specsheriff-marketplace lists the plugin by the relative path of its directory, in .agents/plugins/marketplace.json at the root of the repository where the SpecSheriff guidelines are written, which also holds the marketplace for Claude Code (§tools 14).

The practitioner's guide, the plugin's README.md, gives the commands that install the plugin on a machine:

• codex plugin marketplace add non4me/SpecSheriff@release;
• codex plugin add specsheriff@specsheriff-marketplace.

The plugin's skills run sheriff from the SpecSheriff tools in the plugin, as node <plugin>/tools/dist/cli.js. A skill derives <plugin> from the path of its SKILL.md, <plugin>/skills/<skill>/SKILL.md.

Reason

An agent can use a skill only where the skill is installed. Codex installs a plugin only for the user who adds it, so each user has to install the plugin for Codex CLI. Each release of that plugin holds the same skills and SpecSheriff tools as the release of the plugin for Claude Code with the same version, so that a project's users follow the same procedures and are held to the same checks whichever agent each runs.

The skill spec-init

Text

spec-init runs sheriff init (§tools 3), adding the option --agent codex where it runs from the plugin for Codex CLI (§tools 15).

spec-init then asks the user for each of the following that sheriff.config.json lacks (§tools 3), and writes each answer there:

• the glob patterns that match the files holding the system's code (§9.1);
• the glob patterns that match the files holding its tests;
• the command that runs the tests (§tools 7.3.5).

spec-init then moves on to the settings of the runner that sheriff review would run (§tools 10.1). Unless the user's git configuration records that the user has been asked about that runner's settings (§tools 6d), spec-init does the following for each of those settings that the user's git configuration lacks:

• offers the user the setting's default, to confirm or replace;
• writes the user's answer with git config --global.

spec-init then records that the user has been asked about that runner's settings, as the hook that runs when a session starts does (§tools 6d).

Reason

The user decides where the project keeps its code and its tests, which command runs the tests and which settings the reviewer runs with. The session in which spec-init sets a project up started before the project held sheriff.config.json, so the hook that runs when a session starts asked for none of the settings of the reviewer's runner in that session (§tools 6d). The user pays for the reviewer's first run, so spec-init asks before that run.

Example

The user answers that the code is in src/, the tests are in test/, and npm test runs them. spec-init writes src/** and test/** as the glob patterns and npm test as the command. The most likely mistake is to write src and test, which match no file inside those folders.

An owner works from a browser through Remote Control and asks the agent to choose the Views extension. spec-settings offers a separate terminal window or questions in the chat, and the owner chooses the chat. Вопросы к вам

Вопрос 1. Порядок хука pre-commit и слова «right after the first step» в правиле 10.12

Правило 10.12 говорит, что при коммите проверка ключа, записанного больше одного раза, и проверка по JSON Schema выполняются сразу после первого шага («right after the first step»), то есть раньше остальных собственных инструментов проекта. Но эти две проверки делает sheriff validate, и той же командой он затем делает собственные проверки проекта и остальные свои проверки (согласованный узел «How a project's own check is run»). Поэтому остальные инструменты проекта, которые не меняют файлов, хук может запустить только до sheriff validate или после него, а после него их запускать нельзя: тогда проверки SpecSheriff guidelines шли бы раньше второго шага. Черновик «Хук pre-commit» запускает их до sheriff validate.

Рекомендую вариант А. Он опирается на цель исключения в правиле 10.12, которую называет его обоснование: проверка, которая читает узлы, выполняется только на файлах, прошедших проверки их структуры. При варианте А это так и остаётся.

  • А. Хук запускает остальные инструменты проекта до sheriff validate. После стадии 2 правило 10.12 говорит «эти проверки выполняются раньше любой другой проверки» вместо «сразу после первого шага».
    Что видит человек: хук отвергает те же коммиты, что и при варианте Б, и каждая проверка SpecSheriff guidelines и проекта по-прежнему выполняется после проверок структуры.
    Цена: после стадии 2 меняется одно предложение правила 10.12.
    Риск: не найден. Инструмент, который этот порядок ставит перед проверками структуры, не меняет файлов, а строка 10.1.37b отвергает инструмент, который их меняет.
  • Б. Правило 10.12 остаётся, а у sheriff validate появляется параметр, с которым он делает только две проверки структуры. Хук запускает sheriff validate с этим параметром сразу после первого шага, затем остальные инструменты проекта, затем sheriff validate снова.
    Что видит человек: те же отказы, что при варианте А, а коммит длится дольше, потому что проверки структуры выполняются дважды. Насколько дольше, не измерялось.
    Цена: новый параметр в согласованном списке команд (§tools 2.1) и в согласованном узле о собственных проверках проекта (§tools 7.1.23), с тестами.
    Риск: не найден.

При варианте Б в узле «Хук pre-commit» перед пунктом об остальных инструментах проекта появляется пункт «sheriff validate с этим параметром», а пункт о sheriff validate говорит, что тот делает остальные свои проверки.

Вопрос 2. Какие узлы оценивает sheriff guard

Согласованное правило 10.3 отвергает правку, которая «оставила бы узел одобренным при формулировке, на которую нет одобрения в силе». Буквально это относится к любому узлу спецификации, даже к узлу, которого правка не касается. Черновик «Оценка правки до того, как она сделана» оценивает только узел, который правка добавляет или у которого меняет формулировку либо статус одобрения, как уже делает код sheriff guard.

Рекомендую вариант А. Он опирается на обоснование правила 10.3: агент, который мог бы сам выставить статус одобрения, принимал бы решение, которое принимают только ответственные. Правка, которая оставляет узел как был, такого решения не принимает.

  • А. sheriff guard оценивает только узел, который правка добавляет или у которого меняет формулировку либо статус одобрения. После стадии 2 правило 10.3 говорит так же: «оставила бы одобренным узел, который правка добавляет или меняет».
    Что видит человек: правка файла, в котором есть нетронутый одобренный узел с формулировкой без одобрения в силе, проходит. После правки sheriff reindex делает этот узел черновиком и называет его агенту (§tools 6e).
    Цена: после стадии 2 меняются слова правила 10.3.
    Риск: не найден.
  • Б. Буквальные слова правила 10.3. sheriff guard отвергает любую правку, после которой такой узел остаётся одобренным, где бы этот узел ни был, и называет его.
    Что видит человек: правка отвергается, пока агент не сделает тот узел черновиком, даже если правка касается другого узла или файла.
    Цена: перед каждой правкой sheriff guard читает все файлы спецификации. На большой спецификации это, по оценке, замедляет каждую правку; замедление не измерялось.
    Риск: чтобы сделать свою правку, агент меняет статус узла, которого его задача не касается.

При варианте Б в узле «Оценка правки до того, как она сделана» первый пункт становится таким: «правку, после которой узел спецификации имеет статус approved, тогда как ни одно одобрение его формулировки не действует», а второе предложение обоснования уходит.
