Повторяющиеся sid, термины и имена RecordType · Duplicate sids, terms and names of RecordTypes

tools 7.1.3 · s-vke5hakwf3uyrjs · предложение от 2026-11-22 · ждёт вашего согласия
Обоснование
Узлы с одним и тем же sid, термином или именем RecordType могут храниться в разных файлах, поэтому каждый повтор находится, только если прочитать все узлы спецификации.
Reason
Nodes that hold the same sid, term or name of a RecordType may be kept in different files, so each duplicate can be found only by reading every node of the specification.

Новое, предложено рецензентом: у прежнего узла не было обоснования.

Пример
В ячейке TableRule лежит узел, sid которого скопирован из правила в другом файле. sheriff validate отвергает этот sid и называет оба узла. Ближайшая ошибка — сравнивать только узлы вне ячеек: тогда этот повтор пропускается.
Example
A cell of a TableRule holds a node whose sid was copied from a rule in another file. sheriff validate refuses that sid and names both nodes. The easiest mistake to make is to compare only the nodes outside cells, and such a comparison misses this duplicate.

Формулировка по частям

Щелчок по части выделяет узлы, на которые она ссылается; щелчок по узлу внизу выделяет части, которые на него ссылаются.

Что убрано из узла

  • Counting locations: no row asks for it any longer. Row 10.1.5 (§10.1.5) checks each node's location, which makes the check that no two nodes share a location redundant (the owner, 2026-11-12).
  • Counting the sids of the archive: an archived node holds no sid (§2.6).
  • The implements link to the main table of checks (§10.1): the node implements its rows, as the agreed drafts of this stage do.
  • The check of term nodes outside the contracts section: it moved to the new node "Term nodes outside the contracts section" (§tools 7.1.3a (new)).
